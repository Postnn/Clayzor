# Clayzor — инструкции для агента

## Первое правило — структура базы данных неизменна

Структура базы данных Clayzor неизменна. Любые предполагаемые изменения базы данных необходимо заранее согласовать с пользователем, до реализации. Без отдельного явного согласования запрещены изменения схемы, SQL-миграции, создание или изменение таблиц, представлений, процедур и других объектов БД. Серверные журналы операций не внедрять и не использовать.

Clayzor — суперпроект с сабмодулями в `src/` и `tests/`. Стек — .NET 10 Blazor Server (Interactive Server), MudBlazor 9.x и MudBlazor.Extensions 9.x, Dapper и Microsoft.Data.SqlClient 6.x, Windows Integrated Auth через Negotiate. SQL должен работать на SQL Server 2008 R2.

## Работа с задачей

- Перед правкой прочитай локальный `AGENTS.md` затрагиваемого модуля и профильные правила из таблицы ниже.
- При неоднозначных требованиях укажи допущения и задай уточняющий вопрос через опросник. Если есть несколько разумных трактовок или более простое решение, обсуди их до реализации.
- Для многошаговой задачи кратко запиши план и проверяемый результат каждого этапа. Для ошибки сначала воспроизведи её, затем подтверди исправление. При рефакторинге проверь поведение до и после.
- Делай минимальное изменение под запрос. Следуй стилю существующего кода, избегай преждевременных абстракций и посторонних правок. Удаляй зависимости и код, ставшие лишними из-за твоего изменения. О ранее существовавшем мёртвом коде сообщи отдельно.
- Изменения Git (включая add, commit и push), а также обновление документации и инструкций выполняй только по прямому указанию пользователя.

## Ключевые обязательные требования к формам редактирования

[FORM-01–09 и DR-01](docs/agents/forms.md) обязательны для текущих и новых приложений, самостоятельных страниц, модальных и вложенных редакторов. Правила регулируют отмену и черновики, оформление, фокус и клавиатуру, справку и тему, присутствие редакторов. Поиск и просмотр наследуют применимые правила интерфейса. Запись относится к формам с подтверждённой операцией сохранения.

## Проверка изменений интерфейса

- Перед правкой воспроизведи проблему в браузере на исходном сценарии и зафиксируй размеры, computed styles и фактическое переполнение. Не подбирай CSS вслепую: по DOM выясни, какие `height`/`max-height`, flex-сжатие, `overflow` и переносы текста создают дефект.
- Исправляй подтверждённую причину минимальным изменением общего компонента или его CSS. Не маскируй проблему скрытием переполнения и не ломай уже принятое поведение: пустое и заполненное состояния, обычный и длинный контент, активные и неактивные элементы проверяй раздельно.
- После изменения пересобери статические ресурсы и повтори исходный сценарий в Chrome на десктопе и при ширине 320–480 px. Для панелей и гридов сравни границы элементов, `clientHeight`/`scrollHeight`, размеры рабочей области; при визуальных изменениях проверь снимок. Ослаблять тест ради прохождения запрещено.
- При нескольких пунктах исправляй и отчитывайся последовательно. После всех пунктов выполни сборку и профильные тесты; не объявляй исправление завершённым без фактической проверки результата.

## Git и сабмодули

Перед коммитом внутри сабмодуля всегда проверяй `git status`.

Если первая строка — `HEAD detached ...` и в этом состоянии есть локальный
коммит, который нужно сохранить на ветке:

1. Сначала убедись, что ветка `main` — предок текущего коммита
   (текущий коммит просто "впереди" `main`):
   `git merge-base --is-ancestor main HEAD` (код возврата 0 = да).
2. Если да — прикрепи HEAD к ветке и подвинь её на текущий коммит:
   `git switch -C main`
3. Если нет (ветка `main` разошлась или указывает на посторонний коммит) —
   НЕ выполняй `switch -C` (он перезапишет указатель `main`). Остановись
   и спроси пользователя, что делать.

Если `git status` показывает `On branch main` — HEAD уже на ветке,
ничего прикреплять не нужно.

- После коммитов в сабмодулях отдельно фиксируй обновлённые ссылки на них
  в суперпроекте (`git add src tests` → commit) — иначе возникает рассинхрон.
- Файлы сборки .NET (`bin/`, `obj/`) не коммить: они в `.gitignore` каждого
  сабмодуля.

## Фиксация контекста по этапам

По завершении каждого этапа обновляй актуальный handoff в `promts/_handoff/`.
Для одной задачи используй один файл, не создавай дубли после каждой правки.
Записывай цель этапа, изменённые файлы и поведение, выполненные проверки с их
результатами, SHA коммитов, состояние запущенных приложений, нерешённые проблемы
и конкретное следующее действие. Не выдавай непроверенное за выполненное.
Перед сменой задачи или при риске потери контекста обновляй handoff даже для
незавершённого этапа, явно отмечая незавершённость и последний ошибочный тест.
