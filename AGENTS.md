# Clayzor — инструкции для агента

Clayzor — суперпроект с сабмодулями в `src/` и `tests/`. Стек — .NET 10 Blazor Server (Interactive Server), MudBlazor 9.x и MudBlazor.Extensions 9.x, Dapper и Microsoft.Data.SqlClient 6.x, Windows Integrated Auth через Negotiate. SQL должен работать на SQL Server 2008 R2.

## Работа с задачей

- Перед правкой прочитай локальный `AGENTS.md` затрагиваемого модуля и профильные правила из таблицы ниже.
- При неоднозначных требованиях укажи допущения и задай уточняющий вопрос через опросник. Если есть несколько разумных трактовок или более простое решение, обсуди их до реализации.
- Для многошаговой задачи кратко запиши план и проверяемый результат каждого этапа. Для ошибки сначала воспроизведи её, затем подтверди исправление. При рефакторинге проверь поведение до и после.
- Делай минимальное изменение под запрос. Следуй стилю существующего кода, избегай преждевременных абстракций и посторонних правок. Удаляй зависимости и код, ставшие лишними из-за твоего изменения. О ранее существовавшем мёртвом коде сообщи отдельно.
- Изменения Git (включая add, commit и push), а также обновление документации и инструкций выполняй только по прямому указанию пользователя.

## Ключевые требования к формам редактирования — обязательны

Перед любыми изменениями форм, общих контролов и новых приложений прочитай [единый контракт FORM-KEY-01…09 и DR-01](docs/agents/editing-forms-key-requirements.md). Он обязателен для **существующих и новых форм текущих приложений и всех новых приложений на Clayzor**. Новое приложение/модуль обязано сослаться на этот контракт в своём `AGENTS.md` и подключить общие механизмы. Требования являются условиями приёмки; локальный legacy opt-out не освобождает от них.

1. **FORM-KEY-01 — Отмена.** При изменениях предложить «Закрыть без сохранения», «Отменить мои изменения и загрузить из БД» и «Продолжить редактирование». Повторная загрузка оставляет форму открытой; сначала успешное чтение, затем безопасный сброс только подтверждённой ревизии. Ошибка чтения/хранилища сохраняет ввод; Unknown не стирается. «Обновить» сохраняет draft для сверки.
2. **FORM-KEY-02 — Placeholder.** Текст placeholder однострочного поля центрирован по вертикали; исправление только в общих компонентах/стилях.
3. **FORM-KEY-03 — Обязательные поля.** Все обязательные редактируемые поля, включая ClaySelect/ComboBox, имеют желтоватый фон независимо от placeholder и заполненности.
4. **FORM-KEY-04 — Первый фокус.** При открытии редактора фокус один раз получает первое доступное поле после готовности данных/восстановления, без перехвата уже выбранного пользователем фокуса.
5. **FORM-KEY-05 — Видимый фокус.** Tab/Shift+Tab и клавиатурная работа показывают контрастную рамку согласно теме и элементу.
6. **FORM-KEY-06 — Видимые изменения.** Изменённые поля имеют отдельную контрастную рамку, отличимую от фокуса/ошибки; сравнение с принятой baseline включает raw и сохраняет N+1.
7. **FORM-KEY-07 — Следующее поле.** Enter в однострочном вводе и завершённый пользовательский выбор в списке переводят фокус на следующий ввод один раз; textarea, IME, поиск, restore и программная синхронизация сохраняют свою семантику.
8. **FORM-KEY-08 — Справка и тема.** На каждой форме доступны команды справки по `URI_wiki_help` + зарегистрированному пути формы и выбора общей цветовой схемы. Использовать существующий ClayTheme, default Classic Light; смена темы/справка не сбрасывают редактирование.
9. **FORM-KEY-09 — Другие редакторы.** На сущности видны другие редактирующие её сотрудники через общий авторизованный presence, с каноническим ключом, агрегацией вкладок и восстановлением связи. Presence не синхронизирует поля, не блокирует запись и не заменяет CAS.

**DR-01:** несохранённые пользовательские данные не должны безвозвратно пропадать из-за перезапуска IIS, кратковременного обрыва сети или обновления приложения. Нельзя ухудшать уже работающий Clayzor ради совпадения с legacy. Общие компоненты/API имеют одного владельца при параллельной работе агентов; адресные формы подключают принятый контракт. Полные правила, исключения для read-only/поиска/диагностики, новые записи, nested scopes и приёмка находятся в документе по ссылке.

## Git и сабмодули

Перед коммитом внутри сабмодуля всегда проверяй `git status`.

Если первая строка — `HEAD detached ...` и в этом состоянии есть локальный
коммит, который нужно сохранить на ветке:

1. Сначала убедись, что ветка `main` — предок текущего коммита
   (текущий коммит просто "впереди" `main`):
   `git merge-base --is-ancestor main HEAD` (код возврата 0 = да).
2. Если да — прикрепи HEAD к ветке и подвинь её на текущий коммит:
   `git switch -C main`
3. Если нет (ветка `main` разошлась или указывает на посторонний коммит) —
   НЕ выполняй `switch -C` (он перезапишет указатель `main`). Остановись
   и спроси пользователя, что делать.

Если `git status` показывает `On branch main` — HEAD уже на ветке,
ничего прикреплять не нужно.

- После коммитов в сабмодулях отдельно фиксируй обновлённые ссылки на них
  в суперпроекте (`git add src tests` → commit) — иначе возникает рассинхрон.
- Файлы сборки .NET (`bin/`, `obj/`) не коммить: они в `.gitignore` каждого
  сабмодуля.

## Фиксация контекста по этапам

По завершении каждого этапа обновляй актуальный handoff в `promts/_handoff/`.
Для одной задачи используй один файл, не создавай дубли после каждой правки.
Записывай цель этапа, изменённые файлы и поведение, выполненные проверки с их
результатами, SHA коммитов, состояние запущенных приложений, нерешённые проблемы
и конкретное следующее действие. Не выдавай непроверенное за выполненное.
Перед сменой задачи или при риске потери контекста обновляй handoff даже для
незавершённого этапа, явно отмечая незавершённость и последний ошибочный тест.
