## 2. Запрет «магических» кодов записей БД: enum со **строгим именем таблицы**

Обязательное новое правило для **всех** проектов Clayzor:

- Любое **фиксированное числовое значение идентификатора записи в таблице БД**, используемое в C#, Razor или запросе как бизнес-константа, обязано быть объявлено **именованным элементом enum**. Не допускаются `private const int AccountantRoleId = 66`, `HasRoleAsync(43)`, `TypeId == 30`, `LocationId == 55`, `DocumentTypeId = 2365` и аналогичные голые коды.
- **Название типа enum строго соответствует имени соответствующей таблицы БД** (а не имени формы/DTO/проекта). Для `Роли.КодРоли` — `enum Роли`; для других справочников аналогично: `ТипыОборудования`, `Расположения`, `ТипыДокументов` — только после проверки точных имён таблиц.
- **Название элемента** соответствует русскому наименованию записи в БД с технически корректной нормализацией для C# (пробелы/пунктуация → `_`, сохранение смысла). Значения — фактические коды таблицы. Не придумывать «красивые» значения и не переименовывать роль по месту её использования.
- **Все такие перечисления хранятся в `Clayzor.Lib.Entities`**, в структурированном каталоге/namespace для идентификаторов справочников. Не создавать локальные enums в Web-приложениях, Services или Controls. XML-комментарий к enum: имя исходной таблицы и колонки-кода; к значениям — исходное наименование/назначение. Не создавать по одному enum на форму.
- В сигнатурах, где параметр представляет известный фиксированный код, принимать enum, а не `int`: например `CurrentUser.HasRole(Роли.Бухгалтер)` и `CurrentUser.HasRole(Роли.Бухгалтер, ownerPersonId)`. **Числовое преобразование** допускается только на границе Dapper/SQL (`(int)role`) или для сопоставления с кодом из БД.
- Не создавать enum для переменных первичных ключей произвольных записей (`EquipmentId`, `EmployeeId`, `PhoneId` и т.п.), математических констант, чисел пикселей, таймаутов, `0/1` булевых признаков. Для специальных `0`/`-1`, обозначающих «все организации», «не выбрано» и т.п., использовать отдельные **именованные семантические константы/типы**, только если это **не настоящие записи справочника**. Не искажать enum фиктивными строками БД.
- Если код справочника зашит непосредственно в `SQLQueries`, по возможности заменить SQL-литерал параметром и передавать enum из вызывающего кода. При необходимости сохранить DB-side constraint сначала объяснить причину и покрыть тестом; не превращать SQL-константу в конкатенацию пользовательского текста.
- Если для таблицы нет достоверной схемы/наименования, **не придумывать соответствие**. Проверить БД или legacy, вынести неподтверждённое в отчёт; запрещено молча закреплять произвольное имя enum.

Конкретный обязательный пример:

```csharp
// Clayzor.Lib.Entities; точные наименования остальных элементов сверить с БД.
/// <summary>Фиксированные значения КодРоли из таблицы Роли.</summary>
public enum Роли : int
{
    /// <summary>Бухгалтер, Роли.КодРоли = 66.</summary>
    Бухгалтер = 66,

    /// <summary>Главный бухгалтер 1С, Роли.КодРоли = 68.</summary>
    Главный_Бухгалтер_1С = 68,

    /// <summary>Специалист по инвентаризации оборудования.</summary>
    Специалист_по_инвентаризации_оборудования = 43,

    /// <summary>Дежурный инженер.</summary>
    Дежурный_инженер = 102,
}

// Правильно:
var canEdit = CurrentUser.HasRole(Роли.Специалист_по_инвентаризации_оборудования);
var canAccount = CurrentUser.HasRole(Роли.Бухгалтер, ownerId)
    || CurrentUser.HasRole(Роли.Главный_Бухгалтер_1С, ownerId);

// Неправильно:
private const int AccountantRoleId = 66;
var hasRole = await service.HasRoleAsync(66);
```

**Особое замечание:** сейчас код называет `42` как `SimSpecialistRoleId`, но в legacy `Role` значение `42` — `Администратор__тарифов_связи`. **Обязательно проверить реальное название и смысл роли 42 в `Роли`/`vwРоли`**. Ни в коем случае не объявлять `Роли.Специалист_SIM = 42` по догадке. Если бизнес-право для операций SIM действительно использует роль 42, сохранить поведение, но назвать роль по БД и отразить возможное смысловое несоответствие в отчёте.

Проверить как минимум 42, 43, 44, 66, 68, 102, 103, типы оборудования 27/30, расположение 55 и тип документа 2365. Для каждого элемента составить таблицу: `таблица`, `ключевое поле`, `код`, `название в БД`, `enum`, `места использования`. При доступной тестовой БД добавить проверку, что enum-значения и названия не расходятся с данными. Для кода 2365 запрос выполняется к соответствующей **базе документов**, а не автоматически к инвентаризации.

## 3. Единый `Employee CurrentUser`: ни одной независимой проверки ролей в формах/Services

**Обязательное требование:** в каждой форме, которой нужны данные пользователя или права, при первичной инициализации должен быть доступен объект **типа `Employee` с именем `CurrentUser`**. Единственный источник логики прав, языка и замещений — общая сущность `Employee` в `Clayzor.Lib.Entities`.

- Использовать/расширить существующий `Clayzor.Lib.Entities.Inventory.Employee` (lookup), либо **бережно переместить его в общий доменный namespace** с обновлением всех использований. Не оставлять две конкурирующие сущности `Employee` с разной семантикой. Существующие `EmployeeSelectDataSource`, Users и формы должны продолжать работать.
- Получать реального текущего сотрудника **на сервере** из доверенной идентичности/контекста SQL, а не из параметра URL, JS или клиентского ввода. Legacy читает `Сотрудники` по `SID = SUSER_SID()`; роли с учётом замещений — `fn_ТекущиеРоли()`. **Проверить фактическую идентичность SQL-сеанса и Windows/Negotiate principal**. Если соединение работает под сервисной учёткой, без безопасной привязки к пользователю **не применять** `SUSER_SID()` как якобы текущего пользователя. На ошибке определения личности — отказ в правах, не подстановка пользователя по умолчанию.
- `Employee` содержит подтверждённые `Id`, `Name/FIO`, язык (`Язык`, `Language`/culture), необходимые сведения о замещениях и эффективные роли с контекстом лица (`КодЛица`). Не копировать весь 70-тысячный legacy Employee без нужды; перенести требуемую семантику и тесты. Логика `GetLanguage`/культуры и учёт замещений не дублируется на страницах.
- **Единственный API** проверки: метод(ы) `Employee.HasRole(Роли role, ...)`, `Employee.HasRoleAsync(...)` и/или `Employee.RequireRoleAsync(...)`. Важны оба режима: роль без конкретного лица и роль по конкретному `personId`; учесть `КодЛица=0` («все лица») и параметр `zeroContains`, как в legacy. Чётко документировать, что означает `HasRole(role)` без лица: не допустить случайной подмены полномочия по одному лицу глобальным полномочием.
- Эффективные роли при замещении должны использовать подтверждённую серверную SQL-логику; проверить, что даты/период замещения соблюдены. Никакого самостоятельного упрощённого объединения ролей `RoleId IN (...)` в конкретных формах.
- На первом рендере форма асинхронно загружает `CurrentUser`, **до расчёта кнопок и доступности**. Придерживаться правила проекта: загрузка БД в `OnAfterRenderAsync(firstRender)`/существующем first-load pipeline, а не двойная загрузка при prerender. В каждой форме типизированное поле/свойство `Employee CurrentUser`; общий scoped loader/provider допустим только как инфраструктура получения и кэширования `Employee`, **не как альтернативная реализация `HasRole`**.
- Перечитывать актуальные права перед **каждым серверным изменением** (включая вызовы методов сущностей и фоновые/внешние действия). Одноразовый снимок ролей формы годится для UX, но **не является достаточной авторизацией записи**: сотруднику могли отозвать роль после открытия формы. Реализацию свежей проверки централизовать внутри `Employee`; при недоступности SQL/невозможности определить права — deny/fail closed. Не передавать `CurrentUser` или ID сотрудника от клиента как доказательство полномочий.
- При смене владельца/арендатора/лица, для которого проверяется роль, пересчитывать разрешения через `CurrentUser`. Область проверки должна соответствовать сохраняемым данным и проверяться повторно на сервере.
- Учитывать lifetime Blazor Server: никаких static mutable `CurrentUser`/Roles, общего кэша между пользователями или повторного использования circuit-контекста для другого пользователя. Не добавлять N одинаковых запросов на роли при открытии одной формы; загрузить effective roles совместно с сотрудником, использовать снимок для UI, свежую проверку — для write path.
- Сохранить тестируемость: предусмотреть подменяемый **источник данных текущего Employee** для bUnit/unit-тестов без пересоздания нескольких реализаций прав.

Пример желаемого использования (конкретный способ получения `Employee` выбери согласно текущему DI и lifecycle):

```csharp
private Employee CurrentUser { get; set; } = default!;

// В существующем первом async-load формы:
CurrentUser = await Employee.LoadCurrentAsync(Db, cancellationToken);
_canEdit = CurrentUser.HasRole(Роли.Специалист_по_инвентаризации_оборудования);

// Перед серверной операцией: свежая проверка ПРАВ ЧЕРЕЗ ТОГО ЖЕ Employee.
await CurrentUser.RequireRoleAsync(Db, Роли.Специалист_по_инвентаризации_оборудования, ownerId);
await equipment.SaveAsync(Db);
```

Синтаксис — ориентир; не переносить `DbManager` в модель как глобальное поле и не обходить существующий SQL gate. Если по объективной причине нужен provider, API `Employee` всё равно остаётся единственным владельцем проверки.

## 4. Рефакторинг каталога `Kesco.App.Web.Inventory/Services`

### `EquipmentFormService.cs`

- Разобрать все методы на матрицу `метод → собственник логики → права → изменения → тест`. Сейчас сервис объединяет CRUD всех связанных сущностей, проверки ролей, пакетное чтение, сложные операции и синхронизацию АТС.
- Простые чтения/CRUD `Equipment`, `EquipmentLocationPeriod`, `EquipmentResponsiblePeriod`, `EquipmentSimCard`, `EquipmentSimService`, `EquipmentLicense`, `EquipmentComputerSnapshot`, `EquipmentSoftwareInstallation`, `EquipmentAccounting`, `EquipmentAccount`, `UpsServerLink` и т.д. оставить/перенести в соответствующие сущности в `Entities`. **Не** плодить сервис из одного метода на каждую сущность.
- Удалить самостоятельные `HasRoleAsync`, `HasRoleForPersonAsync`, `EnsureInventoryEditAsync`, `EnsureAccountAccessAsync`, `EnsureNetworkAccessAsync`, `EnsureUpsAccessAsync`, `EnsureLicenseAccessAsync` в той части, где они реализуют **семантику наличия роли**. Все проверки ролей вызывает `Employee`. Проверки бизнес-контекста (тип оборудования, владелец, доступность операции, целостность записи) могут оставаться в доменной логике; их нельзя путать с проверкой ролей.
- Пакетную загрузку `GetFormDataAsync` через `DbManager.RunAsync` + `QueryMultipleAsync` **сохранить**: она уменьшает число round trips. Перенести SQL/read-models в `Entities` (либо обоснованно оставить очень тонкий координатор сборки данных без inline SQL), не нарушить порядок наборов, права на чтение секретных полей, обработку SQL-ошибок и отмену. `EquipmentFormReadRequest/Result` должны лежать рядом с этим механизмом, а не независимо от него.
- Сохранить атомарность записи `Equipment + diff телефонных связей`, rollback, отделённую синхронизацию АТС (Xorcom/CCM) и безопасное повторение, без повторного SQL UPDATE при ошибке внешнего действия. Узкий координатор допустим для **этого** сценария и управления UPS/составными операциями, если он действительно необходим.
- В `GetPhoneConfigAsync` (в т.ч. HTTP endpoint `PhoneConfigHandler.ashx`), SIM/PIN/PUK, логинах/паролях и бухгалтерии не допустить расширения доступа. Проверки Employee актуальны **на самом серверном endpoint**, а не только на открытой форме.

## 7. Обязательные тесты и защитные сценарии

Тесты **не должны** подтверждать только вызовы `mockService.HasRoleAsync`, потому что эта архитектура удаляется.

- `Роли.Бухгалтер == 66`, корректные коды 42/43/44/68/102/103 из проверенного справочника; другие enum и источники данных не расходятся; имена enum строго равны таблицам.
- Получение именно текущего сотрудника: найден, не найден, ошибка SQL, SQL principal != authenticated principal, разные пользователи в разных circuits. При недоверенной/отсутствующей идентичности права отсутствуют.
- `CurrentUser.HasRole`: обычная роль, роль для лица `A`, запрет для лица `B`, `КодЛица=0` как global-scope, сочетание глобальных/локальных ролей, роль по действующему замещению, истёкшее замещение, роль отсутствует. Не расширить права в сравнении с legacy.
- Язык `ru/en` и fallback при пустом/неподтверждённом значении; данные другого пользователя не перетекают между сессиями.
- Отзыв роли после открытия формы: UI мог ранее показывать команду, но сервер **не выполняет запись** после отзыва. Прямой вызов write method без предварительного рендера формы также запрещает операцию.
- `EquipmentIns`, `EquipmentForm`, `ModelEquipmentForm`, `PhoneTemplateForm` получают `Employee CurrentUser` и используют его в правах. Проверка прав по владельцу/арендатору/лицу без расширения доступа.
- Невозможность получить Employee или роли из БД: fail-closed, без успешного сохранения. Показ ошибки и сохранение черновика ввода.
- Пакетная загрузка секций через `QueryMultiple`: правильный порядок result sets, условные секции, read-only доступ, отсутствие загрузки паролей/PIN/PUK в общий запрос.
- Регрессии: телефонный diff и АТС, создание оборудования через установленную процедуру, бухгалтерия, SIM, лицензии, сеть, UPS, даты и locale, `ClaySelect`, статический `ClayGrid`.
- Статический guard/test на очевидные `const int .*RoleId`, `HasRoleAsync(42/43/...)`, `DocumentTypeId = 2365`, `TypeId == 30`, `LocationId == 55` в production-коде. Не запрещать обычную арифметику и значения из входных данных; неподтверждённые коды регистрировать как долговой список, не подменять ложными enum.

Выполнить `dotnet build Clayzor.sln`, профильные и полный `dotnet test` (если полный набор не завершается — честно указать причину и хотя бы независимые профильные тесты). По возможности выполнить browser smoke на рабочих маршрутах формы и проверку доступа под двумя учётными записями. **Не выполнять разрушающих записей в production-БД**; пользоваться тестовой средой/откатными фикстурами.

## 8. Критерии приёмки

Задание считается выполненным, только если:

1. В `Services` нет бессмысленных CRUD-прокси, параллельных реализаций прав и raw SQL, который должен принадлежать Entities. Оставшиеся services документированы по назначению.
2. `Роли` и другие фиксированные таблице-зависимые enum **существуют в Lib.Entities**; в исходниках исправлены известные magic IDs, включая 66/68, 42/43/44/102/103, 27/30, 55, 2365 (при подтверждении схемы/наименований).
3. Формы имеют **`Employee CurrentUser`**, сведения о текущем сотруднике, языке, ролях и замещениях обслуживаются одной реализацией в `Employee`; отсутствуют случайные `HasRole*` реализации в Forms/Services. Авторизация повторно проверяется перед серверной записью.
4. Сохранена работа legacy-сценариев, телефонной синхронизации, атомарных операций и оптимизации пакетной загрузки; нет регрессий SQL Server 2008 R2 и недопустимых расширений доступа.
5. Фактически изменены root и nested **`AGENTS.md`**; правила не противоречат друг другу, ссылаются друг на друга, а не остаются только в ответе агента.
6. Есть тесты и отчёт: что перемещено, что осталось, какие enum и откуда проверены, как реализованы язык/замещения, результаты build/test/браузера, незакрытые ограничения.

**Формат итогового отчёта агента:** (1) короткая карта `было → стало` для всех файлов `Services`, (2) полный список добавленных enum `таблица/поле/код/имя`, (3) пример использования `Employee CurrentUser` в форме и на write-path, (4) перечень обновлённых `AGENTS.md`, (5) реальные результаты тестов и обнаруженные ограничения.
