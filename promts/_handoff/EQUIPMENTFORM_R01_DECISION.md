# EquipmentForm R01 — решение о согласованности SQL и АТС

Дата: 22.11.2026. Статус: **на выборе владельца; реализация не изменяется**.

## Текущее поведение

`EquipmentForm.SaveAsync` сначала завершает SQL-запись оборудования и телефонных связей, затем вызывает синхронизацию Xorcom/CCM. Неуспешные операции сохраняются только в `_pendingPhoneSync` текущего Blazor circuit. Закрытие circuit или перезапуск приложения теряет очередь повтора. Пользователь видит предупреждение, но другой пользователь и новый circuit очередь не получают.

Legacy использует `TransactionScope(ReadCommitted)` вокруг SQL и вызова синхронизации. Это не доказывает откат физического изменения АТС: внешний side effect сам по себе не участвует в транзакции SQL Server.

## Варианты

### A — принять текущее исключение

SQL и АТС сохраняются отдельно; retry остаётся circuit-local.

- Нужны явный мониторинг и назначенный ответственный за ручную сверку/восстановление.
- После потери circuit текущий пользователь должен получить инструкцию выполнить синхронизацию вручную; новый circuit не показывает старый pending.
- Минимальная стоимость, но расхождение с legacy и риск пропущенной синхронизации сохраняются.

### B — durable outbox (рекомендуется обсудить первым)

В одной SQL-транзакции с изменением оборудования сохраняется запись намерения синхронизации. Отдельный обработчик выполняет внешний вызов после commit и фиксирует результат.

Минимальный контракт: `OperationId`, equipment/phone key, вид операции, параметры, состояние, число попыток, время следующей попытки, последняя ошибка, создано/изменено. Нужны уникальный ключ намерения, идемпотентность либо дедупликация на стороне АТС, блокировка при параллельных обработчиках и ручной повтор.

Риски: текущие процедуры АТС могут не поддерживать безопасный replay; требуется подтвердить идемпотентность и правила при изменении телефона/оборудования между попытками. Не внедрять таблицу и фоновый процесс без выбора владельца.

### C — legacy-like

Сохранить единый `TransactionScope` и вызывать текущие процедуры синхронизации внутри него.

До выбора необходимо подтвердить фактические external calls, их длительность, возможность отката и поведение при исключении после физического изменения. Долгие транзакции увеличивают блокировки; SQL Server 2008 R2 поддерживает используемый механизм, но это не делает внешнюю операцию транзакционной.

## Матрица состояний

| SQL committed | АТС succeeded | Circuit lost | Повтор Save | Текущий результат | Безопасность replay |
|---|---|---|---|---|---|
| нет | нет | нет | да | Ошибка, draft сохраняется | Допустим после проверки отсутствия SQL-записи |
| нет | да | любой | да | Возможен внешний side effect без SQL | Только после ручной сверки АТС |
| да | да | нет | да | Обычный reload; dirty-state определяет повтор | Не повторять уже успешную операцию |
| да | да | да | новый circuit | SQL и АТС согласованы | Повтор не нужен |
| да | нет | нет | да | Pending доступен в том же circuit | Только после проверки идемпотентности |
| да | нет | да | новый circuit | Pending потерян, расхождение не восстанавливается автоматически | Нужна ручная сверка либо outbox |
| неизвестно | нет/неизвестно | любой | любой | Результат SQL неизвестен | Сначала прочитать SQL и АТС |
| неизвестно | да | любой | любой | Возможен частичный side effect | Сначала прочитать SQL и АТС |

Если телефон или оборудование изменены в другой сессии между попытками, старый pending нельзя применять автоматически: нужна проверка актуальной версии и составного ключа. Для B это обязательное условие обработчика; для A — обязательное условие ручного восстановления.

## Решение владельца

- [ ] A — принять исключение и организовать ручное восстановление.
- [ ] B — проектировать durable outbox после подтверждения идемпотентности АТС.
- [ ] C — восстановить legacy-like транзакцию после исследования внешних вызовов.

До отметки выбора R01 остаётся открытым, текущая circuit-local реализация и её регрессионные тесты сохраняются.
