### 2.2 Явное подтверждение Delete и сохранённое состояние

`Tel.razor.cs`, `DeleteAsync()`:

- вызывает `ConfirmAsync("Удаление номера", DeleteConfirmation(HasPendingSync))`;
- вопрос всегда содержит «Удалить номер, состав его PBX-группы, связи с оборудованием и параллельные вызовы?»;
- при pending дополняется предупреждением, что SQL-данные уже сохранены, а для восстановления АТС после закрытия потребуется ручная синхронизация;
- при отказе не вызывается `DeleteConfirmedAsync()`.

После подтверждения `DeleteConfirmedAsync()` загружает `PhoneFormService.GetDeleteSnapshotAsync(phoneId)`, строит `PhoneSyncPlanner.BuildDelete` из актуальных *сохранённых* телефона, станции и связей, а не из черновика. Если запись уже исчезла, SQL Delete и АТС не вызываются. Для Xorcom предварительная очистка выполняется до SQL Delete с попыткой восстановления при отказе SQL. Это согласуется с критичными ограничениями логики legacy `Tel.aspx.cs:4058+` и `Phone.GetPhoneEquipments(true)`.

**Вывод:** подтверждение и последствия соответствуют утверждённому поведению. У legacy нет аналога pending между circuit: этот механизм — новая, явно документированная защита.

### 2.3 Cancel / Refresh / внутренняя навигация

Код `Tel.razor.cs` сохраняет две независимые характеристики:

- `HasUnsavedDraft` — несохранённые изменения основного телефона или связей относительно baseline;
- `HasPendingSync` — неуспешные операции внешней АТС после зафиксированного SQL Save.

`CancelAsync()` и `BeforeInternalNavigationAsync()` используют `CloseConfirmation(...)` и при обоих состояниях упоминают оба риска. `RefreshAsync()` спрашивает только о потере черновика и повторно загружает DB с `preservePending: true`; pending остаётся в текущем circuit. `NavigationLock ConfirmExternalNavigation="@IsModified"` вызывает системное подтверждение при **внешнем** уходе; ограничение браузера на настраиваемый текст `beforeunload` корректно отражено в документации.

**Вывод:** логика по сравнению с Tel_6 не ухудшена, а новая проверка внутренних переходов полезна.

## 5. Остаточные ограничения и решение по merge

В **новом коммите Tel_7 не обнаружено блокирующих дефектов**. Ранее выявленное замечание TEL6-UI-01 можно закрыть.

Условия, сохраняющиеся из предыдущих аудитов:

1. **Реальные АТС:** внешний эффект Meridian/Xorcom/CCM и восстановление после сбоя не тестировались на настоящих станциях. Mock доказывает порядок вызовов, не внешнее состояние.
2. **SQL-интеграция:** в тестовой БД не было подходящих фикстур для проверки выбора розеток в разных помещениях одного офиса, конкурентного занятия портов/розеток и полного CRUD связей PBX/оборудования.
3. **Незавершённая синхронизация:** pending хранится только в Blazor circuit; после разрыва требуется ручной регламент, durable outbox отсутствует по принятому решению.
4. **Полный тестовый прогон:** согласно последнему отчёту агента, не выполнялся; профильные запуски следует сохранить в журнале приёмки.
5. **Права:** дополнительных проверок ролей в C# для синхронизации требовать не нужно; существующий контракт SQL Server принят владельцем проекта.
