# Промт для агента: разработка формы телефонного номера Tel в Clayzor

**Роль:** Senior .NET / Blazor Engineer, архитектор миграции legacy WebForms → Clayzor.  
**Цель:** реализовать полноценную форму создания, просмотра, редактирования, копирования и удаления корпоративных телефонных номеров, функционально эквивалентную legacy, но архитектурно более качественную, быструю, безопасную и удобную.  
**Целевой проект:** `Postnn/clayzor`, сабмодуль `src/Kesco.App.Web.Inventory`.  
**Legacy:** `KescoDev/Kesco.App.Web.V4.Inventory/Inventory/Telefon/Tel.aspx`.  
**Дополнительный источник:** `KescoDev/Styles/js`.

> **Главный принцип:** переносить бизнес-правила, зависимости, ограничения, фильтры и пользовательские сценарии, но **не** копировать устаревшие механизмы WebForms (`DataTable` как UI-state, `BinderValue`, `cmdasync`, HTML-инъекции, PostBack и т. п.). Результат оценивается по корректности поведения и измеримым улучшениям, а не по буквальному сходству исходного кода.

Веди работу последовательными законченными этапами. Не ограничивайся аудитом или версткой: реализуй реальную бизнес-логику, тестируй и проверяй. Прежде чем принимать неоднозначное архитектурное решение, найди первоисточник; при существенном противоречии с legacy или риске изменения данных представь точный вопрос и обоснование. Не придумывай правила.

8. Связанные таблицы, побочные действия и порядок сохранения.
9. Тесты для проверки.

Используй конкретные значения enum, а не позиции в комбобоксе:

| Код | Тип телефонного номера |
|---:|---|
| 0 | PBX группа / фиктивный |
| 1 | Цифровой |
| 2 | Аналоговый |
| 3 | ISDN |
| 10 | DECT |
| 100 | Короткий номер |
| 101 | Короткий мобильный |

**Раздели сохранённое состояние, черновик, подтверждённый выбор и вычисленные возможности.** Не теряй несохранённые данные при временном изменении поискового текста.

## Этап 2. Единый механизм правил доступности полей

Исходная реализация `FieldAvailabilityController`, `CreateFieldAvailabilityControllers`, `UpdateAvailabilityControlsEditState` различает три сценария:

- **Available** — поддерживается конфигурацией: видимо и редактируемо при наличии прав.
- **Hidden** — не поддерживается и не содержит значения.
- **IncompatibleExistingValue** — не поддерживается, но содержит старое/черновое значение: legacy показывает его в read-only и предупреждает о несовместимости.

В новой форме сохрани **все три состояния**. Не удаляй данные скрытием Razor-фрагмента. Legacy очищал часть таких значений при сохранении; новая реализация должна перед потенциально разрушительной очисткой явно показывать её последствия и требовать подтверждения, сохраняя исходные данные при отмене.

Реализуй небольшой типизированный вычислитель, например `PhoneFormRules` → `PhoneFormAvailability`. Это не должен быть глобальный «движок форм»; ограничься реальными сценариями Tel. Расчёт UI-состояния не должен выполнять SQL в getters/rendering: нужные свойства станции и результаты проверок загружай отдельно.

**Минимальная матрица:**

| Элемент | Фактическое правило legacy |
|---|---|
| Розетка | Тип 1 или 2 |
| Порт АТС | Порт существует для выбранных типа и станции (`SELECT_СуществуютПортыАТС`) |
| Группа перехвата | Станция 0 либо станция с ID 1–99 |
| Автонабор | Возможность определяется сочетанием типа/станции, через `SELECT_АвтонаборДоступен` |
| Ведомый от | Допустимый тип из 1, 2, 3, 10, 200 и `PhoneStation.IsDrivenBy` |
| Отображаемый от | Допустимый тип из 1, 2, 3, 10, 200 и `PhoneStation.IsDisplayedFrom` |
| Параллельные вызовы | Выбранная станция с `IsParallelCalls` |
| Члены группы | Тип 0 и выбранная станция |
| Оборудование | Тип 1, 2, 10 или ID >= 200 |
| Основной номер сотрудника | Указан сотрудник |
| Срок возврата | Дата доступна при установленном чекбоксе |

Уточни и реализуй **не только показ, но и недоступность, предупреждения и обработку прежнего значения**. Правила `IsGroup6Available` и `IsGroup6NumberAvailable` различаются:

- Станция 0 — именованные группы из конфигурационной секции `pickupGroups`.
- Станции 1–99 — группы `0..15`.
- Остальные — поле недоступно.

`0` — допустимая группа, не `null`. Для группы действуют проверка длины до 20 символов и проверка присутствия в актуальной выдаче.

Проверь переходы: выбор типа до станции и наоборот, смена/очистка/отмена выбора, повторный выбор, быстрые последовательные изменения, ответ старого запроса после нового, вновь ставшие допустимыми значения. Поздние асинхронные результаты запрещено применять к новому состоянию.

**Критерий:** все условия проверяются unit-тестами независимо от Razor.

## Этап 3. Современная, но узнаваемая компоновка формы

Сохрани **смысловые группы и относительный порядок** исходной формы; не копируй HTML-таблицы и фиксированные размеры вроде 892px.

**Верхняя область: компактная двухколоночная сетка.**

| Левая группа | Правая группа |
|---|---|
| Номер телефона | Станция |
| Тип номера | Порт АТС |
| Переадресация (`БыстрыйНабор`) | Группа перехвата |
| Номер автонабора | Контекстные сведения АТС |
| Сотрудник | Ведомый от |
| — | Отображаемый от |
| Компания заказчик | Розетка |

Физическое расположение улучшай при сохранении смысловых связей. Зависимые элементы должны скрываться или оставаться read-only без разрыва сетки. Порядок Tab согласуй с визуальным, а не со случайными `TabIndex` legacy.

**На всю ширину:** поля `Подключено` и `Описание АТС`, у второго — команда заполнения по сотруднику. Автозаполнение не должно перетирать вручную изменённый текст без понятного правила.

**Связанные секции:** параллельные вызовы, основной номер сотрудника, read-only «Входит в группы номеров», редактируемые «Члены группы», оборудование, срок возврата. Параллельные вызовы должны располагаться рядом со связанными действиями, а не произвольно внизу.

**Нижняя область:** две компактные radio-группы:

- Услуги связи: внутри холдинга (0), местная городская (1), внутри страны (3), международная (4), гостиница (5).
- Отображение в справочнике: не отображать (0), отображать (1), жирным (2), в начале группы (4), в начале группы жирным (6), всегда (8).

Далее примечание (300 символов) и закреплённый стандартный `ClayChanged` в `Footer` формы.

**Команды:** `OK`, `Применить`, `Копировать`, `Удалить`, `Обновить`, `Отмена` — через `ClayToolbar`/`ClayToolbarButton` и `ClayEntityForm` с корректной видимостью и правами. Подписи полей — семантические label, не disabled `TextBox` как в legacy.

**Визуальная проверка:** 1440/1155/1024/768/480/375/320 px, без горизонтального расширения документа, обрезанного текста и скачков интерфейса. На узких экранах переход к одной колонке. Следуй общему стилю Clayzor и используй готовые компоненты. Если для реального legacy-контрола отсутствует общий аналог (например, radio-группа), реализуй минимальную переиспользуемую обёртку в RCL по правилам `AGENTS.md`.

## Этап 4. Типизированные серверные источники `ClaySelect` и реальные фильтры

Не заменяй сложные SQL-фильтры простым поиском по названию или клиентским фильтром первых N строк.

### 4.1. Тип номера

`DbsPhoneType_BeforeSearch` ограничивает типы выбранной телефонной станцией. Реализуй этот фильтр и серверную проверку актуального значения.

**Важная асимметрия legacy:** при выборе станции обратный фильтр по типу **намеренно отключён**. Пользователь может выбрать станцию, несовместимую с выбранным типом, и получить внятную ошибку типа. Не вводи жёсткую взаимную фильтрацию, скрывающую несовместимость.

### 4.2. Станция

Поиск и восстановление станции по ID; сохраняй особый порядок `DSOPhoneStation.SQLOrderBy` (`Sort`, не только алфавит). В случае несовместимости типа и станции показывай ошибку, **не обнуляй** станцию. Сохрани переход к оборудованию станции.

### 4.3. Розетка

Разбери `DbsSocket_BeforeSearch`, `DSOSocket`, используемые `FOpt`, правила определения расположения:

- Телефонная станция → её оборудование → актуальное расположение → офис.
- Если есть связанное оборудование телефона, фильтр может использовать расположения этого оборудования.
- Иначе поиск по офису станции и его потомкам.
- Учитывай живые/свободные розетки и `SocketInclude` для текущей выбранной розетки, даже если она уже считается занятой.
- Учитывай иерархию расположений (в частности `L/R`) и отсутствие расположения.
- При ошибке построения контекста **не** открывай поиск по всем розеткам: используй fail-closed поведение.

Устрани N+1-цепочку синхронных конструкторов `PhoneStation` → `Equipment` → `Location`. Используй минимальное число параметризованных серверных запросов. Отдельно проверь, как черновик изменения оборудования влияет на поиск розетки.

### 4.4. Оборудование

`DbsEquipment_BeforeSearch`, `DSOPhoneEquipment`, `SELECT_fn_ОборудованиеДляТелНомера`: фильтры по сотруднику, станции, типу номера, розетке, самому телефону и уже добавленному оборудованию. Сохрани составной выбор `КодОборудованияИПодключения`; в модели храни **типизированную** пару `EquipmentId`, `ConnectionEquipmentId?`, а не строку с `;`. `0`/пустое/`NULL` нормализуй только на границе legacy-контракта.

### 4.5. Члены PBX-группы

Исключи текущий телефон и уже добавленные номера, ограничь выдачу выбранной АТС. Все исключаемые ID передавай безопасно, не собирай сырой `NOT IN` из пользовательской строки. Сохрани восстановление текущего выбранного элемента по ID.

### 4.6. Ведомый/отображаемый номера

Фильтры различаются:

- `DrivenBy`: `ВедомыйОт IS NULL`.
- `DisplayedFrom`: `ВедомыйОт IS NULL AND ОтображаемыйОт IS NULL`.

Не допускай ссылки на самого себя или циклических зависимостей; дополнительные ограничения подтверждай по реальным SQL/триггерам. Условия не должны исчезать из-за обобщения одного `PhoneSelectDataSource`.

### 4.7. Сотрудник и компания заказчик

По умолчанию — работающие сотрудники. Компания выбирается из бизнес-справочника **лиц-заказчиков**, не из произвольных лиц. При выборе сотрудника legacy пытается подставить его организацию; сохрани корректную бизнес-реакцию, но не затирай вручную установленное значение без подтверждённого правила.

**Критерий:** каждый источник покрыт тестами SQL и параметров, `GetByIdAsync`, лимита/`HasMore`, смены фильтра и отмены устаревших запросов.

## Этап 5. Валидация: блокирующие ошибки, разрешённые предупреждения, информация

Не копируй `OnRenderNtf` в Razor. Валидация должна работать при значимых изменениях, при `blur` там, где необходимо, и **повторно на сервере непосредственно перед Save**. Отдели её от представления.

### 5.1. Формат и длина

| Поле | Проверка |
|---|---|
| Номер | Обязателен, максимум 4 символа, `^[0-9#\\*]+$` |
| Тип | Обязателен |
| Станция | Обязательна |
| Заказчик | Обязателен |
| Переадресация | До 50 символов, необязательный `+`, затем цифры / `#` / `*` |
| Автонабор | До 50 символов, тот же формат |
| Номер параллельного вызова | До 50 символов, тот же формат |
| Подключено | До 100 символов |
| Описание АТС | До 100 символов, без кириллицы |
| Группа перехвата | До 20 символов и значение из актуального списка |
| Примечания | До 300 символов |
| Две задержки параллельного вызова | Неотрицательные целые числа |

Номера телефона **строковые**: `#`, `*` и ведущие нули должны сохраняться.

### 5.2. Полный номер

Используй `Phone.CalculateFullNumber` как контракт: приоритет `DisplayedFromFullNumber` перед `DrivenByFullNumber`, затем комбинация префикса станции и короткого номера. Изучи триггеры `vwТелефонныеНомераИзменение`, формирующие фактический полный номер; UI-расчёт носит предварительный характер, если окончательное значение назначается БД.

Проверяй:

1. Дубликат короткого номера на той же станции (исключая редактируемый ID).
2. Дубликат независимого полного номера.
3. Запрещённые пересечения полных номеров по префиксу (в обе стороны).
4. Специальную семантику ведомых и отображаемых номеров: не проверяй их как полностью независимые.

Замени форматируемые SQL-проверки `SELECT_Check_ТелефонныйНомерИспользуется` и `SELECT_Check_ТелефонныйНомерРазрешен` на параметризованные запросы с корректным экранированием спецсимволов `LIKE`.

### 5.3. Описание АТС

Описание обязательно, когда **нет** `DrivenBy` и поле `Подключено` пустое либо **не** начинается с `№`. Если введено — не содержит русских букв.

Для генерации используй английские фамилию/имя сотрудника, при их отсутствии — подтверждённую `fn_TransLit` с SQL-параметром; станции с `АТСDescriptionCapital` требуют верхнего регистра. Не заменяй пользовательский ввод фоновым пересчётом без ясного правила.

### 5.4. Порт АТС и группа перехвата

Порт обязателен, **если** для текущих типа+станции существуют порты. Выбранный порт должен присутствовать в списке свободных портов с включением **собственного текущего** порта. При смене зависимости показывай несовместимое значение, не скрывай ошибку. Аналогично для группы перехвата (включая значение `0`).

### 5.5. Сотрудник/заказчик

Обязательно хотя бы одно из «Сотрудник» или «Подключено».

Сохрани проверки:

- PBX-группа и сотрудник: `Employee.IsGroupWork`.
- Компания заказчика среди работодателей сотрудника (`NTF_CheckPostInCompany`).
- Компания заказчика на расположении АТС (`NTF_CheckLocationPhoneStation`).
- Короткий мобильный номер и переадресация на SIM другого заказчика (`NTF_CheckShortMobileNumber`).
- Переадресация на номер, выданный другому сотруднику (`NTF_CheckQuickCallEmployee`).

**Критическая особенность:** ряд legacy-уведомлений имеет `Status=Error`, но `CanSaveEntity=true`. Не превращай такие уведомления в блокировку. Каждое правило классифицируй как `Blocking`, `WarningAllowed` или `Info` по фактическому контракту, а не по цвету сообщения.

### 5.6. Даты, параллельные вызовы, справочник

- Раздели срок возврата самого номера и сроки отдельных связей с оборудованием.
- Дата не должна быть в прошлом; уточни бизнес-дату/часовой пояс и границы суток, поскольку legacy сравнивает с датой от `DateTime.UtcNow`.
- Параллельные номера: запрет дубликатов, само-вызова, недопустимых значений задержек.
- Если номер вызывает другие параллельно, может требоваться отображение в справочнике. Если он сам — участник чужого параллельного вызова, действует иное информационное исключение (`CheckForParallelCallPhoneSibling`).
- Отображение в справочнике использует enum 0,1,2,4,6,8, без преобразования в индексы.
- При смене типа «Услуги связи» в некоторых случаях фиксируются: для типа 0 — `InsideHolding`, для типов 100/101 — `International`. При возврате к другому типу восстанавливай **выбор пользователя**, а не навязанный временный дефолт; изучи `_phoneServicesSelectedByUser`, `_viewInRefSelectedByUser`, `_initialPhoneServicesKind`.

**Критерий:** все блокирующие проверки препятствуют сохранению, но разрешённые предупреждения не блокируют его. Нет SQL-запросов на каждом рендере.

## Этап 6. Связанные списки и диалоги

### 6.1. Параллельные вызовы

Поддержи список, добавление, редактирование, удаление, `NotUsed`, две задержки, кто/когда изменил. Действия над коллекцией до общего Save остаются в **черновике**. Диалог с отменой не изменяет исходный список. Используй устойчивые ключи вместо индексов `DataTable`. При изменении самого номера подтверждай очистку существующих параллельных вызовов; отмена должна восстанавливать старый номер и список.

### 6.2. PBX-группа

Список членов группы со ссылками, добавлением и удалением, исключением дубликатов/самого себя. При смене АТС с непустым списком требуется подтверждение; отмена полностью восстанавливает прежнюю станцию, фильтры и связанные данные. Сохраняй diff при общем Save. Отдельно выводи read-only «Входит в группы номеров» (`GetPhoneNumberGroups`) — это **другая** связь.

### 6.3. Оборудование

Модель связи содержит `EquipmentId`, `ConnectionEquipmentId?`, модель/расположение/SN, признак основного номера, тип, срок возврата, примечание, другие номера на оборудовании, сведения об изменении.

Восстанови условные колонки legacy `UpdateEquipmentGridAppearance`:

- Оборудование подключения — только если встречается в данных.
- Другие номера на оборудовании — только если есть.
- Срок возврата в read-only — по фактическому наличию сроков.
- Действия — только при разрешённом редактировании.

Сохрани ссылки на карточку оборудования, просроченные сроки и корректный составной ключ. Для срока возврата отдельной связи используй диалог, изменение без перезаписи всей связи и обновление только её секции.

### 6.4. Почему legacy иногда сохраняет оборудование немедленно

`DbsEquipment_Changed`, `AddEquipmentAndSave`, `DeleteEquipment` выполняют запись сразу, потому что SQL-фильтр розеток может зависеть от уже записанного оборудования. Это **техническая зависимость**, не обязательный UX-контракт.

Разберись, какие функции/представления требуют сохранённого состояния и возможно ли передавать новый набор оборудования явно. **Предпочтительно:** черновик связей + серверный расчёт зависимых фильтров с учётом черновика, без промежуточных записей.

Если реальный SQL-контракт этого не позволяет, реализуй минимальную контролируемую операцию записи, не скрывая её от пользователя. Не сохраняй молча все несвязанные поля формы только из-за выбора оборудования. При неуспехе восстанови согласованность UI и БД.

Проверяй реальные уникальные ограничения и триггеры перед изменением семантики.

**Атомарность:** основная запись и необходимые связанные изменения — в короткой явной SQL-транзакции с `ReadCommitted`, если это соответствует подтверждённому контракту. Не держи транзакцию открытой вокруг АТС. Учитывай один `DbManager` connection/circuit, gate `RunAsync` и запрет прямого `SqlConnection` в UI.

## Этап 8. Независимый сервис синхронизации АТС

Изучи `Synchronize`, `GetRequiredSynchronizations`, `SyncMeridian`, `SyncXorcom`, `SyncCCM`. План зависит от исходной и новой станции, сохранённых/удалённых связей оборудования, `XorcomName`, изменения телефона и необходимости CCM даже при текущей не-CCM станции.

Используй реальные процедуры:

- Meridian: `sp_Meridian_PortSync`.
- Xorcom: `sp_XORCOM_PhoneNumberSync` (проверять существование `@Удаление`).
- CCM: `sp_CCM_PhoneSync` (по уникальному набору оборудования, включая изменённые/удалённые связи и оборудование подключения).

Раздели **SQL commit** и **внешнюю синхронизацию**. Явные статусы:

1. Данные не сохранены.
2. Данные сохранены, синхронизация не нужна.
3. Синхронизация выполняется.
4. Данные сохранены, синхронизация успешна.
5. Данные сохранены, синхронизация частично или полностью не удалась.

Планируй только необходимые операции; не повторяй их без причины. Логируй коды возврата, ошибки и затронутые ID, но не секреты. Обеспечь безопасный повтор подтверждённых шагов **без повторного INSERT/UPDATE основной формы**. Не имитируй внешнюю интеграцию, если на тестовом стенде она недоступна. Не закрывай форму с сообщением о полном успехе при ошибке АТС.

## Этап 10. Производительность и отсутствие лишних обновлений

- Не создавай каскады `new Phone(...)`, `new PhoneStation(...)`, `new Equipment(...)`, `new Location(...)` с синхронным SQL для каждой строки или каждого изменения.

- Используй targeted refresh связанных секций, а не полную перезагрузку Tel.
- Давай видимый busy/error-state для реальных операций с БД.
- Измеряй число запросов первичной загрузки и смены зависимых полей. Оптимизируй только доказанные лишние запросы, без спекулятивной инфраструктуры.
