## C. Реестр расхождений и рисков

Статус **«подтверждено кодом»** означает видимое расхождение в исходниках; **«верифицировать на БД»** — место с потенциальными триггерами/ограничениями, для которого нельзя делать вывод о фактическом повреждении БД без прогона.

### Блокирующие / высокий приоритет

**TEL-01 · P0 · Составной ключ телефонного оборудования нарушен (подтверждено кодом).**  
Legacy `Phone.SavePhoneEquipment` сравнивает пару `(EquipmentId, EquipmentConnectionId)`; legacy удаление/редактирование строк опирается на оба значения. Новый `Services/PhoneSaveBuilder.cs::AppendEquipmentDiff` группирует по `EquipmentId`, использует `ToDictionary(EquipmentId)` и обновляет или удаляет по одному `EquipmentId`. `Tel.razor.cs::OnEquipmentSelected` запрещает две связи одного оборудования с разными соединительными устройствами, `UpdateDependentState` исключает `EquipmentId` из выдачи. В `PhoneFormService.GetAsync` запрос `SELECT_ТелефонДругиеНомераОборудования` возвращает строку на каждую связь, затем результат превращается в `ToDictionary(EquipmentId)`: при повторяющемся ID возможно исключение уже при открытии карточки. `SQLQueries.UPDATE_ТелефонОборудование` и `DELETE_ТелефонОборудование` не проверяют `КодОборудованияПодключения`. **Сделать строго точный diff по `PhoneEquipmentKey` в моделях, UI, SQL WHERE, загрузке и серверной валидации.** Сверить фактический физический ключ таблицы и триггеры. `NULL` и `0` нормализовать по проверенному контракту.

**TEL-02 · P1 · Редактирование PBX-группы и порядок SQL UPDATE (подтверждено кодом; влияние триггера проверить на БД).**  
Legacy `Phone.Save` специально сохраняет для существующей записи `SavePhoneGroup()` **до** `SaveFields()`, а при INSERT — наоборот. Новый `PhoneSaveBuilder.Build()` всегда пишет главный UPDATE перед группами. Не менять порядок вслепую; изучить причины, тестировать изменение группы/станции/типа с членами и триггеры, затем восстановить необходимый порядок в одной транзакции. Сохранить `@@IDENTITY` на INSERT, пока договор с триггером не проверен.

**TEL-03 · P1 · Синхронизация АТС пропускает изменения групп/параллельных вызовов (подтверждено кодом).**  
`PhoneSyncPlanner::Build` определяет `mainChanged` и `equipmentChanged`, игнорируя `OriginalRelations.GroupMembers` и `.ParallelCalls`. В legacy `Save`/`GetRequiredSynchronizations` при сохранении запускает Meridian/Xorcom исходя из станции, включая изменения связанных списков. АТС может остаться с прежней конфигурацией после успешного commit. Планировать минимально достаточные операции по diff **всех** влияющих на АТС сущностей. Учитывать `NotUsed`, обе задержки, добавление/удаление, смену станции, старый/новый Xorcom и CCM. Проверить контракт `sp_Meridian_PortSync`, `sp_XORCOM_PhoneNumberSync`, `sp_CCM_PhoneSync`; запретить повтор лишних успешных команд.

**TEL-04 · P1 · Полный номер: пропущено пересечение для зависимых номеров (подтверждено кодом).**  
Legacy `TxtPhoneNumber_OnRenderNtf` проверяет совпадение полного номера **для независимых**, но пересечение по префиксу — **без этого ограничения**. Новый `PhoneFormService.ValidateServerAsync` добавляет оба `SELECT_ТелефонДубликатПолногоНомера` и `SELECT_ТелефонПересеченияПолногоНомера` только когда оба зависимых поля пусты. Разделить условия, сохранив исключение собственной записи. Тесты: независимый, `DrivenBy`, `DisplayedFrom`, обе стороны префикса, свой ID, пустые/ошибочные связи. Проверять полный номер, полученный из авторитетных данных на сервере, а не слепо доверять вычисленному браузером.

**TEL-05 · P1 · Гонки выбора сотрудника и описания АТС (подтверждено кодом).**  
`Tel.razor.cs::OnEmployeeChangedAsync` выполняет последовательно `GetEmployeeOrganizationAsync`, `RefreshAutomaticAtsDescriptionAsync`, `GetDefaultEmployeePhoneAsync` без версии выбора/identity guard. При последовательных выборах A→B поздний ответ A может записать заказчика/основной номер для B. `RefreshAutomaticAtsDescriptionAsync` также допускает устаревший ответ. Применить отмену/версионирование результатов на уровне всех зависимых async-операций, запретить перезаписывать последующее ручное изменение заказчика/описания; защитить смену страницы/ID и Dispose. Создать bUnit/асинхронные тесты с `TaskCompletionSource` и завершением запросов в обратном порядке.

**TEL-06 · P1 · Источник организации сотрудника не соответствует legacy (подтверждено кодом).**  
Legacy `DbsEmployee_Changed` использует `Employee.OrganizationId`, которое маппится на `Сотрудники.КодЛицаЗаказчика`. Новая `SQLQueries.SELECT_ТелефонОрганизацияСотрудника` выбирает `TOP 1 КодЛица FROM vwДолжности ORDER BY КодДолжности DESC`. Это другое бизнес-значение. Исправить источник на `КодЛицаЗаказчика` (или точно документированный эквивалент), не подменять работодателем последней должности. Подтвердить на тестовых сотрудниках с несколькими должностями/работодателями.

**TEL-07 · P1 · Выбор розетки не обновляет зависящие справочники (подтверждено кодом).**  
В `Tel.razor` `SocketSource` связан через `@bind-Value="_model.SocketId"`, но нет события обновления зависимостей. `UpdateDependentState` задаёт `EquipmentSource.SocketId`, `SocketSource.SocketId` и параметры доступности только при других событиях. После смены/сброса розетки список оборудования может фильтроваться по старой розетке. Сделать обработчик подтверждённого выбора/очистки розетки, пересчёт серверных фильтров, invalidation устаревших результатов `ClaySelect`, тесты последовательностей действий.

**TEL-08 · P1 · Неправильный исходный выбор radio для новых номеров (подтверждено кодом).**  
`Phone.ServicesKind` и `Phone.ViewInDirectory` — `int` с default=0; оба `ClayRadioGroup` показывают значение 0 сразу. В legacy для **нового обычного типа** `УслугиСвязи` не выбирается автоматически, группа radio `IsRequired=true`; для типа 0 принудительно `InsideHolding`, для 100/101 — `International`. Аналогично при создании новой PBX-группы `ViewInRef=NotDisplayed` по умолчанию, а для остальных новых типов не следует симулировать выбор пользователя. Ввести отдельное nullable-состояние UI для ещё не сделанного выбора, корректную обязательность и явное превращение в enum/поле при сохранении; сохранить пользовательский выбор после переключений A→B→A и копирования. Не допускать неявного 0 при пустом выборе.

**TEL-09 · P1 · Отсутствует побочный эффект основного номера сотрудника (подтверждено кодом).**  
Legacy `CbDefaultPhone_ValueChanged` при выборе основного номера и `ViewInRef == NotDisplayed/пусто` устанавливает `Displayed` (1). В новой форме `OnDefaultChanged` меняет только `IsDefault`. Восстановить правило и сохранить явные другие варианты отображения. Проверить наличие конфликтующего основного номера сотрудника и согласованность с триггерами.

**TEL-10 · P1 · Недостаточная повторная серверная проверка ссылок и фильтров перед записью (подтверждено кодом; последствия проверить на БД).**  
В `ValidateServerAsync` есть проверка типа/станции/порта/дубликатов/зависимостей, но отсутствует явная серверная проверка: член PBX-группы принадлежит допустимой станции, оборудование действительно допустимо для выбранных типа/станции/сотрудника/розетки, выбранная розетка активна/свободна и относится к разрешённому офису/расположению, изменение составного ключа допустимо. Фильтры `ClaySelect` не заменяют авторизацию и server-side validation; stale/вручную сформированное значение не должно записываться. При серверной проверке не терять уже сохранённые, но ныне исключённые значения: обеспечить сценарий read-only + явное решение. Уточнить FK/триггеры на тестовой БД.

**TEL-11 · P1 · Семантика прав редактирования заказчика требует завершения (подтверждено наличие только role43; точные права установить).**  
Новая форма сообщает «роль 43 и доступ к компании заказчика», но `PhoneFormService.HasRoleAsync(43)` и `EnsureWriteAccessAsync` проверяют лишь наличие роли, без контекста `CustomerId`. В рамках соседнего архитектурного задания разрабатывается общий `Employee CurrentUser` с `Роли`, областью `КодЛица` и замещениями; **не создавать второй механизм в Tel**. После интеграции использовать общую проверку для чтения/записи/удаления с учётом подтверждённых правил legacy, и повторно проверять до SQL. Не считать право чтения равно праву записи. Если legacy не содержит ограничения заказчика, зафиксировать источник требования до навязывания новой политики.

**TEL-12 · P1 · Частичные ошибки синхронизации и повтор (подтверждено кодом).**  
`RetryPendingSyncAsync` запускается до `_saving=true`, так что двойной клик может инициировать одновременные внешние вызовы. Повтор пересчитывает весь первоначальный план, включая успешные процедуры; для удаления номер уже удалён, но после восстановления синхронизации форма может остаться в состоянии `_deleted=true`. Сделать явную модель результата по каждой операции, повторять только failed/pending, блокировать параллельные нажатия, не выполнять повторный DB INSERT/UPDATE/DELETE, обеспечивать корректный выход после удаления и уведомления пользователя. Тесты двойного клика, частичного успеха, refresh/закрытия, reconnect.

### Важные функциональные и интерфейсные расхождения

**TEL-13 · P2 · Предупреждение о заказчике на расположении может быть ложным (подтверждено кодом).**  
Legacy `SELECT_CHECK_ТелефонныеНомера_ЛицаНаРасположенииТелефоннойСтанции` делает `IF EXISTS(SELECT FROM @Лица WHERE КодЛица=@КодЛицаЗаказчика) DELETE @Лица` — если заказчик допустим, предупреждений нет вообще. Новая `SELECT_ТелефонЗаказчикиНаРасположенииСтанции` делает `DELETE FROM @Лица WHERE КодЛица=@CustomerId`, оставляя прочих допустимых клиентов и вызывая ложное предупреждение. Исправить семантику «если выбранный допустим — вернуть пусто; иначе вернуть варианты». Тест с двумя допустимыми лицами и выбранным одним.

**TEL-14 · P2 · Неблокирующие замечания теряются после успешного сохранения (подтверждено кодом).**  
`PhoneFormService.SaveAsync` возвращает `Issues` даже при `Saved=true`; в `Tel.razor.cs::SaveAsync` `ShowIssues(result.Issues)` вызывается лишь при `!result.Saved`. `WarningAllowed`/`Info` (PBX employee, прочие заказчики, чужая переадресация) после успешной записи не показаны. Разделить ошибки, предупреждения, информационные уведомления; сохранить непустой список после успешного refresh, не блокировать запись на `WarningAllowed`.

**TEL-15 · P2 · Расположение секции «Параллельные вызовы» (подтверждено разметкой).**  
Legacy `Tel.aspx` ставит грид + быстрый ввод параллельного номера **после** `Номер автонабора` и **перед** `Сотрудник`. Новый `Tel.razor` ставит секцию **после** `Описание АТС`. Вернуть визуальную последовательность, компактную левую колонку, выравнивание подписи и элементов с учётом data state; сохранить `ClayGrid`. Обеспечить быстрый ввод номера плюс добавление по Enter и редактирование параметров через диалог, если это согласуется с общим UX. Старые поля не переименовывать.

**TEL-16 · P2 · Недостаточная валидация внутри диалога параллельных вызовов (подтверждено кодом).**  
`PhoneParallelCallDialog.Apply()` без собственной проверки закрывает диалог и переносит в общий черновик номер любого формата. Ошибка проявится лишь при глобальном Save. Добавить обязательность, regex `^\+?[0-9#*]+$`, max50, отсутствие дубля/совпадения с текущим, неотрицательные целые задержки в допустимом диапазоне и инлайн сообщения. Legacy округляет дробные задержки до целых, проверить точную конверсию; не обрезать произвольно. При ошибке диалог остаётся открыт и не мутирует исходный список.

**TEL-17 · P2 · Время изменений в гриде выводится в UTC (подтверждено кодом).**  
`Tel.razor.cs::FormatUtc` форматирует `dd.MM.yyyy HH:mm:ss 'UTC'`, тогда как legacy `Grid.SetColumnLocalTime` отображает локальное время браузера; общий `ClayChanged` умеет DST. Использовать единый механизм браузерного локального времени по дате события для строк PBX/оборудования/параллельных вызовов; не конвертировать через текущее смещение или часовую зону сервера. Тесты лето/зима.

**TEL-18 · P2 · Конфигурация pickupGroups и выбор розеток требуют строгой проверки (частично подтверждено).**  
`PhonePickupGroups.ForStation(0, Configuration["pickupGroups"])` ожидает строку с разделителями, тогда как legacy читает именованный `ConfigurationManager.GetSection("pickupGroups")` как словарь; проверить фактическую конфигурацию хоста. Если группы не загружены, **не разрешать произвольный строковый PickupGroup**, сейчас `PhoneFormValidator` проверяет принадлежность только если `AvailablePickupGroups.Count > 0`. Для розеток draft-aware фильтр при связанном оборудовании без LocationId не должен бесконтрольно переходить в поиск по офису станции. Проверить `Office.Enabled`, `Alive.Enabled`, `Free.SocketInclude` и fail-closed при отсутствии обязательного контекста. Сохранить доступность текущего ID для отображения, но не разрешать недопустимый новый выбор.

**TEL-19 · P2 · Часть связанных контекстных изменений не инвалидирует фильтры (подтверждено кодом).**  
Кроме выбора розетки (TEL-07), проверить после изменения `CustomerId`, `Connected`, `DrivenBy`, `DisplayedFrom`, станции, типа и номера: клиентский список, `FullNumber`, выбор ответственного, `AtsDescription`, `DefaultPhone`, доступность порта/розетки/оборудования и предупреждения. **TEL-22 · P2 · Отсутствует полноценная проверка Tel в браузере и с реальной БД (пробел покрытия).**

- Две строки оборудования с одинаковым оборудованием, но разными устройствами подключения без потери/краха; точное изменение одной связи и изоляция другой.

- Отказ от синхронизации после commit не вызывает повторный SQL Save, одновременный повтор невозможен, успешные операции не повторяются без нужды.
- Только `ClayGrid`; секция параллельных вызовов находится перед полем сотрудника; все времена `Changed` в клиентской зоне.
- Права и компания/замещения перепроверяются на сервере; новые enum и `CurrentUser` не дублируются при интеграции с архитектурным агентом.

## F. Ограничения по выполнению и публикации

Работа должна быть реализована в исходниках и тестах, **не ограничиваться объяснением или редактированием документации**. Работать в отдельных ветках по правилам репозитория, не производить merge без согласованного процесса. Соблюдать `AGENTS.md` относительно `git add`/commit/push: не выполнять их без явного разрешения или действующего поручения, точно указывающего публикацию. Тестовые данные и секреты не коммитить. Не менять DDL production и не запускать фактические звонки/настройки АТС на боевом окружении. Если необходим DB-скрипт диагностики, выполнять только чтение, а правки предлагать отдельно. Сохранять технологичность и производительность Blazor реализации, не копировать старые WebForms-компоненты или его устаревшую архитектуру.
