## 1. Установленные факты: НЕ перепутать страницы и два слоя меню

### 1.1. Где legacy действительно показывал меню

- `Inventory/default.aspx` содержит `<uc:MainMenu id="InvMainMenu" ...>` и **не содержит грид**. В `default.aspx.cs` убираются лишние стандартные кнопки из `MenuButtons`.
- `Inventory/Default/Grid.aspx` содержит `<div id="divMenu"><uc:MainMenu ... /></div>` **над** `<div class="v4formContainer" ...><csg:Grid ... GridAutoSize="True" /></div>`.
- `Grid.aspx.cs` задаёт параметры динамического грида из БД: `IsUseQueryTable=true`, фильтры, пагинация, автоподбор размеров, префиксы `InvFields_`, `InvFilter_`, `InvRows_`, `InvSort_`.
- Меню скрывается, если передан URL-параметр `return` (любой) либо `hidemenu=true/1` (без учёта регистра для `true`); `hidetitle=true/1` отдельно скрывает legacy `.v4pageTitle`; при `return=2` меняется нижний отступ грида. Это не терять: пометить, что именно в новом гриде соответствует `hidetitle`/`return=2`, и не скрывать вместо заголовка важные команды без проверки.
- `Styles/js/Kesco.V4.js` переставлял части DOM в `#v4form` и пересчитывал высоту `.v4formContainer` как высоту окна минус верхние/нижние блоки. **Это принцип компоновки, не код для копирования.**

### 1.2. Разделение ответственности

- **`Menu.Inventory.V4/MainMenu.cs`**: определяет корни меню, читает данные, строит URL, проверяет условия для настроек и операций.
- **`Controls.V4/MenuSimple.cs`**: рекурсивно рисует группы и ссылки, активный элемент, пиктограммы, разделители, встроенные дополнительные кнопки/Help; не знает таблицу `Запросы`.
- **`STYLES/js/Kesco.Menu.js` + `css/Kesco.css`**: dropdown с задержкой ~300 мс на pointer-enter/leave, абсолютное позиционирование, вложенные подпункты справа, динамический z-index, выравнивание столбца иконок по их ширине. **Скроллирования и контроля выхода за viewport там нет**, его добавить в новой реализации.

Новая архитектура ДОЛЖНА повторить это разделение: независимый компонент **отображения** меню в `Clayzor.Lib.Web.Controls`, данные/бизнес-семантика Inventory в `Clayzor.Lib.Entities`, прикладная сборка структуры и URL — в Inventory (тонкий компонент `InventoryMainMenu`/composer). Никаких SQL-запросов внутри Razor-компоненты общего меню; никакой зависимости Controls от Inventory.

## 2. Точная семантика данных меню

### 2.1. Пункты из `Запросы`

В legacy `MainMenu.FillRootMenuSubItems` трижды выполняет:

```sql
SELECT * FROM Запросы WHERE ТипЗапроса = @КодТипаЗапроса ORDER BY КодЗапроса
```

Сопоставление аргументов зафиксировано:

- `ТипЗапроса=1` → «Инвентаризация» (`Inv_lblInventory`);
- `ТипЗапроса=2` → «Несоответствия» (`Inv_lblInconsistencies`);
- `ТипЗапроса=3` → «Отчёты» (`Inv_lblReports`).

Поля: `КодЗапроса` (стабильный ID), `Запрос` (caption), `ФормаСписка`, `Пиктограмма`. Порядок **по `КодЗапроса`**, а не по алфавиту. Не удалять пустые разделы, не придумывать другие категории/фильтры/права. Проверить живую схему и выборку `SELECT КодЗапроса, Запрос, ТипЗапроса, ФормаСписка, Пиктограмма, ПунктМенюОтчета, ФормаОтчета FROM Запросы ...` в доступной `DS_user` **read-only**. Не выводить полный SQL запросов и персональные данные в отчёт/браузер. Если нет доступа к БД, НЕЛЬЗЯ подменять реальные пункты статически составленным списком — создать тестовую fake-data fixture и явно отметить блокер интеграции.

Новый `appsettings.json` уже указывает `ClayGrid:Dynamic:SettingsTable="Запросы"`, `GridIdQueryParam="id"`, `DS_user`, префиксы `InvFields_`, `InvFilter_`, `InvRows_`, `InvSort_`. **Меню не должно создавать второй механизм динамического грида**. Для обычных запросов направлять на существующий `Home.razor` (`/?id=<КодЗапроса>`). Текущий `ClayGrid` читает тот же ID через `NavigationManager.Uri`.

Рекомендуемый способ чтения — один параметризованный SELECT с `ТипЗапроса IN (1,2,3) ORDER BY ТипЗапроса, КодЗапроса` и второй по ID для контекстного пункта отчёта; эквивалентность порядку доказать тестом. Помещать SQL-константы в **`Clayzor.Lib.Entities/SQLQueries.cs`**, типизированные данные/read-helper в Entities; пользоваться существующим scoped `DbManager` + Dapper и правильной `DS_user`. Не вводить Repository/ORM/новый DALC. Не использовать `SELECT *` при новом коде. Если для фиксированных значений 1/2/3 обнаружится справочник-каталог в БД, соблюдать `AGENTS.md` об именованных enum по настоящему имени таблицы; не создавать фиктивный enum при непроверенной схеме.

### 2.2. Формирование URL — две НЕ взаимозаменяемые ветки

Из `MainMenu.GetUrlByRow()`:

**А.** `ФормаСписка` пуста → legacy `UrlGrid(КодЗапроса)` = `/Default/Grid.aspx?id=<код>` (относительно `URI_inventory`). В Clayzor этот случай должен вести на новую страницу **`/?id=<код>`**, а не на legacy ASPX. Не ломать уже работающие `?id=...`, `CLID`, shared-параметры грида. **Б.** `ФормаСписка` непуста:

- Если начинается с `@`, текст после `@` — ключ настройки `appSettings` (например, `URI_...`, фактические имена берутся из строк БД). Значение нужно найти через конфигурацию; не считать `@URI_` готовым URL.
- Если указан прямой абсолютный `http(s)` URL — использовать его.
- Иначе legacy разрешал относительный путь относительно адреса текущей страницы; адаптировать базовый адрес корректно для новой структуры и проверить реальный целевой путь, а не механически склеивать строки.
- **К ВНЕШНЕЙ форме добавлялся `idQuery=<КодЗапроса>`**, а не `id`! Сохранять существующие query/fragment и правильно добавлять параметры.
- Затем legacy добавлял `menuId` для индикации выбора. ID получался как `Запрос.GetHashCode()` — **не переносить в новую систему как идентичность**: это не стабильный DB ID и потенциально коллизионный. Активный пункт определять по `КодЗапроса` и текущему `id`/`idQuery`, а совместимость со старым `menuId` отдельно проверить и описать. Не ломать URL внешних приложений без основания.

Для всех вариантов создать проверенный typed URL builder с корректным кодированием, `?`, `&`, `#` и query без двойного `id/idQuery`, без `javascript:`/`data:`/`vbscript:`, без HTML/JS инъекций. Если ключ конфигурации не найден — логирование и безопасный disabled/error state, **не переход на `?menuId=...` и не заглушка вымышленным адресом**. Исходные подписи Razor кодирует как текст; не использовать `MarkupString` для данных из БД. Внешние ссылки открывать в том же контексте, что legacy, пока фактами не подтверждена необходимость нового окна.

### 2.3. Остальные корневые пункты (порядок обязателен)

Порядок `MainMenu.RenderMainMenu()`:

1. **Инвентаризация** (DB тип 1)
2. **Несоответствия** (DB тип 2)
3. **Отчёты** (DB тип 3)
4. **Операции** (hard-coded, не «все запросы типа 4»)
5. **Контекстный отчёт**: ОДИН отдельный корневой пункт, только если текущий `id` присутствует и соответствующая строка `Запросы` содержит непустой `ПунктМенюОтчета`. Caption = `ПунктМенюОтчета`, URL берётся через `ФормаОтчета` как **ключ конфигурации** (legacy удалял `@` из ключа). Если ключ/URL отсутствует — не копировать `javascript:alert`, показать понятную недоступность; не приписывать `idQuery`, пока legacy-код/реальный отчёт этого не требует.
6. **Настройки инвентаризации**: только при действующем разрешении. Legacy проверяет Windows-группы `BUILTIN\Administrators`, `TEST\Programists`, `EURO\Programists`, `TEST\SupportTeam` через `Page.User.IsInRole`, ссылка из **`URI_inventory_queries`** + при выбранном `id` параметр `_idQuery=<id>E` (суффикс `E` важен). В новом `web.config` этот URI **сейчас не найден**; реальное значение legacy `uri.local` не подтверждено. **До внедрения рабочего перехода проверить целевой адрес/права и спросить пользователя, если адрес недоступен.** Не открывать настройки всем пользователям и не придумывать свой C#-механизм ролей; применять утверждённую схему identity/CurrentUser, учесть реальные Windows-группы и серверный контроль доступа.

**Операции → «Очистить настройки формы».** В legacy пункт добавляется только при наличии контекста динамического грида (`grid.aspx?id=...` либо внешняя форма с `idQuery=...`) или дерева `Locations/`; операция была `cmd(... ClearFormParams)` на Grid listener. Код `Grid.cs` сбрасывает фильтры, параметр количества строк, порядок и видимость колонок, вызывает `SaveVisibleAndOrderParam(true)`/`SaveControlSettings(true)` и reload. В новой форме Home создать **типизированную команду** сброса параметров текущего динамического `ClayGrid`, с подтверждением и возвратом к значениям по умолчанию определения, включая фильтры/порядок/видимость/сортировку/пагинацию по подтверждённой схеме. Новые параметры группировки и быстрого поиска следует включать, если они теперь часть сохраняемого состояния, но документировать точный диапазон сброса. Не выполнять legacy `cmd` и не удалять настройки всех пользователей/всех запросов. У `ClayGrid` нет публичной готовой функции с полным legacy-контрактом — расширить его минимальным методическим интерфейсом/параметром, не переписывая динамическую архитектуру. **Особо проверить**, что после удаления/сброса настроек `SaveDynamicState()` не сохраняет обратно старое состояние во время re-render; целевой грид остаётся единственным экземпляром и корректно перечитывается. Для внешних legacy-форм и `Locations` — только после подтверждённого соответствующего bridge-контракта, не имитировать работоспособность.

Дополнительно сравнить поведение `MenuSimple`: значок текущего пункта (зелёная точка), отдельная колонка пиктограмм, индикатор вложенных уровней, разделители, Help и дополнительные `MenuButtons`. Не дублировать Help/кнопки, уже имеющиеся в toolbar `ClayGrid`; составить таблицу «что мигрируем/что уже существует/что нельзя переносить без проверки».

## 3. Клиентское поведение: подробный разбор STYLES и новая спецификация

Из `Kesco.Menu.js`: `dd.init(menuId)` проходит по вложенным `<ul>`, привязывает `mouseenter`/`mouseleave`, задерживает открытие/закрытие примерно на 300 мс, меняет `display`, `height`, `opacity`, z-index; вложенный popup позиционируется вправо по фактической ширине пункта; `setItemsWidth` выравнивает ширину колонок пиктограмм. `Kesco.css` рисует горизонтальные верхние пункты (`height:26px`), dropdown начиная с `top:27px`, второй уровень справа. `MenuSimple.cs` рекурсивно строит `<ul>/<li>` и даёт текущему пункту визуальный индикатор.

**Перенести смысл, а не опасную технику**: никакого `new Function`, `setTimeout` через JS-строки, глобальных jQuery-селекторов, z-index без управления, HTML-конкатенации с заголовками БД. Новая компонента должна поддерживать 2+ уровня вложенности (хотя у этого Inventory основные DB-запросы плоские), крупные списки, быстрый переход, состояния loading/error/empty и строгую доступность.

**Обязательное новое требование — видимость и скроллирование:**

1. Каждый dropdown/submenu ограничен **фактически доступной высотой viewport**, а не фиксированными 400px. Если подпунктов больше, внутри панели появляется **вертикальная прокрутка** (mouse wheel, touch, trackpad, клавиатура); горизонтальный scrollbar меню обычно не нужен, длинные подписи не выталкивают панель за край и доступны через title/перенос в разумных пределах.
2. Открываемое подменю не обрезается контейнером грида, drawer, `MudMainContent` или `overflow:hidden/auto` родителей. При необходимости использовать существующий MudPopoverProvider/portal; предварительно проверить, что `ClayMenu`/MudMenu поддерживают требуемую рекурсию и viewport collision. Если нет — отдельная общая компонента с минимальным JS для измерения/позиционирования.
3. Рядом с правой границей submenu открывается **влево**, а рядом с низом — позиционируется вверх/уменьшает max-height. При resize, zoom и прокрутке якоря положение пересчитывается. Использовать фактические `getBoundingClientRect()`, viewport, безопасные отступы; не переопределять старый CSS глобально.
4. Корневые горизонтальные разделы при малой ширине не должны выходить за экран: компактный mobile trigger/`Ещё` либо горизонтальная прокрутка **корневой полосы**, но сами открытые popup не должны обрезаться в этой полосе. Проверить сценарий с открытым drawer.
5. Сохранить удобную задержку hover при pointer (`~300ms` как ориентир), но **click/tap** должны открывать сразу. Попадание курсора от parent к submenu не должно закрывать меню случайно. Клик вне меню и `Escape` закрывают; после закрытия фокус возвращается на активатор.
6. `Tab`, `Shift+Tab`, `Enter`, `Space`, `ArrowUp/Down/Left/Right`, `Home/End` должны обеспечивать предсказуемое перемещение и прокрутку к сфокусированному пункту. Правильно использовать `aria-expanded`, `aria-controls`, `aria-current`, роли меню либо нативную семантику ссылок; не блокировать обычные ссылки для клавиатуры.
7. Отдельные CSS-классы компоненты, размеры из `--clay-*`/Mud palette, светлая/тёмная тема, hover/focus/active, единая колонка иконок (не ломать верстку при PNG/GIF разной ширины), fallback для отсутствующей пиктограммы без сломанного изображения.
8. Не дублировать HTML-контейнеры при каждом открытии; очистить JS event listeners/ResizeObserver/ссылки при Dispose; не хранить состояние меню глобально между Blazor circuits.

Проверить в браузере **не только отсутствие горизонтального overflow у страницы**, но и геометрию _каждой_ открытой панели: левый/правый и верхний/нижний края внутри viewport, последний пункт достижим прокруткой, правильный z-index поверх грида, нет перекрытия модальных диалогов. Сценарии 320×568, 360×640, 600×700, 900×700, 1155×750, 1440×900, дополнительный низкий viewport ~400px и zoom 125%/200%; тест с длинными подписями и 50–100 пунктами.

## 4. Перекомпоновка текущей `Home.razor` — отдельная обязательная задача

**Текущий факт:** `Home.razor` содержит только `<ClayGrid ... Dynamic=true .../>`. `MainLayout` даёт AppBar + responsive drawer + `MudMainContent Class="pa-6"`. `ClayGrid.razor.cs` сейчас рассчитывает высоту таблицы жёстко относительно viewport: `calc(100vh - 280px)`, `-330px`, `-380px` в зависимости от раскрытых trays, а `ClayGrid.razor` имеет собственный `MudPaper Class="pa-4 ..."`. Простое добавление меню сверху ухудшит высоту, будет перекрывать таблицу/пагинацию и создавать несколько конфликтующих областей прокрутки.

**Обязательный результат:** полноразмерная страница Inventory с верхним горизонтальным меню **под глобальным AppBar** и над содержимым грида, без дублирующей навигации из drawer и без уничтожения его существующих ссылок/поведения. Разнести в DOM три области: `navigation header`, `grid working area`, `grid paging/footer`. Пользоваться CSS grid/flex с `min-height:0`, измеряемыми размерами, `dvh`/ResizeObserver при необходимости. Не использовать отрицательные margin как основной способ компенсации `.pa-6` и не менять layout всех форм глобально без регрессионной проверки. Нужны чёткие bounds: меню не забирает всю высоту, сам грид/его таблица прокручивается корректно, toolbar, фильтр, подвал и заголовки не пропадают. **Выпадающие панели выводить вне scroll-клиппинга грида**.

Подход к высоте грида выбрать после изучения текущего `ClayGrid` (возможно — дополнительная опция «занять доступную высоту контейнера» с сохранением прежнего поведения по умолчанию). Нельзя просто подставить ещё одно `calc(100vh - Npx)` для Home. Если нужен минимальный общий API для container-driven height, добавить его обратносовместимо и покрыть тестами. Не превращать страницу со стандартным гридом в нестандартный самописный грид.

**Поведение маршрутов:**

- `/` без `id`: как legacy `default.aspx`, **меню без самовольного выбора первого запроса**; показать нейтральное приглашение выбрать запрос. Не оставлять текущую ошибку «Не указан код запроса» как единственный контент стартовой страницы.
- `/?id=N`: меню + один существующий dynamic `ClayGrid` с определением N из БД. Активный пункт подсвечен; заголовок берётся из определения/реальных данных.
- Смена N→M **на том же маршруте** реально обновляет один грид, его identity/definition/колонки/SQL/параметры и активный пункт. Уточнить реакцию `Router`/`Home` на изменения query: `ClayGrid.OnParametersSetAsync` не может переинициализироваться, если страница вообще не re-render. Использовать доказанный механизм (`[SupplyParameterFromQuery]`, key/событие маршрута, etc.) и bUnit/UI-тест. Избегать принудительного reload страницы без причины.
- Учитывать `CLID`, shared/персональные настройки и существующие URL-фильтры. Не переносить фильтры запроса N на запрос M, если это не поддерживается текущими правилами `ClayGrid`. `?id` не должен случайно дублироваться; reset не должен пересбрасывать состояние других запросов.
- `?return=...`, `?hidemenu=true/1`, `?hidetitle=true/1`: задокументировать, как legacy-флаги влияют на меню и заголовки; реализовать подтверждённое соответствие на Home без поломки grid-toolbar/попапов. Если старый контракт embedding/return не поддерживается в Clayzor — оставить явно известное ограничение, а не заявлять полной совместимостью.

Условия прокрутки при 1) обычном меню, 2) раскрытой панели фильтров, 3) раскрытой панели группировки, 4) обеих панелях, 5) открытом drawer, 6) popup над высоким гридом — отдельные UI-тесты. Важно сохранить работу выбора строк, печати, Excel, справки, контекстных фильтров, настроек колонок и существующих диалогов.
