Ты выполняешь **приёмочный аудит перед дорогостоящим вводом в эксплуатацию**, а не косметическую доработку. Наличие поля, кнопки или зелёного unit-теста не равно подтверждению эквивалентности legacy. ## 2. Что уже похоже на корректный перенос — не ломать при исправлениях

Следующие утверждения **подтверждены структурой C#/Razor/SQL**; результат реального исполнения всех сценариев не заявляется:

1. Основные поля `Equipment` сохраняются через подтверждённый `UPDATE_Оборудование`; телефонные связи могут быть сохранены одним SQL batch/transaction (`EquipmentPhoneSaveBuilder`), а `ReturnDate/Notes` изменяются отдельно от изменений состава номера.
2. Дочерние списки представлены `ClayGrid`, а не произвольными таблицами; диалоги привязаны к соответствующим секциям, обновляется нужный раздел.
3. Строки SIM и учётных записей в общем чтении не включают PIN/PUK и пароль; секреты читаются отдельно после проверки роли. **Это правильная архитектура, но именно при ошибке отдельного чтения обнаружен блокирующий дефект, описанный ниже.**
4. Добавление расположения «На руках» с отсутствующим действующим ответственным предусматривает вставку обеих записей одной транзакцией. Изъятие ответственного и новое расположение также оформлены транзакционным builder.
5. Обновление периода SIM-услуги и установки ПО учитывает границу окончания: интерфейс показывает включительную дату, SQL хранит исключительную дату (`DATEADD(day,1)`/обратное чтение). Не заменять схему дат локальными предположениями.
6. Лицензия — отдельная запись/section, дневной компьютерный snapshot хранит компоненты RAM/HD/SSD, бухгалтерский учёт — отдельная история.
7. Legacy специально **не предусматривает удаление UPS-тестов** (`LinkUps.DetectTestsDelta` содержит закомментированный блок удаления). Не добавляй Delete только ради симметрии CRUD.
8. `PhoneConfigHandler` присутствует как HTTP endpoint и `EquipmentForm` вызывает его с MAC; проверить контракт и разрешения, но не создавать дубликат обработчика.

## 3. Подтверждённые дефекты и отклонения — исправление до приёмки

### EQ-AUD-P1-01. Ошибка чтения секретов способна затереть ранее сохранённые пароль/PIN/PUK

**Доказанная цепочка:**

- `DbManager.QueryAsync<T>` возвращает `[]`, а `ExecuteScalarAsync<T>` возвращает `default` при connectivity `SqlException` (например, SQL error 53).
- `EquipmentFormService.GetAccountPasswordAsync()` преобразует `null` в `string.Empty`. `EquipmentAccountDialog.razor`, `OnAfterRenderAsync`, не отличает отказ чтения от реально пустого пароля, позволяет редактировать Notes/ограниченные права и возвращает пустой `Password` на UPDATE.
- `EquipmentFormService.GetSimSecretsAsync()` использует `QueryAsync` + `SingleOrDefault() ?? new EquipmentSimSecrets()`; `EquipmentSimDialog.razor` при пустом ответе считает секреты считанными и возвращает пустые поля на Save.
- `EquipmentAccount.UpdateAsync` и `EquipmentSimSaveBuilder.BuildSave` пишут эти значения как часть обычного сохранения.

**Требование:** fail-closed для отдельного чтения. **Отсутствие строки** (удалена конкурентно) и **невозможность прочитать** отличаются от легитимного пустого секрета. Не меняй глобальный контракт DALC без анализа других потребителей; используй точечный API чтения, который выбрасывает connectivity error или явный статус результата. При ошибке редактирования запрети подтверждение и SQL write; при корректном чтении обеспечь сохранение исходных секретов, если пользователь менял только другие поля. Пароли не выводить в логи, DOM, отчёты и тестовые failure messages.

**Обязательные тесты:** ошибка 53 + любые другие типовые connectivity, null/no row; update Notes при существующем пароле; изменение договора SIM без изменения кодов; отказ и повтор; успешное сохранение кодов. Реальные password/PIN/PUK в тестах не использовать; `CommandLog` должен подтвердить отсутствие UPDATE при неуспешном read.

### EQ-AUD-P1-02. Повтор незавершённой синхронизации телефонных связей недоступен через «Применить» и теряется при уходе

**Код:** `EquipmentForm.razor.cs`:

```csharp
private bool IsModified => _loaded && _model is not null && Snapshot() != _originalSnapshot;
private bool CanSave => IsModified && _canEdit && !_loading && !_saving;
```

`EquipmentForm.razor`: `<ClayToolbarButton ... Disabled="@(!CanSave)" OnClick="@(() => SaveAsync(false))" />`.

После успешного `UpdateWithPhonesAsync` форма пересчитывает `_originalSnapshot` и выполняет `LoadCurrentAsync(Id)`; `_pendingPhoneSync` сохраняется, если equipmentId тот же. При ошибке АТС `IsModified == false`, **«Применить» заблокирована**, хотя текст предлагает повторить через неё. Более того, `NavigationLock`, `CancelAsync` и `BeforeInternalNavigationAsync` ориентируются только на `IsModified` и не предупреждают о потере pending.

**Обязательное исправление:** отдельные `HasUnsavedDraft`, `HasPendingPhoneSync`, корректные `CanApply`, `CanClose`/confirmation. При pending доступна повторная синхронизация через **реальную кнопку** без нового SQL UPDATE. Сохрани уже успешные этапы; если сейчас pending хранит весь дифф, докажи, что повтор не дублирует успешно отправленные команды, либо минимизируй pending до неудачных операций. При закрытии/навигации показывать, что SQL уже сохранён, но повтор в этой форме будет потерян; при Refresh — отдельно проверить сохранение pending в текущем circuit. Переход на другое оборудование должен не перенести pending на чужую запись. Durable outbox **не добавлять без согласования**.

**Тест:** bUnit щелкает **rendered** «Применить» и «Отмена», не вызывает приватный `SaveAsync` через reflection. Выполняются ошибка ATS после SQL Save → `1 SQL update`, `1 sync` → «Применить» → `0 новых SQL update`, `1 новая sync` → pending очищается; отказ закрытия, подтверждение закрытия, Refresh и смена `id`. Нынешний `EquipmentFormTests.SyncFailure_RetriesWithoutRepeatingDatabaseSave` вызывает сохранение напрямую и не подтверждает доступность кнопки — дополнить, а не удалить.

### EQ-AUD-P2-03. UPS Save обновляет все строки даже без изменений — отклонение от legacy diff

**Legacy:** `Kesco.Lib.Entities/Corporate/Equipments/LinkUps.cs`, `DetectServersDelta` обновляет сервер только когда изменился `TurnOffConfigured`, `DetectTestsDelta` — тест только когда изменились дата, батарея, серверы или Issues.

**Clayzor:** `Inventory/UpsSaveBuilder.cs`:

- `currentServers.Where(originalById.ContainsKey(...))` → `UPDATE vwПодключенияUPS` для **всех** существующих серверов.
- `currentTests.Where(originalTestsById.ContainsKey(...))` → `UPDATE vwПодключенияUPSтестирование` для **всех** существующих тестов.

Это лишние операции с возможными триггерами и конкурирующими правками. **Требование:** строить действительно минимальный diff по полям, которые legacy считает значимыми; не удалять тесты; проверять уникальность ключей и отсутствие лишних UPDATE. Не использовать сравнение по ссылкам на mutable объекты.

**Тест:** два неизменных сервера + два неизменных теста → нет SQL UPDATE, только фактические операции; изменение одного флага → ровно один UPDATE; изменение только одного Issues → ровно один UPDATE; add/remove сервера и add test; два параллельных пользователя и конфликт версий. `EquipmentUpsPersistenceTests.DetailsDiff_ComposesTransactionWithoutTestDelete` не проверяет случай отсутствия изменений.

### EQ-AUD-P2-04. Отсутствует функциональность выбора проверенных серверов в UPS-тесте

**Legacy:** `Inventory/Equipment/LinkUps.aspx.cs`: `OpenTestDialog`, `InitializeTestServersGridDataTable`, `ToggleTestServer`, `FilterUncheckedTestServerRows`, `PatchIssuesMsgWithUncheckedServerWarning` и `ConfirmTestParams`. Доступные имена собираются из компьютерных серверов UPS, пользователь отмечает, какие получили оповещение; при непроверенных в Issues добавляется диагностическое предупреждение с проверкой ограничения длины.

**Clayzor:** `EquipmentUpsTestDialog.razor` содержит обычный `ClayTextBox` для `Value.Servers`; отдельного grid/выбора серверов и предупреждения о непроверенных не обнаружено.

**Требование:** восстановить поведение, а не просто поле. Серверы должны быть сопоставлены по реальному legacy-формату хранения (изучи `TestServerNamesContainer`, разделитель, валидность имён) и не подменяться произвольной свободной строкой; сохранить редактирование исторических тестов. Добавить типизированный UI выбора серверов с правилами доступности, предупреждениями и сохранением. Не придумывать статус сервера без подтверждения legacy.

**Тест:** серверы компьютерного типа с именами и без, marked/unmarked, повторное открытие, новых/существующих тест, запрет неверных имён, длина Issues, отмена диалога (SQL=0), SQL после подтверждения.

### EQ-AUD-P2-05. Неоднозначная область проверки прав при сохранении UPS

`EquipmentFormService.SaveUpsDetailsAsync` выбирает **первый** `ServerEquipmentId` из исходного/нового набора, вызывает `EnsureUpsAccessAsync` для него, после чего записывает diff для всего UPS. Если среди серверов есть записи разных владельцев, проверить, разрешает ли доменная/SQL-модель изменения всех таких строк. **Это риск, не доказанный обход прав**: SQL view/триггеры могут выполнить полноценную проверку.

**Требование:** сопоставить legacy права и фактический SQL-контракт `vwПодключенияUPS`, пользователя SQL соединения, роли по владельцу и разрешённость редактирования UPS в целом. Составить таблицу сценариев: один сервер, несколько владельцев, только новый сервер, только тесты, пустой список серверов, отзыв права. Не добавлять дубль C# authorization «на всякий случай»; сначала докажи границу полномочий и выбери узкое исправление.

### EQ-AUD-P2-06. Неуспешное чтение оборудования может выглядеть как «не найдено»

`EquipmentFormService.GetAsync` вызывает `DbManager.QueryAsync<Equipment>`; при connectivity error тот возвращает пустую коллекцию. `LoadCurrentAsync` при `model is null` устанавливает `_notFound = true`. Поэтому временная потеря соединения может отображаться как отсутствие оборудования, а не ошибка загрузки. Поскольку `GetFormDataAsync` использует `RunAsync`, у него иная модель ошибок. Требуется различить **genuine not found**, **connectivity** и **SQL exception**, не подменять одни другими.

**Тесты:** SQL error 53 перед первым SELECT, корректный пустой SELECT, ошибка batch секций, последующий Retry. Не загружать другую запись при позднем ответе после смены `id`. Убедиться, что форма не ломает Blazor circuit при исключении.

## 4. Исследовать и получить доказательство — не считать дефектом до проверки

### EQ-AUD-R01. Транзакционная граница телефонных связей и внешних АТС отличается от legacy

Legacy `Equipment.Save` исполняет телефонный diff, вызов АТС и иногда сетевую операцию внутри `TransactionScope(ReadCommitted)`. Clayzor фиксирует SQL transaction, затем вызывает `SynchronizePhonesAsync` и хранит circuit-local pending. Это может быть **осознанным архитектурным отступлением** для уменьшения блокировок БД, но оно меняет гарантию «SQL откатывается при неудачной АТС».

В документе обоснуй фактические правила: какие ошибки legacy откатывают SQL, какие нет; что клиент видит в Clayzor; как выполняется повтор, компенсация и информирование пользователя; почему допустима eventual consistency. При недостатке данных получи решение владельца, не прячь за словами «равнозначно legacy». **Не вызывай реальные АТС без разрешения.**

### EQ-AUD-R02. Персистентное состояние основной формы после сохранения дочернего бухгалтерского учёта

`RefreshAccountingAsync` меняет поля `_model.OwnerId`, `TenantId`, `DocumentReceiptOuId`, `DocumentWriteOffId` и некоторые baseline-поля, но `_originalSnapshot` основной формы напрямую не пересоздаётся. Эти поля входят в `Snapshot()`. Проверь сценарий: после SaveAccounting дочерняя транзакция уже состоялась, а основной `EquipmentForm` может остаться «грязным» и при «Применить» повторно обновить основную таблицу. Это особенно важно при параллельной смене владельца/документа другим пользователем. Существующий `EquipmentFormTests.RefreshAccounting_PreservesModifiedMainFields` проверяет сохранение черновика, но не всю SQL-семантику после дочерней записи.

Нужно установить ожидаемое legacy-поведение по `BuhEquipment`, проверить две ветки: основной черновик не менялся / пользователь уже изменил одно из тех же полей. Не стирать черновик при фиксации дочернего изменения. Изменения SQL — только при доказанном несоответствии.

### EQ-AUD-R03. Конкурентное редактирование периодов и «последней записи»

Проверить реальные ключи `От`, точность `datetime` SQL Server 2008 R2 (округление миллисекунд), порядок сортировки и условие редактирования только последнего периода. Проверить сценарии, когда после открытия формы появился новый период у другого оператора. В частности, `DeleteAccountingAsync` принимает только `equipmentId` и текущего владельца, SQL удаляет `TOP 1 ORDER BY От DESC`: нужно не удалить **не ту** новую строку по устаревшему подтверждению. Но legacy может иметь тот же контракт — зафиксировать это и запросить решение, если улучшение меняет поведение. Проверить `UPDATE` по `От` и `@@ROWCOUNT`.

### EQ-AUD-R04. Полное совпадение серверной валидации с legacy

Сверить все зависимости `ValidateTypeConfig`, `ValidateMACConfig`, выбор модели/типа/владельца, обязательный SN, три MAC, сеть и отсутствие/наличие модели, документ/дата списания, услуги SIM и договоры. Сверить **не только UI**, но и прямой вызов backend с неверными значениями (необходима серверная fail-closed защита). Код legacy `Equipment.ValidateMACConfig` удалял все неhex символы и проверял длину, Clayzor нормализует MAC в `OnMacChanged`, имеет иной whitelist. Фактическая целевая семантика для нестандартных разделителей должна быть согласована по legacy, а не угадываться.

### EQ-AUD-R05. Реальные права/замещения и признаки доступности дочерних кнопок

Проверить сочетания ролей 42/43/44/66/68/102/103, конкретные лица владельца/арендатора, замещения и данные `fn_БухгалтерскийУчет`. Выяснить, какое действие допускается у пользователей с одной специальной ролью без 43; не переносить право 43 автоматически на SIM/бухгалтерию. Проходить **прямой вызов** save-метода, отказ SQL, отзыв роли после открытия. Для Tel/Xorcom/CCM права обеспечиваются SQL synchronization procedures — не дублировать их в C#.

### EQ-AUD-R06. Остальные особенности, которые нельзя молча отбросить

- SIM: прежняя активная SIM с тем же номером; предварительное подтверждение, перенос лица ПДн, списание конкурирующей SIM атомарно, откат при ошибке, доступ PIN/PUK; сохранение номера и договора без сброса секретов.
- SIM-услуги: тарифный план, `_BLOCK`, обязательность, история, два поля фактического периода, стоимость в день/месяц/включения, суммы, плановые даты и условные предупреждения. Отсутствие в текущем гриде отдельных данных, которые legacy действительно выводила, фиксировать в матрице; не добавлять фиктивные поля, которых нет в подтверждённой схеме.
- Расположения/ответственные: «На руках», текущий ответственный, новая локация при изъятии, запрет дублирования, допустимые даты/UTC, срок возврата ≤3 месяцев, предупреждения о несовместимом оборудовании на одном рабочем месте.
- Компьютер: сохранение дневного снимка **за текущую дату**, история старых, сериализация компонентов и округление HD, `MemoryBanks`, стандартные конфигурации; нельзя изменять исторический snapshot, если legacy позволяла только добавить текущий.
- ПО/лицензии: корректные внешние ссылки по `SoftwareId`, признак деинсталляции, период inclusivity, запрет дублирования или превышения количества, обновление only needed, тип лицензирования и неотображаемые поля.
- Бухгалтерия: материал/ОС, обязательные документы, инвентарный номер, арендатор, старт/конец, права 66/68 по лицу, удаление именно допустимого периода, синхронизация видимых полей основной формы.
- Телефоны: ключ связи, аппарат-посредник, срок возврата/примечание, базовый номер, гостиничный номер, выбор подходящих номеров, не дублировать запись, корректный SQL diff и PBX ветки.
- Учётные записи: роли, секретность паролей, сохранение неизменённого пароля, корректный composite key `EquipmentId + Login` и отсутствие write при read-ошибке.
- UPS: add/remove server, переключение выключения, тесты, ограничение по типам серверов, выбор адресатов теста, сохранение только изменённых строк и отсутствие удаления тестов.
- Router, сеть, Wake-on-LAN, инвентаризация, внешний PhoneConfig/Beeline: составить карту **реализовано / отложено по согласованию / непроверено**; ничего не запускать на реальном оборудовании без согласования. `SIM detail`/внешняя тарификация в текущей документации отложены — не выдавать за «полная parity».

## 7. Критерии приёмки / STOP conditions

Работа **не принимается**, если выполнено хоть одно условие:

- пароль/PIN/PUK может быть заменён пустым при чтении, которое завершилось ошибкой, или нарушены права получения секретов;
- кнопка «Применить» недоступна для реального pending ATS, повторяет SQL UPDATE, теряет pending без предупреждения либо дублирует уже успешную внешнюю команду;
- UPS Save создаёт UPDATE неизменённых строк без обоснования и зафиксированного разрешения, а выбор серверов в тесте работает иначе, чем legacy, без согласования;
- основные или дочерние SAVE/DELETE ошибочно изменяют данные другого EquipmentId/PhoneId/UPS/теста;
- проверка основного и дочерних SQL не различает отсутствие записи, ошибку соединения и отказ прав;
- тесты проверяют только private handler или generated SQL, а реальное состояние кнопок/диалогов/отмены не проверено;
- отсутствует объяснение осознанных отличий от legacy, особенно SQL commit ↔ внешняя АТС;
- реальные АТС, сеть, схема SQL, триггеры или секреты затронуты без разрешения;
- нет итоговой сравнительной матрицы и протокола восстановления тестовых данных.

## 8. Мой вердикт как независимого проверяющего

**На проверенной ревизии принимать `EquipmentForm` без доработки нельзя.** Причины: подтверждены опасная потеря секретов при fail-soft чтении, недоступность UI-повтора АТС и потеря pending при уходе, лишние SQL UPDATE по UPS и недоперенесённая логика отметки проверенных серверов UPS. Архитектура компонентов и ряд SQL-контрактов корректны, но наличие большого количества существующих тестов эти пробелы не закрывает: соответствующие тесты либо отсутствуют, либо вызывают приватные методы в обход реальных кнопок.

**Границы уверенности:** это независимый source-based аудит GitHub с прямой проверкой конкретных legacy-методов и новых C#/SQL-файлов; я **не запускал** здесь сборку, browser и тестовую SQL-базу. Фактические SQL-триггеры, права в БД, состояние реальных АТС и все редкие варианты исторических данных необходимо дополнительно подтверждать. Не выдавать риск за доказанную ошибку без воспроизведения.
