# Этап 1. Полная инвентаризация условий отображения

**Это самый важный этап. Не переходи сразу к исправлению CSS.**

Построй матрицу соответствия legacy и Blazor для каждого поля, блока, табличной секции, команды и действия.

Для каждого элемента установи:

- точное место в legacy;
- исходное условие отображения;
- условие доступности для чтения и редактирования;
- источник значения;
- реакцию на изменение зависимых полей;
- наличие и корректность реализации в Blazor;
- ожидаемое поведение после исправления;
- тест, подтверждающий соответствие.

При анализе legacy учитывай одновременно серверные условия `<% if (...) %>`, `data-feature`, `data-phone`, `data-mac`, `data-netname`, методы `ShowAdvGrids`, `DisplayAndRequiredTypeFields`, `SetInitControls`, `RenderDocumentHeader`, `FillGrid_*`, а также `eqmnt.display.*` из JavaScript.

Не считай, что отсутствие `Visible` в ASPX означает постоянную видимость: часть элементов скрывается CSS и показывается скриптами.

### 1.1. Правила для основных полей

| Элемент | Что необходимо воспроизвести |
|---|---|
| Тип оборудования | Обязательный выбор и сортировка по ID/алфавиту |
| Модель | Зависимость от типа, но также возможность выбрать модель первой |
| SN | Обязательность зависит от типа и наличия выбранной модели |
| Сетевое имя | Показывать с учётом признака типа и выбранной модели |
| MAC | Учитывать число интерфейсов модели |
| MAC 2 | Показывать только при наличии второго интерфейса |
| MAC ILO | Показывать только при наличии третьего интерфейса |
| Телефонные номера | Учитывать телефонный признак типа и выбранную модель |
| Видеокамера | Только для IP-телефона, тип 30, при соответствующей телефонной функциональности |
| Пул телефона | Только для соответствующего IP-телефона, а не всех телефонных типов |
| SIM-характеристики | По признаку `ЕстьХарактеристикиSIM` |
| Должность | Восстановить условное поле legacy, выяснив фактический источник и назначение |
| Лицензия | По `ЕстьХарактеристикиSoft` |
| Компьютер | По `ЕстьХарактеристикиКомпьютера` |
| Установленное ПО | По `ЕстьХарактеристикиКомпьютера`, независимо от лицензий |
| Учётные записи | По MAC-характеристике типа и роли дежурного инженера |
| Маршрутизатор | По фактическому наличию действительной записи маршрутизатора |
| Бухгалтерский учёт | Не скрывать данные только потому, что нет прав на изменение |
| Арендатор | Сохранять режим ReadOnly, предусмотренный legacy |

Не используй `HasMonitorCharacteristics` для управления флажком видеокамеры. Это разные бизнес-характеристики.

Для MAC учитывай, что legacy `ModelEquipment.MacAddressFeature` преобразует `Net` в маску: 0 — нет полей, 1 — MAC, 2 — MAC + MAC 2, 3 и более — все три поля. Текущий расчёт по `NetworkInterfaces` эквивалентен этому правилу, если корректно обработано отсутствие модели. Не заменяй работающий расчёт без необходимости.

### 1.2. Раздели сохранённое и редактируемое состояние

В legacy `ShowAdvGrids()` выполняется при первоначальном построении табличных секций, а `DisplayAndRequiredTypeFields()` реагирует на изменение типа/модели в основной части формы.

Это не одно и то же.

Раздели:

- состояние оборудования, загруженное из БД;
- текущий черновик основных полей;
- подтверждённый выбор типа/модели;
- права пользователя;
- состояние связанных табличных секций.

Не допускай, чтобы временная очистка типа во время ввода поискового текста внезапно скрывала существующие данные, уничтожала несохранённые телефонные связи или сбрасывала другие поля.

Для каждой зависимой секции явно определи, должна ли она следовать сохранённому типу или черновику. За основу возьми фактический жизненный цикл legacy.

Условия видимости, права редактирования и необходимость очистки данных должны вычисляться раздельно.

**Результат этапа:** согласованная с исходным кодом матрица поведения и исправленный механизм вычисления состояния формы. При необходимости выдели небольшие чистые функции для его тестирования.

# Этап 2. Исправление состояния типа, модели и зависимых полей

В `EquipmentForm.razor.cs` проверь и исправь:

- `OnTypeIdChanged`;
- `OnTypeChanged`;
- `OnModelIdChanged`;
- `OnModelChangedAsync`;
- `ClearHiddenFeatures`;
- `UpdateOptions`;
- `ShowNetworkName`, `ShowPhones`, `ShowPhonePool`, `ShowCamera`, `MacCount`.

### 2.1. Очистка выбранных значений

Сейчас обработчик очистки модели может оставить прежний `_selectedModel`. Аналогичная проблема существует со сбросом выбранного типа.

Исправь все такие случаи.

При очистке модели не должны продолжать отображаться старые характеристики, PN и зависимые MAC-поля.

При очистке типа не должны сохраняться устаревшие признаки предыдущего типа.

При этом ввод поискового текста и Escape не являются подтверждением изменения бизнес-сущности.

### 2.2. Изменение типа

После подтверждённой смены типа:

1. Проверь необходимость сброса выбранной модели.
2. Обнови фильтр моделей.
3. Пересчитай видимые поля и обязательность заполнения.
4. Не очищай несвязанные данные без необходимости.
5. Не теряй несохранённые изменения в табличных секциях.
6. Не допускай применения запоздавшего результата асинхронного запроса.

### 2.3. Изменение модели

Проверь случаи:

- модель выбрана без типа;
- модель выбрана после типа;
- модель относится к другому типу;
- модель очищена;
- выбор отменён через Escape;
- быстро выбраны две разные модели;
- ответ первого запроса поступил после второго.

При выборе модели без типа соответствующий тип должен автоматически устанавливаться, как в legacy.

Исправь `EquipmentModelSelectDataSource`: сейчас `SearchAsync()` возвращает пустую выдачу при отсутствии выбранного типа, хотя legacy разрешает поиск без такого ограничения.

### 2.4. Полные характеристики модели

В legacy `RenderModelData()` выводит не только PN, но также:

- мультимедиа;
- диагональ;
- CPU;
- количество и название сетевых интерфейсов;
- тип памяти и число банков;
- драйвер;
- ресурс;
- примечание модели.

Сейчас Razor фактически показывает только PN, причём текущий `GetByIdAsync` источника моделей не загружает все необходимые поля.

Восстанови загрузку и отображение этих характеристик. Не выполняй отдельный SQL-запрос для каждого поля и не подменяй отсутствующие значения фиктивными данными.

**Результат этапа:** стабильное состояние основных полей, полная информация о модели, правильная реакция на изменение и отмену выбора.

# Этап 3. Восстановление условных блоков и прав доступа

Проверь все действия, которые в legacy зависят от ролей, владельца и характеристик оборудования.

### 3.1. Учётные записи

Legacy показывает блок учётных записей только при соблюдении условий по роли дежурного инженера и MAC-характеристике типа.

Новая форма отображает его практически безусловно.

Восстанови правила видимости и доступа.

Отдельно проверь авторизацию чтения паролей, добавления, редактирования и удаления. Скрытая кнопка не заменяет серверной проверки прав.

### 3.2. UPS

В legacy операция подключения UPS предусмотрена для IT-оборудования (`TypeId < 100`), кроме SIM, с проверкой роли специалиста по инвентаризации относительно владельца оборудования.

Сейчас блок подключения UPS отображается для любого оборудования.

Исправь:

- условия наличия команды;
- проверку роли с учётом владельца;
- фильтр выбора UPS;
- ограничение поиска расположением, применяемое legacy;
- доступность редактирования связей.

Отдельно сохрани чтение существующих UPS-связей. Возможность просмотра подключений и право добавлять UPS — разные вещи.

### 3.3. Подключение к рабочей сети

В legacy команда появляется при наличии компьютерных характеристик и роли исполнителя заявок службы поддержки пользователей.

В новой форме она определяется в основном состоянием сетевого подключения и общей ролью редактирования оборудования.

Восстанови фактические условия `RenderDocumentHeader()`.

Проверяй не только возможность нажать кнопку, но и полномочия при выполнении серверной операции.

### 3.4. Лицензии, SIM, бухгалтерия

Убедись, что:

- право изменения лицензии пересчитывается при изменении владельца или арендатора;
- права изменения SIM соответствуют legacy;
- бухгалтерские сведения доступны для разрешённого просмотра даже без права изменения;
- доступность действий в табличных секциях не наследуется безусловно от `_canEdit`;
- серверная операция самостоятельно проверяет авторизацию.

Не объединяй все права в одну переменную `_canEdit`.

### 3.5. Вспомогательные операции

Проверь отдельно права и условия показа:

- «Конфигурация» IP-телефона;
- «История имён»;
- «Копировать»;
- детализация SIM оператора Билайн;
- WakeOnLan;
- редактирование сроков возврата;
- операции с UPS.

Для внешних функций, недоступных на текущем стенде, не создавай фиктивную реализацию. Отражай документированные инфраструктурные ограничения.

**Результат этапа:** ни одна команда не показывается или не выполняется в недопустимом контексте, при этом разрешённое чтение не теряется из-за отсутствия права записи.

# Этап 5. Полное восстановление табличных секций

Это отдельная крупная часть работы. Недостаточно вывести несколько текстовых колонок с кнопками CRUD.

Для каждой секции сравни:

- условие отображения;
- порядок;
- состав и порядок колонок;
- условия скрытия отдельных колонок;
- представление пустых и специальных значений;
- ссылки;
- выделение важных состояний;
- действия над строкой;
- правила добавления/редактирования;
- обновление зависимых секций после сохранения.

### 5.1. Телефонные номера

Legacy показывает колонку оборудования подключения только при наличии соответствующих связей.

При ограниченном режиме просмотра колонка срока возврата также может скрываться, если сроки отсутствуют.

Восстанови условный набор колонок, обозначение основного номера, ссылки на номер и оборудование подключения, сведения об изменении и визуальное выделение просроченного срока.

Проверь предупреждение о нескольких телефонных номерах для оборудования в гостиничном номере (`CheckUniqueNumberInHotel`).

### 5.2. Компьютер

Legacy `FillGrid_Computer()` строит динамический набор колонок RAM1...RAMn, HD1...HDn, SSD1...SSDn в зависимости от реального содержимого.

Также он показывает стандартные конфигурации и даты их назначения, скрывает неиспользуемые колонки и соблюдает определённый порядок.

Текущий Blazor-грид с общими значениями RAM/HD/SSD не воспроизводит это поведение.

Используй существующие `RamComponents`, `HdComponents`, `SsdComponents` и данные стандартных конфигураций.

Не теряй данные отдельных модулей ради упрощённой суммы.

### 5.3. SIM и дополнительные услуги

Восстанови зависимость команд добавления/редактирования SIM от наличия существующей записи.

Если SIM уже зарегистрирована, форма не должна предлагать создание второй независимой карточки.

Для дополнительных услуг проверь `ОтПлан`, `ДоПлан`, обязательные услуги компании, тарифный план и условия вывода колонок, применяемые в `FillGrid_SimUsl`.

Часть плановых полей в новой модели пока отсутствует. Сначала подтверди SQL-контракт их чтения и сохранения. Не вводи произвольную семантику.

### 5.4. Лицензии и ПО

Для лицензий восстанови полный набор полей, включая URL проверки лицензии, и корректное переключение между добавлением и редактированием.

Для установленного ПО восстанови независимую от лицензий видимость, ссылки на ПО, отображение периода и признаки деинсталляции.

### 5.5. Расположения и ответственные

Сохрани раздельные операции назначения, изъятия и изменения примечаний/сроков.

Проверь ограничения по датам, специальное расположение «На руках» (55), транзакционное изменение связанных данных и обновление двух таблиц без полного сброса формы.

Исторические записи не должны случайно изменяться или удаляться.

### 5.6. Бухгалтерский учёт и маршрутизатор

Бухгалтерская секция должна показывать разрешённые данные независимо от права их изменения.

Удаление должно соответствовать подтверждённому контракту последней записи.

Для маршрутизатора восстанови отображение описания и инвентарных модулей, с сохранением ссылок и режима read-only.

### 5.7. UPS и последняя инвентаризация

В legacy подключённые UPS выводятся компактной сводкой в верхней части формы, со ссылками на информацию о подключениях.

Восстанови этот пользовательский сценарий, а не только нижнюю таблицу.

Для последней инвентаризации обеспечь корректное отображение даты, сотрудника, примечания, неисправности и расхождения расположения.

Вместо технического `ID расположения` при наличии данных показывай понятное название/путь с предусмотренной ссылкой.

### Общий компонент табличных секций

Текущий `ClayDetailGrid<TItem>` поддерживает только текстовый `TextSelector`. Он не обеспечивает все legacy-сценарии условных колонок, ссылок и форматирования.

При необходимости минимально расширь общий компонент:

- условная видимость колонки;
- шаблон содержимого ячейки;
- условное оформление значений/строк;
- сохранение стандартных действий и read-only режима.

Не создавай отдельные копии таблиц для EquipmentForm и не переписывай все секции на произвольный HTML.

**Результат этапа:** восстановлены состав, условная видимость и смысловое представление данных во всех секциях.

# Этап 8. Автоматические тесты

Используй существующую инфраструктуру xUnit и bUnit. Не создавай ещё один тестовый стек без необходимости.

Особое внимание — таблице сценариев видимости.

## Обязательные группы проверок

**Тип и модель:**

- модель отсутствует;
- модель с 0, 1, 2 и 3+ сетевыми интерфейсами;
- тип с телефонным признаком;
- IP-телефон типа 30;
- монитор, не являющийся IP-телефоном;
- компьютер без программного признака;
- программное оборудование без компьютерного признака;
- SIM;
- маршрутизатор с существующими и отсутствующими данными.

**Роли:**

- пользователь без прав изменения;
- специалист по инвентаризации;
- дежурный инженер;
- исполнитель заявок поддержки;
- SIM-специалист;
- специалист по лицензиям;
- бухгалтерские роли;
- разные владельцы и арендаторы.

Проверь не только вычисленные свойства, но и фактическую Razor-разметку, наличие элементов, состояние Disabled/ReadOnly и недоступность серверных операций.

**Переходы состояния:**

- очистка типа;
- очистка модели;
- выбор модели без типа;
- смена типа;
- Escape при редактировании;
- повторный выбор прежнего значения;
- поздний асинхронный ответ;
- изменение владельца и фильтров;
- несохранённые телефоны при изменении типа;
- навигация на другой ID;
- disposal во время загрузки.

**Данные таблиц:**

- нулевое/одиночное/множественное содержимое;
- условные колонки;
- просроченные и пустые сроки;
- динамические RAM/HD/SSD;
- видимость специальных действий;
- ссылка на сущность;
- просмотр без права редактирования.

### Важное замечание по существующим тестам

В `ClaySelectDataSourceTests.cs` есть тест `EquipmentModelWithoutType_ReturnsEmptyWithoutDatabaseCall`, который закрепляет текущее ограничение поиска моделей без выбранного типа.

Это не подтверждение совместимости с legacy, а тест существующего поведения нового кода.

После восстановления поиска без типа данный тест необходимо осмысленно изменить, а не оставлять ошибочное требование ради прохождения тестов.

Также расширь существующие `EquipmentFormTests.cs` и профильные тесты источников данных. Не ограничивайся тестом порядка первых нескольких кнопок.

### Проверки сборки

Из корня Clayzor:

```bash
dotnet build Clayzor.sln
dotnet test tests/Clayzor.Lib.Web.Controls.Tests/Clayzor.Lib.Web.Controls.Tests.csproj
```

При известном зависании полного testhost выполни независимые профильные тесты, зафиксируй проблему и не объявляй полный прогон успешным без доказательств.
