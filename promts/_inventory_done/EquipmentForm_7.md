## 1. EQ7-P1-01 — обязательные чтения не должны превращаться в «нет данных» при SQL connectivity

### Наблюдение

В `Clayzor.Lib.DALC/DbManager.cs` read-методы `QueryAsync<T>` и `ExecuteScalarAsync<T>` при ряде connectivity-ошибок возвращают пустую коллекцию или `default(T)`. В `EquipmentFormService` следующие методы вызывают их без различения «пусто по данным» / «БД недоступна»:

- `GetUpsServersAsync()`, `GetUpsTestsAsync()`, `GetUpsLinksAsync()`;
- `GetSimCardsAsync()`, `GetSimServicesAsync()`, `GetDuplicateSimIdAsync()`;
- `GetAccountingAsync()`, `GetLocationsAsync()`, `GetResponsiblesAsync()`, `GetAccountsAsync()`, `GetLicensesAsync()`, `GetComputerHistoryAsync()`, прочие критичные дочерние reads.

Самое опасное: `OpenUpsDialogAsync` перехватывает SQL-ошибку, но `GetUpsServersAsync` может её *не передать* и показать пустой редактор существующих связей. `OpenSimDialogAsync` получает `null` от `GetDuplicateSimIdAsync` не только когда дубликата нет, но и при потере связи. Этот результат влияет на подтверждение списания другого оборудования.

### Требование

- Составить **карту всех чтений**, влияющих на запись, удаление, массовые действия и формирование исходного снимка/диффа. Разделить: обязательные (ошибка должна быть исключением), необязательное декоративное чтение, поиск/фильтр.
- Для обязательных чтений использовать имеющиеся fail-closed API `QueryRequiredAsync<T>` / надёжный scalar-эквивалент, не переписывая весь DALC и не меняя молча контракт других потребителей.
- Для проверки дублирующей SIM запрос должен различать `0 rows` и `SQL не выполнен`; перед SQL-списанием повторно удостоверяться в актуальности найденного дубликата и подтверждения, если данные могли измениться между SELECT и UPDATE.
- По ошибке чтения UPS не открывать диалог с пустыми списками, не выполнять SQL diff; при ошибке после открытия — не заменять исходный снимок пустым. Уведомлять об ошибке и разрешать повторное открытие.
- Подтверждение/CRUD должны быть fail closed при потере соединения; никакого удаления или перезаписи по «пустому» результату чтения.

### Тесты

`EQ7_READ_*`: SQL error 53/10054 в **первом и втором** SELECT UPS, повтор после восстановления; SIM duplicate lookup с реальным дубликатом и connectivity; пустой результат без ошибки как нормальный случай; история бухгалтерии/расположений/ответственных не очищается при connectivity; сохранённый черновик и открытый диалог не превращаются в отсутствие данных. Для каждого теста проверить лог SQL-команд: **нет INSERT/UPDATE/DELETE при неуспешном обязательном чтении**. Проверить также сценарий позднего ответа после смены EquipmentId/dispose.

## 2. EQ7-P1-02 — вернуть единую авторизацию `Employee CurrentUser`, доказать корректность областей роли

### Наблюдение

В `EquipmentForm.razor.cs` вычисляются флаги через `Service.HasRoleAsync(43/42/102/103)` и `HasRoleForPersonAsync(...)`, **поле `Employee CurrentUser` отсутствует**. `EquipmentFormService.HasRoleAsync(int)` вызывает `SELECT_ТекущийПользовательИмеетРоль`, в котором `fn_ТекущиеРоли()` фильтруется только `КодРоли`, без `КодЛица`. Это не доказывает обхода реальных SQL-триггеров, но не соответствует установленной архитектуре и оставляет область полномочий непроверенной.

См. корневой `AGENTS.md`: `Employee` — единственный владелец ролей, SID, principal, замещений; `EquipmentFormService` не должен вводить собственные `HasRoleAsync/HasRoleForPersonAsync`; перед записью и внешним действием проверка должна быть свежей и привязанной к актуальному оборудованию/владельцу.

### Требование

- Изучить реальный `Employee` (не копировать целиком legacy) и **перевести страницу на `Employee CurrentUser`** в first-load, полученный из серверной доверенной Windows/SQL identity. Доказать соответствие Negotiate principal и SQL `SUSER_SNAME()`/SID и не принимать application service account за пользователя.
- Использовать enum `Роли` и подтверждённые областные правила (`КодЛица=0` — глобально; owner/tenant; замещения и сроки). Не заменять их проверкой «роль встречается где-нибудь». Не угадывать значение роли 42.
- При смене владельца и арендатора пересчитывать соответствующую доступность. На каждой серверной операции брать **актуальные ID/владельца из БД**; подтверждать права после смены владельца в другом circuit и после отзыва роли.
- Сохранить права legacy, а не навязывать всем действиям одно правило «только 43»: отдельно исследовать 42 (SIM/услуги), 43 (оборудование/UPS), 44 (лицензии), 66/68 (бухгалтерия), 102 (учётные записи/конфигурации), 103 (рабочая сеть); проверить историческое использование ролей по лицу и без лица. Если действия в legacy допускают роль одного владельца, не расширять права на других.
- Проверить `fn_ТекущиеРоли()` в SQL-контексте *действительно вызывающего пользователя*, включая замещение. Защитные триггеры/вьюхи не заменяют корректную UX/Service авторизацию.
- Сохранить функциональность Users/других форм и запретить параллельные самостоятельные role SQL pathways. Минимальный последовательный переход с гарантией компиляции.

### Обязательная отрицательная матрица

Пользователь А с ролью 43 только у владельца X; оборудование у X и Y; пользователь B без роли; global-role; замещение; отзыв роли после открытия; смена владельца в другом circuit; direct вызов service без рендера; невозможность определить Employee или principal mismatch. Повторить для SIM, аккаунтов, бухучёта и UPS. Проверить **не только disabled-кнопки, но отсутствие DML и внешних вызовов** при запрете. Не объявлять доказанным обход по одному отсутствию фильтра owner: зафиксировать результаты реальных триггеров отдельно.

## 3. EQ7-P1-03 — безопасное редактирование существующей бухгалтерской записи (не только удаление)

### Наблюдение

`EquipmentFormService.SaveAccountingAsync()` проверяет возможность по `accounting.OwnerId` из черновика. `EquipmentAccounting.SaveAsync()` выполняет `UPDATE ОборудованиеБухУчета ... WHERE КодОборудованияБухУчета=@Id` и не сверяет затронутое оборудование, владельца на момент исполнения, `Изменено`/конкурирующее изменение, число строк. При `0 affected` может наступить ложный success. Исправление конкурентного *DELETE* в EQ5/EQ6 **не распространяется на UPDATE**.

### Требование

- Для edit подтверждать существование **именно** `accountingId`, его принадлежность текущему оборудованию, исходную версию/время изменения и право над текущим фактическим владельцем, а не только выбранным новым owner в черновике; для смены бухгалтерии — проверить разрешение изменять оба задействованных контекста по подтверждённым правилам.
- Параметры и права перепроверять в одном атомарном SQL-контексте с UPDATE. Для delete сохранить существующую логику exact-id + latest + `UPDLOCK,HOLDLOCK` без утечки session isolation.
- `@@ROWCOUNT`/status должны быть проверены: 0 строк — явный конфликт/«обновите запись»; не сигнализировать success. При конкуренции или SQL exception не затереть черновик.
- Взять у legacy `EquipmentBuxMove_form.aspx.cs` валидацию документа списания: недоступный пользователю документ нельзя использовать; не полагаться исключительно на UI-filter справочника. Сверить номер, материал/ОС, даты, обязательные поля, side effects триггеров, менять только при доказанном расхождении.
- SQL 2008 R2, без лишнего повышения session-wide isolation/XACT_ABORT, без прямых записей минуя авторизацию.

### Тесты

`EQ7_ACC_*`: существующая строка удалена во втором circuit; строка перенесена в другое оборудование; изменён владелец; изменилась версия/примечание; два редактирования одного ID; 0 rows; owner X→Y, роль только по X, только по Y, по обоим; недоступный документ; SQL 53 и сохранение draft; обычный INSERT, UPDATE, DELETE с trigger enabled. Перед/после проверить состояние всей истории, поля и audit (`Изменил`, `Изменено`).

## 4. EQ7-P1-04 — SQL↔АТС: зафиксировать решение владельца, не менять молча

### Известная неэквивалентность R01

Legacy `Kesco.Lib.Entities/Corporate/Equipments/Equipment.cs`, `Save(bool...)`, использует `TransactionScope(ReadCommitted)` вокруг сохранения оборудования, телефонного diff и вызова `PhoneAndEquipmentSynchronize`. Новая `EquipmentForm.SaveAsync()` сначала COMMIT SQL, затем синхронизирует Xorcom/CCM и сохраняет неудачные операции в `_pendingPhoneSync`, существующий только в памяти Blazor circuit. При закрытии circuit и падении приложения retry исчезает; после успешного SQL можно получить рассогласование с АТС.

**Запрещено** агенту самостоятельно выбирать новую архитектуру, включать `TransactionScope` вокруг внешних вызовов, добавлять durable outbox/фоновые процессы, менять процедуры АТС или выдавать текущую семантику за эквивалентную legacy.

### Результат агента — аналитическая часть

Предоставить короткое техническое решение **без реализации, пока нет выбора владельца**:

- **A — принятие исключения:** сохранение SQL отдельно от АТС, circuit-local retry; какой мониторинг и кто вручную восстанавливает сбои, какие пользователи видят pending после потери circuit.
- **B — durable outbox:** транзакционное сохранение pending в БД, идемпотентность/дедупликация, восстановление после рестарта, конкуренция и ретраи; указать минимальную схему и риски.
- **C — legacy-like:** установить точную семантику нынешних stored procedures/external calls и возможность отката; транзакция SQL не откатывает физический внешний side effect сама по себе. Проверить совместимость с SQL Server 2008 R2 и последствия долгих транзакций.

Приложить матрицу состояний `SQL committed? × ATS succeeded? × circuit lost? × repeated save?`, оценку безопасного replay, изменение телефона/оборудования в другой сессии между попытками. До решения владельца оставить текущую реализацию и явную запись «не соответствует legacy / R01 open», все регрессионные тесты retry сохранить.

## 7. EQ7-P2-03 — Net, диагностика сетевых портов, сетевые действия

Legacy `Equipment_form.aspx.cs::DisplayNet` выполняет не только поиск и построение ссылок. Он:

- сравнивает количество найденных портов `vwЛокальнаяСеть` с `EQ.ObjModel.Net` и условиями MAC/MAC2;
- выделяет сомнительные подключения красным;
- отдельно обрабатывает switch/router и скрывает секцию при определённых количествах портов;
- обновляет `eqmnt.ping.existInLocalNet/state()` и имеет путь `WakeOnLan`.

Новая EquipmentForm отображает `_networkPorts` ссылками на `/Net/Net`, но не reproduces все эти правила. Кроме того, действие Attach/Detach, которое в legacy выполняется в составе сохранения, теперь отдельное: проверить именно его поведение при ошибках сохранения/перезагрузки.

### Требование

- Восстановить проверенные бизнес-условия сетевых предупреждений, необычные исключения switch/router, `*`-префикс и связь с модельной характеристикой `Net`. Если legacy `ping`/WakeOnLan/внешняя диагностика не переносится технически — составить строгую таблицу `функция → доступность legacy → новый аналог / причина отсутствия` и вынести решение на владельца; не объявлять полноту.
- `SetNetworkAttachmentAsync`: **не** полагаться на `IsModified` как на доказательство успешного сохранения. Если Save завершился, но повторная загрузка завершилась ошибкой и `_model == null`, не продолжать обращение к `_model.Id` и не запускать attach/detach. Класс ошибки должен быть сохранён и показан без `NullReferenceException`.
- Проверить actual count после SQL 53 в `GetNetworkAttachmentCountAsync`: чтение `default(int)=0` нельзя принимать за подтверждённое «отключено». Серверная проверка роли 103, типа оборудования, текущего владельца и возможных внешних побочных эффектов — обязательно.
- Нельзя удалять/перезаписывать Net-данные, оставленные для независимого ревью; тесты на своей изолированной паре портов/оборудований.

Тесты `EQ7_NET_*`: модель Net=1/2/3, два найденных порта без двух MAC, switch/router, скрытые `*` имена, сетевой indicator, attach/detach после ошибки Save или SQL reload, потеря SQL 53 при проверке счётчика, защита от изменения ID в confirmation, при наличии согласованного WOL — только mock.
