### EQ5-P1-01. `EquipmentTypeId` теряется по дороге к UPS-тесту

**Код:** `Components/Pages/Equipment/EquipmentForm.razor.cs`, `CloneUpsServers()` (на базовом снимке строки около 1930–1937); `EquipmentUpsDialog.razor`; `EquipmentUpsTestDialog.razor`; `Rules/UpsTestServerSelection.cs`.

**Текущая цепочка:** SQL `SELECT_ID_СервераПодключенияUPS` возвращает `T.КодТипаОборудования` → модель `UpsServerLink.EquipmentTypeId` заполнена → `OpenUpsDialogAsync()` вызывает `CloneUpsServers(originalServers)` → **метод не копирует `EquipmentTypeId`** → `AvailableNames()` и `BuildRows()` допускают только `ТипыОборудования.Компьютер` (1) → в окне теста реальные компьютеры становятся нераспознанными, недоступными для выбора. Вложенные тесты `EquipmentUpsTestDialogTests` передают готовые `UpsServerLink` с заполненным типом и потому эту интеграционную ошибку не видят.

**Исправить:** сохранить `EquipmentTypeId` при клонировании. При необходимости проверить перенос всех остальных существенных полей `UpsServerLink`; избежать разрастания локальных копий маппинга. Не заменять условие выбора «компьютер» на «любой тип» — это сломает legacy-логику.

**Обязательные тесты:**
- От SQL row `КодТипаОборудования=1`, `НазваниеСервера="srv-a"` до `OpenUpsDialogAsync` → `EquipmentUpsTestDialog`: `srv-a` виден, узнаётся, чекбокс активен, выбор сохраняет ожидаемый `Servers`.

- Test должен проходить через **настоящий метод клонирования** (или форму), а не только через `Rules.BuildRows()` с вручную заполненными объектами.

### EQ5-P1-02. Два новых UPS-теста `Id=0` ошибочно считаются дубликатами

**Код:** `src/Clayzor.Lib.Entities/Inventory/UpsSaveBuilder.cs`, начало `Build()`; `EquipmentUpsDialog.razor`, `AddTest()`.

**Воспроизведение:** открыть UPS, дважды добавить новый тест в дочерний список, нажать OK; у обоих новых тестов `Id=0`. Сейчас `currentTests.GroupBy(item => item.Id).Any(group => group.Count() > 1)` выбрасывает `InvalidOperationException` **до формирования SQL**, хотя добавление двух новых записей допустимо. `DetailsDiff_ComposesTransactionWithoutTestDelete` проверяет только одну новую запись.

**Исправить:** ID=0 — не реальный идентификатор сохранённой записи. Уникальность проверять для **положительных** ключей, сохранив запрет дубликатов реально существующих `Id>0`. Убедиться, что `originalTests` содержит только сохранённые записи и не пересекается с новыми по фиктивным ID. Не запрещать пользователю создать две строки в интерфейсе.

**Тесты:** 2 новых `Id=0` → ровно 2 INSERT `vwПодключенияUPSтестирование`, корректные и независимые параметры; 2 одинаковых существующих `Id>0` → отказ до SQL; смесь из одного редактирования и двух новых → один UPDATE и два INSERT, без DELETE; ошибка второй записи при выполнении → rollback всего diff на тестовой БД/при контролируемом сбое.

### EQ5-P1-03. Проверка полномочий только по первому серверу UPS

**Код:** `Services/EquipmentFormService.cs`, `SaveUpsDetailsAsync()` (около 377–395), `EnsureUpsAccessAsync`; `EquipmentForm.OpenUpsDialogAsync()`.

Текущая реализация получает **первый** `ServerEquipmentId` из `originalServers + currentServers`, вызывает `EnsureUpsAccessAsync` только для него и затем исполняет SQL diff по **всем** связям указанного UPS. Этот первый ID не обязан быть сервером, из карточки которого пользователь открыл диалог. Массив исходных/текущих серверов не является доверенным источником информации о владельцах и правах. Ранее документированное чтение UPS-триггера подтверждает проверку глобальной роли 43, но **не** проверку владельца каждой изменяемой связи.

**Риски:** пользователь с правом на один сервер может изменить другой сервер и его связь с UPS; либо пользователь с правом на исходное оборудование получит ложный отказ из-за другого первого сервера. Даже если серверный Blazor UI обычно не допускает произвольных ID, write-path обязан проверять полномочия самостоятельно.

**Порядок:**
1. Составь подтверждённую матрицу доступа по legacy `LinkUps`, меню EquipmentForm, модели владельцев/арендаторов и реально действующему SQL trigger. Не смешивай глобальную и локальную роль 43.
2. Предложи владельцу системы **одно явно сформулированное правило** для UPS, содержащего серверы нескольких владельцев. До решения — fail-closed на неоднозначных multi-owner изменениях, не расширяй доступ.
3. При реализации должен проверяться достоверный контекст операции (UPS ID, исходная связь с редактируемым оборудованием) и **актуальные** затронутые строки из БД, а не только первый ID из списка. Чтение прав на UI не заменяет повторной серверной проверки непосредственно перед записью. Не доверять переданному ownerId.
4. Различать изменение теста самого UPS, добавление связи, удаление и правку флага. Не требовать права на произвольный чужой сервер, если его запись операцией не затрагивается, без принятого бизнес-правила.

**Обязательные отрицательные тесты:** два разных владельца A/B и право только на A (A первый; B первый; изменение B; удаление B; добавление B; только тест UPS), изменение владельца между открытием и сохранением, отозванная роль, SQL role есть глобально, но нет по лицу, попытка сохранения другого UPS id. При запрете — **никаких INSERT/UPDATE/DELETE**. При успешном пути — только согласованные изменения. Проверить соответствие транзакции и SQL trigger, без отключения trigger.

### EQ5-P1-04. Удаляется «последняя сейчас» бухгалтерская запись, а не та, которую подтвердил пользователь

**Код:** `EquipmentForm.razor.cs`, `DeleteAccountingAsync(EquipmentAccounting latest)`; `EquipmentFormService.DeleteAccountingAsync(int equipmentId, int? ownerId)`; `SQLQueries.DELETE_КодОборудования_ОборудованиеБухУчета`.

**Воспроизведение:** пользователь А открыл карточку, последняя строка имеет `Id=41`; пользователь Б создал более позднюю строку `Id=42`; пользователь А подтверждает удаление `Id=41`. UI передаёт лишь equipmentId и устаревший ownerId; SQL `DELETE ... WHERE id IN (SELECT TOP 1 ... ORDER BY От DESC)` удалит `Id=42`. При этом проверка права сделана по владельцу, переданному из старого состояния, а не обязательно по владельцу удаляемой строки.

Это **унаследованный legacy-риск**, но его существование в legacy не делает его безопасным. Предыдущий агент документировал его как `R03`, а пользователь просил приёмку с высокой стоимостью последующих доработок.

**Исправить при согласовании изменения legacy-поведения:** сервер принимает конкретный подтверждённый `EquipmentAccounting.Id`, сверяет `EquipmentId`, проверяет, что запись всё ещё является последней на момент изменения, повторно устанавливает полномочия на актуального владельца, и только затем удаляет в защищённой SQL-транзакции. При конфликте «запись устарела» — отказ без удаления с предложением обновить данные. Учесть одинаковые даты `От` (детерминированный tie-break), SQL Server 2008 R2, блокировки/изоляцию или эквивалентную атомарную conditional delete. Не делай отдельный SELECT, а затем незащищённый DELETE — это прежняя гонка.

**Тесты:** обычное удаление ID=41, новая запись 42 между открытием/подтверждением, запись с другой датой, смена владельца, нет роли, пустая история, параллельные транзакции и SQL ошибка. При любом конфликте запись 42 не должна исчезать.

Если владелец решит оставить точную legacy-семантику, отметь **явное письменное исключение из приёмки**, не называя гонку исправленной.

## 2. Не скрывать ранее зафиксированные расхождения и решения владельца

### R01 — SQL → АТС: транзакционность и сохранность pending после разрыва

**Подтверждённый legacy-контракт:** `Kesco.Lib.Entities/Corporate/Equipments/Equipment.cs`: `Save()` создаёт `TransactionScope` (`ReadCommitted`), выполняет изменения и `PhoneAndEquipmentSynchronize(...)` до `scope.Complete()`; при исключении синхронизации `Complete` не вызывается. Новая реализация сначала коммитит SQL, затем запускает АТС и хранит failed operations в `_pendingPhoneSync` внутри Blazor-компонента. Это **осознанное, но существенное семантическое отличие**.

Положительное исправление предыдущего агента **сохранить**: на `Применить` без новых SQL UPDATE повторяются только неуспешные Xorcom/CCM; успешные операции не повторять. Однако после закрытия вкладки, гибели circuit или рестарта приложения pending исчезает. Предупреждение пользователя — не механизм восстановления.

**Не внедрять автоматически outbox/фоновые задания и не менять процедуры АТС.** Подготовить owner-facing краткое решение:
- вариант А — принять неустойчивый к перезапуску `circuit-local pending` как документированное исключение, установить регламент ручной сверки/синхронизации;
- вариант Б — durable журнал/outbox + идемпотентность/возобновление, отдельная согласованная задача;
- вариант В — восстанавливать legacy-область транзакции, отдельно доказав допустимость внешних вызовов внутри неё.

До выбора владельца **полная** приёмка SQL↔АТС не подтверждена. Тесты должны явно разделять «работает в том же circuit» и «восстанавливается после нового circuit».
