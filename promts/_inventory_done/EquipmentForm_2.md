# Этап 1 (P1). Полная модель переходов «Тип → Модель → Характеристики»

## 1.1. Очистка типа

Сейчас ветка `OnTypeIdChanged(null)` устанавливает лишь `_model.EquipmentTypeId = null` и вызывает `UpdateOptions()`. Она оставляет старый `_selectedType`, `ModelSource.Filter.EquipmentTypeId`, а также ID и объект ранее выбранной модели. Поэтому `ShowComputer`, `ShowSim`, `ShowLicense`, `ShowAccounts` и другие условия могут вычисляться по старому типу, а часть основных секций — по старой модели.

Не исправляй это простым тотальным `null` на каждом вводе в `ClaySelect`: его механика изменения текста, восстановления через Escape и подтверждённого выбора уже специально защищена. Введи **чёткую разницу между промежуточным состоянием поиска, подтверждённым черновиком и сохранённым типом**.

Протестируй:
- очистка выбранного типа, затем Escape;
- очистка типа с подтверждением, без выбора новой модели;
- выбор другого типа с моделью старого типа;
- выбор модели без типа;
- новая модель с тем же типом;
- смена типа и обратный выбор прежнего;
- поздний `GetByIdAsync` от предыдущего типа/модели;
- смена `id` маршрута при открытом popup;
- `ReadOnly` и отсутствие права 43.

После подтверждённой очистки не должно быть видимого поля, условия, фильтра или доступной команды, использующих прежний тип как актуальный. При отмене поиска через Escape прежний корректный выбор обязан восстанавливаться.

## 1.2. Не терять данные при смене типа/модели

`ClearHiddenFeatures()` сейчас сразу присваивает пустое сетевое имя, MAC1/MAC2/MAC iLO, `PhonePoolId=null`, `CameraIsConnected=0`, когда соответствующие признаки становятся недоступны. Проверь, соответствует ли это действительной семантике legacy и как ведут себя изменения, сделанные **до** смены.

Запрещено терять пользовательские значения в последовательности `тип A → тип B → Отмена/Escape → тип A`, при отмене общего редактирования, при неудачной серверной проверке или сохранении. Если окончательно подтверждённое изменение требует очистки несовместимых значений — сделай её явной, логически обоснованной, тестируемой и согласованной с контрактом сохранения, а не побочным эффектом поискового события.

## 1.3. Сохранённый тип ≠ черновик типа

Legacy `ShowAdvGrids` первоначально строит секции из сохранённой записи; `DisplayAndRequiredTypeFields` управляет полями при выборе модели/типа. В новой форме часть связанных коллекций загружается по сохранённому типу (`LoadCurrentAsync`), но видимость `ShowComputer`, `ShowSim`, `ShowLicense`, `ShowAccounts` вычисляется по `_selectedType`, который может относиться к несохранённому черновику.

Проверь и определённо раздели:
- отображение **уже существующих данных** (их нельзя скрывать так, чтобы пользователь решил, что они удалены);
- редактируемость и добавление **новых данных**;
- поля, зависящие от текущего выбранного типа/модели;
- серверные права и сохранённые признаки.

Для обратимых изменений явно показывай существующие несовместимые данные read-only и предупреждай о последствиях, если это требуется бизнес-контрактом. Не выполняй несанкционированную очистку связанных таблиц.

# Этап 2 (P1). Защита несохранённых изменений телефонного списка

Тест `RestoringSameType_PreservesEditedPhoneList` покрывает только **повторный выбор того же типа**, а не смену через другой тип.

- Сначала воспроизведи сценарии и подтвердить фактическую потерю данных.
- Не обновляй `_originalPhones` при простом переключении типа, если SQL-данные не были сохранены. Это baseline для diff, а не произвольный кеш текущей выборки.

- Если изменение типа действительно требует отказаться от несовместимых телефонных связей — запроси подтверждение с точным текстом последствий; при отказе восстанови тип/модель и телефоны.
- Исключи ситуацию, когда `ShowPhones=false` скрывает изменённые телефоны, а Save молча сохраняет только основную запись и считает всё завершённым.
- Протестируй быстрое переключение A→B→A, добавление/удаление и редактирование срока, ошибку БД, отмену и возвращение на форму.

**Выход:** инвариант «неподтверждённый UI-переход не меняет persisted baseline и не теряет dirty-коллекции».

# Этап 3 (P1). Корректная и минимальная синхронизация телефонов с АТС

- какие изменения требуют CCM;
- как выбирается оборудование подключения;
- когда резервным объектом является текущее оборудование;
- как обрабатывается удаление;
- каково условие приоритета Xorcom над CCM при смешанном списке (не меняй уже исправленное правило без теста);

Сохрани порядок: сначала атомарная операция БД, затем синхронизация; не оборачивай сетевые/внешние вызовы в долгую SQL-транзакцию. Реализуй понятный статус `данные сохранены / синхронизация неуспешна`, безопасное повторное выполнение **только** нужной синхронизации и защиту от двойного запуска. Не обновляй `original` в UI так, чтобы единственный способ повторить неудачную синхронизацию исчез.

Добавь тесты на дифф из 0/1/нескольких записей, только изменённый срок, add/remove, Xorcom+CCM, соединительное оборудование, fallback, частичный сбой, retry и повторный Save. **Не вызывай реальные АТС в тестах.**

# Этап 7 (P2). Проверка контрактов выбора и валидации

Сверь ещё раз server-side параметры и защиту от устаревшей выборки:

- модель без типа; затем nullable фильтр по типу;
- поставщик определяется единственным отличным от владельца лицом документа;
- смена владельца меняет фильтры, но не сбрасывает самостоятельно выбранные документы/поставщика;

- любое выбранное значение показывается по ID, даже если временно выпало из новых фильтров;
- отсутствие модели и характеристик не должно делать невидимые поля обязательными;
- SN обязателен в тех сочетаниях, где это требует `IsSnRequired` при выбранной модели;
- MAC форматируется/нормализуется согласованно с legacy; незаполненные MAC допускаются, если legacy не требовал их обязательности;
- время списания соответствует UTC и смещению на дату, включая DST;
- `SaveAsync` при конфликтах роли/валидации сохраняет пользовательские значения в форме.

Проверь семантику `AutoDialNumber/AutoDialDelay` при добавлении телефонной связи: legacy при создании in-memory `PhoneEquipment` присваивает `PhoneNumber.PhoneAutoDialNumber`, а текущий `AddPhoneAsync` задаёт пустую строку. Не объявляй это ошибкой БД до проверки, какие поля реально сохраняются/передаются синхронизации; если функциональное отличие есть — устрани его.

# Этап 8 (P2). Согласованность обновлений после отдельных операций

После работы с расположением, ответственными, SIM, бухгалтерией, UPS и телефоном часть значений `_model` и текущих source-фильтров обновляется без полной перезагрузки. Проверь:

1. Последовательность `новое расположение → новый фильтр телефона/UPS → выбор → Save`.
2. «На руках» без текущего ответственного; изменение ответственного в **другом окне** между открытием диалога и записью; атомарность операции и выбор сотрудника только при необходимости. Не ломай уже исправленный сценарий.
3. Запись бухгалтерии, которая изменяет владельца/арендатора/документы, при существующих несохранённых изменениях основной формы. `RefreshAccountingAsync()` учитывает исходные значения, но надо проверить dirty-state, `_originalSnapshot`, `_confirmedOwnerId` и права после сохранённого изменения.
4. Изменение расположения/ответственного в другом окне во время открытой формы: отсутствие ложных данных и нежелательного перезаписывания.
5. Возврат из диалога при смене `id` или уничтожении компонента; запрет записи в новую карточку из старого диалога.

Для реальных конфликтов используй согласованный серверный контракт и показывай обновление данных, а не silently overwrite.

# Этап 9 (P2). Производительность и визуальная приёмка

`LoadCurrentAsync` сейчас выполняет много независимых запросов **последовательно**: тип, роли, модель, телефоны, расположения, ответственные, лицензию, SIM, ПО, бухгалтерию, UPS, историю, сеть и т. д. На широких карточках это может заметно замедлять открытие.

- Замерь фактические round trips, длительность initial load и последовательности запросов через предусмотренный тестовый стенд. Не называй предполагаемое улучшение измеренным.
- Объединяй допустимые чтения батчами/multi-result или эффективной загрузкой, соблюдая контракт `DbManager` и последовательность на одном connection. Не запускай слепо параллельные SQL-команды на одном соединении.
- Разграничь критические данные для первого отображения и второстепенные read-only секции, но не показывай пустые как «нет данных» до завершения загрузки.
- Минимизируй повторные запросы при переключении типа, модели, вкладки или использовании диалога.

В браузере проверь ширины **1440 / 1155 / 1024 / 768 / 480 / 375 / 320**, масштаб 100% и 150%, реальную клавиатуру и Escape. Сравни **расположение** блоков с legacy: верхняя сводка, SN+списание, тип+модель, телефоны, сеть/MAC, примечание/пул, секции учета, владелец/документы, услуги SIM. Сохрани компактный деловой интерфейс без горизонтального переполнения и чрезмерных пустот, не копируя фиксированные размеры WebForms.

Не добавляй CSS в Razor. Стили компонента в `clay.css`, страницы — в `app.css`; используй общие контролы.

# Этап 10. Внешние зависимости и критерий закрытия

Отдельные блокеры уже известны:

- **Wake-on-LAN**: ожидается `sp_WakeOnlan`, отсутствующая на тестовом стенде (см. issue #3 в Inventory, если актуально).
- **Детализация Билайн**: отсутствует подтверждённое приложение/URI и рабочая интеграция (issue #4, если актуально).
- **Маршруты карточек**: ссылки на документы/расположения добавляй только при подтверждённом URI.

Не называй их «готово», не вставляй mock, выдающий успешный результат. Если в обновлённом окружении появились необходимые зависимости — реализуй и отдельно протестируй с реальным контрактом; иначе оставь отдельными не закрытыми пунктами.

## Отчёт и Definition of Done

Пошагово предоставляй:

- `Шаг / legacy-контракт / выявленный дефект / затронутые файлы / что изменено / тест / результат`.
- Для каждого P1 — падающий тест **до** правки и зелёный **после**.
- Для P2 — обоснование приоритета, скриншот/DOM или целевой профильный тест.
- Список фактически выполненных команд build/test с количеством test cases; если полный testhost зависает, не подменяй неполный результат «все тесты пройдены».
- Число запросов и время до/после, если измерено.
- Список незакрытых внешних блокеров.
- Сводку SHAs сабмодулей, состояние git; commit/push/merge — только по прямому разрешению.

**Финальная приёмка:** нельзя терять несохранённые данные от смены зависимого поля; нельзя запускать лишнюю или неверную синхронизацию; нельзя оставлять ложные элементы интерфейса; нельзя падать из-за отзыва прав; нельзя утверждать функциональную готовность на основании лишь unit-тестов, когда не проверены браузер и реальные SQL-контракты.
