## Обязательные исправления

### P1-01. Повтор синхронизации АТС недоступен через «Применить»

**Код:** [`EquipmentForm.razor.cs`](https://github.com/Postnn/Kesco.App.Web.Inventory/blob/4c7846cacf98/Components/Pages/Equipment/EquipmentForm.razor.cs), `CanSave` (строка ~150), `SaveAsync` (~2032), `RetryPendingPhoneSyncAsync` (~2138); [`EquipmentForm.razor`](https://github.com/Postnn/Kesco.App.Web.Inventory/blob/4c7846cacf98/Components/Pages/Equipment/EquipmentForm.razor), кнопка «Применить».

`CanSave = IsModified && _canEdit && !_loading && !_saving`. После UPDATE и ошибки АТС установлен `_pendingPhoneSync`, но `_originalSnapshot` уже обновлён, а `LoadCurrentAsync()` перегружает сохранённую модель, так что `IsModified == false`. Состояние кнопки «Применить» не позволяет вызвать сохранённую retry-операцию. Тест `SyncFailure_RetriesWithoutRepeatingDatabaseSave` вызывает Save программно и не проверяет реальную кнопку.

**Исправление:** отдельная кнопка «Повторить синхронизацию» либо `CanSave = (IsModified || _pendingPhoneSync != null) && ...` с понятным текстом состояния, без повторного UPDATE. **Тест:** в bUnit по ошибке первой синхронизации проверить состояние реальной кнопки, нажать через DOM, снять ошибку и убедиться, что повторился только sync, `UpdateWithPhonesCalls` остался 1.

### P1-02. Компьютер/ПО записываются при несохранённой смене типа

**Код:** `ShowComputer`, `CanEditComputer`, `OpenComputerDialogAsync`, `OpenSoftwareDialogAsync` в `EquipmentForm.razor.cs`; `SaveComputerAsync` (~495), `SaveSoftwareInstallationAsync` (~442) в `EquipmentFormService.cs`.

Секции используют `_selectedType`, то есть **черновой тип**. При выборе компьютерного типа на исходно некомпьютерном оборудовании команды добавления сразу доступны, хотя новый `ModelId` ещё не записан. Сервис проверяет роль 43 и валидность записей, но не характеристики **сохранённого** типа оборудования. Можно записать конфигурацию/ПО, отменить изменение основной формы и получить несогласованную БД.

**Исправление:** в UI блокировать немедленные операции до сохранения соответствующей модели; на сервисе проверять фактический тип по оборудованию и право (для записей ПО и компьютера), либо реализовать атомарный согласованный бизнес-процесс. **Тесты:** исходный тип без компьютерной характеристики → выбрать компьютер в черновике → попытаться добавить конфигурацию и ПО → ни одного SQL-write; прямой вызов сервисов на некомпьютерном оборудовании должен отказать.

### P1-03. Недостаточная проверка доступа к изменению UPS

**Код:** `EquipmentFormService.SaveUpsDetailsAsync()` (~363–380).

Метод вычисляет `serverEquipmentId` как **первый** положительный ID из `originalServers/currentServers`, вызывает `EnsureUpsAccessAsync(serverEquipmentId)`, затем сохраняет diff **всех** серверов и тестов. Если в списке серверы разных владельцев, право на первый не даёт права менять остальных. Также возможен ложный отказ пользователю, имеющему доступ к своему серверу, но не к первому.

**Исправление:** передавать явный контекст текущего сервера/оборудования, независимо получать на сервере сохранённые связи, сравнивать настоящий diff с клиентским и проверять полномочия по всем затронутым связям. Не доверять `originalServers`, полученному от клиента, в качестве источника истины для ACL. Проверить и серверный `AddUpsLinkAsync`: принадлежность цели типу UPS и требуемому офису сейчас обеспечивается поиском, но не повторно сервисом.

**Тесты:** UPS + серверы владельцев A/B; роль только на A, только на B, на обоих; попытка удалить или добавить чужую связь; неверный офис или тип UPS; устаревший клиентский baseline.

## P2 — функциональные и UX дефекты

### P2-01. Фильтр UPS не обновляется после перемещения

В `LoadCurrentAsync()` выполняется `UpsSource.LocationId = model.LocationId`. В `RefreshLocationsAsync()` меняются `_model.LocationId` и `PhoneNumberSource` через `UpdatePhoneSourceFilters()`, но **не** `UpsSource.LocationId`.

**Исправление:** синхронизировать фильтр UPS в едином методе обновления зависимых source-фильтров после каждого изменения расположения. **Тест:** перенос из офиса A в B без перезагрузки → UPS lookup возвращает результаты B и исключает A.

### P2-02. Кнопка добавления в бухгалтерском учёте и лицензии может отражать старые права

`OnOwnerChangedAsync()` → `RefreshAccountingAccessAsync()`/`RefreshLicenseAccessAsync()` меняет `_canUseAccounting` и `_canEditLicense`, но не вызывает `UpdateOptions()`. При этом `_accountingGridOptions.ShowAddButton` и `_licenseGridOptions.ShowAddButton` присваиваются только в `UpdateOptions()`, а `ClayGrid` действительно отображает действие по `options.ShowAddButton`. Серверные права проверяются повторно — это **UI/UX**, не доказанный обход ACL.

**Исправление:** пересчитать опции после завершения актуального async-ответа; закрывать условия от late result. **Тест:** смена владельца с правом на владельца A и без права на B, и обратно, без загрузки страницы; проверка фактической кнопки в DOM и возможности действия.

### P2-03. Повтор частично успешной синхронизации запускает уже успешные операции

`PendingPhoneSync` хранит полные списки `Original/Current`, а `SynchronizePhonesAsync()` возвращает только список текстов ошибок. При повторном вызове вычисляется тот же diff и повторяются все действия, включая уже успешные Xorcom/CCM. Это не соответствует требованию «повторить только нужную синхронизацию» и может иметь внешние побочные эффекты.

**Исправление:** возвращать структурированный результат по ATS/PhoneId/EquipmentId/типу команды; повторять только неуспешные операции. Учитывать исторический приоритет Xorcom над CCM при смешанных типах. **Тест:** две Xorcom-операции, одна успешна, другая неуспешна → retry вызывает только вторую.

### P2-04. Ошибка первичной пакетной загрузки не обрабатывается локально

`LoadCurrentAsync()` ловит лишь ожидаемую отмену и не обрабатывает отказ SQL/недоступность view в `GetFormDataAsync()`. Проверь, перехватывает ли исключение общий `ClayDbReconnectOverlay` или error boundary; иначе будет аварийное завершение рендера/circuit вместо сообщения с повтором загрузки.

**Исправление/тест:** SQLException на `QueryMultipleAsync` → пользователь получает recoverable ошибку, загрузка может быть повторена, остальные данные не записываются.

## Открытые ограничения и вопросы (не объявлять дефектами без нового контракта)

- Поле SIM «Должность» присутствует в legacy-разметке, но прямой binding и запись в основном `UPDATE` не найдены. Назначение и источник требуют подтверждения.
- Ссылка фактического расположения при расхождении инвентаризации отсутствует до подтверждённого URI; текст и путь присутствуют.
- WakeOnLAN и детализация Билайн остаются внешними блокерами (issue #3/#4, по документации проекта). Не имитировать успех.
- Последняя инвентаризация размещена под гридом расположений по актуальному UI-решению, а не вверху legacy; это сознательное расхождение, не ошибка БД.

## Правило всех проектов: только ClayGrid

- Все табличные секции реализуются **через `ClayGrid`**, статически либо динамически согласно источнику данных.
- Не возвращать `ClayDetailGrid`, `MudTable`, `MudDataGrid` или собственные `<table>` в прикладные формы; новые потребности решать через API общего `ClayGrid`.
- В проверенных Razor-страницах `Kesco.App.Web.Inventory`, `Kesco.App.Web.Users` и `Clayzor.App.Web.MedicalTests` использование `ClayDetailGrid` не найдено; общий компонент удалён из `Clayzor.Lib.Web.Controls`.
