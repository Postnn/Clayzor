## Оставшиеся замечания

### TEL4-F01 — P2. План синхронизации может устареть после серверного перерасчёта полного номера

**Где:** `src/Kesco.App.Web.Inventory/Components/Pages/Telefon/Tel.razor.cs`, метод `SaveAsync` (около строк 695–748); `Services/PhoneFormService.cs`, `SaveAsync`/`ValidateServerAsync`; `Services/PhoneSyncPlanner.cs`, `AtsMainChanged`.

**Подтверждение по коду:** `PhoneSyncPlanner.Build(request, ...)` вызывается **до** `Service.SaveAsync(request)`; `PhoneFormService.ValidateServerAsync(request)` при сохранении изменяет `request.Phone.FullNumber`, пересчитывая его по текущим данным SQL (`SELECT_ТелефонАвторитетныйПолныйНомер`). Пост-коммитный `SynchronizeAsync` использует первоначальный, не пересчитанный `operations`.

**Сценарий:** телефон на Xorcom, старый полный номер `1001`; пользователь меняет только примечание, пока зависимый номер либо префикс станции в БД уже изменился, поэтому на сервере авторитетный полный номер стал `2001`. Начальный план не видит ATS-изменения, SQL Save сохраняет другой `FullNumber`, но конфигурация АТС не синхронизируется. Возможны и аналогичные сценарии для Meridian/CCM. Это дефект при конкурирующих обновлениях, не обязательный на обычном тестовом номере 1002.

**Исправить:** формировать **итоговый** sync plan после финальной авторитетной валидации/пересчёта (либо пересчитать после возвращения `Service.SaveAsync` с мутированным `request`), не повторяя выполненный pre-save Xorcom cleanup. Предварительный план для необходимости pre-sync может быть отдельным ограниченным планом, не полагаться на preview полного номера. Не выполнять повторный SQL Save. Предусмотреть ошибку SQL и компенсацию pre-sync.

**Тесты:** `original.FullNumber == preview.FullNumber`, но `ValidateServerAsync` устанавливает иной `FullNumber` перед `SaveAsync`/SQL write; после commit в mock-плане есть Xorcom/Meridian; при неизменённом полном номере лишней синхронизации нет; при A→B старый Xorcom очищен **ровно один раз**, новый сконфигурирован после Save.

### TEL4-F02 — P2. Delete использует *исходный*, но не обязательно *актуальный* сохранённый снимок

**Где:** `Tel.razor.cs`, `DeleteConfirmedAsync` / `_originalPhone` / `_originalRelations`; `PhoneSyncPlanner.BuildDelete`.

**Сравнение с legacy:** legacy `Tel.Delete()` прямо перед удалением вызывает `Phone.GetPhoneEquipments(true)` — принудительное чтение актуальных связей. В текущем Tel `BuildDelete` получает `_originalRelations` из загрузки формы и **не перечитывает** БД перед удалением.

**Сценарий:** пользователь A открыл Tel с одним связанным оборудованием; пользователь B добавил ещё одно оборудование и сохранил; пользователь A нажал Delete без Refresh. План CCM может не содержать добавленного оборудования; если станция изменена в БД, старая Xorcom тоже может быть выбрана неверно. То, что R1 исключает несохранённый черновик, не исключает эту гонку.

**Исправить:** непосредственно перед planning Delete загрузить с SQL актуальный read-only persisted snapshot телефона, станции и связанных устройств, не подменяя им черновик UI и не вызывая `Save`. Использовать его для `BuildDelete`, `preDelete` и планирования компенсации; проверить, что запись ещё существует. Предусмотреть повторную гонку между чтением и удалением (по возможности проверка версии/конкуренции) и не вводить ложную видимость распределённой транзакции.

**Тесты:** после первичной загрузки изменяются связи в mock-БД; Delete синхронизирует все **текущие** сохранённые EquipmentId; draft station и draft equipment игнорируются; запись уже удалена другим оператором — корректное сообщение без необоснованного вызова АТС.

### TEL4-F03 — P3. Сообщение при выходе неверно описывает незавершённую АТС-синхронизацию

**Где:** `Tel.razor.cs` `IsModified`, `CancelAsync`, `BeforeInternalNavigationAsync`.

**Подтверждение по коду:** `IsModified` становится true из-за `_pendingOperations.Count > 0`, даже если SQL Save уже успешен. При закрытии показывается «Закрыть форму без сохранения изменений?», при навигации — «Покинуть форму без сохранения изменений?». На самом деле сохранение БД прошло; закрытие теряет память о failed sync operations, поскольку durable outbox осознанно не реализован.

**Исправить:** при `_pendingOperations.Count > 0` отдельное подтверждение с текстом: «Данные уже сохранены в БД, но синхронизация АТС не завершена. При закрытии повтор из этой формы будет недоступен; потребуется ручная синхронизация». Не вводить новый outbox, не терять предыдущее предупреждение. Отдельная проверка Cancel, внешнего/внутреннего перехода и Delete-with-pending.

### TEL4-F04 — интеграционное ограничение, не дефект реализации

Реальные CRUD связей PBX/оборудования, конкурентное занятие порта/розетки, `sp_Xorcom_PhoneNumberSync`, Meridian и CCM не подтверждены на тестовой БД/АТС. Mock и проверка SQL-синтаксиса не могут заменить проверку внешнего эффекта и реальных ограничений БД. Перед промышленным включением нужен согласованный изолированный интеграционный сценарий с откатом. Не вызывать продуктивную АТС без отдельного разрешения.
