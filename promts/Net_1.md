## 3. **Критично: поиск оборудования по «Подключено» и «Примечание»**

### 3.1. Что делает legacy на самом деле

Методы `RenderConnected()` и `RenderDescription()` **независимо** вызывают `RenderLink(net.Connected)` и `RenderLink(net.Description)`. `RenderLink` работает по одному алгоритму:

1. При пустой строке не выводит ссылок. **Исходная строка остаётся в textarea**.
2. Первым проходом применяет regex **без изменения** (C# verbatim string для переноса):

   ```csharp
   @"((?:(?!\d+\.|-)[*a-zA-Z0-9_\-]{1,50}(?<!-)\.?)+(?:[a-zA-Z0-9])?)"
   ```

   Режим `RegexOptions.Multiline`. Для каждого `Match.Success` берёт `Groups[1].Value`.
3. Если токен **начинается именно с** `"ilo-"` с условием `StartsWith("ilo-", StringComparison.InvariantCulture)`, выполняет `v = v.Replace("ilo-", "")` (это не общий case-insensitive `RemovePrefix`). Значение токена после такого преобразования используется **и для поиска, и в подписи ссылки**.
4. Добавляет токен в `List<string>` только если `!netList.Contains(v)`. Это сравнение строк legacy **с учётом регистра**, с сохранением порядка первого появления. Не переписывать без доказательства на `HashSet(StringComparer.OrdinalIgnoreCase)`, не сортировать и не склеивать похожие имена.
5. Вторым проходом по **тому же исходному тексту** извлекает MAC адреса, regex:

   ```csharp
   @"(\b([0-9A-Fa-f]{2}[:.-]?){5}[0-9A-Fa-f]{2}\b)"
   ```

   Режим `RegexOptions.Multiline`, значение `Groups[1].Value`; добавляет по тому же `netList.Contains` **после** всех токенов первого прохода.
6. Для **каждого** токена делает `Trim()` и обращается к базе с параметром `@СетевоеИмя` через `SELECT_Оборудование_По_СетевомуИмениИлиМакАдресу`.
7. Если есть запись, берёт `Rows[0]["КодОборудования"]` и добавляет ссылку с текстом найденного **токена** в `Config.equipment_form + "?id=" + EquipmentId`. Если записи нет — **не добавляет ссылку, но не удаляет текст из исходного поля**.
8. Под textarea выводит ссылки в порядке токенов, разделённые пробелами. **Нет фоново редактируемого списка найденного оборудования**, отдельной таблицы или механизма связи «порт — оборудование» для этого поиска.

**Важные особенности, которые легко случайно сломать:**

- **Два независимых источника**: нельзя искать только по `Connected`, объединять обе строки в одну, использовать `Description` оборудования вместо `Net.Description` или брать текст из соседнего порта.
- **Не полнотекстовый поиск**: нельзя делать `LIKE '%<полная строка>%'`, `Contains`, внешний справочник или поисковый сервис вместо точной legacy-семантики.
- **MAC — это дополнительный проход**. При записи `AA:BB:CC:DD:EE:FF` первый regex может дополнительно извлечь отдельные `AA`, `BB`, ...; legacy **не отфильтровывает** эти фрагменты автоматически. Отражение этого нюанса — обязательная регрессия; устранение ложных ссылок возможно **только как явно согласованное изменение** после сравнения с legacy.
- `domain\host` даёт отдельные текстовые кандидаты (в том числе `host`); SQL может найти `DOMAIN\host` по суффиксу имени. Нельзя использовать слепую нормализацию разделителя `\` в .NET.
- `host.example.com` может являться одним кандидатом; IP-адрес с точками **не** означает поиск по IP. Например, у `192.168.1.20` regex может дать хвост `20`; нельзя подменять фактический результат «улучшенным IPv4-парсером» без согласования.
- Первичный regex пропускает кириллический текст и часть знаков препинания; не надо менять его на `\w+`, который захватит и другие символы.
- `ilo-` **не эквивалентно** `ILO-`. Не превращать автоматически в `OrdinalIgnoreCase` или `Replace` только одного префикса.
- Текст **не изменяется** по результатам поиска. Не сохранять в БД нормализованные имена, MAC, ссылки или HTML вместо введённых данных.
- Изначально ссылки строятся из **сохранённого** `net.Connected` / `net.Description`, а не из незаписанных изменений textarea. После «Применить»/успешного сохранения ссылки надо пересчитать по новой сохранённой записи. Не выполнять сетевой SQL на каждый `oninput` без отдельного требования.

### 3.2. Точная семантика SQL-резолвера

В `Kesco.Lib.Entities/SQLQueries.cs` legacy определён запрос:

```sql
SELECT TOP 1 * FROM vwОборудование WHERE
       СетевоеИмя = @СетевоеИмя
    OR (CHARINDEX('\', СетевоеИмя) > 0
        AND СетевоеИмя LIKE '%\' + @СетевоеИмя)
    OR MACадрес = @СетевоеИмя
    OR MACадрес2 = @СетевоеИмя
    OR MACадресILO = @СетевоеИмя;
```

Проверить и обеспечить **каждый** вариант соответствия отдельно:

1. Полное сетевое имя (`СетевоеИмя = token`).
2. Имя с доменным префиксом, содержащее обратную косую черту (`DOMAIN\HOST` → поиск по `HOST` через суффикс). Это **не** общий частичный поиск по подстроке и не суффикс FQDN через точку.
3. `MACадрес`.
4. `MACадрес2`.
5. `MACадресILO`.

`TOP 1` в legacy **без `ORDER BY`**. Это реальная неоднозначность: если одному токену соответствуют несколько единиц оборудования, старый выбор недетерминирован. **Не выдумывай** новый приоритет `MAC`/сетевое имя или «первый по ID» и не выдавай его за сохранение legacy. Выяви наличие коллизий на тестовых данных, зафиксируй их в отчёте; решение об изменении политики выбора — отдельно. Для уникальных совпадений поведение должно быть идентично.

SQL-параметр должен оставаться параметром, а не частью C#-конкатенации. У `LIKE` токен с `_` интерпретируется SQL Server как шаблонный символ, если его не экранировать: это **исторический риск ложных совпадений**, его нужно отдельно протестировать и отметить, но не менять молча. Аналогично **не применять MAC-нормализацию из `Equipment.NormalizeMacAddress` без доказательства**: legacy передаёт токен буквально, включая `:`, `-`, `.`; сравнения определяет фактическая collation/формат хранения `vwОборудование`. Тестировать как совпадения, так и отсутствие совпадений для MAC с разделителями.

### 3.3. Как перенести без потери логики и N+1

- В `Clayzor.Lib.Entities/Inventory` размести **чистый и тестируемый extractor** кандидатов с воспроизведением порядка regex, transform `ilo-`, дедупликации и `Trim` при поиске. Это не `Equipment` CRUD и не полноправный generic search; не клади regex в Razor и не дублируй в `Connected`/`Description`.
- Там же предоставь read-only резолвер `token -> КодОборудования?` через `DbManager` и `SQLQueries.cs`, с типизированной минимальной проекцией. Не загружай `SELECT *` с секретными или неиспользуемыми полями, если достаточно ID. Не превращай отсутствие записи в исключение.
- Legacy вызывает по SQL-запросу **на каждый** токен. Для нового приложения по возможности используй **пакетное параметризованное чтение** обоих полей, не меняя результатов резолвинга (допустимо несколько ограниченных пачек при большом числе токенов и лимите SQL Server 2100 параметров). Вариант реализации выбирай после проверки на SQL Server 2008 R2; не делай по запросу на каждый символ/на каждый render.
- Сохраняй порядок источника и метку, из какого именно поля найден токен; один и тот же токен может давать ссылки под обоими полями. Кэш допустим только в рамках одной загрузки/состояния формы, а не общий между пользователями; при успешном сохранении очистить и разрешить по новой версии данных.
- **Отмена, жизненный цикл, гонки**: `CancellationToken` на запросы, отмена при уходе со страницы, результат старой загрузки/старого сохранённого текста не должен перезаписывать более новый. Текстовый draft и состояние сохранения независимы от ошибок резолвера. При недоступности SQL чтение ссылок не должно удалять или перезаписывать исходное содержимое полей.
- Безопасная разметка: экранировать текст токена, не применять `MarkupString` к пользовательским полям, не переносить HTML из legacy; открытие **только существующего положительного `EquipmentId`** по настроенному `URI_equipment_form` через `clayOpen`. Никаких пользовательских URL, `javascript:` или raw HTML. Подпись ссылки — токен, а не найденное `СетевоеИмя`/модель оборудования.
- Не скрывать ошибку SQL под видом «оборудования нет». В UI достаточно недеструктивного сообщения о проблеме формирования ссылок, в диагностике — безопасная ошибка без SQL-параметров/секретов. Ошибка ссылок сама по себе не даёт права переписать текстовое поле.

### 3.4. Обязательная тестовая матрица распознавания

Добавь **прямые тесты чистого extractor** с точными упорядоченными списками кандидатов, отдельно — тесты SQL-сопоставления и визуального представления. Тестовые сценарии:

| № | Вход / ситуация | Что проверять |
|---|---|---|
| R01 | `""`, `null`, пробелы, многострочный пустой текст | Нет ссылок, нет сбоев; исходное значение не меняется |
| R02 | `server01` | Один токен; точное сетевое имя |
| R03 | `srv-01`, `srv_name`, `server.example.org` | Дефис/подчёркивание/точки — извлечение именно исходным regex |
| R04 | `ilo-server01` | Ищется/показывается `server01` после legacy-преобразования |
| R05 | `ILO-server01`, `ilo-ilo-server01` | Регистр и множественный `Replace` строго как legacy |
| R06 | `DOMAIN\SERVER`, `corp\server01` | Порядок кандидатов первого regex и SQL-суффикс `\server01` |
| R07 | `AA:BB:CC:DD:EE:FF`, `AA-BB-CC-DD-EE-FF`, `AABBCCDDEEFF`, `AA.BB.CC.DD.EE.FF` | Второй regex; неизменность формата; двойное обнаружение частей MAC первым regex, если применимо |

| R13 | Несколько имён/МАС в одной заметке, переносы строк, разделители | Порядок всех токенов первого прохода, потом новых MAC второго |

| R15 | `name_x` + доменные имена SQL | `_` в `LIKE`: реальный legacy-эффект отдельно проверен и задокументирован |

Нужны **реальные тесты**, не простые проверки наличия подстрок в исходниках. Для R07/R09 отдельно отрази в тестах фактические особенности наследованного алгоритма, включая неожиданно распознаваемые фрагменты. Желательно зафиксировать «golden» сравнение на одинаковых входах legacy/.NET 10 и проверять результат без зависимости от живой БД. **Любое улучшение распознавания — отдельная задача**, не часть незаметной миграции.

## 5. «Переключить на» / «Обменять с» — **три разных сценария сохранения**

Оба списка приходят из `dbo.fn_ЛокальнаяСеть_СоседниеПорты(@КодЛокальнойСети)`, сортируются `ORDER BY СетевоеИмя, Порт`; подпись строки **точно** `СетевоеИмя + ', порт:' + Convert(varchar,Порт)`:

- «Переключить на»: **только** `Занят = 0` (`SELECT_СоседниеПортыНеЗанятые`).
- «Обменять с»: **все** соседние порты (`SELECT_СоседниеПортыВсе`).
- Стартовое значение `-1`/«выберите порт» означает «не выбрано»; это sentinel, **не** реальная запись. При выборе переключения сбросить обмен и скрыть его строку; при выборе обмена сбросить переключение и скрыть его строку. На сервере всё равно запретить оба выбора одновременно, выбор самого себя, неизвестный или уже недопустимый порт.

Сверь по исходному `SaveData` и реализуй буквально заполнение полей **без неожиданной потери других данных**:

| Режим | Порт-источник `netFrom` | Порт-назначение `netTo` |
|---|---|---|
| **Обычное редактирование** (оба = -1) | Из формы сохраняются `КодЛицаЗаказчика`, `Примечания.Trim()`, `Подключено.Trim()`, `КодСотрудника`, `КодРозетки`, срок возврата согласно checkbox | Не изменяется |
| **Переключить на свободный** | Заказчик = выбранный; `Примечания=""`, `Подключено=""`, сотрудник и розетка `NULL` | Заказчик = выбранный; получает `Примечания.Trim()`, `Подключено.Trim()`, сотрудника и розетку из черновика источника |
| **Обменять с** | Получает прежние заказчика, примечание, подключено, сотрудника и розетку **цели** | Получает выбранного заказчика, `Примечания.Trim()`, `Подключено.Trim()`, сотрудника и розетку **источника** |

**Исторический нюанс:** при переключении/обмене legacy **не переносит и не обновляет** `СрокВозврата`; он задаётся только при обычном сохранении. Требуется проверить бизнес-смысл и отразить это явно в тестах. **Не решать самостоятельно**, будто срок «должен автоматически ехать с подключением», и не обнулять его побочно при частичном UPDATE.

В legacy многошаговые `Net.Save(false)` вызываются последовательно и **без явной транзакции**. В новой версии порты должны быть защищены от **частичного сохранения при ошибке второго/третьего UPDATE**: атомарная транзакция, блокировка/проверка актуальных записей, откат всей операции, отдельные проверки для переключения/обмена. Две вкладки/два пользователя не должны бесконтрольно перезаписывать одно и то же состояние. Реализуй минимальный целевой coordinator **только при необходимости транзакционного двухпортового сценария**; простое чтение и одиночный CRUD принадлежат Entity. Проверки допустимости должны выполняться заново на сервере **в момент записи**, а не только по загруженным dropdown.

**Наблюдаемая неоднозначность legacy-валидации:** `ValidateInput` проверяет просроченный срок возврата под `else if (efSwitchTo.Value != "-1" && efExchangeWith.Value != "-1")`, хотя UI взаимно исключает эти выборы. Это фактически недостижимая ветка при штатном выборе. Не утверждай в отчёте, что legacy всегда запрещает просроченную дату; воспроизведи тестом, разъясни расхождение. Любую дополнительную проверку согласуй как явное улучшение, не выдавая её за порт 1:1.

## 6. Валидация, безопасность и PoE

Минимум legacy `ValidateInput`:

- «Заказчик» обязателен (`Inv_msgPersonEmpty`: **«Не выбран заказчик.»**).
- Если указана розетка, но **оба** «Сотрудник» и «Подключено» пусты, запрещать сохранение (`Inv_msgSocketOnlyWithEmployeeOrConnected`: **«Вы указали розетку. В этом случае необходимо указать сотрудника или что подключено.»**). Не путать «Примечание» с «Подключено»: примечание **не заменяет** это условие.
- Сохраняй логические NULL, даты, исходное значение подключённого текста (тримминг только на записи как в legacy). Ошибку валидации показывай без мутации черновика.
- Проверить отдельно поведение при новой/недоступной записи, ошибке `PersonCustomer`, невалидном `id`, отсутствии доступного выбора, исключениях SQL и отозванных правах.

**PoE:** кнопка **«Перезапустить PoE»** (`Inv_lblPOE`) появляется **только** при `net.POE == 1`, действие требует подтверждения и вызывает `sp_ResetPoEport` с `@КодЛокальнойСети = net.Id`; legacy использует timeout **120 секунд**. После успеха/ошибки всегда выключается блокирующий overlay. При ошибке — **«Ошибка при перезапуске PoE»** с безопасным сообщением. Повторный клик во время выполнения запрещён. Операция внешняя, возможны реальные последствия — **не вызывать её в browser smoke без отдельного разрешения**. Проверять право на сервере перед запуском, даже если кнопку скрыли в браузере, и не полагаться исключительно на видимость `PoE` из черновика (перепроверить запись).

Права **не придумывать**: в этом code-behind нет прямой проверки `HasRole(103)` или `HasRole(43)` на запись в `Net`; выяснить серверные ограничения по `vwЛокальнаяСеть`, `sp_ResetPoEport`, триггерам и предназначению формы. Использовать `Employee CurrentUser`, проверять свежую идентичность и права перед изменением/PoE, строго fail-closed; не создавать собственные SQL-аналоги `HasRole`. Коды фиксированных ролей только через подтверждённые enum из `Entities`.

## 9. Тесты вне парсера и критерии приёмки

- Обычное сохранение, «Применить», «ОК», отсутствие UPDATE при неизменённом черновике и закрытии.
- Переключение на свободный порт **с точной картой полей**; обмен между двумя заполненными портами; не изменяется `СрокВозврата` в сценариях переноса/обмена; сохранение незатронутых колонок и корректные NULL.
- Искусственная ошибка на втором/третьем UPDATE => откат **всех** изменений; повторное выполнение не меняет чужие данные; конфликт двух вкладок, занятость порта после загрузки, попытка подмены ID в запросе.
- Заказчик отсутствует; розетка заполнена, но оба «Сотрудник» и «Подключено» пусты; `Подключено` пусто, но заполнено только «Примечание» => **ошибка**; недопустимые даты и историческая ошибка валидации — отдельно.
- Роль отозвана после открытия; `CurrentUser` не определился; mismatch principal, ошибки SQL — **ни записи, ни PoE**. Не применять роль оборудования «наугад» вместо реальных прав сетевой формы.
- PoE видимость по БД, подтверждение, проверка роли до SQL, правильный `id`, timeout 120 s, блокировка повторной команды, снятие overlay при ошибке. В тестах — stub, **не настоящий reset**.

**Интеграция / UI**:

- Ссылки под обоими textarea открывают именно нужное оборудование через `clayOpen` и остаются на форме порта; не открывают произвольные URL.
- Сохранение обновляет родительский грид адресно и не перезагружает весь Web-app; popup закрывается/не закрывается по выбранной кнопке.
- Browser smoke на тестовом стенде на широком экране и 320–480px: отсутствие наложений, скролла по горизонтали, дублирующихся команд/лишних полей, корректный Tab, несбивающиеся `ClaySelect`.
- Нет N+1 SQL на длинных полях, неожиданной автонормализации MAC или перезаписи текстовых областей ссылками; dispose, cancellation/race проверены, а не только задекларированы.

## 10. Обязательный отчёт агента перед приёмкой

В ответе пользователя на завершение работы предоставь:

1. **Матрицу `legacy → новая реализация`** с `file:line` для каждого поля, действия, SQL и всех веток `SaveData`.
2. **Отдельную матрицу поиска**: источник токенов → порядок обоих regex → `ilo-` → дедупликация → пять SQL-предикатов → ID → `clayOpen`. Указать точное покрытие R01–R20 и результаты на реальных/фиктивных данных.
3. Расхождения, которые **не удалось устранить или нельзя менять без решения**: `TOP 1` без `ORDER BY`; wildcard `_` в `LIKE`; фрагменты MAC/IP; `Location.Value = net.Id`; необычная ветка валидации даты; сохранение срока возврата при переключении/обмене; права PoE и редактора.
4. Уточнённые реальные права/схему/триггеры БД, количество SQL round trips для ссылок, описание транзакций, поведение при конфликте и отказе.
5. `git diff --stat` и список затронутых файлов; доказательство отсутствия изменений в несвязанных участках/работе параллельного агента; фактические build/test/browser/DB результаты.
6. Итоговый статус по каждому критерию: **PASS / FAIL / BLOCKED** с конкретными причинами. Участки **BLOCKED** не обозначать как готовые. Никакого merge до отдельного разрешения.

### Условия, без которых задача **не принимается**

- Ссылки по «Подключено» **и** «Примечание» отсутствуют, неверно извлекаются, пересортировываются, смешиваются, ведут на не то оборудование или подменяют исходный текст.
- Вместо пяти legacy-условий поиска реализован `LIKE` по всей строке/поиск только по имени/MAC1; не проверены MAC2/ILO и доменный `\HOST`.
- Миграция молча «исправила» regex, нормализацию, коллизии `TOP 1` или `LIKE`-wildcards без сравнительных тестов и фиксации решения.
- Вместо `vwЛокальнаяСеть` используется `vwЛокальнаяСетьПрисоединениеРабочейСети`; потеряно переключение/обмен или появилась частичная запись при ошибке.
- Нет свежей серверной проверки прав перед записью/PoE, или доступны операции по чужому/подменённому ID.
- Отсутствуют регрессионные тесты на реальное поведение, невоспроизведены ключевые сценарии в браузере или данные незаметно модифицируются на production.

**Ожидаемый результат:** работоспособная и протестированная форма порта `Net` с точным сохранением данных и проверяемой legacy-семантикой автоматических ссылок на оборудование из обеих текстовых строк; перечисленные аномалии имеют явные решения или документированы как BLOCKED, а не скрыты.
