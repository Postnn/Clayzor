# Промт: справка и выбор темы на каждой форме — FORM-KEY-08

**Обязательное задание от 26.11.2026; владелец H — help/theme/shell.** Прочитай [ключевой контракт](../../docs/agents/editing-forms-key-requirements.md), [оркестратор](00_ORCHESTRATOR.md) и актуальные AGENTS. Работа идёт от actual HEAD с сохранением уже принятых исправлений. Это задание на реализацию; текущий документальный пакет не объявляет UI исправленным. Общий охват и source audit: [дополнение](SOURCE_AUDIT.md).

Решения пользователя имеют приоритет над прежним Cancel/Refresh, required-empty и необязательностью presence. DR-01, права/CAS, R01/R04, ClayTheme/Classic Light и beta-план сохраняются. Общие файлы меняет назначенный владелец; независимые adapters могут готовиться параллельно. Все требования действуют и для новых приложений.
## Цель и границы

H отвечает за справку/темы и shell. Готовую presence-панель предоставляет P; H только подключает её, не создаёт второй сервис.


Обеспечь для каждого самостоятельного экрана приложения доступные из его toolbar или меню команды «Документация» и «Тема оформления». Для редактора существующей сущности показывай сотрудников, которые сейчас работают с той же сущностью. Сделай общие компоненты и контракты Clayzor; используй уже работающие части и не ухудшай их ради технического совпадения с legacy.

Требование справки и темы относится к карточкам, спискам, поисковым формам, отчётам и диагностике, включая открытие отдельным URL/окном без предварительного посещения главной страницы. Встроенный редактор внутри уже открытой формы может использовать её общую панель, если справка указывает на соответствующий раздел и команды доступны при работе с редактором. Самостоятельно открываемая форма должна иметь эти команды сама. Это не требование добавлять дублирующие панели в каждый вспомогательный confirm-диалог или поповер.

Присутствие относится к работе с определённой доменной сущностью и подтверждённым доступом. Не регистрируй фиктивную «редактируемую сущность» для PingHost, произвольного отчёта, окна поиска или новой записи с ID `0`. Просматривающая карточка существующей сущности может показывать список редакторов и, если выбран единый контракт, отдельное состояние «просматривает». Это не разрешение автоматически считать просмотр редактированием.

Не меняй права доступа, идентификацию пользователя, CRUD, внешний обмен, правила черновиков, неизвестных исходов операций и конфликта версий для упрощения этой работы. Не выдумывай номера ролей и новые разрешения: найди действующие проверки и используй их в серверных адаптерах.


## Справка конкретной формы

1. Введи минимальный общий контракт метаданных формы и один resolver URL. Форме достаточно передать стабильный ключ; прикладной реестр задаёт путь документации, при необходимости раздел/`HelpId`. Компонент кнопки не должен извлекать идентификатор документации из произвольной текущей query-строки.
2. Прочитай действующую реализацию `ClayAppSettings` и способ загрузки конфигурации. По уточнению пользователя оставь существующий ключ **`URI_wiki_help`** единственным параметром справки форм. Подключи его штатным способом; переименование, второй ключ и fallback между ключами не вводить. Не смешивай `URI_wiki_help` с отдельным `URI_help_clayGrid`.
3. Зафиксируй поддерживаемый формат базового URL. Для стандартной базы-каталога нормализуй соединение base + путь документации; для установленного legacy-префикса используй явный режим совместимости с его кодированием. Если фактическая конфигурация использует query-префикс или шаблон, сохрани её смысл и закрепи отдельным тестом. Не применяй `new Uri(base, absolutePath)` вслепую: начальный `/` может заменить путь базы, а query-префикс не является каталогом.
4. Реестр должен иметь проверяемое соответствие «новый route/алиасы → путь документации». `.aspx`-алиас и маршрут без суффикса ведут в один документ. При новом имени маршрута сопоставь реальный путь legacy по исходникам, а не простым добавлением `.aspx`: например, имя Razor-компонента само по себе не доказывает имя прежней формы.
5. Учитывай стабильный прикладной префикс документации и правила `PathBase`. В legacy в ключ входил виртуальный путь приложения; в новой системе этот участок должен задаваться согласованной конфигурацией/реестром. Переезд приложения за reverse proxy и изменение публичного адреса не должны незаметно менять раздел справки. Не добавляй текущий `id`, фильтры, return URL, токены, черновик и фрагменты пользовательского ввода.
6. Кодирование выполняется один раз на соответствующей границе. Покрой пробелы, кириллицу, `%`, `#`, `?`, завершающий/начальный `/` и уже кодированные фрагменты. Не позволяй значению из query подменять схему или домен документации. Принимай только поддерживаемые безопасные URL и предсказуемые пути; параметры раздела берутся из доверенных метаданных формы.
7. Кнопка видна и доступна с клавиатуры, имеет текст/accessible name «Документация», tooltip и ссылку на форму. Используй существующий `ClayButton`/общую навигационную возможность. Открытие документации оставляет редактор и несохранённые данные на месте. Не вводи локальный `window.open`, не провоцируй перезагрузку текущей формы. Для внешней новой вкладки обеспечь безопасный opener-контракт.
8. Ошибку конфигурации не маскируй рабочей на вид кнопкой, которая ничего не делает, и не удаляй команду молча. Покажи понятное состояние «Справка не настроена»/причину недоступности, сохрани работу формы; в поставке приложения проверь наличие конфигурации и mapping для всех форм. Секреты и полный пользовательский URL в диагностику не писать.
9. Кнопка справки формы не заменяет и не переименовывает существующую документацию грида: контексты должны быть различимы.

### UI7-B. Выбор темы на каждой форме

1. Повторно используй `ClayThemeSelector`, `ClayThemeHost`, `ClayThemeState`, каталог и существующий интерфейс хранилища. На текущем Inventory выбор уже сохраняется для подтверждённого сотрудника; не делай отдельные настройки темы на каждой странице и вторую схему localStorage.
2. Вынеси общие действия в штатное место общей панели/меню. Учитывай уже существующий переключатель `EntityFormLayout` и переключатель `ClayNavigationMenu`: в одной пользовательской панели не должно появиться двух одинаковых кнопок из-за двойного подключения. Охват проверь и для страниц без `EntityFormLayout`.
3. Прямое открытие карточки/отчёта/диагностики должно инициализировать правильную тему без обязательного входа через Home. Не создавай второй независимый theme state/provider в той же области интерфейса и не сбрасывай выбор при открытии диалога.
4. Смена темы немедленно меняет оформление текущего окна и сохраняет личную настройку через действующее хранилище. Не перезагружай приложение/форму, не пересоздавай EditContext, не изменяй поля, dirty-state, черновики, выделение и запущенные операции ради применения темы.
5. Сохрани `ClassicLight` как текущий default, существующие пять вариантов, явный выбранный пункт, отключённое автоматическое переключение ОС и обработку LoadFailed/SaveFailed с повтором. Не удаляй и не мигрируй несвязанные legacy-настройки темы без отдельной доказанной необходимости.
6. Гарантию немедленной синхронизации уже открытых вкладок не приписывай текущему `ClayThemeState`: его документированная область — circuit. Обязательный минимум — единая сохранённая настройка пользователя, корректная загрузка в новых формах и применение в окне выбора. Если существующее приложение уже имеет распространение смены на открытые окна, сохрани его; дополнительный механизм не должен затрагивать черновики и бизнес-состояние.
7. Проверь новые общие цвета обязательности, фокуса и изменений во всех темах, в том числе Classic Dark. Доступность toolbar, перенос кнопок и контрастность не должны зависеть от конкретной формы.


## Приёмка


| Сценарий | Ожидаемый результат | Уровень проверки |
|---|---|---|
| Классическая карточка, поиск, отчёт, PingHost, открытые напрямую | На каждой доступны справка формы и выбор темы; отсутствие главного меню не лишает команд | Статический реестр; браузерная проверка на beta |
| Route без суффикса и `.aspx`, переименованный route, PathBase | Документ один и тот же согласно явному mapping; ID/фильтр/черновик в URL не появляются | Автотест resolver без внешнего сайта |
| База-каталог, legacy URL-префикс, пробелы/кириллица, `%/#/?`, пустая конфигурация | Нет потери base path, двойного кодирования и перенаправления через пользовательский ввод; понятная ошибка конфигурации | Автотест resolver и компонентов |
| Работа со справкой при изменённой форме | Исходная форма, её поля, dirty и черновик сохраняются | Компонентный сценарий; beta браузер |
| Смена всех поддерживаемых тем и ошибка сохранения | Выбор применяется без reload, сохранённая тема доступна при следующем открытии; ошибка/повтор работают; поля не меняются | Существующие тесты state/store + точечные проверки; beta БД |
| Два сотрудника, одна запись, разные route | Оба видят другого; алиас/другое представление не создаёт отдельную группу | Тест key+authorization+registry; beta несколько сессий |
| Один сотрудник с несколькими вкладками | Считается один участник, собственные окна не показаны как другие сотрудники; закрытие одной не удаляет остальные | Автотест lifecycle/aggregation |
| Одинаковый ID в разных типах/областях, составной ключ | Чужие сущности не смешиваются; составной ключ поддерживается, в том числе PhonePoolAttribute | Автотест key и адаптеров |
| Отказ доступа, подмена user ID, смена пользователя | Сервер не раскрывает список/сущность и не доверяет клиентской identity | Автотест авторизации и повторного join |
| Обрыв, TTL, поздний leave, новый circuit, смена сущности | Нет вечных «призраков», дублей и удаления новой lease старым событием; неизвестность канала отображена честно | Детерминированный lifecycle-тест; реальные обрывы на beta |
| IIS recycle/обновление/несколько worker | Список восстанавливается в заявленной topology; черновики не меняются и команды не повторяются | Контракт и конфигурация сейчас; внешняя проверка beta |
| Два сотрудника одновременно сохраняют | Presence не разрешает overwrite; работает существующая проверка версии/конфликтов; никакой чужой ввод не подменяет локальный | Regression по существующему save-контракту |
| Новая запись/отчёт/диагностика | Нет общей группы ID `0` или фиктивной entity; справка и тема присутствуют | Тест eligibility/mapping |

Не выполняй внешние проверки без соответствующей рабочей среды; пользователь оставил их этапу beta. В отчёте отдели реально выполненные проверки от подготовленных beta-сценариев. Реализация общих контрактов, локальная проверка и интеграция кода не должны останавливаться из-за отсутствия внешнего стенда.

Результат задачи: общие компоненты/сервисы, прикладной реестр и адаптеры, подключённые формы, адресные проверки рисков, обновлённые правила AGENTS и отчёт о поддерживаемой topology. Не объявляй UI8 выполненным по одному скриншоту значка и UI7 — по существованию theme-класса без покрытия форм.

## Владение и сдача

Владелец H ведёт metadata/resolver, команды help/theme и общий shell. P отдельно реализует presence; H принимает его готовую панель. U передаёт контракт edit/focus scope; A — Cancel/DR01. Program/config меняет назначенный интегратор. Матрица выше содержит также смежные presence-сценарии: H проверяет только доступность панели/интеграцию, P — сервисный контракт. Не присваивай один файл одновременно двум владельцам. Приложи каталог всех форм, ссылки help, место команд, адаптеры существующих тем, фактические тесты и beta remainder.
