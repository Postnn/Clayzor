# FORM-KEY-01 — Отмена, повторное чтение и сохранность черновика

Дата: 26.11.2026. Владелец: **A — общий DR26 / Cancel contract**. Рабочая записка для интегратора пакета требований. Production-код и исходные отчёты этим документом не изменены.

## 1. Новое обязательное решение пользователя

Режим **«Отменить мои изменения и загрузить из БД» относится к кнопке «Отмена»**. При наличии изменений пользователь выбирает один из трёх явно названных вариантов:

1. **«Закрыть без сохранения»**.
2. **«Отменить изменения и загрузить из БД»**.
3. **«Продолжить редактирование»**.

Второй вариант оставляет форму открытой. Escape, крестик и закрытие самого вопроса означают третий вариант. Разрушительное действие не является default action диалога; Enter без осознанного выбора не должен стирать ввод. Если форма чистая, обычная «Отмена» закрывает её без лишнего вопроса и без обязательного запроса в БД.

Это дополнение к действующему DR-01: **несохранённые пользовательские данные не должны безвозвратно пропадать из-за перезапуска IIS, кратковременного обрыва сети или обновления приложения**. Утрата ввода допустима только для конкретного editable-снимка, от которого пользователь явно отказался; ни Cancel, ни reset не являются доказательством отсутствия эффекта уже отправленной команды.

Новое решение приоритетнее прежних рекомендаций сохранять текущую семантику Cancel/Refresh. Сохраняются права, бизнес-правила, безопасные современные исправления, общий ClayTheme и внешний beta-план. Legacy не задаёт архитектуру нового решения.

Проверен Controls `3ce2104819bb0db7b60fb49ee415fe05204c67d3`, Inventory `b1d23cdb0bb2e14c20f1cabd0d80fc357e532e9b`, super `a968feed66d1267c86ec589b5d02f1c164640118`. Повторный полный обзор всех форм в этом подзадании не выполнялся.

Проблемы вертикального положения placeholder и недостаточной заметности рамок сообщил пользователь. Визуальная причина не установлена: браузерного воспроизведения и сравнения скриншотов в этой работе не было. Обнаруженные CSS-условия и отсутствие общего API ниже — подтверждённые свойства исходников, но не доказательство конкретной каскадной причины каждого наблюдения. Последнее уточнение пользователя: желтоватый фон нужен только пустому обязательному доступному для редактирования полю. После заполнения обычный фон правилен; очистка возвращает желтоватый. Placeholder не определяет Required и не мешает отображению состояния. Это согласуется с legacy `required-empty`; прежняя трактовка постоянной заливки заполненных Required-полей отменена. Существующую empty-required реализацию нельзя объявлять дефектом только за снятие фона после заполнения; наблюдаемое отсутствие фона у пустого поля требует адресной проверки.
