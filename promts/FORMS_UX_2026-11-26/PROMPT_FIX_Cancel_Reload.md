# Промт: единая «Отмена», свежая БД и сохранность ввода — FORM-KEY-01

**Обязательное задание от 26.11.2026; владелец A — общий DR26/Cancel.** Прочитай [ключевой контракт](../../docs/agents/editing-forms-key-requirements.md), [оркестратор](00_ORCHESTRATOR.md) и актуальные AGENTS. Работа идёт от actual HEAD с сохранением уже принятых исправлений. Это задание на реализацию; текущий документальный пакет не объявляет UI исправленным. Общий охват и source audit: [дополнение](SOURCE_AUDIT.md).

Решения пользователя имеют приоритет над прежним Cancel/Refresh и необязательностью presence. Последнее уточнение FORM-KEY-03 сохраняет required-empty: обязательное пустое доступное поле — желтоватое, заполненное — обычный фон, после очистки — снова желтоватое; placeholder не определяет Required и не мешает состоянию. DR-01, права/CAS, R01/R04, ClayTheme/Classic Light и beta-план сохраняются. Общие файлы меняет назначенный владелец; независимые adapters могут готовиться параллельно. Все требования действуют и для новых приложений.
## Пользовательский контракт


### 3.1. Что считается изменениями

Вопрос определяется общим состоянием редактирования, а не только `IsModified` typed-модели. В него входят typed-значения, последний ещё не потерявший фокус ввод, невалидный/raw текст, невыбранный ввод combobox, локальные добавления/удаления строк, private state компонентов и editable-дочерние scope. Обработчик получает актуальное состояние ввода до решения; он не должен требовать blur, успешного parse или исправления валидации, чтобы дать пользователю отказаться от изменений.

Чистая копия строки, загруженная из БД, сама по себе не dirty. Неразрешённая операция не приравнивается к editable dirty: состояние операции проверяется независимо, остаётся обнаружимым после закрытия и блокирует конфликтующие команды по предметному контракту. Если состояние редактирования ещё не установлено из-за pending restore/storage failure, нельзя объявлять форму чистой и удалять её запись. Можно безопасно покинуть её с сохранением recovery-состояния.

Readiness gate отправки бизнес-команды не требует успешно распарсить или смонтировать каждый raw-контрол ради явного отказа от ввода. Пользователь может отказаться от известного ему собственного editable-снимка с pending raw; общий API должен зафиксировать точный покрытый этим решением набор keys/revisions. Неизвестные или более новые поля нельзя молча включить в отказ, а pending restore нельзя выдавать за успешное восстановление.

### 3.2. Результаты трёх действий

| Выбор | Editable-ввод | Сервер | Форма |
|---|---|---|---|
| Продолжить редактирование | Без изменений, включая raw, baseline, scopes и pending restore | Ноль DML/внешних команд; необязательное фоновое чтение не вправе менять выбор | Остаётся открытой; фокус возвращается в тот же доступный элемент |
| Закрыть без сохранения | Удаляется только явно принятый к отказу editable-снимок этого редактора; новые ревизии и чужие scope защищены | Не сохраняет, не удаляет сущность, не повторяет отправленную команду | Закрывается после подтверждённой локальной фиксации отказа; БД для этого перечитывать не требуется |
| Отменить мои изменения и загрузить из БД | После успешного разрешённого fresh read атомарно заменяется только принятый editable-снимок; fresh становится исходной и текущей версией | Только чтение актуальной записи и необходимых разрешённых зависимостей | Остаётся открытой, ошибки валидации отменённого ввода и modified-маркеры принятых полей сняты |

Ветка закрытия не должна предварительно вызывать полный Load. Если browser API не закрыл обычную вкладку, показать честное состояние и штатный путь выхода; уничтоженные по явному выбору значения не должны снова появиться как несохранённые. Не показывать старый cached baseline как свежую БД. Продолжение работы в оставшейся вкладке проходит обычную повторную инициализацию/чтение. При неуспехе локальной фиксации отказа форма остаётся открытой с доступным вводом и retry; нельзя молча заявлять, что изменения удалены.

### 3.3. Сброс новой записи

Если сущность ещё не имеет подтверждённой серверной identity, читать несуществующую строку или выполнять INSERT нельзя. Действие ResetAndStay сбрасывает ввод к **актуальным начальным значениям режима создания** и оставляет форму открытой. Для новой записи подпись действия — «Отменить мои изменения и начать заново». В вопросе должна быть поясняющая строка: «Запись ещё не создана. Будут восстановлены начальные значения новой записи». Контекстные обязательные defaults и права получают через штатный create-contract; если он не готов, старый draft сохраняется.

После успешного Apply с подтверждённым ID это уже существующая запись: reset читает именно её. Unknown create без подтверждённого ID не переводится в чистое новое создание; immutable attempt и запрет дублирующего INSERT остаются до доказанного исхода.

### 3.4. Ошибка чтения, удалённая запись и отказ доступа

При timeout, network fault, отсутствии строки, отказе в чтении, невозможности подтвердить текущего сотрудника либо неполной загрузке обязательного для корректного отображения состояния сброс **не завершён**. Сохраняются old typed/raw/original, operation state и принятые до сбоя draft-ревизии; форма остаётся открытой. Пользователь видит конкретную причину и может продолжить доступное редактирование, повторить чтение либо отдельно закрыть без сохранения.

Отзыв права записи не равен запрету чтения. Если актуальную закрытую/read-only запись по-прежнему разрешено читать, явный Reset может показать её в read-only режиме после успешного перехода; новые возможности Save от этого не появляются. Нельзя представлять разрешённый read-only результат как missing или восстанавливать прежние права из черновика.

Missing существующей записи не означает create. При отозванных правах нельзя показывать fresh server data из неразрешённого чтения. Собственный draft доступен по действующей identity-bound recovery политике, при необходимости только для просмотра/восстановления; новый пользователь не получает старый draft, а восстановление собственного ввода не даёт права записи в БД. Не заменять собственный draft пустым, denied или missing результатом.

## 4. Атомарность, поколения и журнал операций

1. **Перед вопросом** снимок выбора связывается с identity пользователя, form/entity, route generation, owner root, набором editable scopes и их revision. Pending raw включается по фактическим данным браузера, а не выводится только из C# модели.
2. **После выбора** проверяется, что пользователь подтвердил тот же редактор и набор изменений. Поздний callback другого route или закрытого диалога ничего не изменяет. Если после предъявления вопроса появился N+1, прежнее подтверждение не покрывает N+1; требуется новое явное решение.
3. **Для Reset** fresh read выполняется во временное состояние со свежей identity и серверной проверкой прав. Не вызывать старый Load, который сначала очищает видимый state или регистрацию. Чтение не должно автоматически восстановить удаляемый draft поверх только что полученной версии.
4. **В точке принятия** общий draft API выполняет транзакционную замену принятого editable-снимка и его baseline с expected revision / generation fence. Старый epoch/tombstone должен исключать воскрешение отменённого ввода от позднего autosave. Если появилась более новая revision либо обнаружен другой владелец scope, возвратить структурированный отказ и сохранить все данные; не удалять «всё до текущей revision» без принятого пользователем предела.
5. **Только после durable success** переключить visible typed/raw/baseline, восстановить новый registration/ownership и фокус. Сбой put/delete/re-registration или потеря ответа не должен оставлять единственный экземпляр ввода потерянным; незавершённая локальная процедура имеет безопасный повтор/обнаружение результата. Сам этот повтор не исполняет DML.
6. **Scope и revision операции** не совпадают с разрешением удалить редактируемые поля. Immutable sent snapshot, AttemptId, targets, accepted revisions, phase, KnownCommit/Unknown и подтверждённый receipt сохраняются независимо. Cancel/Reset/Refresh/Dispose не могут переводить Unknown в Rejected или разрешать replay.

Запрет удаления attempt не означает бесконечное хранение всех завершённых служебных записей. Их завершение и очистка происходят по отдельному доказуемому outcome/receipt-контракту DR26. Пользовательский отказ от editable-ввода не заменяет это доказательство. Удаление migration backup также ограничивается только явно принятым editable-снимком; backup с новым вводом, другой scope или нужным attempt не уничтожается.

Во время выполнения бизнес-команды сохранить single-flight и существующие guards. Отмена локального ожидания не отменяет уже отправленный серверный эффект. Known commit + failed refresh/storage продолжает быть known commit; повторяется только локальное завершение/чтение. Если редактор после reset открыт с Unknown, статус и read-only сверка остаются видимыми; очистка общего предупреждения не должна прятать единственные recovery-кнопки.

## 5. Обновить, сверка и конфликт

**«Обновить» не является скрытой второй кнопкой «отбросить ввод».** Для чистой формы он читает и показывает актуальные разрешённые данные. Для dirty-формы получает свежие данные для сверки, сохраняя original/local/raw и предлагая существующий контролируемый merge. Название кнопки «Обновить» можно сохранить; tooltip и сообщение объясняют, что несохранённый ввод сохраняется, а полный отказ расположен под «Отмена».

Каждое новое явное обновление получает действительно новый серверный снимок в актуальном route generation. Нельзя называть fresh старый `Clean`, полученный при первом открытии. Merge применяет только явно выбранный результат и принятые revision; отказ от merge ничего не отбрасывает. Выбор «Взять конфликтные поля из БД» меняет именно конфликтные поля и **не равен** полному отказу от всех изменений.

Обычный CAS-конфликт и Unknown — разные состояния. CAS-conflict позволяет read/compare/merge и последующий новый Save по штатным правилам. Unknown допускает read-only reconciliation отправленного immutable intent; совпадение части полей с текущей строкой само по себе не доказывает исход команды или внешний ATS-эффект. «Обновить» может повторить storage recovery/readiness либо доказуемую сверку, но не Begin/Save/DML/ATS/WoL. После известного успеха cleanup retry не проверяет повторно, изменил ли другой пользователь строку, чтобы заново решить уже подтверждённый результат.

При SlBl сохраняется предметная семантика сравнения строк (включая согласованные trim/case правила именно для сравнения), однако она не разрешает исчезновение несохранённого исходного текста. Exact dirty и различия должны оставаться доступны; семантическое равенство внешнего списка не является общим разрешением уничтожить локальный raw.

## 6. Вложенные редакторы, закрытие окна и исключения

Команда относится к одному редактору и принадлежащему ему subtree scopes. Cancel вложенного UPS Test не сбрасывает UPS, Equipment main, соседний child или их N+1. Reset существующего child читает именно его актуальное разрешённое состояние и остаётся в том же диалоге; parent при необходимости получает только безопасное уведомление/сверку, а не blanket Load/Discard. Для локального вложенного объекта без собственной серверной записи используется зафиксированный opening/context contract: отказ от текущего редактирования не удаляет уже принятый в parent draft объект. Новому child восстанавливаются его штатные defaults. Нельзя подменять this-dialog baseline всем текущим parent state.

Если Cancel родительской формы применяется при наличии принадлежащих ей несохранённых дочерних областей, вопрос явно покрывает эти области и revision; никакая другая открытая форма не включается через document-wide selector. Если ребёнок удерживает активную недоказанную операцию, её журнал остаётся доступен после закрытия.

Крестик браузера, native beforeunload, уход по адресу, потеря circuit и Dispose — **не** выбор «Закрыть без сохранения» в прикладном вопросе. Автоматический teardown не удаляет durable draft. Разрешённый уход сохраняет recovery-данные; если приложение отдельно предлагает явный discard при навигации, он использует тот же scoped revision contract. Навигация не исполняет Reset и не подменяется им. События unload не являются единственным местом сохранения последнего ввода.

Крестик/Escape **вопроса об отмене** всегда означают Continue. Для dirty редактирующего modal крестик/Escape не должны обходить защиту его draft. Но Cancel в `DraftConflictDialog` лишь отменяет выбор merge; Cancel в поисковом picker возвращает «выбор отменён», а не пустой результат; Stop диагностики отменяет run. Не превращать эти специальные команды в вложенную каскадную «Отмену» редактирования, не добавлять фиктивный DB reset read-only/selection/diagnostic формам.

## 7. Готовый адресный промт на реализацию

### PROMPT — общий Cancel/Refresh для Clayzor

Реализуй обязательный контракт «Отмена → закрыть / отказаться от ввода и перечитать / продолжить» для существующих форм Clayzor и общего компонента, который применяется новыми формами и приложениями. Сначала прочитай этот документ, действующие `AGENTS.md`, `docs/agents/forms.md`, актуальный DR26, адресные consumer prompts и фактический HEAD. Новое пользовательское решение имеет приоритет над прежним поведением Cancel/Refresh; закрытые бизнес-исправления и guards не откатывай.

**Владение.** Владелец A (общий DR26) меняет Controls draft API/store, общий диалог выбора и общую lifecycle часть. Назначенный владелец `TerritorialEntityCardBase` интегрирует его под согласованным владением файлов. Один Equipment integrator меняет `EquipmentForm.razor.cs`, `.Drafts.cs`, общий dialog base/context и родительские call-sites. Другие агенты параллельно готовят непересекающиеся adapters/tests форм. Никаких разных локальных reset-протоколов и двух writers общего файла. Публикуй минимальный совместимый контракт до полного завершения core, чтобы consumers могли работать параллельно; не ломай публичные API до перевода действующих callers.

**Общий API.** Трёхвариантный результат должен быть enum/типизированным outcome, а не bool/неявный null. Пусть контракт различает `Continue`, `CloseWithoutSaving`, `ResetAndStay`; точные имена типов выбери по проекту. Нужен snapshot identity/scopes/revisions, readiness чтения, безопасный fresh-state loader и revision-checked durable reset/discard с различением Applied/NewerRevision/StorageFailure/ReadDenied/NotFound/StaleContext. Это описание семантики, не разрешение ввести вторую competing state machine вместо уже существующего DR26. Running/Unknown/KnownCommit остаются отдельным журналом.

**Реализуй UI.** На dirty Cancel покажи ровно три ясных действия из ключевого контракта FORM-KEY-01. Безопасный default — Continue; Escape/крестик вопроса эквивалентны ему. Clean Cancel закрывает. Dirty включает raw, последний символ, коллекции, дочерние редакторы и pending restoration; invalid input не мешает отказаться от ввода. После успешного reset форма открыта, baseline и текущие значения равны fresh, dirty-подсветка принятых полей снята, фокус попадает в первое доступное поле только в актуальном editor context.

**Реализуй безопасный reset.** Capture → explicit decision → fresh authorized read в temp state → revision/generation recheck → атомарный local transition → publish fresh. Никакого `DiscardAsync(); LoadAsync()` и очистки памяти в начале чтения. На любом неуспехе до принятия сохраняй старый draft. N+1, чужая вкладка, соседний scope и unresolved attempt не удаляются. Поздний autosave не воскрешает принятый к отказу ввод. Missing/deleted/denied existing entity не становится новой. Create без known ID сбрасывается к fresh create defaults без INSERT; known create success меняет route/key по принятому контракту; Unknown create не сбрасывает attempt.

**Раздели Refresh и Reset.** Refresh dirty формы читает fresh и сохраняет original/local/raw для сверки. Existing merge получает актуальный снимок и revision guard; Cancel merge ничего не меняет. Cleanup retry, readonly Unknown comparison и storage retry не повторяют business command. Состояние Unknown и recovery-control остаются видимыми после refresh/reset/re-render. Не меняй подписи независимых команд выбора/диагностики под видом глобального Cancel.

**Проведи интеграцию всех consumers.** Минимум: общий territorial base и его наследники; Equipment main и все editable child/nested dialogs; EquipmentIns, ModelEquipmentForm, PhoneTemplateForm, Net, Tel, SlBl, LocationFact; остальные новые/изменённые editable forms из inventory пакета. Для selector/search/diagnostic/read-only окон отметь осмысленное исключение с конкретным назначением Cancel. Общий компонент и правила должны работать в новых приложениях без копирования Inventory-кода. Не выдавай исправление двух форм за завершение всех consumers.

**Обнови документацию.** В корневом `AGENTS.md` и профильных правилах форм закрепи ключевое обязательное правило FORM-KEY-01; добавь его в шаблоны новых приложений/форм и в текущий оркестратор. В адресных prompts замени прямые старые указания и добавь ссылку на один общий contract. Исторические source findings оставь историческими; не переписывай описание старого среза так, будто UI уже исправлен. Реестр точечных формулировок сохранён в `CANCEL_INSTRUCTION_UPDATES.json`: 30 записей с классификацией и exact source text; проверены 14 активных repo-prompts/common/orchestrator, отдельно рассмотрен пакет review. `_DONE` и inputs не переписывать. Историческое описание Legacy не выдаётся за ошибочную действующую инструкцию; к нему добавляется явное современное решение.

**Проверки.** Выполни целевые local component/store/JS проверки реального вызова consumer → dialog decision → draft transaction, а не только enum/helper или string asserts. Матрица ниже покрывает конкретные риски изменения. Внешние SQL/ATS/IIS/network/deploy проверки пользователь перенёс на beta; они не блокируют локальную реализацию, но не объявляются PASS по doubles. Здесь C# build/tests не выполнялись: SDK отсутствует. В handoff приложи actual commits, ownership, перечень adapters, case → actual command/result, runtime NOT RUN и beta остаток. Не делай production DML ради проверки Cancel.

## 8. Целевая приёмка

| ID | Сценарий | Обязательный результат |
|---|---|---|
