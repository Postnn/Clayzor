# Промт: общие поля и клавиатура — FORM-KEY-02…07

**Обязательное задание от 26.11.2026; владелец U — общие поля/CSS/навигация.** Прочитай [ключевой контракт](../../docs/agents/editing-forms-key-requirements.md), [оркестратор](00_ORCHESTRATOR.md) и актуальные AGENTS. Работа идёт от actual HEAD с сохранением уже принятых исправлений. Это задание на реализацию; текущий документальный пакет не объявляет UI исправленным. Общий охват и source audit: [дополнение](SOURCE_AUDIT.md).

Решения пользователя имеют приоритет над прежним Cancel/Refresh, required-empty и необязательностью presence. DR-01, права/CAS, R01/R04, ClayTheme/Classic Light и beta-план сохраняются. Общие файлы меняет назначенный владелец; независимые adapters могут готовиться параллельно. Все требования действуют и для новых приложений.


### Цель и рамки

Реализуй единый контракт редактируемых полей Clayzor, обязательный для уже существующих форм, новых форм Inventory и будущих приложений на Controls. Делай изменения в общих компонентах, общем CSS и теме, затем подключай формы к согласованному минимальному API. Не добавляй по одной JS/CSS реализации в каждую карточку и не переноси legacy-обработчики целиком.

Изучи актуальные `AGENTS.md`, `docs/agents/forms.md`, `docs/agents/grid.md`, component-level AGENTS ClaySelect и реальные текущие версии исходников до начала правок. Указанные в аудите commit — база анализа, не разрешение откатывать более новые изменения. Пользователь требует улучшения Clayzor и сохранения уже работающих сценариев. Сохрани асинхронные guards ClaySelect, серверную валидацию, DR-01, доступность, раздельные root/modal scopes и существующие предметные клавиатурные сценарии. Не подменяй бизнес-правила DOM-эвристиками и не создавай вторую систему черновиков.

Общую часть должен вести один назначенный владелец Controls. Другие агенты могут параллельно готовить адаптеры отдельных форм и приёмочные сценарии по зафиксированному контракту. Они не правят одновременно те же файлы CSS, theme provider, form shell, draft/navigation coordinator и компоненты. До интеграции назначь владельца каждого затронутого файла и оформи зависимости. Имена будущих API ниже иллюстративны; сначала используй существующие подходящие абстракции проекта.

В оркестраторе владелец **U** отвечает за общий CSS и контролы этой задачи; **B** сохраняет владение popup/result transport; **H** — общим shell. Изменения shell/внешнего выбора согласуются через их контракты и применяются владельцем файла, чтобы параллельная работа агентов не создавала конкурирующие реализации focus/selection. Для dirty/baseline дополнительно согласовать интеграцию с владельцем DR-01/Cancel.

### A. Геометрия, placeholder и Required

1. Сохрани `--clay-control-height: 32px` и существующий единый размер date/time `180px`. Однострочный input, его отображаемое значение и placeholder должны находиться по вертикальному центру полезной области поля. Проверяй вариант с label/без label, пустой/непустой, leading/trailing icons, dropdown button, spinner, date/time. Плавающий label не является placeholder: корректируй именно нужный слой, не ломай notch и анимацию подписи. Textarea остаётся многострочной.
2. Исправь геометрию централизованно. Не вводи page CSS, per-form magic numbers, дублирование шаблона Mud или фиксированную line-height, обрезающую текст при масштабировании. Существующие общие размеры сами по себе не доказывают правильное фактическое выравнивание.
3. Required-фон определяется семантическими параметрами поля и возможностью ввода. Фон сохраняется при placeholder и без него, при пустом и заполненном значении, при поисковом тексте в ClaySelect, при наличии ошибки и при фокусе. Проверка существования выбранного ID остаётся самостоятельной валидацией: наличие произвольного текста не превращает ClaySelect в валидный выбор.
4. Реализуй общий state-marker/класс в контроле или общей обёртке. `:placeholder-shown` и `:invalid` могут обслуживать специализированные эффекты, но не быть единственным источником Required-фона. Внешний `readonly` input у MudSelect/picker иногда является техническим внутренним устройством интерактивного селектора; доступность изменения нужно брать из семантического состояния компонента, а не одного native-атрибута.
5. В режиме просмотра и disabled-фон Required не применять. Не делать все search/filter-поля обязательными из-за внешнего вида; фильтры ClayGrid сохраняют свою семантику. Если конкретный фильтр действительно имеет объявленную обязательность, это отдельный явный контракт, а не глобальная CSS-эвристика по имени или наличию placeholder.
6. Используй общие theme tokens, существующие `--clay-input-required-bg/fg` и согласованное их развитие. Желтоватый оттенок и читаемость текста/placeholder/иконок должны сохраняться во всех доступных темах, включая dark. Изменение имени/семантики `EmptyRequiredBackground` делай совместимо с остальными потребителями. Не вставляй произвольные hex-коды в страницы.

### B. Начальный фокус и Tab

1. Введи/доработай область редактирования формы, независимую от соседних форм и дочерних диалогов. У неё есть стабильная идентичность экземпляра, состояние готовности данных/контролов и владельцы focus/navigation. Общий shell может предоставлять scope, но нельзя предполагать, что любая карточка использует EditContext: в проекте уже есть MudForm и собственные snapshot-модели.
2. Устанавливай начальный фокус один раз после появления первого доступного редактора и завершения релевантного восстановления. Не ограничивайся `firstRender`, если тогда показывается loader. Повторный render, разрешение lookup, восстановление черновика, reconnect и обновление темы не возвращают пользователя к первому полю. Если пользователь уже выбрал поле/команду, пока шла загрузка, поздний initial-focus не отбирает фокус.
3. Первое/следующее поле определяется текущим логическим и DOM-порядком ввода. Для автоматического перехода исключаются hidden/inert, disabled (включая disabled ancestor/fieldset), семантически readonly, неактивные вкладки, нефокусируемые/отсоединённые элементы и `tabindex=-1`. Не добавляй положительный tabindex для исправления неверного порядка разметки. Составной контрол регистрирует основной ввод один раз; его внутренняя кнопка не должна случайно стать «следующим полем».
4. Нативные Tab/Shift+Tab и доступ к toolbar/вспомогательным кнопкам сохраняются. Readonly-поля могут оставаться доступны нативным Tab, если это требуется их контрактом чтения/копирования; исключение readonly из автоматического «следующего редактора» не означает повсеместный запрет пользовательского фокуса.
5. Дочерний модальный редактор получает свою область фокуса. Родитель не перемещает фокус, пока диалог активен. При закрытии фокус возвращается к инициатору, если он ещё доступен, иначе к безопасному логическому элементу родителя. Для внешней формы поиска/создания сохрани защиту от просроченного результата; если подтверждённый выбор должен продвинуть пользователя дальше, возврат и последующее продвижение должны принадлежать одному событию, без второго скачка.
6. Пустая/readonly-форма не должна бросать исключение или фокусировать скрытый input. Явная команда «отменить изменения и загрузить из БД» вправе после успешной загрузки выбрать первый редактор согласованным способом; не запускай такое действие по простому перерендеру.

### C. Одновременные visual states

1. Обеспечь контрастную видимую рамку при клавиатурном фокусе для всех вводов, picker/selector, checkbox/radio и доступных команд. Не удаляй outline без полноценной замены. Для составного поля рамка отражает активность его реального ввода/внутреннего взаимодействия, а не только фокус внешнего div.
2. Изменённость поля — отдельная рамка, отличимая от focus и invalid. Состояния **Required + dirty + focus + invalid** могут существовать одновременно. Используй независимые визуальные слои, например border для ошибки, inset/side accent для изменений, outline для фокуса, вместо взаимоисключающей перезаписи одного border-color. Конкретный дизайн согласуй с существующими темами; наличие ошибки не должно скрывать фокус.
3. Рамки не меняют геометрию и не обрезаются scroll/overflow контейнерами. Добавь понятную вспомогательную индикацию/доступное описание состояния, где оно иначе выражено только цветом; цвет темы не должен быть единственным способом отличить активный/изменённый/ошибочный ввод. Не используй `aria-invalid` для dirty. Проверяй forced-colors/high-contrast на beta.
4. Публикуй tokens focus, dirty и validation во всех темах, а не только в non-classic ветке. Сохрани уже работающие theme preference synchronization и внешний вид фильтров/таблиц. Новый код не должен зависеть от наличия Inventory CSS в будущем приложении.

### D. Изменённость полей и baseline

1. Dirty означает отличие текущего значения/незавершённого пользовательского ввода от принятой исходной версии поля. `Touched`, focus, blur, validation error, время последнего изменения записи и факт `ValueChanged` сами по себе не равны dirty.
2. Свяжи field-state с существующим принятым baseline и snapshot/revision модели. Предусмотри общий адаптер для MudForm/пользовательских моделей; если EditContext применим, не используй один `IsModified` без проверки возврата к исходному значению. Возврат значения к baseline снимает dirty; начальная загрузка, чистый refresh и техническое разрешение lookup не создают ложных изменений.
3. Для селекторов сравнивай устойчивый идентификатор и фактический незавершённый поисковый текст, а не reference объекта или обновившееся отображаемое имя. Для чисел/дат/времени используй согласованное доменное равенство и невалидный raw-ввод; изменение `12` на промежуточный `12,` не должно бесследно исчезать из состояния формы. Не вводи молчаливую нормализацию пробелов/регистра, если она не определена доменом.
4. Черновик восстанавливается вместе с соответствующей связью к baseline. Не объявляй восстановленный draft новым чистым baseline только потому, что он загрузился первым. При конфликте с новой записью БД отделяй «пользователь изменил относительно своей базы» от «база уже обновлена другим человеком»; UI-подсветка не выполняет автоматического merge.
5. Успешное сохранение ревизии N очищает только принятые значения N. Если пользователь уже ввёл N+1, эти поля остаются dirty. Ошибка сохранения, conflict, running/unknown outcome, failure cleanup не должны стирать индикацию или recovery-state. Поля, сохранённые отдельной принятой секцией, могут сброситься только по реальному результату этой секции.
6. Ключи полей и строк коллекций стабильны при сортировке/вставке/переносе. Изменения nested editor и коллекций учитываются в соответствующем scope/секции; имена не зависят от случайного DOM-индекса. Не путай сохранённую сущность с новым локальным экземпляром формы той же сущности. Поля, не показанные сейчас, сохраняют изменения модели/черновика.
7. Отмена с успешной загрузкой из БД устанавливает принятый свежий baseline и очищает связанные dirty-маркеры по общему transactional-контракту перезагрузки. Ошибка загрузки не превращает прежний draft в «сброшенный». Более подробный жизненный цикл Cancel/DR-01 реализуется по соответствующему общему промту.

### E. Enter и подтверждение выбора

1. Для доступного однострочного редактора Enter завершает текущий ввод и переводит фокус к следующему доступному редактору того же активного scope. Перед переходом текущий ввод должен попасть в предусмотренный существующий model/raw-draft pipeline; нельзя ждать blur и потерять последнее значение. Enter не вызывает неявный Save, submit формы, открытие toolbar action или переход сразу через два поля. Если следующего редактора нет, оставь фокус на текущем: дальнейший Tab остаётся штатным; самопроизвольное сохранение запрещено.
2. Не перехватывай Enter во время composition/IME, на compositionend-пограничном keydown, при `event.isComposing`/совместимом browser fallback. Учти key repeat: удержание Enter не должно пробежать всю форму или многократно подтвердить действие. Не занимай Ctrl/Alt/Meta/Shift-комбинации, уже имеющие документированную семантику. Textarea/contenteditable/multiline получают обычный перевод строки. Нативная клавиатура checkbox/radio/toolbar/grid сохраняется.
3. У ClaySelect Enter при открытой выдаче выбирает активный допустимый вариант. Только успешное завершение этого выбора может один раз продвинуть фокус. Enter, который начал поиск и пока не получил окончательного принятого выбора, оставляет фокус в селекторе. Loading/read-error/несколько результатов/неподтверждённый текст не должны превращать «поиск» в преждевременный Tab. Enter на уже неизменённом подтверждённом выборе может перейти далее без нового поиска.
4. Явный выбор мышью/касанием или клавиатурой тоже продвигает фокус, когда это завершение одиночного выбора. Для multi-select требуется явная граница окончания выбора; выбор каждого тега не завершает всю работу. Не перемещай фокус на hover, изменение active option стрелками, техническую синхронизацию `Value`/`SelectedItem`, начальное GetById, программный reset, draft restore или auto-select после blur, когда пользователь уже перешёл в другое место.
5. Передай/учитывай причину завершения: explicit user accept, Enter auto-select, blur resolution, programmatic sync, restore, cancel/Escape и т. п. Не встраивай переход безусловно в `SelectItemAsync`: сейчас его используют Escape-восстановление и auto-select. Не связывай переход с `SelectedItemChanged`: этот callback вызывается и при разрешении прежнего ID. Успешное подтверждение неизменного значения должно иметь собственный сигнал даже без нового ValueChanged.
6. Селектор должен потребить свой Enter, чтобы общий координатор не обработал его повторно. Клиентская отмена default должна происходить синхронно для действительно обработанного события, а не после кругового серверного вызова. Не запрещай все keydown/preventDefault на документе и не эмулируй Tab синтетическим KeyboardEvent.
7. Защити асинхронный переход идентичностью формы/поля, актуальной ревизией принятия и поколением пользовательского фокуса. После await проверь, что событие не отменено, компонент жив, поле/режим всё ещё актуальны и пользователь не успел сам выбрать иной элемент или открыть дочернюю модаль. Поздний callback не перехватывает фокус. После domain callback/рендера пересчитай доступные следующие поля: выбор может показать, скрыть или заблокировать зависимый ввод.
8. Сохрани явные предметные сценарии, например добавление строки по Enter, сканирование штрихкодов и клавиатуру редактирования ClayGrid. Их взаимодействие с общей навигацией должно быть оформлено явной политикой scope/контрола, без двух обработчиков одного жеста. Нельзя вводить глобальный document-handler, который изменит любой поиск или фильтр приложения.

### F. Результат реализации

Предоставь общий контракт/API, реализацию в Controls, адаптеры всех затронутых текущих форм, обновление документации и ключевого раздела AGENTS, локальные проверки и таблицу оставшихся beta-проверок. Описывай реально выполненные проверки отдельно от запланированных. Добавляй тесты на meaningful state transitions и race conditions; не заменяй ими визуальную проверку и не пиши тесты, которые лишь сверяют наличие собственного CSS-класса. Не переносить уже отложенные внешние проверки в текущий блокер.

| Select: Enter search → choose; explicit mouse; same value | После успешного принятия ровно один переход, не во время незавершённого поиска | Callback cause/generation tests | Mouse/touch/keyboard, popup geometry |
| Select: blur auto-select, GetById, restore, Escape, stale callback | Фокус не крадётся; старый результат не продвигает форму | Асинхронные race tests | Быстрые реальные переключения и открытие модалей |
| Динамическое поле/вкладка, последний input, grid inline editor | Нет перехода в hidden/disabled/другой scope; нет auto-save | Scoped navigation tests | Полная пользовательская последовательность текущих форм |

В текущем документальном задании эти проверки **не объявляются выполненными**. При реализации разделять локально доступные проверки и внешний beta-план; отсутствие живого IIS сейчас не оправдывает пропуск доступной проверки модели/очередности событий.
