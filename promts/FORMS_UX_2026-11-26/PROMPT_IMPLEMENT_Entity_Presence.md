# Промт: другие сотрудники на редактируемой сущности — FORM-KEY-09

**Обязательное задание от 26.11.2026; владелец P — presence.** Прочитай [ключевой контракт](../../docs/agents/editing-forms-key-requirements.md), [оркестратор](00_ORCHESTRATOR.md) и актуальные AGENTS. Работа идёт от actual HEAD с сохранением уже принятых исправлений. Это задание на реализацию; текущий документальный пакет не объявляет UI исправленным. Общий охват и source audit: [дополнение](SOURCE_AUDIT.md).

Решения пользователя имеют приоритет над прежним Cancel/Refresh, required-empty и необязательностью presence. DR-01, права/CAS, R01/R04, ClayTheme/Classic Light и beta-план сохраняются. Общие файлы меняет назначенный владелец; независимые adapters могут готовиться параллельно. Все требования действуют и для новых приложений.
## Цель и границы

P отвечает за presence service/key/auth/lease/панель. H отдельно реализует справку/тему и подключает панель; P не создаёт help resolver или второй theme store.


Обеспечь для каждого самостоятельного экрана приложения доступные из его toolbar или меню команды «Документация» и «Тема оформления». Для редактора существующей сущности показывай сотрудников, которые сейчас работают с той же сущностью. Сделай общие компоненты и контракты Clayzor; используй уже работающие части и не ухудшай их ради технического совпадения с legacy.

Требование справки и темы относится к карточкам, спискам, поисковым формам, отчётам и диагностике, включая открытие отдельным URL/окном без предварительного посещения главной страницы. Встроенный редактор внутри уже открытой формы может использовать её общую панель, если справка указывает на соответствующий раздел и команды доступны при работе с редактором. Самостоятельно открываемая форма должна иметь эти команды сама. Это не требование добавлять дублирующие панели в каждый вспомогательный confirm-диалог или поповер.

Присутствие относится к работе с определённой доменной сущностью и подтверждённым доступом. Не регистрируй фиктивную «редактируемую сущность» для PingHost, произвольного отчёта, окна поиска или новой записи с ID `0`. Просматривающая карточка существующей сущности может показывать список редакторов и, если выбран единый контракт, отдельное состояние «просматривает». Это не разрешение автоматически считать просмотр редактированием.

Не меняй права доступа, идентификацию пользователя, CRUD, внешний обмен, правила черновиков, неизвестных исходов операций и конфликта версий для упрощения этой работы. Не выдумывай номера ролей и новые разрешения: найди действующие проверки и используй их в серверных адаптерах.


## Присутствие сотрудников

#### Идентичность и границы доступа

1. Определи typed key: доверенная область данных/окружения, канонический тип сущности и нормализованный доменный ключ. Используй существующий tenant/data-scope, если он есть; при его отсутствии не выдумывай модель мультитенантности, а изолируй реальные базы/окружения. Сотрудник входит в идентичность участника, **а не в групповой ключ сущности**, иначе разные сотрудники никогда не увидят друг друга.
2. Все маршруты и редакторы одной доменной записи должны приходить к одному ключу; разные типы с одинаковым числовым ID не смешиваются. Для составного ключа используй стабильную typed-сериализацию без неоднозначной конкатенации. Не предполагай, что ID оборудования, телефона и дочернего атрибута взаимозаменяемы: подтверждай соответствие по сервисам и данным.
3. Сервер разрешает регистрацию и получение списка только после аутентификации и проверки доступа к целевой сущности. ID/имя сотрудника и область данных берутся из доверенного серверного контекста; клиент не выбирает, от имени кого он участвует. Проверка повторяется после переподключения/смены контекста. При утрате доступа подписка снимается, локальные данные обрабатываются по существующей политике черновиков, без передачи другому пользователю.
4. Список содержит только минимальные разрешённые сведения: отображаемое имя сотрудника, стабильную служебную идентичность участника в пределах контракта, состояние работы и при необходимости время последнего сигнала. Не передавай поля формы, значения черновика, пароли, бизнес-команды, claims, внутренний circuit ID или необработанные логи.

#### Пользовательское поведение

5. В редакторе виден компактный индикатор/список «С записью работают…», позволяющий узнать сотрудников. Всплывающее содержимое открывается клавиатурой и не отбирает фокус у редактирования. ФИО выводится как текст средствами рендеринга, не через сборку HTML из внешних строк.
6. Несколько окон одного сотрудника показывают одного сотрудника; его состояние агрегируется: наличие активного редактора имеет приоритет над просмотром. Собственные окна не выдаются за другого сотрудника. Если показывается отдельная подсказка «Вы открыли ещё одно окно», она не увеличивает число других сотрудников.
7. «Нет других редакторов» и «Не удалось получить сведения» — разные состояния. Потерю канала не представляй доказательством одиночной работы. Покажи ненавязчивый reconnect/устаревший статус; после восстановления обнови список. Состояние «изменяет» основано на договорённом сигнале редактирования; оно не даёт доступа к содержимому чужих изменений.
8. Присутствие — уведомление. Оно не является блокировкой, разрешением Save, доказательством отсутствия конкуренции или заменой optimistic concurrency. Даже при пустом списке действуют проверки версии записи и конфликтов. Ошибка присутствия сама по себе не должна блокировать уже разрешённый CRUD; существующие условия хранения черновика/неизвестной операции при этом сохраняются.
9. Никакого автоматического `RefreshForce`, применения чужих values, вызова Save, принудительного Dispose, удаления/перепривязки черновика и подтверждения чужой ревизии. Дополнительные уведомления «запись сохранена другим сотрудником» допустимы только как отдельные typed-события с явной UX-обработкой, без принятия локальных изменений за сохранённые.

#### Жизненный цикл и несколько серверов

10. Регистрируй существующую сущность после успешного определения ключа и права доступа; не на prerender с временными значениями. Каждая вкладка/окно имеет независимую lease/регистрацию. Переход на другую сущность снимает старую и создаёт новую; успешное создание записи подключает уже выданный реальный ключ. Несвязанные новые черновики с ID `0` не образуют группу.
11. Предусмотри heartbeat/ограниченный TTL, явный leave на штатном закрытии, async dispose подписок и отмену фоновых задач. TTL нужен, потому что закрытие окна/падение процесса не гарантирует доставку leave. При возвращении канала registration выполняется идемпотентно; новый circuit/connection не создаёт дубль сотрудника.
12. Защити поколением регистрации/lease token/sequence от запоздалых renew/leave и старых событий: завершение старого соединения не удаляет новую регистрацию того же окна, поздний список предыдущей сущности не появляется в новой карточке. Временные интервалы задаются общим конфигом и тестируются с управляемыми часами, без жёстких ожиданий в тестах.
13. После IIS recycle/обновления сервиса присутствие восстанавливается из действующих подключений, а не из содержимого черновиков. Пустой перезапущенный сервер сообщает о восстановлении/неизвестности до получения достоверного snapshot. Потеря временного presence-state не затрагивает долговременный черновик.
14. До выбора транспорта проверь существующую инфраструктуру. Blazor Server может использовать SignalR для своего транспорта; это не означает готовую бизнес-подписку presence. Используй единый общий сервис и адаптер приложения. Не добавляй отдельный хаб только ради названия технологии и не переносись на legacy jQuery SignalR.
15. Укажи реальную поддерживаемую топологию. In-memory registry видит только один процесс и не выдаётся за корректную многосерверную реализацию. Для нескольких IIS worker/node и перекрытия старого/нового процесса при обновлении нужны согласованный общий registry/pub-sub либо другой проверенный механизм доставки и lease. Выбирай его по действующей инфраструктуре; не добавляй Redis, таблицу или брокер без проверки наличия и правил проекта. Если topology ещё не подтверждена, реализуй заменяемый контракт, явно обозначь режим и оставь конкретную beta-проверку, не заявляя межсерверную полноту.


## Приёмка


| Сценарий | Ожидаемый результат | Уровень проверки |
|---|---|---|
| Классическая карточка, поиск, отчёт, PingHost, открытые напрямую | На каждой доступны справка формы и выбор темы; отсутствие главного меню не лишает команд | Статический реестр; браузерная проверка на beta |
| Route без суффикса и `.aspx`, переименованный route, PathBase | Документ один и тот же согласно явному mapping; ID/фильтр/черновик в URL не появляются | Автотест resolver без внешнего сайта |
| База-каталог, legacy URL-префикс, пробелы/кириллица, `%/#/?`, пустая конфигурация | Нет потери base path, двойного кодирования и перенаправления через пользовательский ввод; понятная ошибка конфигурации | Автотест resolver и компонентов |
| Работа со справкой при изменённой форме | Исходная форма, её поля, dirty и черновик сохраняются | Компонентный сценарий; beta браузер |
| Смена всех поддерживаемых тем и ошибка сохранения | Выбор применяется без reload, сохранённая тема доступна при следующем открытии; ошибка/повтор работают; поля не меняются | Существующие тесты state/store + точечные проверки; beta БД |
| Два сотрудника, одна запись, разные route | Оба видят другого; алиас/другое представление не создаёт отдельную группу | Тест key+authorization+registry; beta несколько сессий |
| Один сотрудник с несколькими вкладками | Считается один участник, собственные окна не показаны как другие сотрудники; закрытие одной не удаляет остальные | Автотест lifecycle/aggregation |
| Одинаковый ID в разных типах/областях, составной ключ | Чужие сущности не смешиваются; составной ключ поддерживается, в том числе PhonePoolAttribute | Автотест key и адаптеров |
| Отказ доступа, подмена user ID, смена пользователя | Сервер не раскрывает список/сущность и не доверяет клиентской identity | Автотест авторизации и повторного join |
| Обрыв, TTL, поздний leave, новый circuit, смена сущности | Нет вечных «призраков», дублей и удаления новой lease старым событием; неизвестность канала отображена честно | Детерминированный lifecycle-тест; реальные обрывы на beta |
| IIS recycle/обновление/несколько worker | Список восстанавливается в заявленной topology; черновики не меняются и команды не повторяются | Контракт и конфигурация сейчас; внешняя проверка beta |
| Два сотрудника одновременно сохраняют | Presence не разрешает overwrite; работает существующая проверка версии/конфликтов; никакой чужой ввод не подменяет локальный | Regression по существующему save-контракту |
| Новая запись/отчёт/диагностика | Нет общей группы ID `0` или фиктивной entity; справка и тема присутствуют | Тест eligibility/mapping |

Не выполняй внешние проверки без соответствующей рабочей среды; пользователь оставил их этапу beta. В отчёте отдели реально выполненные проверки от подготовленных beta-сценариев. Реализация общих контрактов, локальная проверка и интеграция кода не должны останавливаться из-за отсутствия внешнего стенда.

Результат задачи: общие компоненты/сервисы, прикладной реестр и адаптеры, подключённые формы, адресные проверки рисков, обновлённые правила AGENTS и отчёт о поддерживаемой topology. Не объявляй UI8 выполненным по одному скриншоту значка и UI7 — по существованию theme-класса без покрытия форм.

## Владение и сдача

Владелец P ведёт сервис, typed key, авторизованные регистрации/lease и отдельную панель. H подключает панель в shell; A согласует editor lifecycle, C — Equipment parent. Help/theme URL/store принадлежат H: смежные строки общей матрицы не являются вторым заданием на их реализацию. Program/config и общий base меняются через интегратора. Представь реестр entity-key/policy для всех редакторов, поддержку составных ключей/aliases, фактическую topology, адресные проверки и beta remainder.
