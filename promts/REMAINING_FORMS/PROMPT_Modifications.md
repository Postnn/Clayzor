# Промт реализации Modifications — «Изменения в БД»

## Задача и границы

Реализуй страницу **Inventory/Reports/Modifications.aspx**: выбор периода, списка разделов из ЗапросыИзмененияБД и необязательного изменившего сотрудника; по команде «Сформировать» — несколько отдельных таблиц результатов с переходами к записям и сотрудникам. Это отчёт по SQL, хранящемуся в БД, а не универсальный CRUD журнала, не самостоятельно вычисляемая история diff до/после и не вызов внешнего report-server.

Прочитай [01_COMMON_RULES.md](01_COMMON_RULES.md), актуальные AGENTS.md суперпроекта, Inventory, Entities/DynamicGrid и Controls/Grid/Select. Не изменяй параллельные исправления других форм; commit/push только по уже предоставленному разрешению. Исследованный срез: legacy `12a6efae7eb310adec06a57f6d80b8d9e76985b4`, Inventory `b3da274962c3c0811f71fbfe196f188ed3b5f659`, Entities `bf909e66d89a9a9c2f3fdc5069dd03b9b56368d7`, суперпроект `05f2fc7561bf2a5648cca7fce991be6e4c12cdb2`. В текущем приложении нет страницы Modifications; есть общий ClayGrid и инфраструктура безопасного динамического SQL.

## 2. Маршрут, интерфейс и initial state

Поддержи `/Reports/Modifications` и `/Reports/Modifications.aspx`; собственных обязательных query-параметров нет. Контекст idQuery от динамического меню не является ID строки отчёта. Сохрани существующее меню и заголовок **Изменения в БД**.

Порядок панели:

1. Общий выбор периода.
2. Раскрывающийся множественный список **Таблицы**, внутри **Выделить всё** и названия из ЗапросыИзмененияБД.
3. Подпись **Изменил:** и необязательный EmployeeSelect, AutoSetSingleValue.
4. Кнопка **Сформировать** (legacy Text имеет ведущий пробел, видимая надпись не переименовывается).

Начальный период — День, обе даты = серверный DateTime.Now.Date; сотрудник пуст; все доступные разделы отмечены. Результат не строится автоматически при открытии: требуется «Сформировать». Смена сотрудника или чекбоксов меняет черновик параметров, не запускает запросы результатов. У legacy удалены все стандартные кнопки EntityPage; не добавляй Save/Apply/Edit/Delete.

Для периода и checkbox-list в исследованном текущем Controls нет самостоятельного полного legacy-аналога. Используй ClayDatePicker/ClayDropDownList/ClayCheckbox в **общих** компонентах Controls, при необходимости минимально добавь общий API; не делай локальную копию контролов для Modifications. Учти существующий IClaySelectDataSource для сотрудника. Все таблицы — ClayGrid, без переноса StringBuilder/HTML table из legacy.

## 3. Семантика периода

Коды PeriodsEnum подтверждены source:

| Код | Вариант | Интервал |
|---:|---|---|
| 1 | День | Одна календарная дата, поле конца скрыто |
| 2 | Неделя | Неделя с понедельника по воскресенье |
| 3 | Месяц | Первое–последнее число месяца |
| 4 | Квартал | Первое число первого месяца — последнее последнего; квартальный номер в описании |
| 5 | Год | 1 января–31 декабря |
| 6 | Произвольно | Две редактируемые даты |

Общий legacy PeriodTimePicker умеет предыдущий/следующий период: день±1, неделя±7, месяц±1 с последним числом месяца, квартал±3months, год±1year. Не заменить весь контрол двумя DatePicker, потеряв тип и стрелки.

Когда начало становится позже конца, конец подтягивается к началу; когда конец раньше начала — начало подтягивается к концу. Для «День» обе даты всегда равны. Ручное изменение одной даты вне «День» переводит тип в «Произвольно». При явном выборе «День» legacy возвращается к текущей дате. SetPeriod для остальных типов использует прежнее начало, если новый числовой код больше предыдущего, иначе now; эту неочевидную политику переключения сравни с действующим UI и явно сохрани либо зарегистрируй корректировку, не замени молча произвольным anchor-date.

В исходном вычислении недели воскресенье DayOfWeek=0 может дать **следующую** неделю. Это техническая особенность старого контрола, требующая отдельного решения/теста; нельзя объявлять математически корректную новую неделю побитовым повторением legacy. На других границах проверяй конец декабря, февраль високосного года, кварталы и custom.

Фильтр отчёта из GetPeriodToSQLParam:

- День: `CONVERT(date, p.[Изменено]) = @DateFrom`.
- Типы2–6: `CONVERT(date, p.[Изменено]) BETWEEN @DateFrom AND @DateTo`, обе границы включены.
- Без начала, без конца для диапазона, при неизвестном типе: **Не определен период.**, заголовок **Информация**, запросы результатов не запускаются.

Legacy фильтрует календарную дату **хранимого Изменено**, а отображает его через ToClientLocalTime. Не применять browser offset в фильтре без явного решения: это меняет состав строк на границе суток. Если оптимизируешь CONVERT в индексный полуоткрытый диапазон, докажи эквивалентность исходной зоне/типу и включение всего последнего дня; параметры DateTime типизировать. Не делать `BETWEEN midnightFrom AND midnightTo` по исходному datetime — это потеряет почти весь конечный день.

## 4. Выбор таблиц и metadata

SELECT_IDS_ЗапросыИзмененияБД:

`SELECT * FROM ЗапросыИзмененияБД WHERE ISNULL(@ids,'')='' OR КодЗапроса IN (SELECT value FROM dbo.fn_SplitInts(@ids)) ORDER BY [Запрос]`.

При начальном чтении @ids='' означает **все определения**. При нажатии «Сформировать» пустой пользовательский выбор, наоборот, означает **очистить отчёт и не выполнять ни одного раздела**. Эти состояния нельзя смешивать, иначе «снять всё» запустит все SQL.

Definition read model: int Id из КодЗапроса, Name из Запрос, SQL из SQL, FormReference из Форма; selected-state хранится отдельно, изначально true. Нужны SQL и URI именно в полном чтении: legacy QueryModificationsDB.Load сам заполняет только Id/Name и не является достаточным источником.

Сохраняй порядок определений по Запрос; UI checkbox-list отражает тот же порядок. Типизированный набор ID валидируется на сервере относительно разрешённых определений. Не передавай клиенту SQL для последующего возврата и выполнения. Если выбранный раздел удалён/недоступен после открытия, сообщи об изменении набора, а не выполняй неизвестный SQL или превращай пустой набор во «все».

В legacy список посылается отдельной командой Checked, а FilterApply использует серверное `_scrollCheckedTables`; начальная синхронизация приходит из JS. При снятии последнего отдельного checkbox setChecked не отправляет пустой массив (у «снять всё» отдельная ветвь отправляет). В новой controlled-модели обязан корректно работать любой переход в zero selections; устранение этой race/ошибки — часть надёжного переноса, не новый feature.

## 5. Формирование результатов

«Сформировать» фиксирует snapshot периода, employeeId и selected query IDs. При валидном непустом наборе:

1. Перечитать необходимые definitions под текущим пользователем.
2. Для каждого definition выполнить SQL определения как подзапрос `SELECT * FROM (<definition SQL>) p` с периодом и необязательным фильтром `p.[Изменил] = @EmployeeId`.
3. EmployeeId=NULL/не выбран означает **все сотрудники**; source-проверка обязательности сотрудника закомментирована. Не сделать поле обязательным и не подставить CurrentUser автоматически.
4. Получить реальную schema/колонки каждого результата. Не предполагать одинаковые колонки для всех разделов.
5. Вывести заголовок definition.Name и отдельный ClayGrid.
6. Разделы с данными — первыми, пустые — после всех непустых; внутри обеих групп сохраняется порядок definitions. Пустой раздел остаётся видимым с заголовком, колонками и **Ничего не найдено.**

Legacy не задаёт дополнительную сортировку записей поверх definition SQL. Для серверной пагинации Clayzor требуется детерминированный порядок: установи его по реальному контракту каждого definition, не сортируй все разнотипные таблицы по придуманной Id или дате автоматически. Не обрезай результат молча ради маленького грида. На большом объёме используй общий серверный paging/query mechanism с правильной schema, а не загрузку всего массива в circuit. Изменение технического способа выдачи не должно терять строки/колонки/фильтр.

Ошибка одного раздела не равна пустому результату. Покажи привязанный к разделу/операции отказ; если выводишь успешные остальные, явно маркируй неполный отчёт. Нельзя оставлять старую таблицу под новым периодом без признака, что она устарела. Поздний ответ предыдущего формирования не затирает более новый набор; cancellation/version запроса, busy state и повторный click проверяются. Форма только читает данные, никаких запись-аудит/UPDATE ради просмотра.

## 6. Точные правила колонок и ссылок

ExtensionsListGridRender получает динамический DataTable и сохраняет порядок колонок результата. Правила переноси через metadata/CellTemplate ClayGrid:

| Колонка | Поведение |
|---|---|
| `Изменил` | Скрыта; хранится как FK для ссылки на сотрудника |
| Первая исходная колонка (ordinal0) | Значение становится ссылкой на запись `configuredForm?id=<value>`; это не обязательно колонка с названием Код/Id |
| `ФИО`, `ИзменилФИО`, `Изменил ФИО` | Ссылка на Employee по скрытому Изменил, legacy берёт отображаемое FIO из Employee, не просто строку SQL |
| `Изменено` | Локальное время клиента через общий UTC→local механизм |
| Остальные | Текстовое значение, DBNull пусто; исходное название/порядок без переименования |

В source первая колонка обрабатывается раньше распознавания ФИО/Изменено. Проверь реальные schema, чтобы не менять форму ключа и не сдвинуть ссылку после исключения скрытых колонок. Отсутствие Изменил/Изменено, NULL/невалидный PK, неизвестный Employee не должны давать скрытый exception и пустой «успешный» отчёт: чёткая ошибка definition или безопасный текстовый fallback согласно документированному контракту. Не делай ключ обязательно int: среди переходов могут быть даты/составные представления, фактический тип нужно сохранить и URL-кодировать.

Для ссылок legacy читает `Форма`, безусловно отбрасывает первый символ, затем трактует остаток как ключ AppSettings и добавляет `?id=`. Ожидаемый стиль — `@URI_...`, но значения metadata здесь не получены. При переносе распознавай подтверждённый формат, а не отрезай первый символ у любого текста. Разрешай конфигурационный ключ общим resolver; ошибку отсутствующего ключа показывай для конкретной ссылки/раздела. Существующие параметры URL/fragment сохранять корректным URI builder, не второй `?`.

Открывай карточки через clayOpen с устойчивым ключом, не прямой window.open; отчёт остаётся на месте. Для ещё не перенесённой целевой формы используй действующую подтверждённую конфигурацию/явный статус недоступности, не выдумывай маршрут по имени таблицы. Поэтому итоговый сквозной smoke отчёта удобнее после переноса остальных карточек.

Employee создаётся legacy отдельно для каждой FIO-ячейки: в Clayzor не воспроизводить N+1. Загрузить/кэшировать в рамках формирования нужные имена с сохранением прав либо использовать подтверждённые SQL-поля, если доказана эквивалентность. Не делиться пользовательским кешем через static. Все значения и заголовки кодировать; сырые SQL-значения не становятся MarkupString/HTML.

## 7. Общие компоненты, SQL и права

Весь доступ к definitions/результатам — Entities, SQL-константы — SQLQueries.cs; используй существующий DynamicSql и его guards, а не создавай альтернативный executor в Web.Services. В приложении допустим только orchestration нескольких чтений и UI-state. В папку Controls не помещать бизнес-SQL Inventory.

Динамическим остаётся **только SQL из авторизованного серверного definition**, параметры EmployeeId/даты/IDs/sort/paging передаются типизированно. Не копировать конкатенацию `_uId` и дат из legacy. Не разрешать URL/клиенту подставить SQL, имя БД, произвольный ORDER BY. Поиск definition ID выполняется из серверного разрешённого набора. Сохранять права SQL текущего пользователя; список metadata сам по себе не даёт права читать базовую таблицу.

У формы нет явной роли в source. Не угадывай «аудитор»/43/66. Установи реальные права DS_user на ЗапросыИзмененияБД и исходные данные, используй Employee CurrentUser и уже принятую политику идентичности. Отказ/смена прав до выполнения и смена роли между разделами не обходятся. Отказ SQL не заменяется пустой таблицей.

Проверь SQL Server2008R2: date/CONVERT/ROW_NUMBER допустимы в целевом контракте, новые функции в добавляемой обвязке не использовать. Запросы самих metadata могут иметь особенности (CTE, ORDER BY, trailing semicolon, дополнительные result sets): source уже предполагает, что SQL пригоден как подзапрос; прочитай реальные definitions и обработай нарушения явно, не «чиня» чужой SQL удалением фрагментов строковыми regex без тестов.

## 8. Печать, экспорт и внешние интеграции

В изученных Modifications.aspx/.cs и ExtensionsListGridRender **нет вызова отчётного сервера, PDF/Excel-генератора или отдельной print-команды**. Результат — HTML на этой же странице. Единственные внешние переходы — карточки записей и сотрудников по конфигурации. Не проектируй фиктивную интеграцию и не обещай существующую печатную форму.

Если общий ClayGrid уже предоставляет печать/экспорт и это сохраняется по действующим правилам приложения, используй его штатные генераторы, с теми же видимыми колонками, фильтрами и snapshot. Не добавляй в рамках обязательной parity отдельный custom PDF/XLSX pipeline или новые кнопки в legacy-панель. В handoff точно укажи, какие общие функции доступны, какие вообще не входят в source-контракт.

Legacy renderer ограничивает высоту таблицы300px при более13 строках, фиксирует шапку, допускает горизонтальную прокрутку. Перенеси функциональный результат общим ClayGrid/общими options и адаптивностью, не копируй локальный CSS, повторяющиеся id=table-container или IE-scroll hack. Число13/300 — исходный порог компоновки, не предел выборки.

## 9. Проверки приёмки

- Оба маршрута и меню, начальный День/today, все разделы отмечены, employee пуст, ноль result-SQL до «Сформировать».
- Все шесть типов периода, prev/next, синхронизация обеих дат, ручной custom, Sunday-edge, конец года/квартала/високосного февраля; сохранённое решение по legacy anchor-date.
- Невалидный/пустой период даёт одно понятное сообщение и ноль запросов результатов; порядок start/end не теряет конечный день.
- Сотрудник пуст = все, выбран = только его изменения, clear возвращает все; значения не конкатенируются в SQL.
- Все/подмножество/один/ноль таблиц; снятие последней индивидуально и через «Выделить всё» одинаково очищает отчёт; race initial JS отсутствует.
- Неизвестный/удалённый/недоступный definition ID, пустой SQL/Форма/неизвестный config key; не исполняется произвольный client SQL.
- Непустые разделы перед пустыми, внутри алфавитный порядок по Запрос; нулевой результат с колонками и «Ничего не найдено.».
- Разные schema и порядки колонок; скрытый Изменил; три варианта FIO-имени; первая исходная колонка как ключ; NULL/недоступный employee; несколько строк одного сотрудника без N+1.
- Изменено у границ UTC/локального дня и DST: состав выборки и отображение соответствуют документированному контракту, не произвольной timezone-модификации.
- URI с существующим query/fragment, ключ с датой/пробелами/спецсимволами, целевые новые/legacy формы, отсутствие ключа; родительский отчёт не закрывается.
- SQL/HTML-инъекции через employee/ids/text/metadata headers нейтрализованы; данные выводятся текстом.
- Один раздел с SQL-error, долгий раздел, отмена/повтор формирования, late response, отзыв прав; частичный/устаревший результат явно отличим от полного.
- Большой объём: server paging/стабильный порядок, нет тихого ограничения первыхN и загрузки всех данных в UI; фиксированные заголовки,320–480px.
- Build, профильные тесты, browser smoke на реальных metadata. Отдельно проверить фактические определения и config URLs; мок с двумя выдуманными таблицами не доказывает production parity.

В handoff: перечень реально проверенных definitions (ID/название/schema/форма без публикации секретов), карта legacy→Clayzor, общие компоненты периода/множественного выбора, SQL/параметры/права, решения по UTC/неделе/zero selections, проверки и незакрытые зависимости. Неполученные строки metadata обозначь как ограничение; реализуемую без них инфраструктуру и тесты доведи до конца.

Хотя legacy-класс наследует EntityPage, в исследованной инициализации нет привязки редактируемой Entity к устойчивому entity-key. **CL-11 presence/совместное редактирование здесь не обязательны.** Не создавать общую «сущность отчёта» или broadcast фильтров другим пользователям.

По CL-10 текущие ClayLocalTime/ClayChanged уже умеют получать offset на дату записи. Проверка startup DapperColumnMapper показала только сопоставление имён колонок; он не нормализует DateTime.Kind. У DynamicGrid current-offset/Kind-зависимости есть отдельное общее задание, а static-grids этого отчёта должны получить тот же согласованный formatter.
