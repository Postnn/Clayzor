# Промт: реализовать Finder — выбор оборудования для телефонного номера

## Задача и границы

Реализуй в Clayzor самостоятельный экран расширенного выбора оборудования, эквивалентный `Inventory/Default/Finder.aspx`. Это **специализированный селектор оборудования для телефонного номера**, а не универсальный конструктор поиска и не карточка оборудования. Он читает предложения SQL-функции, позволяет просмотреть карточку и вернуть выбранное значение вызывающей форме. Сам Finder не создаёт, не привязывает и не сохраняет оборудование.

Обязателен [01_COMMON_RULES.md](../01_COMMON_RULES.md). Перед изменениями сверяй фактический HEAD, локальные незавершённые изменения и текущие AGENTS.md. Изоляция от параллельных исправлений Net/EquipmentForm обязательна. Не считать работу выполненной по наличию Razor-маршрута или обычного ClaySelect: нужны полный список с колонками и рабочий возврат в родителя.

Срез анализа: legacy `12a6efae7eb310adec06a57f6d80b8d9e76985b4`; Inventory `b3da274962c3c0811f71fbfe196f188ed3b5f659`; Controls `ea980be926ae975678314029ba5fc8aa68c675ba`; DBSelect `9b8551dab6228ebcaff7506110c71fddff5b6f03`. На этом срезе отдельного Finder нет, но источник предложений оборудования и общий канал расширенного поиска уже существуют.

## 2. Вход и режимы

Предоставь основной маршрут `/Default/Finder` и совместимый `/Default/Finder.aspx`. Сохрани подключение через настройку `Config.equipment_finder`/её текущий конфигурационный эквивалент. Конкретный legacy URL задаётся внешней конфигурацией; не угадывай домен и query-id.

| Параметр | Значение | Legacy-передача в SQL |
|---|---|---|
| `teltype` | Тип телефонного номера | `@param1` |
| `station` | Телефонная станция | `@param2` |
| `socket` | Розетка | `@param3` |
| `employee` | Сотрудник | `@param4` |
| `telid` | Телефонный номер | `@param5` |

В `FillFinder` отсутствие параметра заменяется строкой `"0"`; только точная строка `"0"` переводится в SQL NULL. Пустая строка и некорректное значение не обрабатываются как нормальный нулевой ввод. В Clayzor нормализуй типизированный ввод до запроса; явно различай допустимое отсутствие и неверный ID. Не выполняй SQL для невалидного ввода и не расширяй выборку молча.

Особенность: текущий `PhoneEquipmentSelectDataSource` возвращает пустой список, если не заданы тип/станция; legacy Finder вызывает функцию и с NULL. Нельзя объявлять их эквивалентными без проверки. Зафиксируй поведение функции для отсутствующих параметров и сохрани сценарии реальных callers.

`return`, `control`, `callbackKey`, `callbackUrl`, `mvc`, `clid` принадлежат legacy-каналу возврата; `requestId` и `returnOrigin` — современному. Обычное открытие без родительского запроса должно давать рабочий просмотр и понятное поведение команды выбора, а не сообщение об успешном возврате в несуществующий opener.

## 3. Список: фактически установленное поведение

Заголовок страницы — **«Выбор оборудования»**.

`SELECT_ORDER_fn_ОборудованиеДляТелНомера` выполняет:

```sql
SELECT *
FROM dbo.fn_ОборудованиеДляТелНомера(@param1, @param2, @param3, @param4, @param5) X;
```

Форма не задаёт дополнительного SQL ORDER BY. Схема результата берётся из функции динамически; исходник функции и полный набор возвращаемых колонок в репозитории не раскрыты. На стенде прочитай metadata результата и сравни фактическую последовательность колонок legacy. Не ограничивайся четырьмя «удобными» полями и не придумывай отсутствующие колонки.

Подтверждены настройки:

- `МодельОборудования` перемещается на позицию 1.
- `РасположениеPath` получает заголовок **«Расположение»**.
- `КодОборудованияПодключения` получает заголовок **«Код»**.
- `КодОборудования` — ссылка на карточку оборудования.
- Код оборудования **не скрывается**: строка, скрывающая его, закомментирована.
- Показываются заголовки даже при пустом результате; есть заглушка отсутствия данных.
- 35 строк на странице, пагинация включена, фиксированный заголовок.
- Группировка выключена; обычные сервисные/detail-колонки выключены.
- Возможности фильтра включены, панель фильтров первоначально скрыта.
- Отдельная сервисная колонка выбора включена с подписью из `ppBtnChoose`.
- `Редактировать`, `Применить`, `Обновить`, `Сохранить` удалены из панели EntityPage. Оставшиеся общие команды, в частности отмену/закрытие и доступную справку, не подменяй CRUD-панелью.

Реализуй список на ClayGrid. Пагинация/фильтрация/сортировка должны происходить на сервере с безопасными параметрами и стабильным порядком при равных значениях. Не заменяй полный поиск выдачей TOP 50 из источника автодополнения: текущий dropdown-source намеренно ограничен и предназначен для другого UX.

## 4. Выбор и ключ — главный интеграционный риск

Legacy Finder вызывает `v4_returnValue(КодОборудования, КодОборудования)`: второй аргумент — снова ID, а не модель. При этом legacy dropdown `DSOPhoneEquipment` использует **составной ключ** `КодОборудованияИПодключения`; `Tel.DbsEquipment_Changed` разбирает его по `;`. Следовательно, один лишь перенос старого Finder callback может потерять `КодОборудованияПодключения`.

Текущий Clayzor использует типизированный `PhoneEquipmentKey` и `PhoneEquipmentLookup`. Обязательное решение:

1. Внутри Clayzor возвращать корректный составной ключ выбранной строки, включая nullable ID оборудования подключения, и восстанавливать описание через существующий источник. Не делать произвольный выбор подключения по одному EquipmentId.
2. Сохранить отдельно обозначенный адаптер legacy ID/text для реальных старых callers, если они остаются. Если одному EquipmentId соответствует несколько строк, потеря подключения должна быть выявлена тестом и устранена в caller/адаптере, а не скрыта.
3. Не выполнять DML из Finder. Дальнейшее добавление/сохранение остаётся ответственностью Tel и его существующего save-flow. Текущий Clayzor добавляет выбор в черновик; перенос Finder не должен неожиданно вводить немедленную запись.
4. Реальный `Tel.DbsEquipment_BeforeSearch` передаёт текущие тип, станцию, сотрудника, розетку; `PhoneId` задаёт `0` и исключает уже связанное оборудование по EquipmentId. Finder самостоятельно читает только пять параметров и не обрабатывает `IDs`. В новом интегрированном пути согласуй исключения с текущим selector: не разрешай дубли и не теряй контекст фильтра.
5. Перед применением результата родитель повторно проверяет актуальность выбора, права и допустимость связи. Закрывшийся/перезагруженный родитель и устаревший запрос не получают чужой результат.

## 5. Общий callback: обязательная предварительная проверка

На исследованном срезе найден конкретный дефект общей инфраструктуры: `claySelectAdvancedSearch.open` сохраняет результат `clayOpen` как `child` и использует `event.source === child`, `child.closed`, `child.close()`; однако `clayFormWindow.open` и `clayOpen` возвращают boolean.

До интеграции Finder этот контракт должен быть исправлен централизованно, с проверкой существующих consumers. Предпочти внутренний API/регистрацию Window handle, сохраняя совместимость публичного boolean-контракта `clayOpen`: его существующие JSInterop consumers могут ожидать bool. Не меняй return type вслепую и не обходи общий механизм собственным `window.open` в форме.

Установленный протокол:

- `ClaySelectAdvancedSearchService.OpenAsync<TItem,TValue>(absoluteUrl, cancellationToken)` создаёт requestId в текущем circuit.
- JS добавляет `return=1`, `requestId` и `returnOrigin`.
- Дочерняя форма вызывает `claySelectAdvancedSearch.returnValue(requestId, value)`.
- Сообщение: `{ type: "clay-select-return", requestId, value }`.
- Родитель принимает только ожидаемый origin, конкретное дочернее окно и ожидаемый requestId; результат десериализуется в TValue.
- Закрытие окна, пользовательская отмена и блокировка popup возвращают null и не изменяют поле. Отмена lifetime через переданный CancellationToken завершает операцию с OperationCanceledException; cleanup остаётся обязательным, значение не применяется и не очищается, штатная отмена не показывается как ошибка выбранной сущности.
- После завершения удаляются обработчики, таймеры и pending-запрос.

Проверь два одновременных Finder/FinderTel, повторное открытие, старый callback после нового запроса. Устойчивый ключ окна должен различать формы и не приводить к перехвату результата другим поиском. Поддержка multiple в этом протоколе на срезе не заявлена: не приписывай Finder множественный выбор лишь из-за hidden `multiReturn`.

## 6. Данные, права и ошибки

Размести полный read model/SQL списка в Entities. DBSelect остаётся источником выбора, UI — оркестрацией чтения/возврата. Переиспользуй SQL-функцию и существующие DTO там, где подтверждено равенство полей; не копируй SQL в Razor.

**Подтверждённый дефект текущего общего lookup:** `SELECT_ТелефонОборудованиеДляВыбора` содержит `WHERE @Search = '' OR ...МодельОборудования... OR ...SN... OR ...РасположениеPath...` без скобок вокруг всей OR-группы. `PhoneEquipmentSelectDataSource.SearchAsync` снимает ORDER BY, дописывает `AND F.КодОборудования <> @ExcludedEquipment...` и возвращает сортировку. Из-за приоритета AND исключения ограничивают только последнюю OR-ветвь: пустой поиск, совпадение модели и SN обходят их. Это отдельная проблема от AND после ORDER BY в FinderTel.

Сначала проверь актуальный HEAD: другой агент мог уже исправить её. Если нет, перед присоединением исключений сгруппируй всё поисковое условие в общие скобки в назначенном общем слое. У изменения SQL/DBSelect один владелец через оркестратор. Сохрани установленную семантику исключения **по EquipmentId**, выделенному из ExcludedKeys; составной ключ результата не превращает это правило в исключение только одного подключения. В `Tel.OnEquipmentSelected` есть дополнительная проверка дубля по EquipmentId: дефект lookup доказывает неверную выдачу, но сам по себе не доказывает повторную запись. Новый Finder и dropdown должны применять один и тот же подтверждённый фильтр, не копируя ошибку.

Именованной специальной роли в Finder нет. Не назначай ему выдуманную роль администратора. Чтение и просмотр карточек происходят в доверенном текущем пользовательском контексте; идентичность и ограничения домена сохраняются. Текущее значение `employee` — фильтр оборудования, не доказательство личности. Ложные caller-параметры не должны обходить серверные ограничения записи в Tel.

При SQL-ошибке, отмене загрузки или утрате соединения показывай ошибку и разрешай повтор; не маскируй сбой под «ничего не найдено». Выбор блокируется на время загрузки/возврата. При смене query-параметров прежние строки и pending return инвалидируются; опоздавший ответ не должен перетереть новую выдачу. Содержимое модели, расположения и SN выводи как текст, не исполняемый HTML.

## 7. Приёмка

| Сценарий | Проверяемый результат |
|---|---|
| Прямое открытие обоих маршрутов | Одинаковая страница, нет 404/CRUD-панели |
| Все 5 параметров, затем каждый отсутствует/0 | Функция получает правильные аргументы в правильном порядке |
| Пустой/нечисловой/отрицательный/слишком большой ID | Контролируемая ошибка без расширения выборки |
| Функция возвращает 0, 1, 35, 36+ строк | Заглушка, корректный выбор и серверная пагинация |
| Одинаковый EquipmentId с разным подключением | Сохраняется составной ключ выбранной строки |
| Код/модель/расположение содержат кавычки и HTML | Безопасный текст, ссылка построена отдельно |
| Выбор из Tel | Верный контекст пяти фильтров, исключение дубликатов, корректный черновик |
| Непустые ExcludedKeys: поиск пустой, по модели, SN и расположению | Исключённый EquipmentId не появляется ни в одной ветви поиска; порядок и остальные фильтры сохранены |
| Несколько подключений одного исключённого оборудования | Исключается оборудование по EquipmentId; возвращаемый ключ остальных строк остаётся составным |
| Отмена, крестик, блокировка popup | Значение родителя не меняется, ожидание завершено |
| CancellationToken/dispose caller | Операция отменена, обработчики сняты, нет очистки значения и ложного уведомления об ошибке |
| Два одновременных поисковых окна | Результаты не перемешиваются |
| Чужой origin/window/requestId | Сообщение игнорируется |
| SQL-ошибка и retry | Ошибка видна; нет ложного пустого результата и повторного возврата |
| Просмотр карточки из грида | Открывается через clayOpen; Finder/родитель не перезагружаются |
| 320–480 px, клавиатура | Доступны фильтр, paging, выбор, ссылка и отмена |

Добавь профильные тесты нормализации параметров, составного ключа и callback. Browser smoke с настоящим Tel обязателен; одних mock-тестов недостаточно. Если DDL функции/старый caller недоступны, перечисли конкретно неподтверждённые поля/сценарии и не объявляй полной приёмки.

**Возврат и идентичность.** Команда «Выбрать» — явный RowAction с типизированной строкой и согласованным `PhoneEquipmentKey`; она не зависит от общего checkbox/batch selection ClayGrid. На срезе Controls этот batch mode основан на `HashSet<int>`/`TryGetSelectionId`, тогда как обычные row actions и dynamic edit/delete уже поддерживают строковый ID. Не обрезай составной ключ, не превращай его в int и не ставь Finder в зависимость от общего рефакторинга batch selection/export. Современный callback должен быть одноразовым: после принятия результата запрос помечен завершённым/удалён, повторное сообщение того же окна с тем же requestId не добавляет оборудование второй раз. До завершения возврата команда блокируется; ошибка транспорта и отмена не маскируются под успешный выбор.

**Фильтры и настройки.** Используй существующие диалоги ClayGrid: редактирование условий — черновик до Apply, Escape/Cancel/закрытие сохраняют прежнее условие. Для value filter и «выбраны все», и «ничего не выбрано» снимают именно пользовательский фильтр значений: это подтверждено legacy Grid.SetFilterByColumnValues и current ClayColumnValueFilterDialog.Apply; не путай этот случай с подтверждением пустого массива в Tree multiple-return. Скрытая панель фильтров не отменяет действующие условия. Очистка пользовательского фильтра не снимает пять входных domain-параметров и согласованные исключения оборудования. Сортировка, порядок/видимость колонок, fixed header и paging уже реализованы в Controls — их нужно настроить и проверить, а не скопировать JS. Legacy settings dialog даёт до пяти sort priorities, но legacy server/header SetOrderSortedColumn ограничивает сортировку тремя; current header path удаляет третий при добавлении, а dialog/state path устроен иначе. Это общий вопрос CL-07: не менять лимит локально и не делать legacy число пять обязательной новой возможностью Finder.

**Клавиатура, выделение текста и фокус.** Tab, Enter и Space на кнопке выбора/ссылке должны выполнять соответствующее действие один раз. Двойной щелчок по обычной текстовой ячейке в Styles выбирает текст; он не является выбором оборудования или открытием редактора. Если этот UX включён общей опцией CL-07, сохраняй уже существующее выделение внутри той же ячейки и не перехватывай input/link/button. Возврат/закрытие карточки не должны перезагружать Finder или уводить фокус в другую открытую форму; после cancel focus возвращается в исходный selector родителя через общий механизм.

**Изоляция.** Задай стабильный уникальный Grid Id и отдельную идентичность каждого запроса выбора, включая одновременно открытый FinderTel. Не используй общие DOM-селекторы, static current row/request или первый `.v4Grid` для определения адреса карточки. Текущий `ClayDragState.DraggedColumn` статичен на процесс — исправление его изоляции принадлежит владельцу CL-07; форма не заводит собственную конкурирующую версию. Включать row drag, group panel или multiple return на основании одного наличия функций в Styles нельзя.

Дополнительная приёмка: Apply против Cancel фильтра; 35→36 строк и возврат с другой страницы; одинаковый EquipmentId с разными подключениями; два Finder/FinderTel с разным контекстом; повторный valid callback; опоздавший callback закрытого запроса; Enter/Space без двойного добавления; text double-click без возврата; сохранённый domain filter после clear user filter. В handoff раздели статически подтверждённый контракт и реально выполненные browser-проверки.
