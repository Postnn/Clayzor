# Промт реализации LocationFact — «Инвентаризация рабочего места»

## Задача и границы

Реализуй сценарий **Inventory/Inv/LocationFact.aspx**: выбор рабочего расположения, список учётного/фактически найденного оборудования, поиск по SN/инвентарному номеру/коду, обычное подтверждение и режим сканера, фиксация повреждения/примечания, необязательное учётное перемещение в одной транзакции с подтверждением. Это не обычный список Equipment и не редактирование единственной карточки.

Прочитай [01_COMMON_RULES.md](01_COMMON_RULES.md), актуальные AGENTS.md Inventory, Entities, Controls/Grid и Controls/Select. Не перезаписывай работу текущего агента EquipmentForm/Net. После его исправлений сверяй shared EquipmentLocation API заново. Срез исследования: legacy `12a6efae7eb310adec06a57f6d80b8d9e76985b4`, Inventory `b3da274962c3c0811f71fbfe196f188ed3b5f659`, Entities `bf909e66d89a9a9c2f3fdc5069dd03b9b56368d7`, суперпроект `05f2fc7561bf2a5648cca7fce991be6e4c12cdb2`. Отдельной формы LocationFact нет; read model последней проверки и операции размещения уже частично существуют.

## 2. Маршруты и начальное состояние

Поддержи `/Inv/LocationFact` и `/Inv/LocationFact.aspx`. Специальных обязательных query-параметров форма не читает. Вход из меню может содержать idQuery — это контекст меню, не EquipmentId и не LocationId. Сохрани динамическое меню и точный заголовок **Инвентаризация рабочего места**.

В верхней части последовательно:

1. **Расположение:** обязательный ClaySelect, рядом **IT-оборудование**.
2. **Поиск по ответственному:** необязательный EmployeeSelect.
3. **Поиск по SN, Инв:№, коду:** специализированный выбор оборудования.
4. **Режим ввода - сканер** и действие с tooltip **Обновить список оборудования**.
5. Грид оборудования.

После первого рендера выбранного расположения нет, список пуст, выбор оборудования disabled, фокус в расположении. IT-флаг и сканер не получают самовольно включённого default: в markup/source они не заданы checked. Не добавляй универсальные Save/Apply/Edit/Delete: legacy снимает стандартные команды этой страницы.

## 3. Контракты выборов и handlers

### Расположение

Legacy BeforeSearch задаёт ТипыРабочихМест в порядке 1,2,3,5,4: компьютеризированное рабочее место, номер гостиницы, оборудование, гостевое рабочее место, склад оборудования. Сохранить набор; читать фактическое поле РабочееМесто у выбранного расположения. `4` — склад; это не конкретный LocationId.

Текущий Clayzor LocationSelect уже ограничивает `РабочееМесто IN(1,2,3,4,5)` и `Закрыто=0`, но возвращает только Id/NamePath1. Минимально расширь подходящий lookup/read для достоверного warehouse-флага; не вычисляй склад по тексту имени. Сверь legacy политику закрытых расположений с имеющимся источником перед принятием совместимости.

При изменении расположения: enable/disable поиска оборудования, очистить **Поиск по ответственному**, обновить warehouse-признак и грид. При очистке: warehouse=false, грид очищен, поиск disabled. Текущий диалог/операция не должны незаметно продолжить сохранение в новом расположении, если пользователь поменял его во время ожидания: привязывай команду к snapshot выбранного LocationId.

### Ответственный и IT

Смена ответственного перечитывает грид; это фильтр, а не назначение нового ответственного. Смена IT-флага перечитывает грид и возвращает фокус в поиск оборудования. IT=false означает **все**, а не только не-IT. IT=true ограничивает тип оборудования `<100` согласно legacy; не переименовывай порог в придуманный справочный код.

### Поиск оборудования

Перед поиском SearchTerm = введённый SearchText, null/пробелы нормализуются по FOptSearchTerm; IT-параметр передаётся независимо. Источник: `dbo.fn_ПоискОборудования(@SearchTerm)` через SELECT_fn_ПоискОборудования. Popup содержит строго **Код, Оборудование, SN, Владелец, Инв.**; значение хранит EquipmentId, DisplayText из колонки Найдено. Источник не ограничивается выбранным расположением: поиск должен позволять найти оборудование, которое реально находится здесь, но числится в другом месте. Иначе исчезнет сценарий перемещения.

Пустое выбранное значение ничего не делает. Непустое в обычном режиме открывает диалог; в scanner-режиме запускает быстрый сценарий ниже. После обработки выбора поиск очищается для следующего считывания. Не вставляй сырую строку сканера в SQL, имя, URI или HTML. Смена текста не равна подтверждённому выбору EquipmentId.

## 4. Что именно показывает грид

SELECT_ОборудованиеНаРабочемМесте — **FULL JOIN двух множеств**, не простой WHERE LocationId=@id:

- Учётная часть: последнее ОборудованиеРасположение данного оборудования в выбранном месте, только несписанное оборудование; модель/тип для названия и IT-фильтра. Название объединяет тип, сетевое имя, модель, PN, SN, номер SIM, примечания оборудования.
- Фактическая часть: последняя запись vwРеальноеРасположениеОборудования в выбранном месте, только несписанное оборудование и применимый IT-фильтр. Запись исключается, если после проверки было более новое учётное перемещение.
- FULL JOIN по EquipmentId сохраняет ожидаемое, но ещё не найденное оборудование и фактически найденное, не числящееся здесь.
- Выходной ID/название — COALESCE учётного и фактического; время/расположение/повреждение/примечание берутся из факта.
- `FirstSortDesc` = ВремяПроверки, только если учётное От < фактического ВремяПроверки; иначе NULL.
- Необязательный responsible-фильтр в source проверяет vwОборудованиеСписок и использует именно ID **учётной** части. Поэтому actual-only строки при таком фильтре исключаются. Сохрани это наблюдение в карте совместимости; исправлять на COALESCE можно лишь как явное решение с тестом, не как незаметную «оптимизацию» запроса.

Параметризуй исходные string.Format placeholders: LocationId(int), nullable IT/boolean с эквивалентной семантикой, nullable ResponsibleId(int). Не выкидывай FULL JOIN/NOT EXISTS и не заменяй их последним известным Equipment.LocationId.

| Видимый порядок | SQL | Заголовок / действие |
|---:|---|---|
| 1 | КодОборудования | **Код**, ссылка на EquipmentForm |
| 2 | Оборудование | **Оборудование**, открывает диалог подтверждения, а не карточку |
| 3 | ВремяПроверки | **Последняя проверка**, локальное отображение UTC |
| 4 | Расположение | **Расположение при последней проверке**, ссылка по скрытому КодРасположения |
| 5 | Примечание | **Примечание**, префикс «Сломано, ремонту не подлежит. » при флаге>0 |

Скрытые поля: КодРасположения, СломаноРемонтуНеПодлежит, FirstSortDesc. Форма вызывает SetOrderBy(Оборудование,Asc), затем SetOrderBy(FirstSortDesc,Desc), затем повторно SetOrderBy(Оборудование,Asc). Дополнительно изучены [Grid.cs](https://github.com/KescoDev/Kesco.App.Web.V4.Inventory/blob/12a6efae7eb310adec06a57f6d80b8d9e76985b4/Kesco.Lib.Web.Controls.V4/Grid/Grid.cs), методы SetOrderByColumnValues/SetOrderSortedColumn/GetResultTableSortingString, и [GridSettings.cs](https://github.com/KescoDev/Kesco.App.Web.V4.Inventory/blob/12a6efae7eb310adec06a57f6d80b8d9e76985b4/Kesco.Lib.Web.Controls.V4/Grid/GridSettings.cs): новая основная колонка принудительно получает ASC, пока её прежний OrderByNumber не1. Поэтому на свежих настройках эта последовательность фактически даёт **Оборудование ASC, FirstSortDesc ASC**, несмотря на имя FirstSortDesc и переданный Desc. Зафиксируй source-трассу и результат smoke; не объявляй задуманный DESC существующим поведением. Если исправляешь сортировку, зарегистрируй это отдельным осознанным отличием и тестом. Пользовательская сортировка отключена empty SetSortingColumns; панели фильтра/группировки/пагинации скрыты, фиксированный заголовок, пять колонок помечены фильтруемыми. Не добавляй шестую служебную колонку там, где действия уже даны ссылками.

«Проверено недавно» = ВремяПроверки !=NULL и `.Date == DateTime.UtcNow.Date`. Именно UTC-день, а не дата браузера. Для остальных — Information-индикация строки и соответствующих текстовых ссылок/примечаний. При этом само время показывается локальным. Проверить обе стороны полуночи, не исправлять это различие молча. Источник/политику времени явно отразить в handoff.

## 5. Обычный диалог подтверждения

Заголовок **Подтверждение нахождения оборудования на расположении**. Кнопки **Подтвердить**, **Отмена**. Один активный диалог на страницу; закрытие/отмена не пишут. Порядок полей:

| Поле | Поведение |
|---|---|
| Код оборудования | readonly |
| Оборудование | Ссылка на карточку, equipment.Name |
| Владелец | Ссылка на Person по текущему PersonOwnerId |
| Инвентарный номер | readonly из BuhInfo.InventoryNumber; строка скрывается, если пусто |
| Сломано, ремонту не подлежит | checkbox |
| Примечание | TextArea, максимум500,3 строки; фокус при открытии |
| Подтвердите, что оборудование находится на расположении | Ссылка на выбранное место по NamePath1 |

Перед открытием загружаются оборудование, владелец, выбранное расположение, последняя фактическая запись, текущее учётное LocationEquipment. Если у оборудования нет владельца, обычный путь показывает ошибку **Невозможно провести инвентаризацию, т.к. у оборудования #N нет владельца**, пояснение **Необходимо указать владельца оборудования**.

Формируемое имя для записи факта: необязательное `NetworkName + пробел`, затем `Model.Name`, затем при наличии ` SN: SN`. Это не обязательно совпадает с длинным именем строки грида. Предел300 символов перед INSERT; имя получать из актуальной серверной записи, клиент не является доверенным источником.

Перед новым оборудованием сбросить все поля и состояние предыдущего диалога. В legacy предыдущие broken/notes восстанавливаются только если у последней фактической записи непустое Description. Это оставляет broken=false при Description пустом; дефект выделен в разделе10, не используй условие на Description как проверку существования факта.

## 6. Подтверждение с перемещением и без

Если текущее учётное расположение отсутствует или отличается от выбранного, перед записью нужен **трёхисходный** вопрос:

- Если прежнее известно: «Расположение оборудования [{0}] не менялось с момента проведения последней инвентаризации: [{1}]. Выполнить перемещение оборудования на текущее место инвентаризации?».
- Если прежнее отсутствует: «Выполнить перемещение оборудования [{0}] на текущее место инвентаризации?».

Варианты **Да / Нет / Отмена** имеют разные последствия:

| Ответ | Учётное расположение | Фактическая проверка |
|---|---|---|
| Да | Добавить новый период выбранного расположения | Добавить запись факта |
| Нет | Не менять | Добавить запись факта в выбранном месте |
| Отмена | Не менять | Не добавлять |

Нельзя трактовать «Нет» как отмену проверки. Нельзя принудительно перемещать при каждом подтверждении. Текст старого расположения — путь NamePath1, не просто ID. При совпадении мест нет лишнего вопроса.

После успеха закрыть только диалог, очистить и сфокусировать поиск. Для обычного места перечитать грид. Для склада legacy намеренно не перечитывает грид автоматически после каждого подтверждения; ручное **Обновить список оборудования** остаётся доступным. При ошибке не закрывать диалог/не очищать черновик как при успехе.

## 7. Режим сканера

Это ускоренное подтверждение выбранного из поиска оборудования, а не отдельный драйвер устройства. Сканер работает как ввод/выбор; не добавляй зависимость от аппаратного API.

- Если учётное место совпадает: выполнить подтверждение без открытия редактирующего диалога; показать на3s **Подтверждено нахождение оборудования <имя> на рабочем месте!** или **…на складе!**, затем вернуть фокус.
- Если место отличается/отсутствует: сохранить трёхисходный вопрос перемещения. Scanner не разрешает перемещение молча.
- Для рабочего места обновить грид; для склада не перечитывать автоматически каждое сканирование.
- Legacy JS дополнительно автонажимает «Подтвердить» спустя1s, если диалог всё-таки открыт при включённом scanner; команда checkScanner также может подтвердить текущий диалог. В новой реализации сделай один типизированный путь запуска, чтобы сочетание auto-click, ValueChanged и команды не записало два факта. Сохрани ускорение, не копируй несколько конкурирующих таймеров.
- Запись, смена расположения, следующий scan и поздний ответ предыдущего поиска требуют согласования состояния. Один подтверждённый scan не должен завершаться под EquipmentId/LocationId следующего. Проверить очередь/блокировку in-flight и отмену устаревшего результата. Не вводи бессрочную дедупликацию: повторное осознанное сканирование может законно создать новую проверку.
- Имя оборудования в toast выводится текстом, не innerHTML из пользовательских данных.

Серверные обязательные проверки должны действовать и здесь. Legacy scanner напрямую обращается к ConfirmEq, минуя часть диалоговой загрузки; нельзя считать его обход прав/актуальности нормальным контрактом. Не переносить notes/broken предыдущего диалога в следующий scan. Нормальные defaults быстрого пути должны быть явными; изменение политики восстановления предыдущего примечания отметить в карте решений.

## 8. Атомарная запись и повторное использование Clayzor

Операция ConfirmEq принадлежит Entities/узкому доменному coordinator. Успех = **все** записи завершены. Последовательность:

1. На сервере установить current user/права, загрузить текущие Equipment/Owner/Location, проверить выбранные PK и актуальность snapshot. Не доверять client equipmentDisplayName, oldEquipmentLocation, isWarehouse или флагу прав.
2. Если withRelocation=true, создать период ОборудованиеРасположение с `От = now −1s`, выбранным LocationId, notes. Legacy комментарий говорит о преобразовании в UTC, но сам LocationEquipment.Save в изученном срезе передаёт dateFrom напрямую. В новой модели `FromUtc` уже явно UTC: использовать один проверенный источник времени, гарантировать relocation timestamp < timestamp факта и не делать двойную конвертацию.
3. Не потерять побочные эффекты **INSERT_ОборудованиеРасположение**: guard против более нового периода; для действующей телефонной станции типа28 с сетевым именем каскад перемещения её несписанных SIM типа27, найденных по префиксу примечания последнего расположения, с сохранением их сроков возврата/примечаний.
4. В той же транзакции выполнить **INSERT_РеальноеРасположениеОборудования_РабочееМесто** в `vwРеальноеРасположениеОборудования`: ВремяПроверки=GETUTCDATE(), `@КодОборудования`, `@Оборудование` до300, `@КодРасположения`, `@СломаноРемонтуНеПодлежит`0/1, `@Примечание` до500.
5. Commit только после обоих успехов. Ошибка факта откатывает перемещение и его SIM-эффекты. Ошибка перемещения не допускает факта. Вернуть типизированный результат, по которому UI решает close/refresh/toast.

**Готовое повторно использовать:** EquipmentActualInventory и существующее чтение последней проверки, Equipment/модели/владельца, EquipmentLocationPeriod, SQL INSERT расположения, LocationSelect. **Не готово:** специализированный источник fn_ПоискОборудования, объединённый грид LocationFact, warehouse/scan-state и атомарный use case «перемещение+факт».

Не вызывай существующий `EquipmentLocationPeriod.InsertAsync` отдельной завершённой транзакцией, после которой вторым вызовом пишется факт: rollback уже не будет общим. Расширь shared механизм так, чтобы обе операции выполнялись одной SQL-транзакцией/соединением, без конкурирующей копии SQL и без DTC по случайности. Не назначай нового ответственного из фильтра dbsResponsible — такого действия legacy нет.

Проверить длины: existing EquipmentLocationSaveBuilder задаёт notes size300, тогда как примечание факта принимает500. При relocation нельзя молча обрезать один из текстов или потерять весь факт из-за скрытого размера. Сверь действительную схему обеих колонок и явно реализуй допустимый контракт/валидацию; не расширяй БД по предположению.

SQL Server2008R2, все значения параметризованы. Запросы и DTO в Entities/ColumnNames; Web не создаёт свой SQL/DAL. Для очереди сканов не использовать static состояние, не делиться черновиком между circuits.

## 9. Права, конкуренция и частичный результат

У source формы нет явного HasRole: чтение/запись под DS_user; при переносе установить фактические DB grants/триггеры. У существующего Clayzor AddLocationAsync есть проверка роли43; это готовый контракт учётного перемещения, но его нельзя автоматически распространить на все чтения/подтверждения без анализа. Через Employee CurrentUser разделить разрешение увидеть список, подтвердить факт и переместить, если БД действительно различает их. Прямой вызов ConfirmEq, scanner, Yes/No одинаково защищены. Ошибка identity/SQL — fail closed, не произвольный пользователь.

Клиентские данные старого расположения нужны для текста, не для разрешения записи. Между диалогом и «Да» оборудование могло переехать, быть списано/удалено, сменить владельца, а расположение — закрыться. Сервер повторно проверяет контекст; если он изменился, сообщает конфликт и требует актуального осмысленного решения, не пишет старый выбор в обход новой истории.

Если commit состоялся, но грид не перечитался, показать отдельный результат «подтверждено, список не обновлён» и повторять только чтение. При неопределённом результате связи не повторять INSERT автоматически. Защита от двойного события должна отличаться от запрета будущих реальных проверок.

## 10. Дефекты source, которые нельзя переносить механически

1. Проверка `loc != null || loc.Unavailable` ошибочна: OR вместо проверки пригодности. Не считать unavailable-расположение валидным складом и не получить null dereference.
2. Broken восстанавливается только при непустом Description; восстанавливай флаг независимо от наличия примечания, сохрани тест на broken=true/notes пусто.
3. Scanner использует поля диалога notes/broken без гарантированного reset; исключи перенос данных между оборудованием.
4. Scanner показывает старое расположение как ID, обычный путь — как NamePath1; сохрани содержательный путь и единый prompt без дополнительного произвольного workflow.
5. После раннего return из ConfirmEq при ошибке перемещения внешний ProcessCommand всё равно закрывает диалог/очищает выбор. Новый UI должен отличать успех от ошибки.
6. SELECT_fn_ПоискОборудования содержит EXISTS по vwОборудование/Модели без корреляции к найденному EquipmentId. Поэтому legacy IT-фильтр может фактически проверять наличие хоть какого-то IT-оборудования. Исправление корреляции должно быть явным и покрыто смешанным набором IT/non-IT, а не замаскировано общим тестом «поиск вернул строку».
7. Пустой DateReturn в LocationEquipment выглядит nullable, но его getter возвращает DateTime.MinValue; изученный [DBManager.cs](https://github.com/KescoDev/Kesco.App.Web.V4.Inventory/blob/12a6efae7eb310adec06a57f6d80b8d9e76985b4/Kesco.Lib.DALC/DBManager.cs) нормализует DateTime.MinValue в DBNull. Это **контракт старого DAL**, а не ошибка отсутствующего срока. В новой Dapper-модели передавать явный NULL и проверить быстрый перенос без срока; не передавать 0001-01-01 в SQL datetime.
8. Ответственный фильтрует только учётную сторону FULL JOIN — это наблюдаемая неоднозначность, а не очевидная опечатка. Зафиксируй отдельно решение о сохранении/изменении; не путай с однозначными техническими дефектами выше.

## 11. Исчерпывающая приёмка

- Оба маршрута, вход через меню, начальный disabled поиск, отсутствие лишних команд, точные подписи/5 колонок, корректный Tab/мобильный320–480px.
- Пять типов расположений, склад4, clear/change location сбрасывает responsible и состояние; unavailable location не создаёт операции.
- FULL JOIN: учётное без факта, факт без учётного здесь, совпадение, более новый переезд, списанное оборудование; фильтр responsible при actual-only; IT true/false.
- Порядок FirstSortDesc/имени, NULL ВремяПроверки, вчера/сегодня по UTC и отображение локального времени, broken prefix.
- Поиск по каждому поддержанному ключу/строке fn_ПоискОборудования, неограниченный текущим местом; несколько результатов, ноль результатов, IT/non-IT при включённом флаге.
- Код открывает карточку, название открывает диалог; карточки оборудования/владельца/расположения через clayOpen без закрытия родителя.
- Полный диалог, отсутствие владельца, отсутствие инвентарного номера, NULL факта, broken с пустыми notes,500/501 символ, имя>300, HTML/кавычки.
- Совпадающее место = один факт; разное/отсутствующее место: Да=перемещение+факт, Нет=только факт, Отмена=ноль записей.
- Atomic rollback при ошибке перемещения, записи факта и каскада SIM; временной порядок relocation<check; тип28/27 и примечания SIM не теряются.
- Scanner same/different/warehouse, ручной refresh склада, уведомление3s/фокус, серия быстрых сканов, повторный scan того же ID, late response, закрытие страницы.
- Ошибка не закрывает/не стирает ввод, после failed relocation нет success toast; успешный commit+failed reload не повторяет запись.
- Конкурентное перемещение/удаление/списание/смена владельца, отзыв прав, прямой handler без рендера, два circuits, double click/auto-confirm.
- Длины notes в обоих хранилищах доказаны; тест SQL2008R2 совместимости отдельно от того, что тестовый SQL2022 принял запрос.

Handoff: карта полей/команд, SQL и зависимости, разрешённые изменения перечисленных legacy-дефектов, транзакция/таймзоны/права, результаты build/профильных тестов/browser/разрешённых test-DB операций. Не принимать перенос без доказательства rollback и scanner-изоляции; непроверенные DDL/metadata указывать конкретно.
