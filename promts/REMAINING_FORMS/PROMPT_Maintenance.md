## Задача и границы

Реализуй в Clayzor страницу, эквивалентную legacy **Inventory/Maintenance.aspx**: список регламентных работ, срок выполнения, ссылка на инструкцию и подтверждение выполнения конкретной работы. Здесь нет карточки ремонта оборудования, редактора регламента или CRUD расписания. Динамический Home с произвольным запросом не заменяет специальное действие «Подтвердить выполнение» и семантику этой страницы.

Прочитай [01_COMMON_RULES.md](01_COMMON_RULES.md) и актуальные AGENTS.md суперпроекта, Inventory, Entities, Controls/Grid. Работай с актуальным checkout после сверки изменений других агентов. Не затирай текущие исправления EquipmentForm/Net; не делай commit/push без уже выданного разрешения. Этот файл содержит результат чтения исходников, а не предложение заново выяснять основную логику.

**Исследованный срез:** legacy `12a6efae7eb310adec06a57f6d80b8d9e76985b4`; Inventory `b3da274962c3c0811f71fbfe196f188ed3b5f659`; суперпроект `05f2fc7561bf2a5648cca7fce991be6e4c12cdb2`. В этом Inventory нет Maintenance-страницы или равнозначного действия. Наличие общих ClayGrid и меню — готовая инфраструктура, не готовая форма.

## 2. Маршрут и входы

Поддержи `/Maintenance` и совместимый `/Maintenance.aspx`. У самой формы нет обязательного id записи в URL. `idQuery`, если он добавлен существующим меню, относится к контексту меню, а не к выполняемой работе. Идентификатор работы берётся из строки грида.

Переход должен работать и напрямую, и через действующую запись меню/URI конфигурации. Проверить фактические metadata до изменения маршрутизации; не создавать второй пункт меню, если пункт уже задаётся БД. Отдельных return, multi, idp/gridId или refreshOpener-сценариев у этой страницы нет.

## 3. Полная модель отображения

При первой интерактивной загрузке получить Employee CurrentUser, затем список из DS_user. У страницы нет обычных команд редактирования: legacy удаляет Refresh, Edit, Save, Apply, ReCheck, Cancel из общей панели. Сохранить назначение экрана и не добавлять «Добавить регламент», удаление или массовое выполнение.

Заголовок страницы и грида: **Регламентные работы**. Состав видимых колонок задан ниже. Достоверно закреплена первая action-колонка (`SetColumnOrder(КодРегламентныхРабот,0)`); относительный порядок остальных берётся из schema `SELECT * FROM vwРегламентныеРаботы`: список в SetColumnDisplayVisible меняет видимость, а не переставляет колонки. Поэтому до окончательной разметки прочитай порядок колонок view на стенде и перенеси его; ниже порядок перечисления в настройке source, не выдуманный DDL view.

| № в списке source | SQL-колонка | Заголовок / отображение |
|---:|---|---|
| 1 | КодРегламентныхРабот | Пустой заголовок; кнопка «Подтвердить выполнение», не текстовый PK |
| 2 | ВыполнитьДо | «Выполнить до», формат yyyy-MM-dd HH:mm:ss, специальная индикация |
| 3 | РегламентнаяРабота | «Регламентная работа» |
| 4 | Ответственный | «Ответственный»; не подменять исполнителем последнего выполнения |
| 5 | Ссылка | «Ссылка»; правила ссылок ниже |
| 6 | ПоследнееВыполнение | «Последнее выполнение» |
| 7 | Сотрудник | «Сотрудник»; ссылка на сотрудника по скрытому КодСотрудника |

`КодСотрудника` скрыт. Код работы хранится типизированно и используется действием строки. Не показывать дополнительный технический столбец ID одновременно с action-колонкой. В ClayGrid разместить действие в существующей сервисной колонке с тем же первым положением, не создавать вторую.

Legacy задаёт `ВыполнитьДо ASC`, отключает пользовательскую сортировку через SetSortingColumns(empty), скрывает панели фильтра/группировки и пагинации, всегда показывает заголовок, использует пустое сообщение из sNotFound. В нём также перечислены шесть бизнес-колонок как фильтруемые и сохраняемые, префикс `InvMaintenanceFilter`. Перенеси соответствующие доступные настройки через штатный ClayGrid, сохрани исходный вид без внезапно открытой общей панели. Не теряй пользовательские настройки из-за объединения с Home. Если существующий grid API не поддерживает это сочетание, добавь минимальную общую возможность и зафиксируй соответствие параметров.

## 4. Сроки и индикация

В code-behind проверка делается относительно **DateTime.Now сервера**, без вызова ToClientLocalTime для ВыполнитьДо. При переносе сначала установи реальный тип/зону источника: нельзя автоматически объявить эти значения UTC из-за наличия других UTC-полей в Inventory.

| Значение ВыполнитьДо | Legacy-результат |
|---|---|
| NULL | Пустая ячейка; ранний выход render, без цвета |
| now > deadline | Error-индикация просрочки |
| now ≤ deadline и now + 1h > deadline | Recommended-индикация приближения |
| deadline ≥ now + 1h | Обычный вид |

Равенство `now == deadline` не считается просрочкой, но попадает в приближение. Равенство `now + 1h == deadline` ещё не приближение. Хотя IsWorkOutdated(NULL) отдельно возвращает true, renderer до него не доходит; не окрашивай пустой срок как просроченный по механически перенесённому helper.

Вынеси вычисление статуса в чистое правило с передаваемым временем для проверок. Цвет/стиль — общая система Clayzor, не локальные CSS-переопределения. Не добавляй произвольный фоновый auto-refresh: у legacy он не установлен; переоценка при загрузке/успешном выполнении обязательна.

## 5. Ссылки и прочие значения

Legacy trim-ит Ссылка. Если начинается с `http` без учёта регистра — делает ссылку в новое окно. Если соответствует `^(\S:\\)` — преобразует диск Windows `C:\...` в `file:///C|/...`. Прочие значения и NULL дают пустую ячейку. UNC-пути этой веткой не поддержаны. Это фактический контракт, а не обещание, что современный браузер разрешит file URL.

Реализуй корректный разбор URI, HTML-кодирование текста и безопасную обработку кавычек. Не исполняй схемы javascript/data и не генерируй HTML из данных. Ссылки на карточки сотрудников открывай через общий `clayOpen`/ClayFormWindow с устойчивым ключом; родительская страница остаётся на месте. Ссылку на инструкцию открывай согласованным общим механизмом. Для разрешённых файловых ссылок честно обработай ограничение браузера, не сообщай об успешном открытии неоткрытого файла. Не добавляй обход прав файловой системы или серверную загрузку произвольного пути.

Если есть ФИО, но отсутствует КодСотрудника, оставь читаемый текст без сломанного перехода. Nullable employee ID, пустое имя и неизвестный сотрудник не должны рушить грид.

## 6. Подтверждение выполнения — точная последовательность

1. Пользователь нажимает кнопку строки. Открывается ConfirmDialog с заголовком **Подтвердите выполнение**, текстом **Подтвердите выполнение регламентной работы** + двоеточие, перевод строки и имя работы. Кнопки — штатные «Да»/«Нет» из ресурсов.
2. «Нет», Escape или закрытие диалога не выполняют SQL и не меняют список.
3. «Да» передаёт только валидный PK выбранной работы. Перед записью сервер повторно проверяет текущую identity/права и актуальность доступности работы. Имя клиента не является доказательством доступа и не участвует в SQL.
4. Выполнить `INSERT_РегламентныеРаботыВыполнение` с единственным параметром `@id` (int): `INSERT INTO РегламентныеРаботыВыполнение (КодРегламентныхРабот) VALUES(@id)`.
5. При успехе перечитать `SELECT_РегламентныеРаботы`: `SELECT * FROM vwРегламентныеРаботы`. Именно БД возвращает новые ПоследнееВыполнение, Сотрудник и ВыполнитьДо; локально их не вычислять.
6. При ошибке записи не показывать success, не обновлять строку оптимистически, разблокировать кнопку и сохранить контекст. При успешной записи и ошибке reload различить «выполнение записано, список не обновлён», а не предлагать слепой повтор INSERT.

Legacy параметр `name` в FinishMaintenance не используется для записи. Не вводить клиентские timestamp/EmployeeId; фактические значения автора/времени формируются БД — проверить DEFAULT/триггеры. Повторное сознательное выполнение может быть новой законной записью, поэтому не добавлять бессрочную дедупликацию. Но один double click/одновременный повтор callback не должен создавать две записи; блокировка in-flight и тест обязательны. Не повторять пишущий SQL автоматически после неопределённого сетевого результата.

## 7. Права и архитектура

У legacy нет явного HasRole в этой форме: список и INSERT идут через DS_user, с окончательной защитой БД. Роль ответственного и имя исполнителя в строке не являются явно заданным правом пользователя на Finish. Не назначай 43, 102 или любую другую роль по названию экрана. Установи реальный доступ по grants/виду/триггерам и текущей серверной модели Employee; отражай его в UI и повторяй проверку write-path. Недоступные данные/SQL 229 — понятный отказ, не пустой успешный список и не разрешение по умолчанию.

Чтение и запись принадлежат Clayzor.Lib.Entities, SQL — его SQLQueries.cs, имена колонок — ColumnNames.cs. Нужны read model списка и узкая операция регистрации выполнения, не CRUD-прокси в Web.Services. Компонент отвечает за грид и диалог. SQL Server 2008 R2; все значения параметризованы; raw SQL вызывается как CommandType.Text. В форму не переносить SQL и DataTable-HTML renderer.

## 8. Обязательная приёмка

Проверь сценариями, а не сравнением имён методов:

- Прямые оба маршрута, вход через текущую запись меню, idQuery не меняет PK работы.
- Все семь видимых колонок, действие первым, остальной порядок по проверенной schema view, точные подписи, скрытый КодСотрудника; нет второго столбца действия и лишних CRUD-команд.
- Сортировка сроков ASC, пустой результат, сохранённые параметры грида, фиксированный заголовок, узкие 320–480px.
- Срок NULL, просрочен на секунду, равен now, через 59m59s, ровно +1h, далёкий срок; выбранная зона времени документирована.
- Ссылка HTTP/HTTPS, Windows-диск, UNC/неподдерживаемая строка, пробелы, кавычки и HTML в названии/URL; отсутствующий employee ID.
- «Нет»/закрытие = ноль INSERT; «Да» = ровно один INSERT выбранного PK и reload; имя из клиента не влияет на БД.
- Проверено, кем/когда БД заполняет выполнение и как пересчитывает следующий срок; без выдуманного расчёта на клиенте.
- SQL отказ до INSERT, отзыв прав после открытия диалога, удалённая/недоступная запись, прямой вызов обработчика без рендера.
- Double click, повторный callback, disconnect во время записи, успешная запись с неуспешной перезагрузкой — нет ложного success или слепого дубля.
- Открытие сотрудника/инструкции сохраняет родительский грид; проверка в браузере, сборка и профильные тесты.

Реальные записи выполняй только на разрешённом тестовом стенде. В handoff укажи карту legacy→Clayzor, SQL/права, результаты и ограничения проверки. Если DDL или стенд недоступны, закончи весь доступный код и тесты, а непроверенную DB-семантику перечисли явно; не объявляй её доказанной.
