# Промт реализации duty_form — «Дежурство инженера»

## Задача и границы

Реализуй карточку дежурства, эквивалентную **Inventory/Duty/duty_form.aspx**: планирование инженера на день, подтверждение прошедшего дежурства, фактический инженер, отгул вместо оплаты, окончательное закрытие и просмотр итогов. Это одна карточка с ключом-датой; отдельный календарь расписания в scope не добавляется.

Прочитай [01_COMMON_RULES.md](01_COMMON_RULES.md) и актуальные AGENTS.md суперпроекта, Inventory, Entities, Controls/Select. Проверь текущие изменения других агентов перед началом; не затирай их и не делай commit/push без предоставленного разрешения. Исследованный срез: legacy `12a6efae7eb310adec06a57f6d80b8d9e76985b4`, Inventory `b3da274962c3c0811f71fbfe196f188ed3b5f659`, суперпроект `05f2fc7561bf2a5648cca7fce991be6e4c12cdb2`. В текущем Inventory отдельной duty-формы/эквивалентного сценария нет.

## 2. URL и ключ

Поддержи `/Duty/duty_form` и `/Duty/duty_form.aspx` с параметром `id`. Без id создаётся новое дежурство; существующее загружается по дате. **PK — колонка Дата, не числовой identity.** DutyTiming после чтения сериализует Id как `yyyyMMdd`; Load преобразует вход через Convert.ToDateTime и затем в yyyyMMdd. Установи реальные URL из metadata/вызывающего грида и поддержи канонический yyyyMMdd, не наследуя зависимость разбора от культуры сервера. Если реально встречаются другие представления даты, добавь явный совместимый разбор и тесты, не разрешай неоднозначные даты молча.

Плохой id, недоступная запись и отказ SQL не превращаются в новую карточку. Дата не должна проходить через UTC-смещение как instant: это календарный день. Плановая/фактическая даты сохраняют смысл независимо от часового пояса клиента.

## 3. Матрица состояний

Фактические свойства DutyTiming:

- `IsClosed = Closed == 1`.
- `CanClosed = !IsNew && !IsClosed && DutyDate < DateTime.Today`.
- `IsHoliday = WorkDay.HasValue && WorkDay != 1`.
- `ClosedType`: 0 невозможно определить; 1 замечаний нет; 2 другой сотрудник; 3 никто не дежурил.

| Состояние | Редактирование | Save-ветка |
|---|---|---|
| Новое | Дата следующего свободного дня, плановый инженер | SaveInsert |
| Существующее сегодня/в будущем, не закрыто | Плановый инженер; дата фиксирована | SaveUpdateSimple |
| Существующее до сегодняшнего дня, не закрыто | Плановый инженер readonly; блок подтверждения | SaveUpdateFact(close false/true) |
| Закрыто | Только итог; «Закрыто», кнопки Save нет | Сервер обязан отвергать запись |

Сегодня ещё не считается прошедшим днём. Используй согласованное с legacy/БД понятие «сегодня»; не заменяй server/DB business date произвольной UTC-датой или датой браузера без решения. Повторно вычисляй состояние перед записью: карточка может остаться открытой через полночь либо быть закрыта другим пользователем.

Для закрытого дежурства legacy UI убирает Save, но прямой вызов Save может попасть в простую ветвь, потому что CanClosed=false. Этот дефект нельзя перенести как разрешение редактировать закрытые записи через API. Прямые вызовы проверяются на сервере.

## 5. Выбор инженеров и календарь

Оба select используют один DutyPeriod в формате yyyyMMdd, равный дате карточки, а при её отсутствии — today. SQL SELECT_ДежурныеИнженеры:

- только сотрудники с Состояние=0 и наличием РолиСотрудников.КодРоли=102;
- вывод «Инженер» / «Дежурств»;
- статистика за календарный месяц выбранной даты, учитывает только строки с РабочийДень IS NOT NULL;
- сотрудник статистики = ISNULL(КодСотрудникаФакт, КодСотрудника);
- Всего=count, Выходных=sum(РабочийДень=0); строка вида `N (в вых: M)`, без статистики пустая строка;
- сортировка по Сотрудник, поиск по Сотрудник и КодСотрудника; просмотр карточки сотрудника через employeeid.

Обычный EmployeeSelect с одним ФИО без фильтра102/статистики не эквивалентен. Реализуй или минимально расширь общий источник DBSelect. Число102 — подтверждённый фильтр кандидатов, **не доказательство права текущего пользователя редактировать расписание**. Используй enum реальной таблицы Роли. Не заменяй этот исторический состав списка новым алгоритмом замещений без проверки ожидаемого поведения.

Рабочий/выходной определяется Employee.CheckWorkDay: фактический инженер имеет приоритет, иначе плановый, иначе NULL. SELECT_Сотрудник_РабочийДень учитывает Праздники, иерархию Территории и территорию рабочего места; fallback-территория в SQL —188, затем DATEFIRST1 и выходные weekday>5. Значение188 требует подтверждения справочного имени, а не догадки. Не рассчитывай результат только через DayOfWeek браузера.

При изменении даты: обновить DutyPeriod обоих источников и пересчитать WorkDay. При изменении любого инженера: пересчитать WorkDay; после планового фокус Save. При варианте2 ранее сохранённый фактический инженер, равный плановому, сбрасывается. Это не означает, что legacy SQL жёстко запрещает выбрать того же человека повторно: такой запрет отдельно не установлен.

Отдельно проверь смену варианта2→1: legacy прячет фактический select, но не обязательно очищает его значение и не пересчитывает WorkDay при смене radio. Тогда календарь может остаться от скрытого другого сотрудника. В write-модели effective employee должен соответствовать выбранному варианту (плановый для1, фактический для2); пересчитать рабочий день/доступность отгула для него. Зарегистрировать это как исправление несогласованного состояния и покрыть тестом двух сотрудников с разными календарями.

DateOfNextDuty ищет первый разрыв расписания от today: SQL добавляет искусственный today−1, берёт минимальную дату, за которой нет следующей, а C# добавляет день. Это не просто max(Дата)+1 и не always tomorrow. Проверить расписание с внутренним разрывом и пустую таблицу. Ошибка загрузки не должна тихо выдавать today как успешный default.

## 6. Проверки перед сохранением

Для нового/будущего: обязательны дата и плановый инженер. Сообщения legacy:

- «Невозможно выполнить сохранение, т.к. не указана дата дежурства».
- «Невозможно выполнить сохранение, т.к. не указан дежурный инженер».

Для факта:

1. Вариант3 без «Подтверждаю закрытие дежурства» запрещён: «Вариант закрытия дежурства 'Никто не дежурил' невозможно сохранить без подтверждения закрытия дежурства».
2. Должен быть явно выбран radio-вариант: «Невозможно выполнить сохранение, необходимо выбрать вариант закрытия дежурства.».
3. Для варианта2 нужен фактический инженер: «Невозможно выполнить сохранение, необходимо указать сотрудника, который дежурил».
4. При checked «Отгул вместо оплаты» нужна дата: «Невозможно выполнить сохранение, необходимо указать дату отгула».
5. Любая непустая дата отгула в legacy проверяется `DateOff > DutyDate`: «Невозможно выполнить сохранение, дата отгула должна быть больше даты дежурства».

Ошибки сохраняют черновик, фокус переводится на отсутствующего инженера/дату. При unchecked legacy очищает DateOff перед SaveUpdateFact, но уже после валидации. Не допускай невидимого устаревшего значения, блокирующего сохранение: явно нормализуй неприменимые поля в копии write-модели и зафиксируй это как устранение дефекта состояния, не как новую бизнес-функцию. Не потеряй введённый черновик при временном переключении вариантов до решения пользователя.

Фактическая SQL-ветвь — **составной межбазовый сценарий**, её нельзя заменить простым UPDATE таблицы:

1. Прочитать прежнюю ДатаОтгула.
2. Нормализовать новую дату: NULL, если вариант не1/2 или рабочий день=1; иначе переданная дата.
3. Определить фактического сотрудника: плановый при1, выбранный при2, NULL при3.
4. BEGIN TRAN/TRY: если была прежняя дата, искать соответствующий интервал в ЗаявкиIT.dbo.НерабочиеДни и, только если ровно одна строка, вызвать ЗаявкиIT.dbo.sp_НерабочиеДниDel.
5. Обновить КодСотрудникаФакт, ДатаОтгула, Закрыто в ДежурныеИнженерыРасписание по Дата.
6. Перечитать окончательно закрытую запись. Если у неё есть отгул, вызвать ЗаявкиIT.dbo.sp_НерабочиеДниIns для интервала [ДатаОтгула, ДатаОтгула+1day) с текстом **Отгул за дежурство**.
7. COMMIT, при ошибке ROLLBACK и RAISERROR. Обе базы должны участвовать в одном подтверждённом транзакционном контракте.

Legacy Binder для пустой DateOff возвращает DateTime.MinValue, а [DBManager.cs](https://github.com/KescoDev/Kesco.App.Web.V4.Inventory/blob/12a6efae7eb310adec06a57f6d80b8d9e76985b4/Kesco.Lib.DALC/DBManager.cs) при создании SQL-параметров превращает этот sentinel в DBNull. В новой типизированной модели используй nullable date и передавай NULL: 0001-01-01 не должно попасть в SQL datetime.

РабочийДень, Оплата и КодЛицаРаботодателяФакт читаются, но показанный UPDATE сам их не вычисляет/не присваивает. Их источник — фактическая схема/триггеры, которую надо прочитать на стенде. Не выдумывай расчёт оплаты, работодателя или рабочего дня при записи. SQL Server2008R2, без THROW/нового синтаксиса.

**Выявленный риск legacy:** удаление прежнего интервала отгула ищет его по вновь вычисленному сотруднику, а не гарантированно по прежнему. При смене фактического инженера возможен оставшийся старый отгул. Проверь реальную процедуру/триггер и исправь переносом корректного старого/нового состояния в едином сценарии; не удаляй чужие интервалы по одной дате. Требуется тест «сотрудник A→B при прежнем отгуле», а не только простой happy path. Если DDL недоступен, отметь именно этот межбазовый контракт непроверенным, не скрывай за зелёным unit-test.

Простые reads/CRUD и SQL — Entities; сложную координацию разрешено оформить узким доменным use case, без второго Employee/авторизации. Не вызывай успешный save повторно ради reload. Конкурентное закрытие, удаление, изменение планового сотрудника или дубль даты должны давать конфликт/ошибку с сохранённым вводом, а не успех при 0 affected rows. Согласуй guard с существующими triggers, не вводя новую DB-схему без необходимости.

## 8. Итог закрытого дежурства и завершение

При IsClosed вместо меню сохранения показывается **Закрыто**, затем блок факта:

- вариант3: «Никто не дежурил», Error;
- вариант1: «Замечаний к дежурству нет»;
- вариант2: «Дежурный инженер:» со ссылкой на фактического сотрудника; «Работодатель:» только если PersonIdFact.HasValue, ссылка на PersonCustomer.ShortNameRus, при недоступности `#id`;
- «Дата отгула:» если задана, dd.MM.yyyy;
- «Оплата:» если Payment.HasValue, число с двумя знаками; нулевая оплата тоже значение, не «нет данных».

После любого успешного save legacy вызывает `opener.refresh()` при наличии и закрывает окно. Перенеси через общий механизм уведомления родителя/ClayFormWindow, с тем же результатом: перечитать родительский список один раз, закрыть только карточку. Если карточка открыта напрямую без opener, не падать и не перезагружать посторонние окна. При ошибке/отмене не закрывать и не посылать успешное refresh.

## 9. Авторизация и ошибки

Legacy отдельно распознаёт SqlException Number229/Class14 при загрузке и показывает **У Вас нет прав для работы с этой формой!**. В явном коде формы нет ограничения «только собственные дежурства» и нет установленной роли редактора. Не добавляй такое правило из предположения. Найди реальные grants/триггеры/настройки доступа, используй Employee CurrentUser и свежую проверку перед каждой записью, сохрани действие DB security. Роль102 нужна кандидатам select и не равна правам оператора.

Отказ доступа, ошибка чтения календаря/списка, отсутствующий PK, ошибка любой межбазовой процедуры должны различаться. Не подставляй пустого пользователя или service-account как изменившего. Данные разных circuits не делят mutable Entity/черновик, даже если общий legacy EntityPage имел синхронизацию форм через серверные страницы.

## 10. Приёмка

- Новая запись при пустом расписании, подряд заполненных днях и внутреннем разрыве; правильная дата, обязательные поля, дубль даты.
- Existing yesterday/today/tomorrow, закрыто0/1, переход через полночь; today не закрывается, closed нельзя изменить прямым вызовом.
- id yyyyMMdd и реально встречающиеся URL-культуры; невалидный id/удалённая запись не создают новую.
- Duty-select показывает лишь нужных кандидатов, месячную статистику всего/выходных, фактического вместо планового, 100-item popup и поиск кода/ФИО.
- Выходной по календарю, перенесённый рабочий выходной, разные территории, fallback188; смена обоих инженеров пересчитывает соответствующую подпись.
- Три варианта подтверждения; отсутствие явного выбора; вариант2 без сотрудника; вариант3 без close; дата отгула пустая/равная/раньше/позже.
- Смена1→2→3, рабочий↔выходной, checked↔unchecked не оставляет невидимых значений в записи и не теряет черновик неожиданно.
- Сохранение факта без close для1/2 разрешено; для3 запрещено. Повторное открытие черновика восстанавливает значения.
- Реальный тест транзакции: успешный отгул, замена даты, смена A→B, отказ Del/Ins, rollback обеих частей; без изменения production.
- 0/1/multiple найденных старых интервалов — не удалить посторонние; employer/payment/workday реально поступают из БД.
- Double click, два пользователя, отзыв прав, сетевой сбой после записи: не создать дубли отгулов и не повторить уже прошедший SQL слепо.
- Закрытый итог со всеми вариантами, NULL/0 Payment, отсутствующий работодатель; UTC Changed и календарные даты не смешаны.
- Успех закрывает только карточку и обновляет родителя; ошибка сохраняет ввод; прямое открытие без opener; узкий экран320–480px и порядок Tab.

В handoff приложи карту переходов, таблицу SQL/параметров, подтверждённые права и DDL-зависимости, результаты build/test/browser/реального тестового save, остаточные ограничения. Отдельно отметь корректировки перечисленных legacy-дефектов. Нельзя принимать форму после одних визуальных проверок, не проверив запись отгула и rollback.

**Фокус и radio.** Legacy code задаёт переходы `rdConfirmType1 → rdConfirmType2_0 → rdConfirmType3_0 → btnConfirm`; плановый инженер имеет `NextControl="btnSave"`, а `kesco.duty.js` фокусирует показанные `dbsDutyEngFact_0` / `baseDateOff_0`. Последний `btnConfirm` нужно сопоставить с реально существующей командой: в прочитанных файлах этой формы не найден отдельный объявленный элемент с таким ID. Не создавай ради строки NextControl новую бизнес-кнопку; используй согласованную доступную команду сохранения/подтверждения и не оставляй ссылку на отсутствующий DOM target. Современный RadioGroup должен сохранять стандартное управление одной группой стрелками/Space и переход Tab из группы; старые три отдельных Radio не являются основанием сломать доступность. Три варианта дежурства — предметные radio, они не равны трём исходам общего confirm dialog CL-06.

**Точные границы дат.** Legacy `v4_string2Date` допускает полные и компактные/неполные даты, заполняет недостающие части клиентским today, двухзначные годы `00…50` относит к 2000-м, `51…99` к 1900-м и технически ограничивает год 1900…2078. Зафиксируй поддерживаемую совместимость общего CL-05 и отличия; не превращай предел parser в новое DB-правило. Ошибочный ввод не должен молча очищаться в NULL после форматирования. `DateOff > DutyDate` проверяется по календарным дням на сервере; timestamp и browser offset здесь неприменимы. Кнопка Today, понедельник первым днём, выбор соседнего месяца и Escape/Enter проверяются на реальном ClayDatePicker/MudDatePicker: наличие календаря уже реализовано, нужны подтверждение поведения и недостающий общий контракт. Month-only picker и редактируемый Time для этой формы не требуются.

Соблюдай Select AGENTS: hover не меняет keyboard index; ReadOnly/Disabled блокируют также `ViewItem`; отдельная ссылка даёт разрешённый просмотр без изменения выбора. Не превращай временный null Clearable при поиске/восстановлении по Escape в подтверждённую смену инженера. При изменении даты/инженера поздняя календарная проверка не может перезаписать состояние уже выбранного другого варианта. Сохрани различие «нет явного radio» и inferred ClosedType=3, включая открытие старого незакрытого дежурства.

**Совместная работа:** до CL-11 подписки установить фактическую применимость inherited entity/presence поведения и нормализованный календарный ключ. Presence не разрешает совместное изменение одного mutable DutyTiming. Чужое закрытие/изменение должно приводить к контролируемому конфликту перед write; локальный ввод сохраняется для решения пользователя, а закрытое дежурство не становится редактируемым после reconnect.
