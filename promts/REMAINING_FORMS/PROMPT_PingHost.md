# Промт реализации: PingHost — проверка доступности устройства в сети

## Обязательное дополнение пользователя от 26.11.2026

Прочитай [ключевые требования FORM-KEY-01…09 / DR-01](../../docs/agents/editing-forms-key-requirements.md) и [общий план внедрения](../FORMS_UX_2026-11-26/00_ORCHESTRATOR.md). Они закреплены в корневом AGENTS и обязательны для всех существующих/новых форм и новых приложений. Новое поведение Cancel (Close/ResetAndStay/Continue), неразрушительный Refresh, желтоватый Required-фон только у пустого редактируемого поля (заполненное — обычный фон, очистка — снова желтоватый; placeholder не определяет Required), focus/dirty/Enter, справка/тема каждой формы и presence сущности имеют приоритет над противоречащими историческими формулировками ниже.

Используй четыре общих задания и их владельцев; не создавай локальный CSS/JS/draft/presence/theme механизм. Для поиска/отчёта/диагностики сохраняется предметная семантика Cancel/Stop и нет фиктивного Save/DB reset/entity0. Новые требования расширяют применимые UI-ветви, права/CAS/DR-01 и уже исправленный Clayzor сохраняются. Внешние проверки остаются beta; фактически выполненные локальные проверки и применимость FORM-KEY фиксируются в handoff. Историческое описание source/legacy не означает приказ копировать его дефект или запускать уже реализованную форму заново.

## Задание исполнителю

Реализуй в Clayzor отдельную форму, заменяющую `Inventory/Equipment/PingHost.aspx`, и необходимый ей общий серверный механизм ICMP-проверки. Доведи до работающих сценариев запуска, остановки, повторного запуска, ошибок и закрытия окна. Сначала прочитай [общие правила](01_COMMON_RULES.md) и актуальные `AGENTS.md`; соблюдай уже выполняющиеся исправления EquipmentForm/Net. Не переписывай их карточки и не создавай вторую реализацию Wake-on-LAN.

Это диагностическая форма без сохраняемой сущности и без CRUD. Она проверяет доступность с сервера Inventory, а не с компьютера пользователя. Отдельной страницы и ping endpoint в проверенном Clayzor-срезе не найдено.

## 2. Маршрут и входной контракт

- Основной новый маршрут: `/Equipment/PingHost`; совместимый маршрут: `/Equipment/PingHost.aspx`. Учитывай реальный `PathBase` приложения, не зашивай `/inventory` во все ссылки.
- Единственный специальный входной параметр — строка `host`. Отсутствие даёт пустую строку. Это hostname или IP-адрес; не EquipmentId и не URL HTTP-сервиса.
- В legacy создание страницы не сохраняет ничего в БД. Автозапуск происходит после соединения SignalR, то есть после готовности канала выдачи результатов.
- В Blazor запускай один раз после первого интерактивного рендера/загрузки идентичности; prerender и reconnect не должны незаметно создавать второй цикл.
- Страница открывается через общий `clayOpen`; окно не закрывает и не перезагружает родителя. Для диагностики не нужен контракт выбора `return=1`.
- При смене `host` в том же экземпляре сначала заверши старый запуск. Результаты старого hostname не должны попадать в новый журнал.
- В source не найдена универсальная серверная связь этой страницы с обязательным EquipmentId. Не вводи обязательный EquipmentId и не отсекай законные DNS-имена только ради упрощения реализации.

## 3. Интерфейс и состояния

Заголовок до разрешения DNS: **«Проверка доступности устройства в сети»**. После DNS — строка вида `Обмен пакетами с HOST [IP] с 32 байтами данных:`. Сохрани смысл и исходные русские названия команд: **«Запустить»**, **«Остановить»**, штатное закрытие окна. В legacy штатная `Refresh` переименована в «Запустить» и перезагружает страницу через базовый класс; команда `Start` также существует. В новой реализации оба пути должны приводить к единственному корректному запуску без обязательного полного reload.

| Состояние | Запустить | Остановить | Журнал |
|---|---|---|---|
| Первичная инициализация | Не допускает повторного запуска | Пока нечего останавливать | Заголовок, затем автозапуск |
| DNS/проверка выполняется | Disabled | Enabled | Результаты поступают последовательно |
| Остановлено пользователем | Enabled | Disabled | Уже выведенные строки остаются |
| DNS/валидация/неустранимая ошибка запуска | Enabled после исправления входа/повтора | Disabled | Видимое объяснение; не бесконечный спиннер |
| Новый запуск | Disabled | Enabled | Старый журнал очищен; новый заголовок |
| Страница уничтожена | Нет активного цикла | — | Нет последующих callback в disposed component |

Сохрани различимость успешных и ошибочных сообщений и автопрокрутку. Выводи hostname и сообщения как текст: строка `время<1мс` не должна превращаться в HTML, а неожиданные символы не должны исполняться. Не копируй `innerHTML` и SignalR-сообщения с исполняемым `<js>`.

Это не табличные данные: не изобретай грид с новым набором колонок. Используй общий каркас/кнопки и прокручиваемый журнал. Не показывай фиктивный `ClayChanged` у несохраняемой диагностики. Общие стили, доступность клавиатурой и ширины 320–480 px обязательны.

## 4. Фактический алгоритм legacy

1. Пустой host → ошибка **«Не указано сетевое имя устройства. Выполнить команду ping невозможно»**, завершение.
2. В непрерывном режиме `MaxAttempt == 0` требуется `PageId`; без него Pinger выдаёт **«Не указан идентификатор страницы.»**. В Clayzor этот WebForms ID заменяет жизненный цикл конкретной сессии/компонента, но не глобальный static-процесс.
3. DNS: `Dns.GetHostAddresses(host)[0]`, ожидание до **5000 ms**. Ошибка/таймаут → **«Не удалось определить IP адрес по hostname: …»**, завершение. Legacy выбирает первый возвращённый адрес; не описывай это как гарантированный IPv4.
4. По умолчанию `PingOptions(128, true)`: TTL **128**, Don't Fragment **true**; буфер **32 bytes**.
5. Перед каждой попыткой задержка **1000 ms**, затем ICMP timeout **1000 ms**. Это не строго один пакет в секунду: время самой попытки добавляется к задержке.
6. Успех: адрес ответа, число байт, roundtrip, TTL. При RTT 0 выводится `<1`, иначе `=N`; статусы ошибок берутся из `IPStatusKescoEnum`.
7. Неуспешный IPStatus — отдельная строка ошибки; следующая попытка продолжает цикл. Исключение отправки — сообщение **«Ошибка выполнения: …»**, null reply — **«Ошибка по неизвестной причине.»**.
8. Непрерывная страница работает до остановки/закрытия. Legacy проверяет наличие страницы каждые 10 попыток и очищает журнал при `inx > 30` (после 31 выведенного результата). Сохрани ограничение роста журнала; если используешь кольцевой буфер вместо полного стирания, зафиксируй это в карте отличий и проверь согласованность UX.
9. Повторный запуск очищает журнал, повторяет DNS и начинает новый набор попыток. Остановка не означает запись в БД и не инициирует WoL/перезапуск/PoE.

## 5. Серверная реализация и исправляемые технические дефекты

Не переноси `Task.Run(...).Wait()`, блокирующий цикл, неосвобождённый `Ping` и бесконечное ожидание завершения страницы. Реализуй один управляемый async task на запуск, `CancellationToken`, корректный `DisposeAsync`, сериализацию Start/Stop и подавление результатов завершённой сессии. Сетевой механизм допускает отдельный coordinator/service для реальной I/O-операции; DALC остаётся SQL-транспортом, Controls — владельцем UI, а не местом для произвольной сетевой бизнес-логики.

Обязательно устрани в рамках переноса следующие наблюдаемые проблемы:

- Страница не подписывает `PingFinished`, поэтому при ранней ошибке legacy может оставить кнопки в состоянии «работает». В новом коде все терминальные пути восстанавливают доступность команд.
- `Stop` в legacy меняет boolean, а уже выполняющаяся задержка/попытка может ещё отправить результат. Новый контракт: после завершения операции Stop старый запуск не добавляет новых строк. Если транспорт нельзя немедленно прервать, дождись/огради его завершение без блокировки UI.
- Ручной повторный `Start` не должен создавать параллельные циклы даже при прямом вызове обработчика, двойном клике или reconnect.
- DNS task legacy продолжает работу после `Wait(5000)` timeout. Не сохраняй эту утечку; используй корректный timeout/cancellation и не обращайся к disposed state.
- IPv6 и неожиданный IPStatus могут не иметь ожидаемого TTL/описания. Выведи корректный текст без падения и без ложного «устройство недоступно» при ошибке самого диагностического транспорта.

Проверка доступа: в `PingHost.aspx.cs` нет отдельной проверки бизнес-роли. Сохрани аутентификацию приложения и установи разрешённую область диагностики по действующим правилам среды; не изобретай роль 43/44. Идентичность не бери из query string. Повторная проверка перед внешним действием — по общему механизму CurrentUser и актуальной политике. Не вызывай shell `ping`, не конкатенируй командную строку. Реальный host проверяй средствами сетевого API; URL со схемой/путём не должен интерпретироваться как адрес для другого протокола.

## 6. Связанный endpoint и граница с EquipmentForm

В Inventory есть четвёртый по отношению к трём физическим `.ashx` обработчик — `Ping.ashx`, зарегистрированный в Web.config. Его нельзя потерять только потому, что файл не попал в список страниц.

Legacy endpoint использует тот же Pinger с `MaxAttempt = 1`, без PageId, и возвращает JSON:

```json
{"Result":"success","Details":{"1":"success"}}
```

`Result` принимает `success`, `warning`, `error`. `Details` — словарь с порядковыми строковыми ключами; успешная попытка хранит буквально `success`, ошибочная — описание. При отсутствии результатов — `error`; при доле ошибок >= 50% — `error`; при ненулевой меньшей доле — `warning`; иначе `success`. При текущем `MaxAttempt=1` обычный `warning` недостижим, но не переименовывай значения контракта. Legacy отвечает HTTP 200 application/json для результата диагностической попытки; auth/ошибки валидации нового endpoint должны иметь явную, документированную семантику.

`eqmnt.ping.state()` вызывает POST `/inventory/ping.ashx?host=...`, передаёт credentials и повторяет вызов через 5 секунд; сетевое имя из `DOMAIN\HOST` превращается в `HOST` на стороне caller. Этот разбор находится в карточке, а не в Pinger. Не удаляй произвольно префиксы из любого входного host формы.

Действия задачи:

1. Обеспечь единый I/O-код для подробной страницы и одного диагностического запроса.
2. Проверь актуальную EquipmentForm после завершения текущего агента: если one-shot индикатор уже добавлен, подключи его к тому же механизму; не дублируй.
3. Если старый endpoint остаётся контрактом действующих клиентов, реализуй authenticated compatibility route с правильным PathBase/методом POST. Не выдавай анонимный универсальный сетевой прокси.
4. Не переписывай весь индикатор, wake-on-LAN и сетевую карточку в этой задаче. Зафиксируй минимальную точку интеграции и подтвердившиеся callers. Прямой вызов формы должен работать даже при отсутствии ссылки в текущем меню.

| № | Сценарий | Ожидаемый результат |
|---:|---|---|
| 1 | `/Equipment/PingHost.aspx?host=…` и новый маршрут | Один и тот же экран и корректно декодированный host |

| 3 | DNS возвращает один IP | Заголовок и последовательные попытки с правильными параметрами |

| 5 | RTT 0, обычный RTT, TTL | Корректные literal `<1`, bytes и время без HTML-интерпретации |
| 6 | ICMP timed out / unreachable / unknown status | Ошибочная строка; цикл продолжает работу, если это ошибка отдельной попытки |
| 7 | IPv6 / отсутствующие options reply | Нет NullReference, результат не фальсифицируется |
| 8 | Stop во время задержки, DNS и отправки | Один завершённый запуск, без поздних строк после завершения Stop |
| 9 | Start→Stop→Start | Очистка, новое разрешение DNS, один цикл |

| 11 | Закрытие вкладки / потеря circuit / DisposeAsync | Ресурсы освобождены; процесс не остаётся в фоне |
| 12 | Два разных окна/пользователя | Независимые журналы, остановка не затрагивает соседний запуск |
| 13 | Более 31 результата | Память/DOM ограничены; правило очистки явно задокументировано |
| 14 | URL-спецсимволы/HTML в host и сообщении ошибки | Вывод как текст, нет исполнения HTML/JS/команды |
| 15 | One-shot endpoint success/error/no result | Совместимые Result/Details; после ответа нет фонового пинга |
| 16 | Анонимный/неразрешённый вызов endpoint | Нет выполнения сетевого действия |
| 17 | Родительская EquipmentForm открыта | Работа диагностики не меняет её черновик и не запускает WoL |
| 18 | Узкое окно, клавиатура, долгий журнал | Команды доступны, текст читаем, автопрокрутка работает |

Таймеры, DNS и ICMP проверяй через управляемый транспорт/clock в поведенческих тестах без реального сканирования сети. На тестовом сервере отдельно проверь разрешённый известный host: отсутствие ICMP-прав или блокировку сети отмечай как ограничение среды, а не как доказательство правильного диагностического результата.

Остановить остаётся доступно во время работы, включая ожидание DNS/ICMP; глобальный blocking wait overlay недопустим. Prerender/reconnect не создают второй цикл. | Медленный DNS, ICMP timeout, обычный success/error, разрыв и восстановление канала: интерфейс реагирует, состояния команд верны, одновременно существует не более одного запуска этого экземпляра. |
| CL-03 | Start/Stop — отдельные сериализованные команды. Фокус не возвращается к Start от каждого входящего сообщения, а остановка не активирует запуск повторно. Общее F2/Insert/Save не назначается диагностическим действиям; возможные shortcuts требуют явного opt-in. | Быстрые Start→Stop→Start, двойной click и клавиатура: один действующий run ID; после завершённого Stop старый run не добавляет строки. | CL-12 | Cancellation/dispose охватывают loop, ожидания, используемый Ping, JS-scroll задачи и обработчики. Проверить более 31 результата, выбранную политику очистки/буфера и безопасный вывод «время<1мс». |

PingHost не сохраняет сущность и не имеет подтверждённого EntityPage.Entity key: CL-11 presence/concurrent-editing, dirty-запрос «сохранить диагностику», фиктивный ClayChanged и CRUD toolbar не нужны. Наследование EntityPage в legacy и первоначальный ActionAfterSignalRConnected сами по себе не доказывают потребность в совместном редактировании. Журнал выводится как журнал, не как ClayGrid.

Для открытия/закрытия используется современный общий механизм. Наличие отключённого legacy Dialog.closeAll не даёт основания завершать другие диагностические окна. Геометрия/настройки сохраняются только в собственных ключах; Kesco.js с origin-wide localStorage.clear() не подключать.
