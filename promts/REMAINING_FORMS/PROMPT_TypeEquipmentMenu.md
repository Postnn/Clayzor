# Промт: реализовать TypeEquipmentMenu — типы оборудования и модели

## Задача

Перенеси `Inventory/TypeEquipment/TypeEquipmentMenu.aspx` в Clayzor как экран **список типов → модели выбранного типа**. Это навигационный экран из двух областей, а не редактор справочника типов. Карточка `ModelEquipmentForm` уже реализована; переиспользуй её.

Прочитай [01_COMMON_RULES.md](01_COMMON_RULES.md) и действующие AGENTS.md. На срезе Inventory `b3da274962c3c0811f71fbfe196f188ed3b5f659` этой страницы нет; главный динамический грид, меню и ModelEquipmentForm присутствуют. Перед работой проверь изменения агента, завершившиеся после среза; не пересоздавай существующие компоненты.

## 2. Маршруты и меню

Предоставь `/TypeEquipment/TypeEquipmentMenu` и `/TypeEquipment/TypeEquipmentMenu.aspx` либо совместимый канонический маршрут с сохранением старых ссылок. Подключи экран к существующему InventoryMainMenu через реальный metadata/config contract. Не добавляй параллельный жёстко прописанный набор пунктов меню.

Заголовок из `Inv_lblEquipmentTypes` — **«Типы оборудования»**. Legacy отображает главное меню. Стандартные кнопки EntityPage `Обновить`, `Редактировать`, `Сохранить`, `Применить`, `Перепроверить`, `Отмена` удалены. CRUD-кнопки для типов не нужны. Не вводи новую возможность редактировать/удалять типы.

## 3. Левая область: точная модель поведения

SQL `SELECT_ТипыОборудования` получает язык текущего SQL-пользователя:

```sql
DECLARE @lang char(2);
SELECT @lang = Язык FROM Сотрудники WHERE SID = SUSER_SID();

SELECT КодТипаОборудования,
       CASE WHEN @lang <> 'ru'
            THEN ТипОборудованияЛат
            ELSE ТипОборудования
       END AS ТипОборудования
FROM ТипыОборудования;
```

Не переноси определение пользователя через служебную SQL-учётную запись. Используй уже установленный Employee CurrentUser и подтверждённое соответствие principal. Сохрани правило ru/не-ru и предусмотренный проектом fallback; не допускай пустой подписи из-за неразрешённой идентичности.

| Свойство | Legacy |
|---|---|
| Колонки | `КодТипаОборудования`, `ТипОборудования` |
| Заголовки | `sCode` («Код»), `Inv_lblEquipmentType` («Тип оборудования») |
| Выравнивание | Обе колонки влево |
| Название | Без переноса в legacy |
| Страница | `RowsPerPage=1000`, page bar скрыт |
| Группировка/фильтры | Панели и filter options выключены |
| Сервисные/detail-колонки | Выключены |
| Пустой результат | **«Типы оборудования не найдены»** |
| Заголовок таблицы | Всегда виден |
| Повторное заполнение | Возвращается на прежнюю страницу; при специальном флаге — последняя |

Выполни список на ClayGrid. Не используй MudTable/свой HTML table. 1000 — legacy-предел страницы, не разрешение тихо отбрасывать 1001-й тип: на фактическом объёме проверь полноту и, если предел имеет значение, реализуй доступ ко всему набору без изменения бизнес-смысла. SQL не задаёт ORDER BY; выбери стабильный порядок только как явно описанную техническую стабилизацию, не меняя названия/набор полей.

На старте справа пусто, пока тип не выбран. Один клик по строке выделяет её, снимает выделение у соседних и загружает модели. Реализуй клавиатурный эквивалент. Не извлекай ID из HTML первой ячейки и текст из второй: используй типизированную строку, чтобы клик по заголовку, HTML в названии или изменение порядка колонок не превратились в неверный запрос.

## 4. Правая область: модели выбранного типа

`LoadModels(value,text)` устанавливает `Preset.SubTitle=text`, помечает `PN` и `CPU` как видимые и вызывает JS. JS строит URL на основе `Config.model_search`:

| Параметр | Значение/назначение |
|---|---|
| `codetype` | ID выбранного типа |
| `gridAddParams` | Строка `codetype` — передать тип при добавлении модели |
| `hidemenu` | `true` |
| `CLID` | `87` — контекст пользовательских настроек списка |
| `idpp` | legacy ID родительской страницы |

Сохрани все пять смысловых составляющих, даже если в Clayzor не потребуется iframe. Предпочти общий компонент динамического ClayGrid внутри страницы с явным контекстом. Если используется существующий embedded-маршрут Home, не дублируй его инфраструктуру и исключи вложенные меню/заголовки там, где legacy их скрывает. Открытие карточек — только общий clayOpen.

Параметр `codetype` должен выбирать модели именно текущего типа. Если пользователь меняет сохранённый фильтр, нельзя незаметно превратить вложенную область в модели всех типов. При переходе между типами перепроверь приоритет обязательного ограничения, дефолтов и сохранённых настроек текущего DynamicGrid. Не подменяй legacy ключи случайным SQL-where.

Создание модели из правой области должно передавать `codetype` в уже существующую `ModelEquipmentForm`. В ней поддерживаются `codetype` и `_codetype`, однако выбор конкретного варианта должен следовать metadata legacy и принятой forced/default семантике, а не предположению. После сохранения модели обновляется соответствующий вложенный список, родительский выбор типа остаётся.

**Установленная неоднозначность:** в `LoadModels` действительно создаётся `GridPreSettings` с subtitle/PN/CPU, но в просмотренном `Default/Grid.aspx.cs` `ParentPage` лишь присвоен локальной переменной и preset явно не применяется. Не заявляй, что legacy гарантированно показывает PN/CPU. Сверь компонент Grid, реальную запись `Запросы`/описания колонок и рабочий экран. Зафиксируй факт применения или мёртвого preset; не выдавай намерение кода за наблюдаемое поведение.

## 5. Данные и ограничения scope

Не создавай новые таблицы типов/моделей и не переносись на другую БД. Чтение и enum живут в Entities; SQL — только SQLQueries.cs. Разрешённая координация страницы ограничивается выбором типа и списком моделей.

Реальные query-id моделей, полный набор/порядок колонок справа, form URLs, SQL удаления и права задаются внешней конфигурацией/таблицами `Запросы` и не представлены в этой странице. `URI_model_search` приходит из конфигурации, а `uri.local` отсутствует в исследованном дереве. Перед реализацией прочитай действующие значения/metadata на стенде. Не угадывай id грида и не сочиняй замещающий SELECT.

`CLID=87` — код клиента настроек, не роль и не тип оборудования. Его нужно сохранить как контекст списка либо явно мигрировать, не вставлять в enum бизнес-ролей.

Ошибки загрузки типов и моделей показывай отдельно от пустого результата. Быстрое переключение A→B не должно позволять позднему ответу A вернуть чужие модели. На переходе обнови context key/отмени старую загрузку, не плодя экземпляры грида. Отмена загрузки не должна стирать успешно сохранённые настройки.

## 6. Компоновка

Сохрани смысл: слева типы, справа модели, выделение активного типа, общее меню. Legacy фиксирует ширину левой области около 340 px и рассчитывает размеры iframe по окну; эти магические пиксели не копируются. Используй существующие общие layout-паттерны и центральные стили. На узком экране области становятся вертикальными или переключаемыми, но выбор типа и действия списка остаются доступны. Не меняй централизованную высоту контролов локальным CSS.

## 7. Приёмка

1. Оба маршрута и пункт меню открывают экран; нет дублированного меню и кнопок CRUD типов.
2. Для ru и не-ru верны названия типов; данные другого SQL-пользователя не используются как текущие.
3. При 0 типов видна точная заглушка, при одном и большом количестве доступен весь ожидаемый список.
4. Клик/Enter по типу выделяет только его; заголовок и пустая область не вызывают LoadModels.
5. A→B→A, включая задержанные ответы SQL, всегда показывает правильный тип и его модели.
6. Родительское ограничение, пользовательский фильтр и сортировка не протекают между экземплярами и не отменяют требуемый контекст.
7. Открытие существующей модели, создание с codetype, отмена и сохранение возвращаются в тот же список без перезагрузки всей страницы.
8. Проверены контекст CLID=87, настройки колонок, смысл PN/CPU/subtitle и idpp на реальных metadata; вывод записан в handoff.
9. SQL-ошибка справа не превращается в пустой список и не мешает выбрать другой тип; retry работает.
10. Кавычки/HTML/спецсимволы в названии безопасны, URL-кодирование корректно.
11. 320/480 px и desktop: доступен выбор, вертикальный скролл, заголовки и открытие модели; нет локального переопределения общего оформления.
12. Нет изменений Net/EquipmentForm, новых справочников или дублирующего CRUD/service слоя.

## 8. Результат и зависимости

Можно реализовать независимо от территориальных форм и телефонии после подтверждения общих правил динамического грида. Зависит от существующих InventoryMainMenu/Home/ModelEquipmentForm и конфигурации списка моделей. В handoff приложи карту двух областей, подтверждённые metadata и маршруты, результаты сборки/профильных тестов/browser smoke, перечень намеренных отличий и конкретных непроверенных интеграций.

## Дополнение по общим скриптам Styles

Прочитай [PROMPT_SHARED_CLIENT_BEHAVIOR.md](PROMPT_SHARED_CLIENT_BEHAVIOR.md) и [03_STYLES_CLIENT_AUDIT.md](03_STYLES_CLIENT_AUDIT.md). Применимы **CL-01** (открытие карточки/refresh), **CL-03** (клавиатура/фокус), **CL-07** (Grid), **CL-12** (изоляция и lifecycle); для metadata-колонок условно **CL-09/CL-10** (rich contact preview / даты). Основной клиентский источник — [Kesco.Grid.js](https://github.com/KescoDev/Styles/blob/fddc5a2157cf906402c50731e84cfa537abd7dba/js/Kesco.Grid.js) вместе с локальным `Kesco.TypeEquipmentMenu.js` и конфигурацией двух областей.

**Два экземпляра с разными задачами.** Слева — статический ClayGrid для двух полей типов; справа — **один** Dynamic ClayGrid моделей. [Текущий Grid/AGENTS.md](https://github.com/Postnn/Clayzor.Lib.Web.Controls/blob/ea980be926ae975678314029ba5fc8aa68c675ba/Components/Grid/AGENTS.md) допускает максимум один Dynamic grid на странице. Не вводить второй Dynamic ради левого справочника и не обходить ограничение скрытым одновременным рендерингом экземпляров A/B. У обеих областей разные стабильные DOM Id, независимые selection/scroll/filter state и callbacks. После смены типа правая область использует согласованную lifecycle identity и актуальные mandatory filters; неполная инициализация/старый SQL-ответ не считаются готовыми данными нового типа.

**Левая область.** Клик и клавиатурная активация работают с typed row, а не с порядком HTML ячеек. Повторное выделение/бездействие на заголовке не вызывает чужую строку. Отсутствие group/filter/options/pagebar у legacy списка типов сохраняется; функции общего Styles не являются основанием показать эти панели. Если включено общее выделение текста по double-click, оно не создаёт второй callback выбора и не открывает редактор типа.

**Правая область.** Переиспользуй уже существующие sorting/filter drafts, column settings, grouping, print/export и сохранение состояния в той мере, в какой их разрешают реальные metadata списка моделей. Cancel фильтра не применяет черновик; Clear user filter оставляет codetype; скрытие панели не отменяет фильтр. Число сортировочных приоритетов — общее решение CL-07: legacy settings UI допускает пять, legacy header/server ограничивает три, current header и dialog/state paths различаются. Это не отдельная локальная реализация. Toolbar/группировка/экспорт не должны возникать только из наличия функции в JS.

**Карточки и обновление.** Текущий DynamicGrid уже открывает add/edit через ClayFormWindowService и регистрирует `RefreshFromChildAsync` существующего экземпляра. Используй этот путь: сохранить ModelEquipmentForm → обновить правый список, сохранить выделенный тип, пользовательские настройки и левый scroll; отменить → без ложного refresh. Адрес формы и codetype берутся у вызвавшего grid instance, не у первого `.v4Grid`. Если тип сменился пока карточка была открыта, полученный refresh не должен вернуть список старого типа. Сценарий исчезнувшей страницы/заменённого экземпляра завершается без вызова stale callback.

**Общий дефект и граница владельца.** `ClayDragState.DraggedColumn` на pinned срезе является process-static и не изолирует даже два grids одного circuit. Исправление instance/drag-session принадлежит CL-07; уникальные DOM Id необходимы дополнительно и сами по себе этот дефект не устраняют. Страница не делает свой static cache/JS bridge и не модифицирует общий компонент параллельно другому владельцу.

Дополнительная приёмка: разные Id левой/правой области; один Dynamic instance; A→B с открытой карточкой A; отложенный SQL A; filter Cancel/Apply/clear при обязательном codetype; drag/cleanup не затрагивает второй grid или другую вкладку; Enter по типу один раз; refresh ребёнка без reload всей страницы и без сброса выбранного типа. Сохранённые state keys проверяются в правильном CLID=87/context, а не в глобальном пространстве имён.
