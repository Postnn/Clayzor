# Промт реализации BeelineParams — параметры договора Билайн

## Задача и границы

Реализуй в Clayzor отдельную форму, эквивалентную `Inventory/Telefon/BeelineParams.aspx`. Изучи этот промт вместе с [общими правилами](01_COMMON_RULES.md), актуальными `AGENTS.md` суперпроекта, Inventory, Entities и Controls. Это форма изменения **двух параметров уже существующего договора**: `TimeZone` и `EmailМенеджера`. Создание договоров, загрузка данных из Билайн, управление личным кабинетом, SIM/PIN/PUK и редактирование остальных реквизитов сюда не входят.

Срез исследования: legacy `KescoDev/Kesco.App.Web.V4.Inventory@12a6efae7eb310adec06a57f6d80b8d9e76985b4`; Inventory `Postnn/Kesco.App.Web.Inventory@b3da274962c3c0811f71fbfe196f188ed3b5f659`; суперпроект `Postnn/Clayzor@05f2fc7561bf2a5648cca7fce991be6e4c12cdb2`. В проверенном новом Inventory маршрута, формы и отдельной сущности параметров Билайн нет. Перед началом повторно сверь HEAD: другой агент продолжает исправлять существующие формы.

## 1. Маршрут, режимы и загрузка

Добавь основной маршрут `/Telefon/BeelineParams` и совместимый `/Telefon/BeelineParams.aspx`, принимай `id` как идентификатор договора. Базовый legacy `EntityPage` берёт `Request.QueryString["id"]`; `BeelineParam.Load()` передаёт его как `Int32`, но затем присваивает `Id = НомерДоговора.ToString()`. **Не превращай это противоречие в догадку о схеме**: проверь реальный тип `НомерДоговора`, поддерживаемые значения и действующие ссылки. Во внутреннем контракте не теряй исходное значение номера и ведущие нули. Если БД действительно числовая, валидируй диапазон до запроса.

Поддерживаемый пользовательский сценарий — открытие существующей записи, изменение двух полей, сохранение или отмена. Отсутствующий, некорректный и недоступный `id` показывают осмысленное состояние; нельзя открывать пустой редактор с разрешённым сохранением. Создание не подтверждено: у сущности есть только UPDATE. Кнопки создания и удаления не добавлять.

Первичная асинхронная загрузка выполняется один раз в принятом first-load pipeline; сначала доверенный `Employee CurrentUser`, затем разрешения и данные. Не делить mutable draft между Blazor circuits. Переключение `id` и отмена запроса не должны позволять устаревшему ответу заполнить другую карточку.

## 2. Поля: точный порядок и доступность

Заголовок: **«Параметры договора Билайн»**. Порядок строк и подписи из legacy сохраняются:

| Порядок | Подпись / элемент | Значение | Поведение |
|---:|---|---|---|
| 1 | Договор основной: | `ContractBaseNumber` / `ДоговорОсновной` | Всегда read-only |
| 2 | Договор МБ: | `ContractMBNumber` / `ДоговорМБ` | Read-only; только мобильный бюджет |
| 3 | Номер телефона МБ: | `PhoneNumberMB` | Read-only; подпись-ссылка открывает SIM-оборудование; только мобильный бюджет |
| 4 | Компания: | `Customer` / `Компания` | Read-only |
| 5 | Имя в Билайн: | `UserName` / `ИмяПользователяВБилайн` | Read-only; только мобильный бюджет |
| 6 | Актуальность: | `Actual` | Read-only дата и время отдельными контролами |
| 7 | Time zone: | `TimeZone` | Обязательный dropdown |
| 8 | Email менеджера: | `EmailManager` | Обязательный текстовый ввод с email validation |

При `MobileBudget == true` показывается также индикатор **«Мобильный бюджет»**. Этот признак вычисляется из непустого `НомерТелефонаМобильногоБюджета`, а не из наличия договора МБ, оборудования или checkbox. При `false` скрыты ровно строки 2, 3, 5 и индикатор. Скрытие выполняй принятым общим layout, сохранив смысловые пары и Tab-порядок.

`efChanged` отображает `Изменил` / `Изменено`. Для `Актуальность` legacy не вызывает `ToClientLocalTime`, тогда как метка изменения живёт по общему правилу Changed: отдельно выясни временную семантику `Актуальность` в БД и не применяй автоматическое UTC-преобразование по аналогии с `Изменено`.

### Список часовых поясов

`PrepareControls()` читает ключи секции `beelineTimeZones`, сортирует **по ключу по убыванию** и использует один и тот же ключ как значение и текст. В репозиторном `Web.config` подтверждены:

1. `Russian Standard Time`;
2. `Kaliningrad Standard Time`;
3. `Ekaterinburg Standard Time`.

Перенеси эту конфигурацию через принятую сборку настроек. Не заменяй значения на `Europe/Moscow`, UTC offsets или локализованные названия без преобразующего контракта с БД/потребителем. Приложение не должно зависеть от доступности Windows registry в Linux ради построения этих трёх вариантов. Если текущее сохранённое значение отсутствует в конфигурации, покажи его и явную проблему; не сбрасывай молча на первый вариант. При отсутствующей/пустой секции показывай ошибку конфигурации, не разрешай запись случайного значения.

## 3. SQL и доменная модель

Чтение использует `vwПараметрыДоговоровСвязиБилайн`. SELECT возвращает `НомерДоговора`, `ДоговорОсновной`, `ДоговорМБ`, `НомерТелефонаМобильногоБюджета`, `КодОборудования`, `Компания`, `ИмяПользователяВБилайн`, `Актуальность`, `TimeZone`, `EmailМенеджера`, `ЕстьЛК`, `Изменил`, `Изменено`.

Сохрани особенности join:

- SIM выбирается из `vwSIMКарты` вместе с `vwОборудование`, только когда `Списано IS NULL`.
- Основной договор берётся через `SIM.КодДоговора`, с fallback на номер параметров договора.
- Компания берётся через `ISNULL(ДоговорыСвязи.Заказчик, ДоговорыОсновные.Заказчик)`.
- Договор Билайн сопоставляется по номеру документа и `КодЛицаИсполнителя = 908`. Это фиксированный код записи: перед переносом подтвердить имя таблицы/строки и оформить enum по AGENTS. Не называть ролью или произвольно менять на другое лицо.
- `ЕстьЛК` возвращается SQL, но данный UI его не использует: не добавляй новое управление кабинетом.

Запись — ровно:

```sql
UPDATE vwПараметрыДоговоровСвязиБилайн
SET TimeZone = @TimeZone, EmailМенеджера = @EmailМенеджера
WHERE НомерДоговора = @НомерДоговора
```

Изменения остальных полей и внешние HTTP-запросы отсутствуют. Они не должны появиться при переносе. Комментарии legacy «Сохранение расположения» являются копией из другой формы, не бизнес-правилом.

Сущность/read model и SQL принадлежат `Clayzor.Lib.Entities`; отдельный Web CRUD-service не нужен. Разделяй неизменяемые прочитанные сведения и черновик двух изменяемых параметров. В write-path повторно загружай существование и контекст записи; не доверяй client-side read-only. Ошибка или нулевой результат UPDATE после конкурентного удаления — не успех. При конкурентной правке избегай молчаливой перезаписи: используй доступный подтверждённый механизм версии/сравнения original двух полей. Не придумывай `rowversion`, которого не проверили в схеме.

## 4. Команды и validation

- `OK` → `SaveAndClose`: проверить поля, сохранить, закрыть после подтверждённого успеха.
- `Сохранить` → `Save`: проверить, сохранить, перечитать данные и сбросить dirty-state, окно оставить открытым.
- `Обновить` / `Отмена`: стандартное предупреждение при несохранённых изменениях, отказ от предупреждения сохраняет draft.
- Кнопки `Редактировать` и перепроверки убраны из legacy. Владелец формы не получает дополнительный режим редактирования всего договора.
- `ValidateInput`: пустой TimeZone → «Необходимо указать Time Zone!»; пустой email → «Необходимо указать Email менеджера!»; некорректный email → «Email менеджера указан некорректно!». Повторить на сервере и проверить допустимость timezone из конфигурации. Не подменять проверку email телефонным или URL-валидатором.
- `Validation.IsEmail` использует именно `RegexPattern.Email`, а не одноимённый extension-method: `^[a-z0-9_]+([-+.'][a-z0-9_]+)*@[a-z0-9_]+([-.][a-z0-9_]+)*\.\w+([-.][a-z0-9_]+)*$` с IgnoreCase. Зафиксируй тестами совместимость `+`, апострофа, регистра и пробелов; замена общим валидатором не должна незаметно менять допустимые адреса.
- Длины по entity comments: TimeZone varchar(300), email varchar(50). Подтвердить реальные колонки/кодировку и ограничить ввод по схеме; legacy markup MaxLength не задаёт. Это закрывает отказ при записи, а не разрешает обрезать значение без уведомления.
- Legacy вызывает UPDATE и без проверки `IsModified`; в Clayzor no-op можно не записывать, но OK должен корректно закрывать неизменённую карточку, а Сохранить не давать ложный успех при ошибке загрузки.
- Не очищай введённые TimeZone/email при SQL error. Обработчик не должен запускать закрытие/обновление после ошибки.

### Переход к SIM

`ShowSim()` использует **загруженный `EquipmentId`**, а не разбирает телефон как идентификатор. Если он отсутствует, сообщение: «Невозможно открыть форму оборудования, т.к. не удалось определить код оборудования по номеру телефона мобильного бюджета.» При наличии открыть существующий Clayzor EquipmentForm с этим ID через `clayOpen`; сохранить родителя и черновик. Ссылка работает только как навигация, не сохраняет договор. Старый JS `Kesco.windowOpen` не копировать.

## 5. Права и интеграционные ограничения

В исследованном code-behind и `BeelineParam.Save` отдельной проверки `HasRole` нет. Это **не доказательство общедоступности записи**: действуют права подключения и представления. Установи действующую политику по SQL grants/пользовательскому контексту и используемому меню; не назначай по догадке роли 42, 43 или 44. Соблюдай обязательный доверенный CurrentUser и повторную серверную проверку разрешений из AGENTS, в том числе при прямом вызове write-method и отзыве прав после открытия.

Маршруты/ссылки динамического меню могут находиться в таблице `Запросы` или внешнем `uri.local`; их значения не доказаны исходниками. Добавь точное сопоставление новой формы в используемый механизм URL, не меняя адреса остальных приложений. Страница не является заменой Tel или EquipmentForm и не должна затронуть их текущие исправления.

## 6. Приёмка

1. Открыть действующий обычный договор: строки МБ и индикатор скрыты, остальные значения совпадают с SELECT.
2. Открыть МБ: все три строки и индикатор видны; ссылка ведёт к правильному оборудованию.
3. Номер МБ есть, EquipmentId отсутствует: сохранение двух параметров работает, переход выдаёт указанное сообщение.
4. Списанная SIM не подставляется как актуальное оборудование; fallback основного договора/компании соответствует запросу.
5. Отсутствующий, ошибочный, слишком большой/нестандартный ID и SQL error не превращаются в создание записи.
6. Варианты timezone и их порядок совпадают с конфигурацией; неизвестное сохранённое значение не теряется.
7. Пустой/некорректный email, пустая timezone, подменённая timezone и превышение длины отклоняются сервером.
8. После OK закрывается только дочерняя форма; после Сохранить остаётся тот же ID с актуальными Changed и dirty=false.
9. Прямой подменённый запрос не изменяет номер договора, компанию, актуальность или связанное оборудование.
10. Ошибка UPDATE и конкурентное удаление сохраняют draft, не вызывают success-path; конкурентная правка явно разрешается.
11. Отмена/обновление с draft: подтверждение Да/Нет, выбор Нет ничего не теряет.
12. Право отозвано после открытия, отсутствующий CurrentUser и несовпадающая идентичность блокируют запись.
13. Date/time `Актуальность` и Changed проверены раздельно, включая клиентский timezone и переход даты.
14. Адаптивность 320–480px, клавиатура, единые Clay-контролы и отсутствие прямого window.open.

В handoff укажи маршруты, перенесённую конфигурацию, подтверждённый тип ID и код 908, матрицу прав, реальные результаты SQL/read-write/браузера, тесты и оставшиеся ограничения. SQL совместимость 2008 R2 проверяется по синтаксису; работа только на SQL Server 2022 не объявляется доказательством запуска на 2008 R2. Не коммить и не пушить без актуальной авторизации пользователя.

Сохрани серверный `Validation.IsEmail`, точные сообщения и уточнение длин из основного раздела. Ошибку нельзя исправлять возвратом прежнего email или обрезкой текста. F2 привязывается к реально разрешённой команде toolbar и не создаёт второй обработчик поверх Select/dialog.

**Граница совместной работы:** CL-11 не включается автоматически. У `BeelineParams.aspx.cs::ActionAfterSignalRConnected()` есть пустой override. Проверь фактическую регистрацию/наследуемое поведение и согласуй с общей инфраструктурой, прежде чем подписывать форму на presence/редактирование. Уведомление о внешнем изменении не должно перезаписывать локальные два параметра; SQL-проверка конкурентного обновления обязательна независимо от presence.
