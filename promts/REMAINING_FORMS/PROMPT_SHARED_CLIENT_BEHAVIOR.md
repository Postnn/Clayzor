# Промт: недостающее клиентское поведение общих компонентов Clayzor

**Задача исполнителю:** доведи общие компоненты Clayzor до необходимых сценариев legacy Inventory, установленных при анализе JavaScript проекта Styles, его серверных callers и текущих Clay-компонентов. Реализуй общую возможность один раз, затем подключи её в зависимых формах. Сохрани уже работающие современные контракты. Этот файл — самостоятельное shared-задание к 16 формам, а не дополнительная бизнес-форма и не разрешение перенести весь старый runtime.

**Цель качества:** построить более надёжную, удобную и поддерживаемую реализацию на архитектуре Clayzor. Соблюдай раздел 11 [COMMON](01_COMMON_RULES.md): бизнес-смысл и нужные пользовательские возможности сохраняются, доказанные дефекты устраняются, технические приёмы legacy заменяются штатными решениями. Подробность source audit не делает старый алгоритм эталоном кода; дефект текущего Clay-компонента также не является неприкосновенным контрактом. Исправляй общий источник проблемы с проверкой его consumers, не создавай локальную копию в каждой форме.

**Защита существующего Clayzor:** раздел 12 COMMON обязателен для каждой CL-задачи. Не изменяй принятые современные правила, defaults, права и существующие пользовательские сценарии ради совпадения с legacy. Отличие от старого кода не доказывает дефект текущего компонента. До общей правки составь карту действующих consumers и сохраняемых контрактов; после интеграции проверь их вместе с новой возможностью. Добавляй нужное расширение совместимо, а доказанный дефект исправляй без потери остальных сценариев. Заявление «сделано как в legacy» не оправдывает регрессию.

**Обязательная сохранность данных:** DR-01 из раздела 13 COMMON и CL-02 ниже применяется ко всем новым/изменяемым формам Clayzor. Приёмка требует восстановления ввода после IIS restart, обрыва сети и обновления приложения; одного предупреждения/NavigationLock/reconnect недостаточно.

Обязательные соседние документы: [01_COMMON_RULES.md](01_COMMON_RULES.md), [03_STYLES_CLIENT_AUDIT.md](03_STYLES_CLIENT_AUDIT.md), [00_ORCHESTRATOR.md](00_ORCHESTRATOR.md) и частные промты затронутых форм. Правила SQL, Employee, сохранения черновика, исходных ключей, прав и внешних операций из COMMON остаются обязательными. Параллельное исполнение распределяется оркестратором по отдельным CL-задачам и непересекающимся файлам.

**Срез исследования — 23.11.2026.** Styles: `fddc5a2157cf906402c50731e84cfa537abd7dba`; legacy Inventory: `12a6efae7eb310adec06a57f6d80b8d9e76985b4`; Clayzor superproject: `05f2fc7561bf2a5648cca7fce991be6e4c12cdb2`; Controls: `ea980be926ae975678314029ba5fc8aa68c675ba`. Остальные закреплённые сабмодули — в COMMON. Перед реализацией сравни актуальный HEAD и результат текущего агента EquipmentForm/Net: уже исправленные дефекты повторно не вноси. Исследование статическое; проверки браузера, БД, контактов и многопользовательского режима здесь не объявлены выполненными.

## 2. CL-01 — окно, адресный результат и совместимость

### 2.1. Существующая основа и подтверждённый дефект

Используй [ClayFormWindowService](https://github.com/Postnn/Clayzor.Lib.Web.Controls/blob/ea980be926ae975678314029ba5fc8aa68c675ba/Services/ClayFormWindowService.cs), [clayFormWindow.js](https://github.com/Postnn/Clayzor.Lib.Web.Controls/blob/ea980be926ae975678314029ba5fc8aa68c675ba/wwwroot/js/clayFormWindow.js), [ClaySelectAdvancedSearchService](https://github.com/Postnn/Clayzor.Lib.Web.Controls/blob/ea980be926ae975678314029ba5fc8aa68c675ba/Services/ClaySelectAdvancedSearchService.cs) и [claySelectAdvancedSearch.js](https://github.com/Postnn/Clayzor.Lib.Web.Controls/blob/ea980be926ae975678314029ba5fc8aa68c675ba/wwwroot/js/claySelectAdvancedSearch.js). Сервис одиночного выбора уже различает пользовательскую отмену/null и lifetime `OperationCanceledException`, восстанавливает сущность через data source и чистит pending request. В текущем JS advanced search ожидает Window от `clayOpen`, тогда как opener возвращает boolean. Исправь общий внутренний bridge, сохранив работающих публичных boolean-потребителей; смена возвращаемого типа без миграции consumers недопустима.

Раздели ключ сохранённой геометрии, экземпляр окна и идентичность запроса выбора. Совпадение `formKey`/pathname не даёт права переиспользовать dirty-карточку другого ID или передать результат другому selector. Нужна явная политика повторного открытия: фокусировать совпадающий контекст либо создать отдельный request/window; не заменять контекст несохранённого окна молча. Учитывай PathBase, кодирование query, допустимые внешние `URI_*`, popup blocked, закрытый parent и изменившиеся размеры экрана.

Текущий opener обращается к `child.opener` и `child.addEventListener('beforeunload', ...)` вне защиты доступа. Для нового или повторно используемого Window внешнего origin доступ к DOM/событиям/геометрии может быть ограничен. Обработай это безопасно: успешно открытая внешняя карточка не превращается в ошибку всей команды; callback/geometry/close-tracking выполняются только поддерживаемым для этого origin способом. Не обходи same-origin ограничения. Это риск по исходнику, browser exception при анализе не воспроизводился.

### 2.2. Современный канал

Для каждого запроса фиксируй допустимые origin, конкретный child/source, requestId, caller и тип ключа. Обрабатывай результат ровно один раз; после завершения/отмены/dispose удаляй обработчики, таймеры и регистрацию. Старая вкладка, повторный message, неверный тип/чужой source/origin не меняют значение. `postMessage('*')`, произвольный callback-code и доверие к возвращённой подписи недопустимы. Ключ загружается через разрешённый resolver с повторной проверкой существования/прав; типы строковых, составных и целочисленных ключей не смешиваются.

Single и multiple должны иметь явный различимый результат. **Отмена сохраняет старое значение; подтверждённый пустой multiple-результат очищает выбор.** Закрытие окна, успешный result и отмена ожидания caller — разные события. Финальное физическое закрытие child не является единственным признаком успеха. Для single не превращай пустой ключ в ID=0. Для multiple зафиксируй валидацию каждого ID, уникальность и детерминированный порядок, лимиты по реальному сценарию, поведение частично недоступных записей без молчаливой подмены выбора.

Refresh после дочерней карточки адресуется конкретному живому caller: обновить сохранённую сущность/табличную часть, сохранить несохранённые поля родителя, фильтр, выделение и scroll где применимо. Глобальный reload родителя не заменяет refresh. Не меняй правило максимум одного DynamicGrid на страницу ради нескольких регистраций refresh.

### 2.4. Приёмка

Два одновременно открытых selectors, повторное открытие того же, popup blocked, пользовательское закрытие, caller dispose, late/duplicate/forged message, строковый и составной ключ, Unicode, успешный single, successful empty multiple, Cancel после изменения checkbox и parent draft после child save. Проверить существующих boolean-consumers opener и реальный legacy caller там, где объявлена совместимость. Unit-тест десериализатора не заменяет browser-проверку source/Window/blur/close.

## 3. CL-02 — черновик, команды и восстановление после сбоев

**Обязательный результат DR-01:** «Несохранённые пользовательские данные не должны безвозвратно пропадать из-за перезапуска IIS, кратковременного обрыва сети или обновления приложения». Нормативный контракт — раздел 13 [COMMON](01_COMMON_RULES.md), владелец и порядок интеграции — G0.6 [оркестратора](00_ORCHESTRATOR.md). Это новое требование пользователя к Clayzor, а не заявление о наличии такой гарантии в legacy. Оно распространяется на применимый ввод каждой формы, включая критерии поиска и вложенные редакторы.

### 3.1. Сохранить полезное поведение и расширить гарантию

Legacy [Kesco.V4](https://github.com/KescoDev/Styles/blob/fddc5a2157cf906402c50731e84cfa537abd7dba/js/Kesco.V4.js) использует общий XHR, XML/JS patching, `v4_stopAsyncEvent`, dirty/validate flags и `v4_dropWindow`; [Kesco.wait](https://github.com/KescoDev/Styles/blob/fddc5a2157cf906402c50731e84cfa537abd7dba/js/Kesco.js) возвращает фокус с учётом overlay. Современный компонент сохраняет запрет повторной команды, доступную отмену и пользовательскую работу через состояние конкретной формы/операции.

Страницы Inventory уже имеют `NavigationLock`/IsModified; [ClayEntityForm](https://github.com/Postnn/Clayzor.Lib.Web.Controls/blob/ea980be926ae975678314029ba5fc8aa68c675ba/Components/Form/ClayEntityForm.razor) сам является layout. Сохрани действующие guards, расширив их совместимым общим механизмом. Legacy beforeunload зависит от `isAsk`, changed и validate; невалидная dirty-форма не должна терять защиту. Dirty учитывает radio/checkbox, скрытый draft и дочерние наборы; возврат к исходным значениям снимает dirty только при отсутствии других незавершённых изменений/операций.

G0.4 и G0.6 решают связанные, но разные части: [ClayDbReconnectService](https://github.com/Postnn/Clayzor.Lib.Web.Controls/blob/ea980be926ae975678314029ba5fc8aa68c675ba/Services/ClayDbReconnectService.cs) после health-check сейчас выполняет forceLoad. Reload согласуется с сохранностью черновика и состоянием неизвестного результата. После утраты процесса/circuit обязательно восстановление из независимой копии; удержание живой формы и сообщение о потере состояния недостаточны. Сохрани восстановление соединения, проверку прав и общий error handler; connectivity failure не означает «записи нет».

Документация [.NET 10: состояние серверного Blazor](https://learn.microsoft.com/en-us/aspnet/core/blazor/state-management/server?view=aspnetcore-10.0) описывает ограничения circuit persistence, в том числе полного обновления страницы, и не гарантирует восстановление circuit. Поэтому его наличие не является доказательством DR-01: проверяется выбранное прикладное хранилище и восстановление в новом процессе/сеансе.

### 3.2. Общий контракт состояния и захват последнего ввода

Согласуй версионируемый DTO/журнал с явным составом полей; имена новых API не выдаются за уже существующие. Не сериализуй целиком Entity, EditContext, DOM, circuit, делегаты или Task. В данных отдельно представлены:

- доверенная область приложения/пользователя, тип формы и устойчивый `draftId`; исходный типизированный ключ, режим new/edit, допустимый parent context;
- исходный snapshot для сравнения, текущие типизированные значения, **raw input** незавершённых/невалидных полей и неподтверждённый текст lookup отдельно от выбранного ID;
- добавления, изменения и удаления дочерних строк, скрытые пользовательские значения и черновик открытого диалога; стабильные ключи строки с учётом вида связи;
- монотонная ревизия, версия формата, версия исходных данных при наличии доменной поддержки, сведения о надёжно записанной ревизии;
- отдельно от draft — snapshot отправленной бизнес-команды и её известный/неопределённый исход. Сохранённое `confirmed/running/busy` не является разрешением выполнить её снова.

Клиентский захват ввода работает при недоступном SignalR и до серверного blur/change/парсинга. Последний символ, paste, autofill, IME, снятие последнего checkbox, пустая строка и неполная дата сохраняются без ожидания успешного server callback. UI, который продолжает принимать ввод во время разрыва, обязан сохранять и этот ввод. Готовая server model и `await` вызова JS из живого circuit сами по себе не закрывают этот сценарий.

Раздели захват, подтверждённую запись черновика и синхронизацию на сервер. Debounce/пакетирование допустимы, когда ещё не отправленная часть уже защищена от заявленных сбоев. Не допускай тихой потери последних N секунд. На восстановлении raw input не округляется и не заменяется последним валидным значением. Повторное подключение компонентов не создаёт дублей listeners; input capture не меняет существующие правила Select/validation/hotkeys. Интеграцию общих input-файлов проводит назначенный владелец вместе с CL-03/04/05.

### 3.3. Хранилище, идентичность, защита и обновление

Выбери общий backend по проверенным возможностям текущего проекта: клиентская надёжная копия/журнал для ещё не доставленного ввода и, если требуется, защищённая серверная копия вне процесса. Одного in-memory/scoped/static state, cache с вытеснением или OnDispose/beforeunload недостаточно. Инфраструктурное хранилище для DR-01 разрешено при обоснованной необходимости; не изобретай бизнес-таблицы каждой формы и не требуй новый Redis/БД без оценки существующих средств. Если используется cache/распределённое хранилище, явно проверь его реальную долговечность, TTL и правила вытеснения.

Идентичность draft не зависит только от circuit ID, build number, пути новой публикации или PK записи. Новая запись без PK и SIM со сменой ключа сохраняют устойчивый `draftId`. Две вкладки, в том числе duplicate tab, не перезаписывают одну общую копию: предусмотрены владение/раздельные экземпляры и обнаружение конфликтующих ревизий. Parent request не возрождает старый Task/callback после нового circuit; связь восстанавливается через актуальный проверенный контекст.

Перечисли сохраняемые поля и способ защиты. Чувствительные поля нельзя молча исключить или автоматически положить открытым текстом в localStorage. Не записывай secrets в URL/log/telemetry. Клиентский payload недоверенный; чтение проверяет формат, лимиты, владельца и текущие права. `userId` из payload не служит авторизацией. После смены пользователя в том же браузере чужой draft не отображается. Повторная авторизация сохраняет возможность владельца восстановить работу, не отключая проверку прав.

Хранилище и ключи должны переживать IIS recycle, завершение процесса и deployment; временный/publish-каталог и очищаемый build-prefix непригодны. При Data Protection настрой сохраняемый защищённый key ring и согласованную идентичность одного приложения между версиями/узлами. Ротация не удаляет ключи, ещё нужные для восстановления. Практические границы конфигурации: [Data Protection configuration](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/configuration/overview?view=aspnetcore-10.0), [размещение ASP.NET Core в IIS](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/iis/?view=aspnetcore-10.0). Нельзя объединять разные приложения/пользователей ради доступности ключей.

Для новой версии приложения нужен явный путь чтения/миграции поддерживаемого старого draft. Сохраняй оригинал до подтверждённого переноса, учитывай переименование/удаление поля, enum, новый required и работающую старую вкладку при rollout. Неизвестный/повреждённый формат не перезаписывается пустой моделью и не уничтожается: пользователь получает доступный защищённый путь восстановления или извлечения данных. Нельзя очищать единственную копию незавершённой работы по circuit TTL, deploy, logout/relogin или произвольному «сроку cache»; политику хранения и явного удаления опиши отдельно.

### 3.4. Восстановление без перезаписи и повторных действий

До применения defaults/инициализаторов найди доступный draft по актуальному пользователю и контексту формы. Загрузи необходимые справочники/серверную версию, сохрани восстановленный raw input и исходный baseline. Не превращай свежую строку БД в новый original поверх пользовательских изменений. При конкурентном изменении/удалении записи или смене прав покажи предметную ситуацию, сохранив черновик до допустимого решения. Восстановление предлагается понятно в интерфейсе либо выполняется автоматически при безопасном однозначном сопоставлении; ручной поиск JSON не является пользовательским сценарием.

Rehydrate присваивает состояние без replay бизнес-handlers выбора, сохранения, подтверждения или смены режима. Не создаёт дочернюю связь NumPool, не запускает ConfirmEq/scan auto-click, DnD-write, INSERT выполнения Maintenance, SlBl-процедуру, формирование отчёта или новый Ping-loop. Последний незавершённый диалог возвращает пользовательский ввод и контекст, но сохранённое «Да» не считается новым согласием. Read-only критерии и выделение не отправляют результат родителю автоматически.

Перед отправкой пишущей или иной операции с внешним эффектом надёжно сохрани идентификатор попытки, отправляемую ревизию и snapshot её контекста. Если эта фиксация не подтверждена, команду не отправляй. После сбоя незавершённая попытка восстанавливается как требующая сверки, а не как разрешение повторить действие. Это не требует нового backend само по себе и не означает гарантии exactly-once.

Для Save/Apply зафиксируй отправляемую ревизию R и неизменяемый snapshot операции. После подтверждённого успеха обнови baseline/реальный ключ только для принятой части; ввод R+1, сделанный позднее, остаётся защищённым draft. Поздний autosave не перезаписывает новую ревизию; явный Discard защищён от её «воскрешения» задержанным запросом. Отмена popup или предложения восстановления не удаляет parent draft. Непрочитанный/неподтверждённый результат записи не очищает черновик.

Если соединение потеряно после фактической записи, исход сначала сверяется по конкретному доменному контракту. Простое отсутствие ответа/старого ключа не разрешает повторный INSERT/rename/mail action. Если существующий API не позволяет доказать исход, сохрани состояние «неопределённо», данные и доступную проверку; не обещай exactly-once без обеспечивающего механизма. Любой допустимый повтор следует отдельному явному действию и правилам соответствующей формы.

### 3.5. Команды, статусы и отказ самого хранилища

Состояния clean/dirty/validating/saving/running/failed/outcome-unknown/disposed и состояния сохранности черновика различаются. Индикатор «черновик сохранён» появляется только после подтверждения долговечной записи соответствующей ревизии, а не после постановки таймера/начала HTTP/сериализации. Этот индикатор не означает запись в рабочую БД.

Перед бизнес-командой заверши и валидируй влияющий на неё ввод, повторно проверь права, отметь operation in-flight и не допускай второй write от click/Enter/F2. Stop/Cancel/dispose не блокируются невалидным полем и не выполняют скрытую бизнес-команду. Busy привязан к конкретному запросу/окну; поздний ответ не разблокирует другой запрос. UI Cancel не доказывает откат уже принятой записи.

При quota/disabled storage/ошибке backend/шифрования не стирай поля и не показывай ложную сохранность. Пока путь защиты недоступен, ограничь новые рискованные действия/автоматическую перезагрузку и предложи рабочий допустимый способ сохранить данные; само предупреждение не считается реализацией DR-01. Управляемый reload/update согласуется с незавершённым сохранением, но бессрочная блокировка страницы не заменяет восстановление. Инициализация нового процесса должна успешно прочитать уже защищённый draft.

### 3.7. Обязательная проверка DR-01

Проверяй в разрешённом тестовом окружении и на интегрированной версии. Не перезапускай чужой рабочий IIS/production. Начни с простой карточки, затем составного NumPool, диалога LocationFact/сценария SlBl и затронутых существующих consumers; подключение каждой формы подтверждается отдельно. Один пилот не доказывает сохранность всей платформы.

| Сценарий сбоя/граница | Что должно быть доказано |
|---|---|
| Ввод последнего символа без blur, paste/IME, invalid date/number и разрыв до server callback | В новом подключении восстанавливается фактический ввод, включая ещё не распарсенный текст и выбор, принятый UI во время разрыва |
| Краткий network loss; SQL timeout с немедленным успешным health-check | Reconnect не теряет draft, не создаёт forceLoad до защищённой записи и не повторяет бизнес-команду |
| IIS/app pool recycle, полное завершение процесса без graceful callback, открытие новой страницы/circuit | Восстановление из независимой копии, без прежней памяти/Task; не только успешное удержание старого circuit |
| Deployment новой версии и full-page refresh | Draft доступен после смены версии/пути публикации; проверены старая схема, миграция, старые вкладки и пригодность ключей |
| Hidden fields, дочерние add/edit/delete, новый объект без PK, mutable key | Восстановлены все части, baseline и исходная идентичность; нет «воскрешённых» удалённых строк и потери неизвестного результата rename/INSERT |
| Два пользователя, две вкладки, duplicate tab, re-auth | Нет выдачи чужих данных/перезаписи; восстановление владельца сохраняется, текущие права проверены |
| Чувствительные поля и ротация ключей | Защита не ломает восстановление после restart/deploy; секретов нет в логах/URL/открытом dump |
| Quota/отказ storage/ошибка расшифровки/неизвестный формат | Нет ложного «сохранено», стирания ввода или перезаписи единственной копии; рабочий путь защиты/восстановления проверен |
| Business commit прошёл, ответ потерян | Данные и контекст доступны; сначала сверка результата; нет второго INSERT/mail/факта/DnD/Ping-loop |
| Новый ввод во время Save/Apply, поздний autosave, Discard | Очищена только принятая ревизия; новая сохранена; устаревший запрос не перезаписал и не воскресил draft |
| БД/права/справочник изменились во время простоя | Конфликт не маскируется новым baseline/defaults; ввод сохранён, недоступное действие не выполняется |

Guard dirty+invalid, повторный Apply, last input→Save, Cancel/Stop/dispose и existing EquipmentForm/Tel/Net проверяются совместно с их владельцами. Unit-тест DTO или reconnect с живым процессом не заменяет приёмку restart/deployment. Если стенд недоступен, зафиксируй конкретные непроверенные случаи и продолжай независимую работу; DR-01 не объявляется принятым до доказательства.

### 3.8. Что передать владельцам форм

Передай общий API/версию и совместимость, таблицу полей/raw/children/baseline/operation для каждой формы, backend и подтверждение долговечности, область ключей/защиту, миграции и политику удаления, фактические результаты трёх типов сбоев и перечень затронутых существующих consumers. Форма подключается через общий контракт, без шестнадцати отдельных систем autosave. UI показывает восстановление простыми словами; внутренние circuit/storage подробности остаются в техническом handoff.

## 4. CL-03 — commit, переход фокуса, ошибки, команды

Доказанная цепочка: legacy `NextControl` → renderer `nc`/handlers → `v4_ctrlChanged`/`v4_setFocus2NextCtrl` → `Kesco.focusNextCtrl`. Источники: [Control](https://github.com/KescoDev/Kesco.App.Web.V4.Inventory/blob/12a6efae7eb310adec06a57f6d80b8d9e76985b4/Kesco.Lib.Web.Controls.V4/Control.cs), [TextBox](https://github.com/KescoDev/Kesco.App.Web.V4.Inventory/blob/12a6efae7eb310adec06a57f6d80b8d9e76985b4/Kesco.Lib.Web.Controls.V4/TextBox.cs), [Select](https://github.com/KescoDev/Kesco.App.Web.V4.Inventory/blob/12a6efae7eb310adec06a57f6d80b8d9e76985b4/Kesco.Lib.Web.Controls.V4/Select.cs), [v4t_keyDown / v4_ctrlChanged](https://github.com/KescoDev/Styles/blob/fddc5a2157cf906402c50731e84cfa537abd7dba/js/Kesco.V4.js), [focusNextCtrl](https://github.com/KescoDev/Styles/blob/fddc5a2157cf906402c50731e84cfa537abd7dba/js/Kesco.js). В нынешних простых Clay wrappers нет общего управляемого Next/Focus/field-error API; базовый Tab браузера/MudBlazor существует.

Добавь минимальный общий контракт стабильного поля/ссылки, `FocusAsync` или эквивалента, успешного commit, next-target, адресных ошибок и фокуса первого ошибочного поля. Используй существующую MudForm/EditContext основу по правилам Controls; не создавай параллельную систему валидации. Server validation остаётся обязательной. Пользовательский невалидный текст хранится до исправления, даже если legacy TextBox/Number возвращали OriginalValue.

Семантика последовательности: input/paste/autofill/IME → актуальная модель → завершённый commit → валидация → одна команда либо переход фокуса. Keyup не является единственным источником изменений. Enter в textarea остаётся переводом строки; composition Enter не исполняет команду; модификаторы и стандартный Tab сохраняются. Popup/диалог/редактируемая ячейка получают приоритет перед горячей клавишей формы. Отсутствующий/скрытый/disabled next-target обрабатывается безопасным конечным fallback; нет бесконечной рекурсии и глобального перехвата Tab.

Конкретные цепочки подключаются из частных промтов: SIM Prefix→Short→Description→Save; PhoneCode Territory→Code→Length→Type→Comment→Save; девять полей Territory; шапка NumPool и возврат в соответствующий selector; **LocationFact Equipment→Equipment для повторного сканирования**. Неверный legacy NumPool NextControl `efNameInternEngAlt` не переносить. Today использует определённый для поля источник даты; серверный default периода не заменяется произвольной браузерной датой. Проверить leap year, 31.04, границу суток/года, min/max, clear, повторное появление DateOff, изменение required и период start/end. PeriodTimePicker содержит серверную логику периодов/стрелок; функция `v4ptp_mouseOver` сама её не заменяет.

Month-only DatePicker и режим «месяц» PeriodTimePicker не равны. Редактируемое время с `date-for`, сегментами HH:mm[:ss] и старой семантикой 00:00 документировано, но не подтверждено как потребность всех оставшихся форм: в BeelineParams соответствующее Time read-only/disabled. В текущем ClayTreeSelectionMode объявлены только None/Single, Multiple оставлен комментарием; готового multiple режима нет. Восстановление SelectedIds не равно DOM-focus. Добавь keyboard tree semantics: focusable node, arrows expand/collapse/next/previous, Home/End по согласованному видимому порядку, Space checkbox и Enter явное действие режима; не запускай общий Save формы случайно. Double-click текста раскрывает/сворачивает узел, быстрый набор ищет среди видимых узлов по согласованному правилу, не меняет поисковый фильтр и не перехватывает ввод в поле. После поиска, раскрытия, child edit, удаления или возврата focus попадает в существующий допустимый узел/поисковое поле. ARIA expanded/selected/checked отражает разные состояния. Дай общий node-tooltip formatter для ID и полного текста, если требуется legacy подсказка `#ID`, без частного DOM-патча страницы.

**Поиск:** нынешний filter при zero flatNodes вызывает LoadRootsAsync; возврат корней описан в текущем Tree AGENTS как часть TF_E. Это установленное поведение существующих consumers, а не автоматически доказанный дефект всех деревьев. Для новой TerritorySearch нужен отдельный empty-search state без подмены результата корнями. Добавь совместимый настраиваемый режим пустой выдачи в общий компонент и явно включи его в TerritorySearch; прежний default других деревьев сохрани, пока для конкретного потребителя не установлена самостоятельная необходимость изменения. Различай совпадения, ancestors как контекст, ограниченную выдачу и обычное browsing. Контракт count должен различать exact total, capped/HasMore и unknown: текущий max+1/truncate не доказывает полное число. Для Territory обязателен полный SQL total типа int до TOP100, отдельно от количества показанных узлов; optional total допустим для других деревьев. Error не становится empty. Текущий IClayTreeView не даёт готового публичного ApplyExternalFilter: добавь минимальный общий filter API/toolbar slot/композицию для быстрого ID/text поиска, содержит/начинается, используя одну существующую фильтровую модель и domain query.

Root scope/ancestor path/HTTP TerritoryData, filter/state persistence и бизнес-ключи остаются из частного промта. Хранение root-scoped state не должно открыть чужую ветку после изменения roots/прав; node text безопасен. Сохрани принятую современную single-path persistence; legacy collapse закрывал descendants, текущее in-memory поведение отличается — явно зафиксируй решение без возврата к сохранению всех ветвей. ## 12. CL-11 — присутствие, сообщения об изменениях и совместное редактирование

Это предметная логика поверх транспорта. Blazor Server SignalR сам по себе её не реализует.

Составь для затронутых форм точную таблицу: наследование/IsCollaborateWork, тип и наличие key, включение SignalUI, события полей/страницы и ожидаемый refresh. В legacy UI имеет дополнительные условия menu buttons и ItemId.ToInt()>0; потому строковый/составной ключ и наличие EntityPage не доказывают отображение всей панели. **PhonePoolAtribute_form явно IsCollaborateWork=false:** не включать автосинхронизацию формы по общему default. BeelineParams содержит пустой override ActionAfterSignalRConnected, его нельзя приравнять к стандартному EntityPage flow без проверки. Read-only отчёт/поиск/Ping тоже не превращаются автоматически в collaboratively editable entity.

Для подтверждённых потребителей реализуй общий адресный контракт присутствия и изменений по `(application, entity kind, typed key)`, доверенной server identity и правам. Состояние чужой сущности/пользователя не передаётся по одному совпавшему ID. UI может агрегировать несколько окон одного пользователя и учитывать editable/dirty; legacy скрывал текущего пользователя и предпочитал editable-сессию при дедупликации. Собственные окна всё равно должны получать необходимые адресные save/refresh события. Client-provided userId/имя не является источником полномочий.

Покажи другим пользователям актуальное присутствие/статус и обрабатывай сохранение/удаление/обновление текущего объекта. Чистую форму можно перечитать по принятому контракту; **dirty-форму нельзя молча перезагрузить или перезаписать чужими данными**. Для реально используемой live-пересылки полевых изменений сохрани предметный сценарий через typed changes и контроль актуальности: безопасно применяемые изменения отделяются от конфликтующих локальных, конфликт предъявляется явно с сохранением draft. Одна панель «кто смотрит» не считается переносом полевой collaboration. Если конкретный caller требует точного совместного редактирования, его приемка включает этот сценарий; изменение прежней семантики должно быть явно описано, а не спрятано в упрощении транспорта.

Не копируй shared mutable Entity между пользовательскими circuits, eval XML-команд и force reload как протокол. Порядок/revision событий и dedup нужны для stale/duplicate/reconnect, но не заменяют проверку актуального SQL состояния перед write. Не добавляй несуществующую rowversion/блокировку/DB-схему без основания; используй доступный concurrency contract формы. При создании/изменении mutable key подписка переключается после успеха, старая удаляется. При disconnect запись присутствия устаревает/истекает; dispose снимает subscriptions, reconnect повторно проверяет права и подписывает актуальный key без replay writes.

Legacy `hubImpossibleConnect` мог через 15 секунд reload; новая логика согласуется с CL-02 и сохраняет незавершённые действия. Chat в исходнике содержит stub/закомментированную UI: создавать новый чат не требуется. Не добавляй SignalR 2.4.x рядом с Blazor только ради имени файла; нужен предметный service/event contract, способ доставки выбирается по архитектуре.

Приёмка: два пользователя одного объекта, разные объекты с одинаковым числовым ID разных типов, два окна одного пользователя, clean/dirty получатель, simultaneous edit одного поля и разных полей, чужое сохранение/удаление, revoke rights, key change/new ID, duplicate/late event, disconnect/reconnect/dispose. ## 14. Порядок исполнения и работа нескольких агентов

1. Оркестратор пересверяет HEAD/AGENTS/существующие исправления и публикует маленькие API-контракты: результаты/отмена, focus/commit, draft/reconnect, Tree multiple, date/UTC, contact provider, collaboration eligibility.
2. Независимо идут ветви: окна+dialogs (CL-01/06), form lifecycle+inputs (CL-02/03/04/05), Grid/Tree/time (CL-07/08/10), contacts/collaboration (CL-09/11) по доступным слотам. Это роли, не требование держать четыре дополнительных агента. Пересечения `Form`, Select, Grid и DI резервируются по конкретным файлам; CL-12 проверяет каждый владелец на своём изменении.
3. Не жди всех CL для старта каждой формы. Read model/UI готовятся по согласованному контракту; интеграция ждёт только своих обязательных CL. Finder single не ждёт Tree multiple; TypeEquipmentMenu не ждёт contacts; Ping не ждёт collaboration. Форму нельзя принять с неработающей нужной ей функцией под ссылкой «будет общая библиотека».
4. Один интегратор последовательно принимает shared API/реализацию, затем consumers, затем caller/menu/metadata и совместные проверки. После изменения common contract зависимые агенты получают версию и миграционную delta; не создают свой shim для прежней версии.
5. Роли и версии фиксируются в handoff оркестратора. Реальный max1 DynamicGrid, Select readonly policy и текущие EquipmentForm/Net reservations остаются ограничениями параллельного плана.

Если contact backend или multiuser стенд недоступны, зафиксируй точную блокировку соответствующего CL/consumer и продолжай остальные; нельзя объявить отсутствующую карточку обычным title или collaboration одним SignalR connect. Согласование владельцев/контрактов внутри задачи не требует повторного разрешения пользователя.

## 16. Что сдать

Передай изменения общих библиотек и минимальных consumers; матрицу CL→реальные символы/файлы/потребители; совместимость публичных API и intentional differences; source→implementation по AUDIT; результаты проверок с условиями окружения; текущие SHA/patch и handoff. Для каждого CL явно: не требуется подтверждённым consumers / уже реализовано и проверено / изменено и проверено / конкретно блокировано. Заявление «Styles перенесён» без этой карты не является приёмкой.

Для CL-02 отдельно сдай доказательство DR-01 по §3.7: реальный restart, network loss и deployment, формат/миграции/ключи, сохранение последнего ввода, unknown-result и ревизии. Отметка «guard/reconnect готов» не закрывает G0.6.

Готовность shared-подзадачи не равна готовности всех 16 форм; существование бизнес-формы не равно проверке её нужных CL. Заверши полный применимый пользовательский сценарий и отрази оставшиеся внешние ограничения точно, не маскируя их общим статусом.

Для каждой изменённой CL-задачи сдай краткую таблицу «проблема legacy/current → решение Clayzor → сохранённый бизнес-сценарий → проверка». Покажи, как устранён конкретный дефект или обеспечена отсутствовавшая возможность, чем подтверждены отсутствие потери данных/повторной команды/чужого состояния и совместимость нужных consumers. Дополнительно приложи карту затронутых существующих consumers, contract/default и результаты до/после на интегрированном базисе. Существующий корректный компонент переиспользуется без искусственного переписывания. Приёмка требует функциональной полноты, качества и отсутствия внесённых регрессий; «работает как legacy» не оправдывает известную ошибку, а «сделано современно» не оправдывает потерянный бизнес-сценарий или сломанный прежний consumer.
