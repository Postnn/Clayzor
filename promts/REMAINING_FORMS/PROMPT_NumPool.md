## Цель и важное различие сущностей

Реализуй в Clayzor эквивалент `Inventory/Telefon/NumPool.aspx`. Прочитай [общие правила](01_COMMON_RULES.md), действующие AGENTS суперпроекта и затронутых сабмодулей. Несмотря на имя файла, она **не является редактором телефонного пула** и не заменяет `PhonePoolAtribute_form`, `PhonePoolLookup` или управление ёмкостями как справочником.

## 1. Режимы, маршруты и идентификатор

Маршруты `/Telefon/NumPool` и `/Telefon/NumPool.aspx`; query `id` поступает через базовый EntityPage. **PK — строковое значение `НомерТфОП`**, а не `КодНомернойЁмкости`, `КодТелефонногоНомера` или identity integer. Сохрани ведущие нули и исходное представление номера, не преобразовывай номер в int/long.

- Нет ID: создание, поля номера и ёмкости доступны, начальный фокус на «Номер ТфОП», четыре набора пусты.
- Существующий ID: чтение карточки и четырёх наборов; номер и ёмкость read-only, начальный фокус «Входящий для».
- Не найдено/недоступно/ошибка SQL: отдельное состояние, не молчаливое создание нового номера.

После создания «Сохранить» устанавливает `id` в URL равным введённому `НомерТфОП`, перечитывает карточку и блокирует номер/ёмкость. «OK» закрывает после успеха. Повторное сохранение не делает второй INSERT.

## 2. Поля шапки и точный порядок

Заголовок по ресурсу: **«Номер ТфОП: {id}»**. В legacy заголовок новой формы имеет пустой id.

| Порядок | Подпись | Поле | Правило |
|---:|---|---|---|
| 1 | Номер ТфОП: | `НомерТфОП` | Обязательный; только новая запись; строка |
| 2 | Номерная ёмкость: | `КодНомернойЁмкости` / display `НомернаяЁмкость` | Обязательный справочник; только новая запись |
| 3 | Входящий для: | `ВходящийДля` / `InpFor` | Свободный текст, необязательный |
| 4 | Входящий на: | `ВходящийНаНомер` / `InpTo` | Свободный текст, необязательный |
| 5 | Контроль: | `Контроль` / `Ctrl` | Числовой ввод, обязательный; для null первоначально `0` |
| 6 | Примечания: | `Примечания` / `Descr` | TextArea, две строки в legacy; необязательный |

Справочник ёмкостей: `vwНомерныеЁмкостиСписок`, ключ `КодНомернойЁмкости`, текст `НомернаяЁмкость`, сортировка по тексту. В popup legacy лимиты 100/101 и AutoSetSingleValue; сохраняй пригодный общий ClaySelect paging, наличие результата «есть ещё» и выбор единственного совпадения. Не подставляй вместо этого `ПулыТелефонов`.

Проверки legacy: `ValueText.IsNullEmptyOrZero()` ёмкости, непустой `Контроль`, `numberTFOP.Value.IsNullEmptyOrZero()`. При переносе валидируй **реальный ID выбранной ёмкости**, а не только display text. `Контроль=0` допустим; допустимый numeric тип/диапазон и текстовые максимумы подтверждай по схеме, не выдумывай «только 0/1» или phone regex. Отдельно тестировать значение `"0"` номера и leading zeros по семантике helper.

Footer — Changed родительской записи; даты дочерних строк имеют свои tooltip. Не показывать фиктивную дату/автора новой записи.

## 3. Четыре набора использования: данные и UI

Сначала широкая секция **«Подключения телефонии»**; следующая линия в legacy содержит слева направо **«Лица заказчики»**, **«Сотрудники»**, **«Телефонные номера»**. На узком экране переносить в этом порядке. Каждая секция имеет две колонки: действие удаления и отображаемое значение. Заголовок секции не превращать в новые доменные колонки «ID/Имя/Автор/Дата»: автор и дата находятся в tooltip. В Clayzor реализовать через статический `ClayGrid`, действия записи в `RowActions`, добавление через принятый общий механизм с `ClaySelect`; не переносить ручной HTML renderer.

| Секция | Связь/ключ | Показ | Добавление |
|---|---|---|---|
| Подключения телефонии | `КодПодключенияТелефонии` | `ПодключениеТелефонии + ' ' + Интерфейс` (`Caption`) | `DBSPhoneConnection` аналог на `vwПодключенияТелефонии` |
| Лица заказчики | `КодЛица` | `ЛицоЗаказчик`, ссылка к лицу | Источник **заказчиков**, не всех произвольных лиц |
| Сотрудники | `КодСотрудника` | `Сотрудник`; префикс `*` при `Private == "1"`; ссылка к сотруднику | Только работающие сотрудники; перед выбором отдельный checkbox `Private` |
| Телефонные номера | `КодТелефонногоНомера` | `Телефон`, ссылка к Tel | Общий список DBSPhone/`SELECT_ТелефонныеНомера`, не контекстная fn_НомераДляТелАппаратов |

Каждый список сортируется по `Name`; у подключения Name исторически может отличаться от Caption (загруженная запись — название подключения, новая — display с интерфейсом). Сохрани понятный порядок по подтверждённому display contract, не сортируй ID вместо имени. Если адаптация меняет наблюдаемый порядок, явно зафиксировать это до приёмки.

### Правила добавления

1. Выбор непустого элемента сразу добавляет строку **в draft**, без SQL до сохранения формы.
2. В каждом наборе не должно быть дубля по его ключу. Наличие одинакового int в разных типах наборов нормально: типы ключей различаются.
3. После добавления selector очищается, фокус возвращается в него; пользователь может добавлять следующие строки без повторного открытия формы.
4. В строке сотрудника `Private` фиксируется в момент выбора; checkbox затем сбрасывается в false. Повторный выбор уже присутствующего сотрудника **не изменяет его Private**. Для изменения признака legacy позволяет удалить строку и добавить заново с другим checkbox.
5. Предварительный tooltip новой строки берёт доверенного CurrentUser и текущее UTC-время; после save перечитать фактические DB Changed. Не принимать автора от клиента.
6. Любое добавление/удаление меняет общий dirty-state, даже если шапка не тронута. Все кнопки сохранения учитывают полный aggregate.

### Удаление строки

Команда получает legacy `Position="Employee;id"`, `Connection;id`, `Person;id` или `Phone;id`, удаляет соответствующий элемент из draft и перерисовывает **только его набор**. Проверка типов и ключей обязательна; не использовать строковую команду как SQL. В code-behind `DeleteConfirm` прямо переводится в `DeletePosition`; вызов ShowConfirm закомментирован. Поэтому отдельное подтверждение **для удаления одной связи не является legacy правилом**. Отмена всей формы восстанавливает несохранённые удаления.

## 4. Aggregate и SQL-транзакция

Модель/read/write размещаются в Entities. Основные поля плюс четыре коллекции образуют один aggregate. Простой Web CRUD-service-прокси не нужен; реальная координация одной транзакции допустима на доменной границе. Чтение можно пакетировать в пять result sets через существующий `DbManager`/Dapper, документируя порядок: карточка, подключения, сотрудники, лица, телефоны. Не выполнять N+1 для tooltip и display names.

### Таблицы и запросы

Ниже полный контракт 20 запросов aggregate из [SQLQueries.cs, регион «Номер ТфОП»](https://github.com/KescoDev/Kesco.App.Web.V4.Inventory/blob/12a6efae7eb310adec06a57f6d80b8d9e76985b4/Kesco.Lib.Entities/SQLQueries.cs#L1568-L1740). Значения параметров подтверждены `PhoneNumberCommonUsage.Load/Save/Delete` и методами `GetListConnection/ListConnectionSave`, `GetListEmployee/ListEmployeeSave`, `GetListPerson/ListPersonSave`, `GetListPhone/ListPhoneSave`, `Delete/ListDelete` дочерних сущностей из списка источников. Все запросы выполняются как `CommandType.Text` через `Config.DS_user`/эквивалентный `CN`, не как одноимённые процедуры.

Во всех пяти частях `@Id` означает **строковый НомерТфОП родителя**. Это не `Entity.Id` дочернего объекта: у загруженной дочерней строки `Id` содержит её foreign key. В `GetList*` параметр `@Id` явно имеет legacy `ParameterTypes.String`; родительский `Load` передаёт тот же параметр под именем `@id`. В новой модели сохраняй строковый тип номера независимо от представления остальных идентификаторов.

В UPDATE legacy получает `@Id` выражением `Id ?? НомерТфОП`, а значения четырёх изменяемых полей передаёт как есть. INSERT не возвращает identity: сохранённый ключ — введённая строка номера.

| Операция | Точная константа | Параметры и действие |
|---|---|---|
| Чтение набора | `SELECT_ID_НомераТфОП_Телефоны` | Только `@Id`; строки связей плюс `Телефон`, `Название`, `ИзменилФИО`. `GetListPhone` использует `Телефон` как `Name` и отображаемое значение, а не `Название` |
| Пакетная вставка | `INSERT_НомераТфОП_Телефоны_List` | Колонки `(НомерТфОП, КодТелефонногоНомера)`; для каждой новой строки `i`: `@НомерТфОП{i} ← newList[i].НомерТфОП`, `@КодТелефонногоНомера{i} ← newList[i].КодТелефонногоНомера` |
| Удаление одной связи | `DELETE_НомераТфОП_Телефоны` | `@Id ← НомерТфОП` и `@КодТелефонногоНомера ← КодТелефонногоНомера`; WHERE содержит оба условия; оба параметра legacy `Delete` передаёт как `ParameterTypes.String` |
| Удаление всего набора | `DELETE_НомераТфОП_Телефоны_List` | Только `@Id`, явно `ParameterTypes.String` в `ListDelete`; удаляет все телефоны только этого номера ТфОП |

`INSERT_*_List` — SQL-заготовки с `INSERT` и списком колонок, **без готового VALUES и без параметра-массива `@Ids`**. Соответствующий `List*Save` дописывает `VALUES (...)` с индексами от `0` до `newList.Count - 1`: например, для сотрудников `VALUES (@НомерТфОП0,@КодСотрудника0,@Private0), (@НомерТфОП1,@КодСотрудника1,@Private1)`. При пустом `newList` INSERT не выполняется. Индекс — технический номер параметра внутри пачки; нельзя подставлять на его место пользовательский текст. Отдельных дочерних UPDATE эти четыре класса не вызывают: legacy diff удаляет отсутствующие связи и вставляет новые; смена `Private` через удаление/повторное добавление должна сохраниться и в новом diff.

Все дочерние SELECT фильтруются по одному родителю и получают подпись автора через LEFT JOIN с fallback `'#' + CONVERT(varchar, Изменил)`. Подключения и лица дополнительно используют INNER JOIN соответственно к `vwПодключенияТелефонии` и `ЛицаЗаказчики`, сотрудники — INNER JOIN к `Сотрудники`; телефонная связь использует LEFT JOIN к `vwТелефонныеНомераИзменение` и сохраняет fallback `'#' + CONVERT(varchar, КодТелефонногоНомера)`. Не меняй JOIN-типы при пакетировании чтения: это изменит наблюдаемый состав наборов. Даты `Изменено` и автор `Изменил` не передаются в перечисленных INSERT/UPDATE — после записи прочитай реальные DB audit-значения; не записывай предварительный tooltip из draft.

Legacy хранит foreign keys этих дочерних DTO строками, местами явно передаёт их как строковые SQL-параметры. Это не подтверждает строковый тип соответствующих DB-колонок: в Clayzor используй подтверждённые типы справочников/схемы, сохраняя точные связи и строковую природу `НомерТфОП`. `DELETE_*_List` не является командой удаления произвольного списка ID: это удаление **всего набора одного номера**, нужное для `DeleteAll`; в обычном сохранении diff применяются точечные DELETE по паре ключей.

INSERT родителя пишет номер, ёмкость, входящий для/на, примечания, контроль. Legacy заменяет **null** `InpFor`, `InpTo`, `Descr` на одну строку-пробел `" "`, null Ctrl на `"0"`; пустая строка при этом остаётся пустой. Проверь ограничения/triggers и сохрани различие до доказанного решения о нормализации. UPDATE меняет только четыре поля `ВходящийДля`, `ВходящийНаНомер`, `Примечания`, `Контроль`; ёмкость и номер существующей карточки неизменяемы и на сервере.

Save legacy оборачивает всё в TransactionScope:

1. Вставляет родителя, если новый; передаёт `НомерТфОП` во все ещё не записанные дочерние строки.
2. Иначе обновляет изменённую шапку.
3. Сохраняет diff подключений, сотрудников, лиц, телефонов.
4. Commit лишь после успеха всех частей.

Удаление карточки `DeleteAll`: в одной транзакции удаляет все подключения → сотрудников → лица → телефоны → родителя. Ошибка любой части откатывает **всю** операцию. Нельзя рассчитывать на неизвестные cascade FK или выполнять удаление родителя первым. Использовать существующий общий transport и одну управляемую транзакцию; проверить trigger effects и rollback на тестовом стенде.

### Diff без потери данных

Legacy `List*Save` перечитывает текущий список, удаляет `oldList.Except(draft, new ExtensionComparer())`, затем INSERT всех `IsNew` строк; comparer сравнивает `Id` **и `Name`**. Такое сравнение может удалить неизменённую связь после переименования сотрудника/лица/телефона. Не переносить эту ошибку: идентичность связи — `(НомерТфОП, foreign key)`, Private — данные сотрудника. Display name/tooltip не являются ключом и не должны вызывать DELETE.

Также нельзя удалять строку, добавленную другим пользователем после загрузки, только потому, что её нет в устаревшем draft. Сравнивай с исходным snapshot и проверяй конфликт актуального aggregate перед записью. Выбери механизм, совместимый с фактической схемой: подтверждённая версия/сравнение original или проверяемый diff; не выдумывай колонку rowversion. Тест отдельно доказывает сохранность сторонней связи.

Пакетные INSERT параметризованы. Размер пачки должен учитывать ограничения SQL Server по числу параметров/строк, не ухудшая атомарность. Пользовательский текст/списки ID нельзя конкатенировать в SQL.

## 5. Команды, возврат и навигация

- `OK` → SaveAndClose, `Сохранить` → Save. Обе кнопки первоначально disabled и становятся доступны при изменениях; предусмотреть корректное закрытие/поведение неизменённой карточки через принятый toolbar.
- `Удалить` появляется только у существующего номера, требует подтверждения с текстом удаления «Номер ТфОП: {id}» и запускает DeleteAll.
- После Save без закрытия legacy делает RefreshPage. После SaveAndClose и DeleteAll устанавливает `window.returnValue=1` и закрывает. Это **статус успеха**, не выбранный телефонный ID.
- «Отмена» следует FORM-KEY-01 (Close/Reset/Continue), reset перечитывает все пять частей карточки до безопасной замены и остаётся открытым; «Обновить» сохраняет ввод для сверки. Cancel не выдаёт success=1; Unknown/late N+1 не удаляются.
- Ссылки на сотрудников/лиц/Tel открываются через общую navigation/config и `clayOpen`, не меняя родительский draft. Tooltip «Изменил: {ФИО} {дата}» локализует UTC для клиента. Legacy передаёт TimeZone при команде Render; в Clayzor используй принятый механизм timezone, не server-local DateTime parsing.
- При ошибки SQL/validation нет возврата success, refresh или закрытия. Сохраняются шапка, все draft-наборы, Private и исходный snapshot.

Подключение через меню/динамические `Запросы` требует проверки реальных URL metadata. Не выдумывай отдельную запись меню. NumPool не должен отправлять команды АТС: явной сетевой синхронизации в его Save/Delete нет; возможные DB triggers проверить отдельно.

## 6. Авторизация и границы повторного использования

В исследованных NumPool/NCU и дочерних CRUD явных `HasRole` нет. Политика доступа определяется не вымышленной ролью «администратор пулов», а подтверждёнными правами SQL/приложения. Соблюдай `Employee CurrentUser`, trusted identity, свежую проверку перед всеми writes и fail-closed. Проверяй право на родительскую запись и выбранные связанные сущности на сервере. Нельзя считать клиентский foreign key существующим/разрешённым лишь потому, что он раньше отображался в selector.

В новом проекте уже есть employee/customer/phone lookup infrastructure. Сверь их точные фильтры: выбор телефона NumPool — общий телефонный справочник, а `PhoneNumberSelectDataSource` в EquipmentForm использует контекстную функцию оборудования и **не является автоматически подходящей заменой**. Источники ёмкостей и подключений добавлять как общие DBSelect на основе Entities, если после пересверки HEAD их ещё нет. Не создавать копию Employee, локальную систему ролей или второй независимый набор SQL.

## 7. Приёмка: проверять aggregate, не только шапку

1. Новый номер: правильные defaults/focus; существующий: совпадают шапка и четыре набора, номер/ёмкость блокированы.
2. Номер с ведущими нулями сохраняется строкой; число ёмкости не подставляется как PK номера.
3. Обязательные поля и numeric диапазон подтверждены; `Контроль=0` допустим, неизвестная ёмкость отклонена сервером.
4. В новой форме заполнить все четыре набора **до первого сохранения**; после создания каждая связь ссылается на новый номер.
5. Добавить только дочернюю связь при нетронутой шапке: dirty=true, запись сохраняется.
6. Удалить только дочернюю связь: dirty=true; до Save БД не меняется. Cancel→Continue сохраняет локальное удаление; Cancel→Reset после успешного fresh read отменяет принятые изменения и оставляет карточку открытой; Cancel→Close отбрасывает только подтверждённый editable draft и закрывает. Unknown/parent и N+1 защищены.
7. Повторный выбор каждого типа не дублирует строку; очистка/focus selector корректны.
8. Сотрудники: только работающие; Private фиксируется, `*` отображается, checkbox сбрасывается; повторный выбор не переключает признак.
9. Удалить и заново добавить сотрудника с другим Private: новое значение сохраняется без потери соседних строк.
10. Смена display name внешней сущности не удаляет неизменённую связь при сохранении другой части.
11. Изменения во всех пяти частях пишутся одной транзакцией; искусственный отказ каждой из дочерних операций откатывает родителя и остальные связи.
12. DeleteAll удаляет все четыре набора и родителя атомарно; отказ подтверждения ничего не делает; ошибка не закрывает форму.
13. Существующая карточка не позволяет изменить номер/ёмкость подменённым серверным запросом.
14. Конкурентные создание, изменение шапки, добавление связи и удаление родителя не дают потери сторонних данных/ложного success.
15. Сохранить новой записи меняет URL и read-only состояние; повторное Save не вставляет дубликаты.
16. OK/Delete возвращают status=1 только после commit; Cancel/error — без success; родитель не закрывается и не теряет состояние.
17. Все ссылки открывают правильные сущности, все tooltip имеют правильного автора/клиентское время, XSS-текст показывается как текст.
18. Отзыв прав после открытия, отсутствие CurrentUser, прямой вызов записи и неверный foreign key отклоняются сервером.
19. Много связей: нет N+1, корректный размер SQL batch, отмена/повтор не дублируют записи.
20. 320–480px, порядок секций, две колонки каждого набора, keyboard/Tab, dirty-confirm и единый стиль Clay.

В handoff отрази всю карту `5 read models / 5 частей записи`, реальные типы/лимиты БД, snapshot/diff/concurrency решение, права, источники новых selector, подтверждённые вызовы и результаты. Приложи фактические build, профильные тесты, CRUD/rollback и browser checks; непроверенные SQL grants/триггеры перечисли отдельно. Не коммить/пушить без актуальной авторизации пользователя.
