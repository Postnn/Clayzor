## 1. EQ6-P1-01 — ложный успех write-path при ошибке SQL-подключения

### Подтверждение по коду

`src/Clayzor.Lib.Entities/Inventory/EquipmentAccounting.cs`, метод `DeleteLatestAsync`:

```csharp
var status = await db.ExecuteScalarAsync<int>(
    SQLQueries.DELETE_КодОборудования_ОборудованиеБухУчета,
    ..., commandType: CommandType.Text);
```

`src/Clayzor.Lib.Entities/Inventory/UpsServerLink.cs`, метод `SaveDetailsAsync`:

```csharp
var status = await db.ExecuteScalarAsync<int>(
    command.Sql, command.Parameters, commandType: CommandType.Text);
```

`src/Clayzor.Lib.DALC/DbManager.cs`, метод `ExecuteScalarAsync<T>` специально для read:

```csharp
catch (SqlException ex)
{
    ...
    if (IsConnectivityError(ex))
        return default;
    throw;
}
```

При `T=int` значение `default` равно **0**, а в обоих новых SQL-контрактах **`0` = success**. Поэтому ошибка соединения (например, SQL error 53/10054/transport failure) может быть ошибочно интерпретирована как успешное удаление бухгалтерского учёта или успешное сохранение UPS. Это подтверждённый P1, независимо от 240/240 unit и 842/842 regression.

В том же `DbManager` **уже имеется** `ExecuteWriteScalarAsync<T>(string sql, object? parameters = null)` с `CommandType.Text`; он **пробрасывает любые `SqlException`, включая connectivity**. Не расширять DALC без необходимости.

### Исправление

1. Перевести **оба** write-path на fail-closed метод `ExecuteWriteScalarAsync<T>` или равнозначный по гарантиям; не использовать `ExecuteScalarAsync<T>` для модифицирующих SQL batch.
2. Проверять **наличие корректного status-result**, не только его числовое значение. Отсутствие SQL-результата или неожиданный status запрещено трактовать как success. Допустимы только документированные статусы `0,1,2,3` для каждого конкретного контракта. При отсутствии статуса — понятная ошибка, без success callback/refresh, с сохранением черновика, где применимо.
3. Не подавлять ошибку соединения в UI. В `EquipmentForm` уже есть ветки `catch (SqlException)` для UPS/accounting: убедиться, что теперь они достигаются. Не сообщать «сохранено» при неизвестном исходе транзакции. Если соединение потерялось **после COMMIT, но до получения ответа**, UX должен говорить «результат неизвестен; обновите запись и проверьте», а не «точно откатилось» и не «успешно».
4. Сохранить семантику статусных исключений: бухгалтерия — stale latest и запрет роли; UPS — stale source-link и отказ роли; status=0 действительно означает успешную транзакцию.

### Обязательные тесты (before-red / after-green)

- `DeleteLatestAsync`: `SqlException` connectivity (`53`, `10054` или используемый в проекте вариант) ⇒ **исключение**, отсутствие ложно-успешного завершения; добавьте bUnit проверку, что родитель не обновляет коллекцию как после успешного удаления.
- `SaveDetailsAsync`: аналогично ⇒ исключение, предупреждение в UI, отсутствие success path.
- Нет результата (`null` / no row) ⇒ отказ, не успех.
- Status `0` ⇒ успех, `1/2/3` ⇒ прежняя семантика, неизвестный status ⇒ fail closed.
- Моделирование ошибки на стадии записи и на стадии возврата результата: отдельно указать, что нельзя считать доказанным rollback при потере связи.
- Проверить, что `ExecuteWriteScalarAsync` действительно используется в коде обоих методов и что тест со старым методом падает (mutation / before-red).

## 2. EQ6-P1-02 — утечка `SERIALIZABLE` в SQL-сессию после удаления бухгалтерской записи

### Подтверждение по коду

`src/Clayzor.Lib.Entities/SQLQueries.cs` — `DELETE_КодОборудования_ОборудованиеБухУчета`:

```sql
SET NOCOUNT ON;
SET XACT_ABORT ON;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN TRY
    BEGIN TRANSACTION;
    SELECT TOP 1 ... FROM ОборудованиеБухУчета WITH (UPDLOCK, HOLDLOCK)
    ...
    COMMIT TRANSACTION;
    SELECT 0;
END TRY
BEGIN CATCH
    IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION;
    ...
END CATCH;
```

**После `COMMIT`, после `ROLLBACK` и при статусных ранних `RETURN` уровень изоляции не восстанавливается.** Это ad-hoc SQL batch, а не хранимая процедура. `DbManager` держит одно лениво открытое SQL-соединение в scoped экземпляре; оно используется последующими запросами этой сессии. После освобождения соединения ADO.NET pooling может сохранить уровень изоляции для следующего пользователя.

Microsoft подтверждает, что `SET TRANSACTION ISOLATION LEVEL` действует на соединение до следующего изменения, а уровень изоляции может наследоваться pooled connection. См. документацию:

- https://learn.microsoft.com/en-us/sql/t-sql/statements/set-transaction-isolation-level-transact-sql
- https://learn.microsoft.com/en-us/dotnet/framework/data/adonet/sql/snapshot-isolation-in-sql-server

### Исправление

Изолировать `SERIALIZABLE` **только** в пределах бухгалтерского удаления, не изменяя последующие команды данного `DbManager` и переиспользуемого pooled connection. Выбрать минимальное проверяемое решение, совместимое с SQL Server 2008 R2. Предпочтительно изучить возможность убрать общий `SET TRANSACTION ISOLATION LEVEL SERIALIZABLE`, сохранив `BEGIN TRANSACTION` и локальные `WITH (UPDLOCK, HOLDLOCK)` на выборке последней строки: `HOLDLOCK` предоставляет SERIALIZABLE-семантику для указанной таблицы на время транзакции. Но решение **должно пройти реальный двухсессионный тест**, включая вставку новой строки между открытием и подтверждением удаления.

Если выбран иной способ, обосновать и проверить сохранение/восстановление исходного isolation level, включая успешный ход, все status-отказы, SQL-ошибку, отмену/разрыв соединения и возвращение в пул. **Не добавлять простое `SET ... READ COMMITTED` только в конце**: это не выполняется на раннем `RETURN`/исключении и может перезаписывать исходный уровень подключения. Не отключать транзакцию, `UPDLOCK`/`HOLDLOCK` или проверки актуального владельца/ролей.

Обратить внимание на другие session-wide `SET` в этом batch (в том числе `XACT_ABORT`): не допускать значимых побочных эффектов на последующие операции. Если они заведомо сбрасываются SqlClient при восстановлении, подтвердить это тестом на том же соединении, а не предположением.

### Обязательные тесты

1. На **одном открытом SQL-соединении** получить `DBCC USEROPTIONS` (поле isolation level) или достоверный аналог; выполнить бухгалтерское удаление, затем снова получить isolation level — значение должно остаться тем же. Не использовать две разные свежие сессии как доказательство.
2. Проверить то же после статусных исходов `0`, `1`, `2`, `3` и после SQL-ошибки. При необходимости использовать отдельные безопасные тестовые условия.
3. Проверить повторное использование подключения из SQL connection pool; не должно появляться «загрязнённого» SERIALIZABLE в случайном следующем запросе.
4. В двух SQL-сессиях повторить ключевой реальный сценарий: пользователь открыл старую последнюю запись → другой клиент добавил новую → пользователь подтвердил удаление старой. Обе записи должны остаться, ошибка «история изменилась». Нормальное удаление подтверждённой актуальной последней записи должно успешно выполняться.
5. Все тесты с включёнными реальными триггерами, без правок production-данных. Никаких висящих транзакций и изменённых session options после теста.
