## 2. Подтверждённые дефекты — обязательные исправления

### NET2-P1-01 — потеря точности SQL-поиска ссылок из длинных токенов

**Файл:** `src/Clayzor.Lib.Entities/Inventory/NetEquipmentLinkResolver.cs`, `ResolveAsync`, цикл формирования `DynamicParameters`:

```csharp
parameters.Add(name, batch[index], DbType.String, size: 50);
```

**Причина:** legacy `NameRegex` содержит повторяемую группу с `{1,50}`, но **не** общий предел длины совпадения. Строка из 51, 100, 200 латинских символов может стать **одним** токеном. `SqlParameter.Size=50` ограничивает число символов, отправляемых SQL Server; длинный токен усекается. В legacy поиск передавал исходный токен целиком.

**Риск:** если в БД есть имя из 50 `a`, поле содержит 51 `a`, то новая реализация способна ошибочно построить ссылку на это оборудование, хотя legacy не нашёл бы точное совпадение. Аналогичный ложный доменный суффикс может возникнуть из-за обрезки. Для `LIKE` важен также неусечённый токен со спецсимволами.

**Сделать:** убрать искусственное ограничение 50 символов при передаче токена. Использовать размер, соответствующий фактическому значению, либо корректную передачу `nvarchar(max)`/аналогичного параметра, доказав совместимость с SQL Server 2008 R2, проверив производительность и сравнение по пяти условиям. Не удалять часть токена «потому что длина сетевого имени 50»: это меняет поведение старого поиска. Держать SQL параметризованным, не вставлять текст токена в SQL-строку.

**Тесты:**

1. Extractor с 50, 51, 100, 200 буквами: проверить, что у длинного текста один полный токен (золотой результат по legacy regex).
2. Resolver с входом из 51 букв: fake-DAL должен подтверждать, что значение и передаваемый размер не приводят к усечению; на SQL 2022 проверить отрицательное совпадение при наличии 50-символьного имени, положительное по полному длинному имени в допустимых тестовых данных.
3. В обоих полях: пара короткого валидного имени и длинного токена; короткое имя по-прежнему формирует ссылку, длинный не подменяется коротким.
4. Повторить инъекционные строки, `%`, `_`, обратную косую черту, `ilo-`, MAC, 501+ токенов. `TOP 1` и wildcard semantics не менять.

**Оракул:** документация Microsoft `SqlParameter.Size`: https://learn.microsoft.com/en-us/dotnet/api/microsoft.data.sqlclient.sqlparameter.size .

### NET2-P1-02 — подтверждение PoE может относиться к другому порту

**Файл:** `src/Kesco.App.Web.Inventory/Components/Pages/Net/Net.razor.cs`, `RestartPoeAsync`.

**Причина:** первая проверка `_model?.Poe == 1` выполняется **до** `await ConfirmAsync`, а `var model = _model; var version = _loadVersion;` устанавливаются **после** него. Если при открытом confirm (тот же route-component с новым query `id`, повторная загрузка) перейти с PoE-порта A на PoE-порт B, старое подтверждение потенциально запустит reset на B. Сервер проверяет право доступа и `PoE = 1`, но **не** что пользователь подтверждал B.

**Сделать:** зафиксировать ID порта, объект/версию загрузки и необходимые признаки **до** открытия confirm. После `await` и после повторной проверки CurrentUser сверять ID, версию, disposed, состояние PoE и наличие той же записи. Если контекст изменился, ничего не выполнять. Нельзя применять результат диалога A к B. Сохранить таймаут 120 с, overlay/finally, проверку identity и текущее подтверждение.

**Тесты:**

1. A (PoE=1) → открыть confirm → не подтверждая сменить `/Net/Net?id=B` (B также PoE=1) → нажать «Да» старого диалога: `sp_ResetPoEport` не выполнялся для B и A.
2. То же при изменении ID/диспозе/потере identity/смене PoE на 0.
3. Неизменный A → «Да»: ровно один вызов с `@КодЛокальнойСети=A`, timeout 120; «Нет»: 0 вызовов; исключение: overlay снят и ошибка показана.
4. Отрицательные сценарии без реального PoE. Физическое устройство без разрешения не трогать.

### NET2-P1-03 — ошибка первичной загрузки скрыта, возможен показ старой записи

**Файлы:** `Net.razor`, `Net.razor.cs`, методы `LoadCurrentAsync`/`LoadDataAsync`.

**Причина:** при `SqlException` обработчик устанавливает `_validationMessage`, но разметка показывает его **только внутри** `else if (_model is not null)`. При первоначальной ошибке `_model=null`, `_notFound=false`, поэтому тело формы пустое и сообщение не видно. При смене `?id=` после успешного просмотра A загрузка B начинается без очистки `_model`; если B не загрузился, в UI остаётся A, хотя URL уже B. `_loaded=false` скрывает часть действий, но данные всё равно могут вводить в заблуждение. Отличать отсутствие записи от SQL/identity-ошибки.

**Сделать:** отдельное состояние `_loadError`, корректное отображение на уровне ChildContent независимо от `_model`, реальная кнопка «Повторить» с повторным запросом, явное состояние загрузки/отсутствия записи, запрет любых изменений и PoE при неуспешной загрузке; убрать или явно обозначить устаревшую модель, не затирать несохранённый черновик без осознанного решения. Обеспечить fail-closed при первичной ошибке CurrentUser. Не превращать connectivity в `not found` и не перезаписывать черновик при ошибке обычного сохранения.

**Тесты:**

1. Первый `Employee.GetCurrentAsync` или `LocalNetworkPort.GetAsync` выдаёт SQL 53/10054: виден отдельный alert + работоспособная «Повторить», нет ложной надписи «не найден», нет действий на БД.
2. После восстановления соединения тот же экземпляр формы успешно загружает порт без смены query string.
3. A загружен → переход на B → SQL ошибка: **ни поля, ни PoE-кнопка A не выглядят данными B**.
4. Настоящий no-row для B → «не найден», без ложной connectivity-ошибки.
5. После ошибки поиска *ссылок* основные поля должны по-прежнему отображаться и быть доступными (это другая, некритичная ошибка); сохранение не очищает введённый текст.

### NET2-P2-01 — предыдущий офис ошибочно применяется при отсутствии офиса у последнего расположения

**Файл:** `src/Clayzor.Lib.Entities/SQLQueries.cs`, `SELECT_ОфисПоКодуОборудования`.

**Legacy:** сначала `SELECT TOP 1 КодРасположения FROM ОборудованиеРасположение WHERE КодОборудования=... ORDER BY От DESC`, **затем** `Location(loc).LocationOffice`. Если у *последнего* расположения офиса нет, `LocationOfficeId` не задаётся.

**Сейчас:** объединение всех `ОборудованиеРасположение` с офисами и `ORDER BY ER.От DESC, O.L DESC`. Если новая запись — склад без родительского офиса, но старая запись расположения была в офисе, запрос вернёт **предыдущий** офис и исключит корректные розетки.

**Сделать:** сначала определить единственное актуальное/последнее расположение оборудования (с учётом tie-break только если подтверждён), затем искать его ближайшего офисного предка. Если у текущего расположения офиса нет — результат null, **не** поиск старого офиса. SQL Server 2008 R2 compatible. Уже согласованный принцип «не использовать код порта как код расположения» сохранять.

**Тесты:**

1. Office A → затем склад без офиса: новый SQL возвращает null, старый офис A не применяется.
2. Office A → комната в Office B: возвращается B, а не A.
3. Несколько уровней офисов: ближайший предок (максимальная `L`).
4. Нет записей о расположении: null, отсутствие SQL ошибок; доступные розетки фильтруются по правилам уже принятого fallback.
5. Сверить с реальным `Location.LocationOffice` на тех же тестовых записях.

### NET2-P2-02 — запоздалый ответ выбора сотрудника может переписать заказчика

**Файл:** `src/Kesco.App.Web.Inventory/Components/Pages/Net/Net.razor.cs`, `OnEmployeeChangedAsync`/`OnCustomerChanged`/`LoadCurrentAsync`, а также `OnSocketChangedAsync` для отображаемого примечания.

**Причина:** `OnEmployeeChangedAsync` ждёт `EmployeeSource.GetByIdAsync`, после чего проверяет только `_disposed` и `_employeeVersion`. При смене загружаемого ID `_employeeVersion` не увеличивается, нет проверки принадлежности исходной модели/ID/выбранного сотрудника. Точно так же поздняя загрузка организации может перекрыть **более поздний ручной выбор заказчика** даже в той же форме; его изменение не увеличивает версию. `OnSocketChangedAsync` не сверяет ID и объект модели для примечания розетки.

**Сделать:** при смене порта инвалидировать pending employee/socket lookups; после каждого await проверять модель/ID/версию/фактический выбор. При отдельном позднем ручном изменении заказчика оно должно иметь приоритет над прежним запросом организации; сохранить поведение legacy «при выборе сотрудника подставить организацию» при отсутствии конкурирующего пользовательского действия. Не вносить клиентскую SQL-логику.

**Тесты:**

1. Выбор сотрудника A → задержать ответ → вручную выбрать заказчика B → отпустить ответ: заказчик остаётся B.
2. Открыт порт 10 → выбор сотрудника pending → переход на порт 11 → ответ старого запроса: ни заказчик, ни сотрудник 11 не изменяются.
3. Аналогично для розетки: примечания прежней розетки не отображаются у новой записи; внутри одной записи быстрые выборы A→B сохраняют примечания B.
4. Обычный выбор сотрудника без гонки подставляет его организацию; очистка сотрудника не сбрасывает заказчика.

## 3. Дополнительные проверки — исправлять только после подтверждения

### NET2-C1 — кодировка `EXCHANGE_ЛокальнаяСеть`

В `SQLQueries.EXCHANGE_ЛокальнаяСеть` для временного хранения `Примечания` и `Подключено` цели используются `varchar(max)`:

```sql
DECLARE @TargetDescription varchar(max);
DECLARE @TargetConnected varchar(max);
```

Проверь **фактические** SQL-типы `vwЛокальнаяСеть.Примечания`/`.Подключено` и их базовых столбцов, collation, Unicode-содержимое, сравни с legacy. Если столбцы `nvarchar`, `varchar(max)` может необратимо менять символы, которые отсутствуют в кодовой странице. При необходимости — без изменения физической схемы — использовать SQL-переменные того же совместимого Unicode-типа/длины. Отрицательный тест с кириллицей, украинскими буквами, специальными символами, если они разрешены хранилищем, и проверка точного байтового/Unicode-содержимого до/после exchange. Не заявлять это подтверждённой потерей данных без проверки схемы.

### NET2-C2 — соответствие `@TargetFree` функции соседних портов

`SWITCH_ЛокальнаяСеть` определяет свободный порт самостоятельно по `SocketId/EmployeeId/Connected`, а UI получает свободные порты по `dbo.fn_ЛокальнаяСеть_СоседниеПорты(...).Занят=0`. Изучи реализацию `Занят`: **точно ли** собственный CASE соответствует штатному признаку? Для switch сервер обязан разрешать именно то, что legacy считает допустимой свободной соседней целью, и отклонять фактически занятую цель. Обязательно проверить порт с одним только примечанием и порт, который стал занят после открытия диалога. Если обнаружится различие, исправить серверную проверку и написать regression test; функция остаётся авторитетом для списка.

### NET2-C3 — надёжность после уже успешного SQL и ошибки JS refresh

В `Net.SaveAsync` сначала выполняется успешный `LocalNetworkPort.SaveAsync`, затем `JS.InvokeVoidAsync("clayModelEquipmentForm.refreshOpener")`, затем reload/close. При `JSDisconnectedException` после подтверждённого SQL не должны оставаться ложное «несохранено», старый dirty snapshot и возможность повторно переключить/обменять порт как новую запись. Проверить обработки JS-ошибок/пропажи opener (в том числе открытие Net из EquipmentForm, а не грида). Обеспечить клиентский state transition «SQL сохранён» до необязательного refresh и безопасное восстановление через повторную загрузку; не делать второй SQL UPDATE при повторе пользовательской операции по ошибке родительского уведомления. Никакого глобального reload.

### NET2-C4 — `NULL` в текстовых полях

`LocalNetworkPort.Validate()` допускает `Connected == null`, но `SaveAsync` вызывает `draft.Connected.Trim()` и `draft.Description.Trim()` без null-check. Проверь фактические `NULL` из `vwЛокальнаяСеть`, состояние при очистке ClayTextArea и прямые вызовы entity. Если пустая строка/NULL допустимы, безопасно передавать `draft.Connected?.Trim() ?? ""` и аналогично для описания (семантика legacy — Trim непустого текста, запись пустого текста вместо NULL только если соответствует DB contract). Не заменять молча историю `NULL`, если в DB они имеют иной смысл. Дополнить тест очистки обоих полей и сохранения.

### NET2-C5 — уведомление о несовпадении организации сотрудника

Legacy `efPerson_OnRenderNtf` показывает **название** компании (`Person.NameRL`/`Employee.Organization.NameRL`), а новая форма показывает лишь `#<OrganizationId>`. При `OrganizationId=0` новая проверка вообще не выводит mismatch. Подтвердить бизнес-смысл и восстановить отображение корректного названия, не превращая warning в дополнительный запрет сохранения. Сравнить с legacy на нескольких сотрудниках и заказчиках.

### NET2-C6 — проверка внешних ограничений

Нет непосредственного подтверждения работы `sp_ResetPoEport` на стенде (агент сообщил, что процедура отсутствует); SQL Server 2008 R2 реально не запускался. Оформить явно как ограничения приёмки, а не «PASS». Не запускать физический PoE без прямой санкции. Не менять `.NET` runtime/DDL/trigger исключительно ради этого ревью.

## 4. Сценарии регрессионной приёмки

Проверить не только после подмены SQL кодовых строк, но и в Blazor + тестовой SQL-БД с действующими триггерами:

| Сценарий | Ожидаемое поведение |
|---|---|
| `Подключено` и `Примечание` содержат одно имя | Две независимые ссылки; исходные текстовые значения сохраняются |
| `ilo-`, FQDN, `DOMAIN\\HOST`, MAC1/MAC2/MACILO | Порядок и пять SQL-условий совпадают с legacy; `TOP 1` остаётся без `ORDER BY` |
| MAC с разделителями, IP и `_` wildcard | Ни новой нормализации, ни неожиданного IP-поиска |
| 51/100/200-символьные токены | Параметры SQL не обрезают токены; нет ложной ссылки на имя из 50 символов |
| 501+ различных токенов | Нет N+1 SQL, ограничение числа параметров работает |
| Нет заказчика / розетка без сотрудника и `Подключено` | Нет записи; отображаются legacy-сообщения |
| Примечание без `Подключено` при выбранной розетке | Не считается подключением, сохранение блокируется |
