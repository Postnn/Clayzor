# Ключевые требования к формам редактирования Clayzor

**Статус: обязательные требования пользователя, редакция 26.11.2026.**

Контракт обязателен для существующих и новых форм текущих приложений Clayzor и для новых приложений на Clayzor. Он распространяется на страницы, отдельные окна, модальные и вложенные редакторы. Это условия реализации и приёмки, а не пожелания к оформлению. Корневой `AGENTS.md` требует читать этот документ вместе с `docs/agents/forms.md`; локальные инструкции и задания формы должны ссылаться на него. При создании приложения добавь ссылку в его `AGENTS.md` и подключи общие механизмы. Для самостоятельного репозитория ссылка должна разрешаться в доступную закреплённую версию контракта; не оставляй неработающий относительный путь.

Явные решения пользователя из этого документа заменяют прежние противоречащие указания о поведении «Отмена», разрушительном «Обновить» и необязательном присутствии других редакторов. Последнее уточнение FORM-KEY-03 сохраняет empty-required: желтоватый фон только у пустого обязательного редактируемого поля; заполненное имеет обычный фон, очистка возвращает желтоватый. Остальные бизнес-правила, права, транзакции, CAS, принятые исправления и DR-01 сохраняются. Legacy служит источником полезных сценариев; переносить его технические дефекты или ухудшать работающий Clayzor ради совпадения запрещено.

## 1. Реестр обязательных требований

| ID | Ключевое требование | Область |
|---|---|---|
| FORM-KEY-01 | «Отмена»: закрыть без сохранения либо отменить изменения, перечитать БД и оставить форму открытой; безопасный отказ от выбора | Редакторы и их собственные вложенные scope |
| FORM-KEY-02 | Placeholder визуально центрирован по вертикали однострочного поля | Все общие однострочные контролы, в том числе составные |
| FORM-KEY-03 | Пустое обязательное редактируемое поле имеет желтоватый фон; заполненное — обычный; после очистки — снова желтоватый. Placeholder не определяет Required и не мешает отображению состояния | Все редакторы, условная обязательность — по фактическому состоянию |
| FORM-KEY-04 | При открытии фокус один раз устанавливается на первое доступное поле ввода | Каждый самостоятельный редактор и вложенный диалог |
| FORM-KEY-05 | Клавиатурный фокус имеет контрастную рамку согласно теме и типу контрола | Все интерактивные элементы формы |
| FORM-KEY-06 | Изменённые поля имеют контрастную рамку, отличную от рамки фокуса | Typed и raw изменения, включая составные/дочерние редакторы |
| FORM-KEY-07 | Enter в однострочном поле и завершённый выбор значения в списочном контроле переводят фокус на следующее поле ввода | Общая навигация в пределах активной формы/диалога |
| FORM-KEY-08 | Каждая форма имеет доступные команды «Справка» и выбора цветовой схемы; URL справки — `URI_wiki_help` и зарегистрированный путь формы | Все формы, включая поиски, диагностические и read-only страницы |
| FORM-KEY-09 | Пользователь видит других сотрудников, которые одновременно редактируют ту же сущность | Все редакторы существующей общей сущности, независимо от route/окна/приложения |
| DR-01 | Несохранённые пользовательские данные не должны безвозвратно пропадать из-за перезапуска IIS, кратковременного обрыва сети или обновления приложения | Весь пользовательский ввод и восстановление |

Для поиска, отчёта, печатного представления или диагностики без редактируемой бизнес-сущности не создавай фиктивные Save, dirty-record, DB reload или presence по идентификатору `0`. Применяются имеющиеся контролы, фокус, справка, тема и сохранность реального пользовательского ввода. В отчёте о выполнении укажи точную область применимости; освобождение одной read-only страницы не освобождает её редакторы.

## 2. FORM-KEY-01 — «Отмена», повторная загрузка и черновик

### Пользовательский сценарий

Без несохранённых изменений «Отмена» закрывает форму/диалог или возвращает к вызывающей странице через существующий контракт навигации. Чистая копия данных в IndexedDB сама по себе не означает наличие изменений.

Если есть изменения, «Отмена» открывает общий диалог с понятным вопросом и тремя явно различимыми действиями:

| Действие | Результат |
|---|---|
| **«Закрыть без сохранения»** | Пользователь явно отказывается от редактирования текущей области; после подтверждённой очистки её editable draft форма закрывается, бизнес-запись не выполняется |
| **«Отменить мои изменения и загрузить из БД»** | Успешно читается актуальная разрешённая версия записи, текущие изменения этой области отменяются, новые данные становятся baseline, форма остаётся открытой |
| **«Продолжить редактирование»** | Ввод, черновик и открытая форма сохраняются без изменений |

Escape, крестик диалога и отмена показа означают «Продолжить редактирование». Деструктивный вариант не должен активироваться случайным Enter. Диалог доступен с клавиатуры и перетаскивается через общий механизм диалогов проекта. После продолжения фокус возвращается в прежний контрол; после успешного сброса — в первое доступное поле этой формы, если пользователь уже не сменил активный контекст.

Dirty учитывает typed state, ещё не разобранный или не покинутый raw input, явное очищение значения и принадлежащие форме несохранённые вложенные данные. У дочернего диалога свой scope: его Cancel не очищает родительский ввод или соседний редактор. Если закрытие parent затрагивает активные дочерние области, диалог явно охватывает их, а очистка использует их точные версии; неизвестные отправленные операции не исчезают.

Для локального вложенного объекта без собственной строки БД повторная инициализация использует согласованный opening/context contract; ранее принятый в parent draft объект не удаляется вместе с текущим редактированием. Крестик браузера, потеря circuit, навигация и Dispose не равны явному «Закрыть без сохранения» и не удаляют durable draft. Cancel вопроса о конфликте, отказ от выбора в поисковом окне и Stop диагностики сохраняют свои специальные значения.

### Безопасная повторная загрузка

1. Зафиксируй идентичность текущей сущности, route generation, область и ревизию отменяемого ввода. Сохрани/защити уже набранный raw; не считай blur единственной точкой появления изменения.
2. Выполни новое чтение БД и актуальную проверку прав через существующий domain/read contract. Значения из предыдущего merge-диалога, старого cache или первоначальной загрузки не заменяют fresh read.
3. Только после успешного чтения, проверки применимости ответа и подготовки состояния переходи к согласованному сбросу editable draft и замене baseline/UI. Определи восстановимый порядок/состояние этого перехода; одного `DiscardAsync(); LoadAsync();` недостаточно.
4. Ошибка чтения, потеря связи, отсутствующая/недоступная запись, смена маршрута и сбой локального хранилища не должны уничтожать исходный ввод. Оставь доступными его просмотр/копирование и повтор допустимого действия. Недоступная запись не превращается в новую, а recovery не обходит права.
5. Защити переход ревизией: ввод N+1, появившийся после подтверждения или во время чтения, нельзя тихо отменить вместе с N. Либо реально заблокируй ввод и поздние callbacks на время принятого перехода, либо обнаружь изменение и оставь данные/повтори осознанное подтверждение. Не удаляй поздний autosave или draft другой вкладки.
6. После успешного сброса прежний editable draft не должен восстановиться при reconnect/F5/позднем autosave. Новое чистое состояние не имеет dirty-рамок; ошибка cleanup не выдаётся за успешный сброс. Различай подтверждённую смену состояния и незавершённое безопасное удаление служебного остатка.

Для **новой записи** ещё нет строки БД. Тот же выбор доступен с честной формулировкой **«Отменить мои изменения и начать заново»**: заново подготовить разрешённые исходные значения режима создания/копирования и оставить форму открытой, не выполнять INSERT и не подставлять чужой ID. Ошибка получения defaults сохраняет прежний ввод. Контекст создания не теряется, identity нового экземпляра остаётся изолированной.

При «Закрыть без сохранения» нельзя заявлять, что ввод удалён, если durable cleanup завершился ошибкой. Оставь форму/восстановление доступными с явным статусом и повтором только очистки; не закрывай форму как будто сброс подтверждён. Для подтверждённого commit завершается только разрешённый cleanup/close — повторная запись запрещена.

### Unknown и другие команды

Editable draft, immutable отправленная попытка и подтверждённый результат — разные сущности. Ни один вариант Cancel не доказывает, что отправленная операция не состоялась. Running/Unknown и необходимые данные для сверки сохраняются независимо от отказа от дальнейшего редактирования. Если безопасно перейти к свежему представлению без потери попытки невозможно, покажи конкретное состояние и путь read-only сверки; не стирай Unknown ради разблокирования Save. При допустимом закрытии unresolved попытка остаётся обнаруживаемой после нового открытия/потери session pointer.

«Обновить» больше не выполняет скрытый discard изменённого ввода. Для dirty формы это fresh read/сравнение и предусмотренный merge/recovery с сохранением пользовательских данных; полный отказ от текущих изменений находится на «Отмена». Read-only обновление списка/справочника сохраняет свой обычный смысл. F5, reconnect, восстановление черновика, смена темы и получение presence не являются согласием на discard и не запускают Save/ATS/PoE/WOL или иной бизнес-эффект.

## 3. FORM-KEY-02/03 — placeholder и обязательность

Placeholder, введённое значение и текст выбранного элемента должны корректно располагаться в однострочном поле. Исправляй общий компонент/общий CSS: согласованные line-height, padding, box-sizing, оболочку и вложенный input, baseline и иконки. Не подгоняй отдельную форму transform/top/локальной высотой. Глобальная высота остаётся `--clay-control-height: 32px`, ширина даты/времени — `--clay-date-time-width: 180px`. У textarea placeholder начинается в корректной первой строке; многострочный ввод не центрируется по высоте всего поля.

Желтоватая заливка применяется только при сочетании **Required + пустое значение + доступность редактирования**. Пустое поле желтоватое с placeholder и без него; после заполнения или выбора фон обычный, после очистки снова желтоватый. Правило одинаково для ClaySelect/ComboBox/DropDownList, даты, числа, текста и прочих применимых контролов. Условное `Required` меняется вместе с бизнес-правилом; placeholder не определяет обязательность и не мешает отображению состояния. ReadOnly/Disabled не должны выглядеть доступными к редактированию. Цвет задаётся семантическими токенами общей темы, сохраняет читаемость в светлой и тёмной схемах; локальные жёлтые inline-стили запрещены. Ошибка валидации сама по себе не включает Required-фон и не скрывает его у пустого обязательного доступного поля; raw, dirty и focus сохраняют свои отдельные состояния.

Возможность редактирования определяется семантическим состоянием общего компонента. Технический `readonly` внутреннего input интерактивного selector/picker не означает ReadOnly всего поля и не исключает его из Required-оформления и автоматической навигации. Для действительно ReadOnly/Disabled поля Required-заливка не применяется.

## 4. FORM-KEY-04/05 — начальный и текущий фокус

Первый фокус устанавливается один раз на первое реально доступное поле ввода в логическом порядке после interactive render, загрузки/восстановления и готовности нужного контрола. Пропускаются скрытые, отключённые, read-only элементы, служебные hidden inputs и элементы с исключением из Tab-порядка. При отсутствии полей выбери осмысленную доступную область без фиктивного ввода. Не ставь фокус на toolbar вместо первого поля.

Этот фильтр относится к автоматическому выбору первого/следующего редактора: учитывай `inert`, disabled ancestor/fieldset, неактивную вкладку, отсоединённый элемент и `tabindex=-1`. Доступ к действительно readonly полям через обычный Tab для чтения/копирования сохраняется по их контракту. Не исправляй порядок разметки положительным tabindex. Составной контрол регистрируется как одно поле, а не набор его внутренних кнопок.

Не перехватывай фокус после каждого render, autosave, ответа lookup, heartbeat, смены темы или reconnect. Если пользователь уже начал работу до завершения загрузки, сохранение его фокуса имеет приоритет. Вложенный диалог ограничивает навигацию своим контекстом и возвращает фокус вызывающему элементу при закрытии; несколько форм и portal popover не должны бороться за `document.activeElement`.

Tab/Shift+Tab показывают контрастную рамку на реальном интерактивном элементе или общей оболочке составного контрола. Это относится также к кнопкам, меню, checkbox/radio, спискам и дереву. Не отключай native outline без равноценной видимой замены. Стиль определяется общей темой и не вызывает скачков размеров/раскладки. Контраст проверяется в каждой поддерживаемой цветовой схеме, включая одновременно Required, Dirty, Invalid и Focus.

## 5. FORM-KEY-06 — изменённые поля

Dirty-рамка отличается от focus-рамки, не исчезает при уходе фокуса и не означает только факт посещения поля. Общая модель сравнивает текущее семантическое значение с принятой baseline; для lookup сравнивается ID/значение, а не загруженная позднее подпись. Незавершённый/невалидный raw также считается изменением, даже когда typed model ещё прежняя. Возврат к исходному значению снимает dirty; автоматическая зависимая очистка из-за пользовательского выбора учитывается как изменение соответствующего поля.

Raw считается изменением при отличии от принятого baseline; исходная ошибка сама по себе не доказывает пользовательского редактирования. Свежий ответ БД сам по себе не заменяет baseline и не делает восстановленный draft чистым: это результат принятого merge/reset/commit. Ключи полей и строк коллекций стабильны при вставке, сортировке, скрытии и повторном рендере. Неудачный Save/Unknown не сбрасывает dirty.

Autosave в браузер не означает сохранение в БД и не снимает dirty. После подтверждённого Apply принимается ровно отправленная ревизия; новый N+1 остаётся изменённым. После восстановления dirty вычисляется относительно сохранённой baseline и свежих данных по согласованному merge-контракту. Программная первичная загрузка/восстановление подписи/показ presence не должны создавать ложное изменение. Согласованное разрешение конфликта может явно принять новую baseline; простая перерисовка — нет.

Для checkbox/radio/коллекции/составного редактора видимо отмечается собственная логическая область изменения. Focus, Dirty, Invalid и Required должны различаться одновременно: например, разные независимые контуры/толщина/рисунок и существующие сообщения валидации. Конкретные токены согласуй в общей теме; одна рамка, которая стирает остальные состояния, контракт не выполняет. Доступность не должна опираться только на различение цветов.

## 6. FORM-KEY-07 — Enter и завершение выбора

Enter в однострочном поле после фиксации текущего ввода переводит фокус к следующему доступному полю активной формы в её логическом порядке. В конце формы не запускай Save, destructive action или переход в другую форму неявно. Не ломай обычный Tab/Shift+Tab и работу кнопок.

Если следующего редактора нет, фокус остаётся в текущем. Удержание Enter не должно пробегать всю форму. Документированные модификаторы и предметные сценарии сканирования, добавления строк и ClayGrid сохраняются через явную политику scope/контрола. Default отменяется синхронно на клиенте только для обработанного жеста; глобальный перехват Enter и синтетическая имитация Tab запрещены.

В ClaySelect/ComboBox/DropDownList и других списочных контролах сначала завершается пользовательское принятие значения, включая разрешённый async callback, затем выполняется **один** переход. Простое перемещение highlight, поиск/открытие списка, загрузка options, программное присваивание, restore и отклонённый callback не считаются выбором. Сбой/отказ принятия оставляет контекст и ввод доступными. Согласуй с общим подтверждаемым popup/result protocol, а не добавляй независимый таймер.

Переход связан с подтверждённым завершением выбора пользователем, включая мышь/касание и принятие уже выбранного значения, а не с любым `ValueChanged`/`SelectedItemChanged`/`SelectItemAsync`. Auto-select после blur, Escape-восстановление и программное разрешение ID не запускают переход. Пока поиск выполняется, результат неоднозначен или значение не принято, фокус остаётся в селекторе. Enter на неизменённом подтверждённом выборе переходит далее без повторного поиска.

Enter при открытом списке сперва выбирает вариант; общая форма не должна обработать то же событие повторно. IME composition/подтверждение составного символа не переводит фокус. В textarea Enter создаёт новую строку. В многоэлементном выборе каждый toggle не завершает работу: переход происходит после явного завершения выбора; выбор через внешний диалог возвращается в scope вызывающей формы. После позднего async результата не перехватывай фокус, если пользователь уже перешёл в другой контекст. Следующий элемент ищется после обновления зависимых полей, а не по устаревшему DOM.

После await проверяются актуальность принятия и поколение пользовательского фокуса. Любое самостоятельное перемещение пользователя после исходного действия, включая другое поле той же формы, отменяет запоздалый автоматический переход.

## 7. FORM-KEY-08 — справка и цветовая схема на каждой форме

Общая оболочка предоставляет команды справки и выбора темы в toolbar или меню **каждой** формы, включая отдельные окна и редакторы без главного меню. Вложенный диалог имеет доступ к командам в своём активном слое; не считай закрытое/недоступное за modal главное меню выполнением требования. На узком экране допустимо общее меню без потери доступности. Уже работающий общий селектор переиспользуется; дублировать theme host/provider или делать локальный набор тем запрещено.

Это относится к полноценным формам/редакторам; каждому вспомогательному confirm-dialog и popover отдельный toolbar не требуется. Встроенный немодальный редактор может использовать доступную общую панель с корректным контекстом справки. Открытие документации сохраняет текущую форму, её несохранённый ввод, draft и операции; используется общий безопасный механизм ссылок/открытия, без локального `window.open` и перезагрузки редактора.

По уточнению пользователя **сохраняется существующий параметр `URI_wiki_help`**. Это единый параметр справки форм; переименование и второй конфигурационный ключ для этой задачи не нужны. Общий resolver строит URL из него и зарегистрированного пути/идентификатора формы. Путь нормализован, стабилен для route aliases, не содержит ID сущности, query с пользовательскими данными, сырой URL или текст черновика. Для modern routes и dialogs без URL нужна явная запись в каталоге; если документация сохраняет legacy путь, он задаётся metadata, а не выводится угадыванием. Отдельный `HelpId` допустим как проверенная часть справочного пути.

В проверенном legacy общий `Page.WikiHelp` использует `URI_wiki_help` как prefix и URL-encoded путь страницы. Сохрани поддержку установленного формата и явно опиши построение URL: query-prefix и path-base нельзя механически смешивать. Не считай `URI_help_clayGrid` заменой справке формы — это отдельный существующий параметр справки компонента. Кодирование выполняется ровно один раз по выбранному контракту; тестируются trailing slash, PathBase, Unicode, aliases и query-prefix. Разрешённый адрес справки — корректный HTTP(S)/поддерживаемый относительный адрес по общей URI-политике; некорректная или отсутствующая конфигурация даёт понятный статус без поломки редактора и не подменяется неявным другим адресом.

Тема едина для приложения через существующий **ClayTheme**, по умолчанию **Classic Light**. Сохрани установленный механизм пользовательского выбора и работу других приложений; не удаляй и не мигрируй `InvTheme`/`UsersTheme` без отдельного задания. Переключение схемы не перезагружает/не закрывает форму, не сбрасывает draft, baseline, cursor или незавершённую команду. Учти доступность в самостоятельных окнах, вложенных диалогах и приложениях, где ещё нет общего shell. Печатный документ может не выводить интерактивные команды на бумагу; его экранная оболочка должна сохранять их доступность.

Сохраняются существующие каталог тем, личное хранилище проверенного сотрудника, LoadFailed/SaveFailed и безопасный повтор. Не приписывай circuit-scoped `ClayThemeState` межвкладочную синхронизацию: минимум — общая сохранённая настройка, применение в текущем окне и корректная загрузка при следующем открытии. Уже работающие дополнительные способы распространения выбора сохраняются.

## 8. FORM-KEY-09 — присутствие других редакторов

В форме существующей сущности показывай **кто ещё редактирует эту же сущность**: достоверное отображаемое имя сотрудника и понятное состояние. Просмотр и редактирование различаются, список наблюдателей не маскируется под редакторов. Несколько вкладок одного сотрудника агрегируются; текущий сотрудник не изображается другим коллегой. Если нужно показать его дополнительные вкладки, это отдельная явная информация.

Идентичность группы — канонический тип сущности и полный ключ в надлежащей tenant/business-области. URL, route alias, имя Razor-класса и случайный draft UUID не являются достаточной общей идентичностью. Разные приложения/пути к одной записи должны сходиться в одной группе. Вложенный редактор использует договорённую идентичность основной сущности, если меняет её, и отдельный scope при необходимости; нельзя соединять независимые записи. Для ещё не сохранённых новых записей нет общей группы `EntityId=0`; после подтверждённого create выполняется корректный переход к настоящему ключу.

Область данных берётся из действующей архитектуры; новую tenant-модель ради presence не вводить. Employee/UserId идентифицирует участника, а не включается в ключ общей группы — иначе сотрудники не увидят друг друга.

Пользователь/сотрудник определяется серверной аутентификацией. Право подписки и сведений о коллегах проверяется на сервере для конкретной сущности; идентификатор из браузера сам по себе не даёт доступ. Presence передаёт только необходимую идентичность и состояние, не значения полей, raw, секреты, draft contents или сведения о чужих недоступных сущностях.

Проверки доступа повторяются при reconnect и смене identity/сущности. Registration generation/lease token защищает от позднего leave/renew прежнего подключения и списка предыдущей записи.

Общий сервис поддерживает join/heartbeat/leave, ограниченное время жизни устаревшего присутствия, смену route/identity, несколько вкладок, reconnect, Dispose и исчезновение клиента без корректного закрытия. Для нескольких экземпляров приложения определи общий источник присутствия/маршрутизацию в пределах разрешённой архитектуры: singleton одного процесса не является межприложенческой реализацией. После потери транспорта не показывай устаревший список как достоверный — явный статус, затем восстановление подписки. Недоступность presence не мешает вводу и не создаёт ложную блокировку Save.

Поддерживаемая topology фиксируется по факту, включая несколько IIS worker и перекрытие процессов при recycle/обновлении. После перезапуска отсутствие полученного актуального snapshot не означает, что других редакторов нет; до восстановления показывается неизвестность/подключение. Недоступность внешнего стенда не разрешает выдать режим одного процесса за межсерверную реализацию.

Presence **информирует** и не заменяет CAS/права/конфликты, не блокирует чужую запись и не синхронизирует значения полей/черновики. Legacy-передачу `TranslateCtrlEvent` нельзя переносить как обязательное поведение. Heartbeat не делает SQL business write и не запускает Save, а reconnect presence не восстанавливает автоматически внешние действия. Старое локальное отключение совместной работы в legacy не освобождает актуальный редактор от FORM-KEY-09.

## 9. Реализация, параллельная работа и приёмка

Общее поведение реализуется в Controls/общих сервисах и shell, формы объявляют metadata, state bindings и свои domain read contracts. Не добавляй form-local CSS, отдельные JS-таймеры или копии draft/presence/theme/focus реализации. Используй существующие компоненты и минимальные совместимые расширения; работающие consumers Inventory, Users, Medical и новых приложений сохраняются.

Оркестратор назначает одного владельца каждого общего файла/API. Draft/Cancel, input UX, help/theme shell и presence могут исследоваться и разрабатываться параллельно по согласованным интерфейсам. Пересечения `ClaySelect`, `ClayEntityForm`, base editor, `Program.cs`, settings, CSS/тем и SQL интегрирует назначенный владелец; агент формы подключается к принятой версии, не создаёт собственный обход.

Минимальная содержательная приёмка:

| Группа | Проверяемый результат |
|---|---|
| Cancel | Clean close; три dirty-ветви; raw до blur; новый/существующий/вложенный редактор; свежие данные БД; неуспешный read/storage; N+1; Unknown и confirmed cleanup; 0 незапрошенных business writes |
| Вид и навигация | Placeholder; пустой Required — желтоватый, заполненный — обычный, после очистки — желтоватый, с placeholder/без; первый фокус; Tab/Shift+Tab; Focus+Dirty+Invalid+Required одновременно; Enter/IME/textarea; выбор async/внешний/multiple без двойного перехода |
| Dirty/DR-01 | Initial clean; change/revert; raw invalid; autosave остаётся dirty; restore; Apply N с N+1; успешный Cancel-reset не воскрешается |
| Help/theme | Доступ с каждой формы/редактора без главного меню; валидный URL из metadata/URI_wiki_help; совместимость legacy prefix; все схемы; переключение сохраняет состояние |
| Presence | Два сотрудника и одна сущность; разные сущности; aliases/несколько приложений; повторные вкладки; readonly; expiry/reconnect/Dispose; запрещённый scope и отсутствие передачи значений |
| Совместимость | Репрезентативные Inventory/Users/Medical consumers, принятые права/транзакции/CAS/DR-01, отсутствие локальных обходов общих контролов |

Для каждой формы веди матрицу FORM-KEY-01…09/DR-01: применимость, actual call path, результат проверки, конкретное ограничение. «Есть CSS-класс» не доказывает правильный вид; «есть метод» не доказывает полный пользовательский сценарий. Наблюдение пользователя и source-level анализ обозначай отдельно от собственного браузерного запуска. Адресные локальные проверки выполняются в доступной среде; внешние SQL/IIS/ATS/production и многобраузерные проверки по решению пользователя оставлены beta. NOT RUN не превращается в PASS, а выявленный локальный дефект не откладывается в beta под видом внешней проверки.
